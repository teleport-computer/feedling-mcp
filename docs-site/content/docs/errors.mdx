---
title: Errors
description: Handle Feedling's stable JSON error envelope.
---

Feedling errors use a stable machine-readable slug:

```json
{
  "error": "invalid_payload",
  "detail": "The request body is invalid",
  "request_id": "req_..."
}
```

## Common errors

| Status | Slug | Meaning |
| --- | --- | --- |
| `400` | `invalid_payload` | Request body or parameters are invalid. |
| `401` | `unauthorized` | Authentication is missing or invalid. |
| `403` | `forbidden` | The caller lacks permission. |
| `404` | `not_found` | The requested resource does not exist. |
| `409` | endpoint-specific | The request conflicts with current state. |
| `413` | endpoint-specific | The decoded attachment or request is too large. |
| `429` | endpoint-specific | A business cap or temporary upstream capacity limit was reached. |
| `500` | `internal_error` | Unexpected server failure; retain `request_id`. |
| `503` | `service_busy` | Temporary capacity failure; retry with backoff. |

Clients should branch on `error`, not human-readable `detail`. A new message may
be added to `detail` without changing the stable slug contract.

When an error includes `blame`, use it to decide the next action:
`user_provider` means the user's model provider settings need attention,
`provider_transient` means retry/backoff is appropriate, `user_environment`
means the user's self-hosted runtime or VPS needs attention, and `system` means
Feedling owns the failure.
Treat unknown `blame` values as `system`/generic copy and do not drop the error
or notice.

Not every historical route uses the same slug for the same status, and not every
`429` is transient. See [retry safety](/docs/reliability#retry-safety) before
retrying a failed write.
