Feedling errors use a stable machine-readable slug:

```json
{
  "error": "invalid_payload",
  "detail": "The request body is invalid",
  "request_id": "req_..."
}
```

## Common errors

| Status | Slug | Meaning |
| --- | --- | --- |
| `400` | `invalid_payload` | Request body or parameters are invalid. |
| `401` | `unauthorized` | Authentication is missing or invalid. |
| `403` | `forbidden` | The caller lacks permission. |
| `404` | `not_found` | The requested resource does not exist. |
| `409` | endpoint-specific | The request conflicts with current state. |
| `413` | endpoint-specific | The decoded attachment or request is too large. |
| `429` | endpoint-specific | A business cap or temporary upstream capacity limit was reached. |
| `500` | `internal_error` | Unexpected server failure; retain `request_id`. |
| `503` | `service_busy` | Temporary capacity failure; retry with backoff. |

Clients should branch on `error`, not human-readable `detail`. A new message may
be added to `detail` without changing the stable slug contract.

When an error includes `blame`, use it to decide the next action:
`user_provider` means the user's model provider account, plan, credentials, or
model settings need attention,
`provider_transient` means retry/backoff is appropriate, `user_environment`
means the user's self-hosted runtime or VPS needs attention, and `system` means
Feedling owns the failure.
Treat unknown `blame` values as `system`/generic copy and do not drop the error
or notice.

Public runtime `error_class` values, their `blame`, and their safe localized
fallback text now come from one server registry. If a runtime boundary receives
an unregistered dynamic value, Feedling returns the registered
`error_class_unregistered` system-owned fallback instead of forwarding the raw
value. The rejected value is not stored or fingerprinted; operators receive
only content-free counters grouped by contract domain, boundary, release, and
writer. Clients should continue to display the server-provided safe text and
treat newly introduced classes generically when they do not yet have local
copy. These rejection counters are best-effort diagnostics: if persistence
fails, Feedling records a content-free warning in service logs, so dashboard
totals can be lower than the actual number of rejected values.

Not every historical route uses the same slug for the same status, and not every
`429` is transient. See [retry safety](/docs/reliability#retry-safety) before
retrying a failed write.

## Pi stream diagnostics

For resident clients using the pi driver, `agent.model.call.done` and
`agent.model.call.error` traces may include `detail.pi_stream.schema_version=3`.
All fields in this projection are scalars. `text_blocks`, `thinking_blocks`,
`tool_blocks` (pi `toolCall` blocks), and `other_blocks` count assistant
`message_end` blocks.
`stop_reasons` is a comma-separated string of distinct allowlisted reasons in
encounter order, capped at eight reasons and 80 characters without splitting an
enum. Unknown reasons become `other`. `stop_reason_first` is the first nonempty
normalized reason; `stop_reason_last` is the last observed assistant end reason
(or an empty string when that end has none). `stop_length_seen` and
`stop_max_tokens_seen` scan all parsed assistant ends, including those beyond
the summary cap. These shape fields contain no reply text, reasoning text,
tool arguments, or arbitrary upstream stop-reason strings.

Interpret these as observations, not mutually exclusive diagnoses. Check
`parse_failed=false`, `parse_error_count=0`, and field types before classifying
thinking-only or tool-call-only output. `update_text_seen=true` with
`text_chars_total=0` is an update-only-text candidate, not proof of its cause.
A length flag can coexist with another shape. A successful model-call trace is
not proof that the reply was delivered to the user.

Version 3 no longer emits nested `blocks` or list-shaped `stop_reasons`.
Version 2 includes scalar counts, but its old nested fields may have become
Python-representation strings after size limiting. Older unversioned traces
lack these scalar counts. Records are not backfilled: check version and field
types, and report coverage separately during rolling upgrades.

When a pi turn has no usable reply and the final assistant `message_end` reports
`stopReason=error`, existing specific classifications (quota, authentication,
rate limits, and upstream availability) take priority. An unmatched error uses
`provider_error_unclassified` with `blame=provider_transient`; a turn with no
error stop reason continues to use `provider_empty_reply`. Trailing user echoes
or tool results cannot replace that assistant end. If no assistant end exists,
legacy streams may fall back to the last end without a role field. This changes
the failure classification, not retry behavior.

For a failed pi model call whose selected end is an error, `detail.pi_error_head`
contains the first 300 characters of the stripped provider `errorMessage`, if
present. This field contains provider text and is visible in the trace and
admin projection. It is separate from the content-free stream shape and does
not replace the server-authored failure text shown to users. Other trace detail
strings retain their existing limits (including the separately authorized
parse-failure reply excerpt).


## Agent body generation

`POST /v1/agent-body/generate` accepts `schema_version: 1`, `grid_size: 24`,
a nonblank `client_request_id` of at most 128 characters, and `allowed_palette`
with 1–255 `#RRGGBB` colors in index order. Successful `rows` contain exactly
24 rows of 24 integers: 0 is empty, and 1 through the palette length select colors.
At least one cell is nonzero. The result includes an opaque `generation_id`.
`client_request_id` is a diagnostic correlation value, not an idempotency key;
repeating a request can generate a different body and incur another model call.

The endpoint requires an account API key and rejects runtime tokens. Hosted
accounts use their active tested chat route, including its reasoning setting.
The backend reads available identity, genesis persona (up to 6,000 characters),
and up to 12 memory summaries through existing authenticated readers.

Resident accounts run a hidden generation on their own consumer's normal agent.
A fresh poll must advertise `agent_body_generate_v1`; the additive
`agent_body_job` field contains a job ID, expiry, fixed instructions with palette
colors, and palette count. The consumer reads its identity card and at most 12
memory summaries, then calls its CLI or HTTP agent in an isolated background
turn. Known CLI drivers use the existing tool-free profile; HTTP uses its
existing request protocol. The turn does not enter Chat or post a chat reply.
Unavailable context is labelled as unavailable.

Resident jobs use the existing user-scoped CAS mailbox, bound to the consumer
and agent entry. Only fixed instructions and temporary grid indices enter that
mailbox; identity/persona/memory text does not. The waiting request removes grid
indices after reading them. Expired payloads are removed by the waiting request
or the next poll; a process crash can leave expired data until the next access.
Only a content-free completion receipt is retained. No preset is saved or applied;
saving remains a client action. Concurrent resident generations cannot overwrite
an active job or unread result; the extra request receives a failure.

The response deadline is 85 seconds after authenticated handler entry, including
context reads. Direct provider calls receive at most 70 seconds of network
inactivity timeout. Invalid output can be repaired once only when at least 25
seconds remain. The resident converts epoch expiry to a monotonic deadline and
reserves five seconds for delivery. An in-flight synchronous network call can
finish after the HTTP deadline; its result is discarded and no repair starts
afterward. Server grid validation applies to both execution paths.

| Status | Slug | Meaning |
| --- | --- | --- |
| `400` | `agent_body_invalid_request` | Request fields fail validation. |
| `400` | `model_api_not_configured`, `model_api_not_tested`, `model_api_key_envelope_missing`, `model_api_key_decrypt_failed`, `model_api_config_invalid` | The hosted chat route cannot be loaded. |
| `409` | `agent_body_provider_config_failed` | Check provider credentials, access, quota, or configuration. |
| `409` | `agent_body_resident_update_required` | The resident is offline, outdated, or has not advertised body generation. |
| `409` | `agent_body_agent_unavailable` | This import-only account is not running an agent. |
| `429` | `agent_body_generation_failed` | Provider rate limit; `retryable: true`. |
| `502` | `agent_body_generation_failed` | Provider failure, empty reply, or unavailable/conflicting resident task. |
| `502` | `agent_body_generation_invalid_output` | Output violates the grid rules after repair. |
| `504` | `agent_body_generation_timeout` | Deadline reached or insufficient time remains for repair. |

Every failure omits `rows`; there is no random or template fallback. Generation
diagnostics contain request/generation identifiers, status, duration, attempt
count, provider/model, error class, and (on success) a nonzero count and short grid
hash. Ordinary resident prompt/reply trace excerpts, raw parse-failure archives,
and model-call logs are suppressed for the hidden generation scope.
