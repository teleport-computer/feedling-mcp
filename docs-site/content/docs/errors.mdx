Feedling errors use a stable machine-readable slug:

```json
{
  "error": "invalid_payload",
  "detail": "The request body is invalid",
  "request_id": "req_..."
}
```

## Common errors

| Status | Slug | Meaning |
| --- | --- | --- |
| `400` | `invalid_payload` | Request body or parameters are invalid. |
| `401` | `unauthorized` | Authentication is missing or invalid. |
| `403` | `forbidden` | The caller lacks permission. |
| `404` | `not_found` | The requested resource does not exist. |
| `409` | endpoint-specific | The request conflicts with current state. |
| `413` | endpoint-specific | The decoded attachment or request is too large. |
| `429` | endpoint-specific | A business cap or temporary upstream capacity limit was reached. |
| `500` | `internal_error` | Unexpected server failure; retain `request_id`. |
| `503` | `service_busy` | Temporary capacity failure; retry with backoff. |

Clients should branch on `error`, not human-readable `detail`. A new message may
be added to `detail` without changing the stable slug contract.

When an error includes `blame`, use it to decide the next action:
`user_provider` means the user's model provider account, plan, credentials, or
model settings need attention,
`provider_transient` means retry/backoff is appropriate, `user_environment`
means the user's self-hosted runtime or VPS needs attention, and `system` means
Feedling owns the failure.
Treat unknown `blame` values as `system`/generic copy and do not drop the error
or notice.

Public runtime `error_class` values, their `blame`, and their safe localized
fallback text now come from one server registry. If a runtime boundary receives
an unregistered dynamic value, Feedling returns the registered
`error_class_unregistered` system-owned fallback instead of forwarding the raw
value. The rejected value is not stored or fingerprinted; operators receive
only content-free counters grouped by contract domain, boundary, release, and
writer. Clients should continue to display the server-provided safe text and
treat newly introduced classes generically when they do not yet have local
copy. These rejection counters are best-effort diagnostics: if persistence
fails, Feedling records a content-free warning in service logs, so dashboard
totals can be lower than the actual number of rejected values.

Not every historical route uses the same slug for the same status, and not every
`429` is transient. See [retry safety](/docs/reliability#retry-safety) before
retrying a failed write.

## Pi stream diagnostics

For resident clients using the pi driver, `agent.model.call.done` and
`agent.model.call.error` traces may include `detail.pi_stream.schema_version=2`.
The projection adds scalar `text_blocks`, `thinking_blocks`, `tool_blocks`
(pi `toolCall` blocks), and `other_blocks` counts from assistant `message_end`
events. It also records `stop_reason_first` (the first nonempty, allowlisted
reason, unknown reasons mapped to `other`, or an empty string if none),
`stop_length_seen`, and `stop_max_tokens_seen`. The two booleans scan all parsed
assistant end events, even after the legacy stop-reason list reaches its cap.
These fields contain no reply text, reasoning text, tool arguments, or arbitrary
upstream stop-reason strings.

Interpret these as observations, not mutually exclusive diagnoses. Check
`parse_failed=false`, `parse_error_count=0`, and field types before classifying
thinking-only or tool-call-only output. `update_text_seen=true` with
`text_chars_total=0` is an update-only-text candidate, not proof of its cause.
A length flag can coexist with another shape. A successful model-call trace is
not proof that the reply was delivered to the user.

Older traces lack the versioned scalar fields. Their nested `blocks` and
`stop_reasons` can be truncated strings after size limiting; they are not JSON
objects/arrays and are not backfilled. Keep those records outside the new-field
denominator and report coverage separately during rolling upgrades. The shared
trace limiter and its size bounds are unchanged.
