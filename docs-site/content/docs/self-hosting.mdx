Self-hosting is an experimental, operator-managed path. The repository contains
images, Compose references, and service units, but it does not currently provide
a supported one-command production stack or an SLA. Treat this page as a
deployment review checklist, not a claim that a generic VPS matches Feedling's
managed confidential-compute environment.

Read [architecture and trust boundaries](/docs/architecture) first for the
logical component, data-flow, and encryption model used by this guide.

## Cache diagnostic metadata

Runtime V2's existing per-user attempt log may contain allowlisted numeric cache
usage and a nullable system-prefix change observation. Treat this as plaintext
operational metadata with the log's existing access controls. Prompt/reply bodies
remain on their existing content-isolated paths; no plaintext content digest,
credential, or endpoint is added to the log. The keyed comparison state is only
in process memory, bounded to 256 user-route baselines with a 30-minute idle TTL;
it is lost on worker restart/eviction and is not shared between workers.
It does not identify a durable chat session or establish provider cache behavior.
See [Runtime V2 prompt caching](/docs/architecture#runtime-v2-prompt-caching)
for the exact observed wire ranges and unknown states. This does not enable new
Resident/VPS diagnostics or require a database migration.

## Optional managed Genesis plaintext worker

`FEEDLING_GENESIS_WORKER_ENABLED` remains opt-in and requires the runtime-token
secret. An absent enclave URL selects strict per-job plaintext eligibility for
managed uploaded/backfill jobs; it does not enable decrypting sealed records.
The worker needs authenticated backend access to the user's configured provider
credential and PostgreSQL. Configure these within your chosen host trust boundary:
local plaintext processing exposes authorized import material to that host and
the selected provider. See [managed import recovery](/docs/workflows/memory#managed-import-eligibility-and-recovery)
for partial effects and retry costs. This does not change the Resident consumer
queue or the direct plaintext import thread.

## Resident version observations

Consumers freeze a revision declaration at startup and send it with polls and
responses in `X-Feedling-Consumer-Commit`. The optional
`X-Feedling-Consumer-Commit-Source` identifies `consumer_env`
(`FEEDLING_CONSUMER_COMMIT`), `image_env` (`FEEDLING_GIT_COMMIT`), or
`git_checkout` (the consumer's own repository at startup), in that precedence
order. Explicit empty, `dev`, or `unknown` environment values remain unknown;
an unpacked distribution does not borrow an ancestor repository's revision.
Changing the checkout or environment after import does not update this report.

These are self-reported distribution/checkout labels, **not proof of loaded
source bytes**. A dirty checkout or incorrect image label can disagree with the
running code. The backend's expected update target and compatibility claim are
separate and never fill a missing consumer revision. The process spawner
inherits its runner environment; an isolated container instead uses its own
image environment, without copying the supervisor's revision label.

Each bounded `consumer_state.poll_consumers` entry stores the protocol version,
commit, and source with that identity's poll timestamp. Operator diagnostics
return those observations with age and `recent`; later polls from another
identity or response activity do not refresh them. Missing version data in an
old-client poll clears that identity's prior report. Old persisted observations
without these fields remain unknown, even when a newer global writer has a
version. A commit reported without provenance is labeled `legacy`.

Supervisor heartbeats separately store their runner image declaration in
`version`, with `version_source=image_env` in the heartbeat payload and readback.
Absent or old provenance is `unknown`. A fresh heartbeat proves neither the
consumer's revision nor that a child loaded that image's source. Deployment and
coverage acceptance still require evidence for the intended environment and
running children; these fields do not authorize a restart or deployment.

## Resident startup during enclave outages

Hosted and self-hosted resident consumers retry the startup decrypt-source probe
on transport errors and HTTP 429, 502, 503, or 504. The probe shares the runtime
settings: `FEEDLING_ENCLAVE_FETCH_ATTEMPTS` (default 3), exponential backoff from
`FEEDLING_ENCLAVE_FETCH_BACKOFF_SEC` (default 0.5 seconds), and
`FEEDLING_ENCLAVE_CONNECT_TIMEOUT_SEC` / `FEEDLING_ENCLAVE_READ_TIMEOUT_SEC`
(default 5 / 20 seconds). Other HTTP failures, including deterministic 4xx
responses, end the probe immediately.

If the probe fails, the consumer logs an error, reports decrypt health as
`unreachable`, and continues polling. Cycles whose decrypt-history reads fail
are skipped; later cycles can recover when the source becomes reachable.
Startup authentication and encryption-module checks still must succeed.

For an effective-off account, startup instead makes one authenticated backend
history read (`limit=1`, omitted image bodies, 10-second timeout), even without
an enclave URL. A valid page, including an empty page, reports `backend_ready`;
HTTP, transport, JSON or page-shape failure reports `backend_unreachable`.
Failure logs an error and continues polling; it is not a hard startup block.
Idle checks use the same account-local backend route. These results never read
or write the runner's shared enclave health file. A whoami mode change clears
the previous route's health and probe throttle before another poll report.
Consecutive unreadable claimed messages report `backend_degraded`; only an
actual successful message read clears that degradation, not a reachability probe.

## Resident plaintext history

Upgraded consumers read history and omitted plaintext bodies from the
authenticated backend when whoami reports `content_encryption_effective=off`,
including when `FEEDLING_ENCLAVE_URL` is unset. Backend history failures keep the
poll checkpoint for retry; a successful empty page can advance it. An unavailable
individual body stays unreadable without blocking other rows. Old sealed rows
are not decrypted: their identifiers and sequence metadata remain for cursor
progress, but they cannot supply conversation context, Capture text, or a
per-turn memory-selection anchor. Encrypted and unknown accounts keep their
existing decrypt-service paths.

`io_cli chat-image` also checks effective mode through the authenticated backend.
For explicit `off`, it reads backend history and any omitted message body,
decodes single images or multi-image bundles locally, and writes private image
files. It requires no enclave URL in that mode. Sealed, malformed, or unavailable
bodies fail without decrypt fallback; encrypted or unknown mode keeps the enclave
history path. The backend's existing whoami public-attestation lookup is unchanged,
so this CLI routing change does not establish zero backend-to-enclave traffic.

`io_cli voice-transcript-read --call-id <id>` reads an effective `off` account's
own plaintext voice archive through the authenticated backend and decodes it
locally, with no content-decrypt fallback or enclave URL requirement. It preserves
full Unicode text, metadata, and 6000-character pages. Sealed legacy archives,
mixed sealed/plaintext rows, foreign owners, malformed bodies, and failed reads
remain unreadable; a preview is never substituted for the full transcript.

This voice command stops if the mode request fails or its response has no valid
user identity. A present null or non-string effective mode is also an error.
Only an authenticated successful response with `on`, or a missing, empty, or
unrecognized **string** effective mode, retains the legacy enclave path. Unknown
strings are not normalized into `off`. This stricter error handling applies to
this voice command and the identity command described below. The existing whoami
attestation lookup remains separate, so this is not a claim of zero backend
attestation traffic. Plaintext archives are visible to the backend and resident
host under their existing trust boundaries.

`io_cli identity-read` uses the same strict authenticated mode check when a
backend URL is configured. Effective `off` reads the existing backend identity
endpoint and projects the caller's plaintext card locally, without an enclave
URL or content-decrypt fallback. It validates the owner and rejects sealed,
mixed, or malformed bodies. A `local_only` card returns metadata only. Valid
empty or sparse JSON objects keep the canonical card defaults; a truly absent
card returns `identity: null`. Profile fields and replacement metadata are
preserved. Encrypted and valid unknown modes keep the enclave-first path;
legacy enclave-only configuration also remains supported.

The CLI uses the backend's `days_with_user`, including its existing memory-anchor
repair, rather than the client machine's clock or a stale value embedded in the
card. Ordinary anchored cards retain their day count. Legacy cards with no or
invalid anchor, or a repaired earlier memory date, can differ from the old
enclave projection. Auxiliary memory lookup remains best effort.

`GET /v1/identity/get` still returns raw envelopes for authenticated clients in
all modes. A missing row returns HTTP 200 with `identity: null`; a stored
non-object (including JSON null) returns HTTP 500 `identity_storage_invalid`.
A database read or explicit enrichment failure returns HTTP 503
`identity_read_unavailable`, with no database exception details. Clients must
not treat these failures as permission to initialize or replace a card.

These failure guarantees apply to this endpoint and the new CLI read path.
Existing Resident reads still have their own error handling. Legacy unmanaged
Genesis reinitialization can continue after a failed read of a Genesis-owned
card; this change does not fix or authorize that existing write behavior.
`doctor` first requires an authenticated, well-formed whoami response. Exact
`off` requires backend API, identity, memory and chat probes, and does not run
the enclave identity content probe. Exact `on`, a missing mode field, or any
other string (including empty, whitespace and `OFF`) preserves the five-probe
compatibility contract. Explicit null/non-string modes, malformed identities,
and failed mode requests fail before later probes; they never imply plaintext.

Doctor output uses schema `io_cli.doctor.v2`. The five boolean `checks` keys
(`api`, `enclave`, `identity`, `memory`, `chat`) remain present. New
`required_checks` and `skipped_checks` explain readiness: for plaintext,
`checks.enclave` is `false` and its skip reason is
`not_required_for_plaintext`; it is not counted in `failed`. `ok` and exit status
use only required checks. Consumers that previously required all check values
to be true must use `ok` or the exit status instead. On mode-read failure,
`account_mode` is `unavailable`, `api` fails, other probes are marked skipped
with `account_mode_unavailable`, and the command exits nonzero. Probe failures
are never marked skipped. Empty identity/history responses can pass these
reachability checks; success does not prove raw content is readable.

The whoami public-attestation lookup is unchanged: configured cache misses may
still request enclave metadata. Skipping the content probe does not guarantee
zero enclave network traffic. Plaintext identity
content is visible to the backend and resident host within their existing trust
boundaries; no new decryption service or plaintext API is added.

This history policy is independent of the memory-selection switch below.
Startup and health probes follow the account mode described above; other
Resident operations, including the separate memory-selection fallback, may
still depend on the enclave. Plaintext history and attachments are visible to
the authenticated backend and resident host; neither an ordinary VPS nor this
routing change adds a hardware confidentiality boundary.

## Resident plaintext memory selection

An upgraded consumer uses `POST /v1/memory/turn-selection` only when whoami
explicitly reports plaintext content encryption. The backend operator can set
`FEEDLING_RESIDENT_PLAINTEXT_RECALL=off|shadow|on` (default `off`; redeploy to
change it). Encrypted and unknown accounts retain their existing decrypt-service
path. This switch is independent of Runtime V2 recall and does not install an
embedding model or enable vector preparation.

The repository's test deployment accepts the GitHub repository variable
`TEST_FEEDLING_RESIDENT_PLAINTEXT_RECALL`. Unset or empty means `off`; otherwise
it must be exactly `off`, `shadow`, or `on` (lowercase, without surrounding
whitespace). The test deployment rejects other values before calling the
deployment command. The value is passed only to the test backend through the
normal compose deployment. Changing the variable alone does not update running
workers: redeploy, then verify the existing workers' mode and the Hosted or
self-hosted consumer version separately. Production and pre deployment wiring
are unchanged.

Start with `shadow` to observe comparisons, then enable `on` after the relevant
checks pass. Shadow still returns the decrypt-service result; a missing
background comparison is unmeasured, and a comparable result is not necessarily
an equal result. Verify the actual backend response and memory injected by the
consumer for the same turn before claiming that it used local selection.
Rollback uses `off` followed by the same normal redeployment and runtime
verification; it does not require changing account encryption or stored data.

With `on`, the backend reads that account's plaintext history and memory cards
to select lexical matches. Remaining sealed cards are excluded from local
selection; a selection page containing sealed history still uses the existing
decrypt-service fallback. That selection-route behavior is separate from the
consumer history reader's unreadable-row policy above.
Protect plaintext access at the backend as well as at the resident process.
A generic host provides no additional hardware trust boundary through this
switch. See [the selection and fallback contract](/docs/workflows/memory).

The lexical tokenizer loads its dictionary separately in each backend worker
on first use; the default-off route does not load it. Measure per-worker memory
growth and other-request latency before enabling it across a deployment.
Per worker, account checks and local selections each allow two outstanding jobs,
enclave calls four, and shadow and response diagnostics one each. A timed-out
job keeps its permit until it finishes; overload returns an unavailable result
or skips optional diagnostics rather than queueing unlimited work.

Hosted consumers upgrade through the runner release; independent consumers must
upgrade on their own machines. Old consumers continue to work through the
decrypt service. Assess migration over seven days, tracking hosted and
independent residents separately: every active plaintext resident must have
new-route records and plaintext resident selection requests at the decrypt
service must reach zero before claiming the migration complete. Missing
diagnostics are not evidence of zero traffic.

## Agent body generation

Upgrade both backend and consumer for `POST /v1/agent-body/generate`. Hosted
Model API accounts use their active tested chat route. Resident accounts use
their own CLI or HTTP agent through a hidden job, even when a server-side model
credential also exists. An offline or old consumer causes
`409 agent_body_resident_update_required`. Consumers following `main` need a
production-channel release; deploying only test does not update them.

The direct ASGI path temporarily sees authorized context; residents read identity
and memory through their authenticated APIs. Protect plaintext and agent/provider
credentials on your infrastructure. A generic VPS does not gain confidential-VM
guarantees by upgrading. The endpoint returns a grid without saving or applying
a preset. See [the contract](/docs/errors#agent-body-generation).

## Choose the trust model first

### Resident clients on Windows

Local resident IPC depends on the Python runtime exposing `socket.AF_UNIX`.
When it is absent, the consumer logs `ipc_unsupported` and disables the listener;
`io_cli` reports a structured error for `identity-redistill`, `send-file`, and
`send-image`. No TCP listener is substituted. This is explicit degradation,
not a claim of full Windows support. Normal polling and text replies use HTTP,
not this socket; `io_cli send` and `wait-for-wake` remain unsupported verbs.

Both processes honor an explicit `FEEDLING_HOME`. Otherwise Windows uses Python's
native temporary directory plus `feedling_home_<fingerprint>`; POSIX keeps its
existing `/tmp/feedling_home_<fingerprint>` default. Choose the same private,
persistent directory for both processes when state must survive temporary-file
cleanup. The fingerprint is not an authorization boundary; hosted keyless
consumers still require per-user pinned paths.

When a CLI driver exits successfully with non-empty stdout but the resident
cannot parse a deliverable turn, the consumer keeps a local diagnostic copy in
`$FEEDLING_HOME/reply-parse-failures`. Each `.raw` file is mode `0600`, the
directory is mode `0700`, each body is capped at 256 KiB, and rotation retains at
most 20 files and 2 MiB total. A larger body is stored as a bounded prefix; the
SHA-256 in its filename describes the complete stdout. The corresponding backend
trace includes the byte length, SHA-256, exit code, driver, parse-empty stage,
timestamp, the exact first 80 characters, and the local artifact path so an
operator can correlate the failure directly. It never carries the complete
stdout. Successful turns and genuinely empty provider responses do not create
these files.

The current simple/OpenAI HTTP and CLI agent paths already share
`FEEDLING_AGENT_TURN_TIMEOUT_SEC` (300 seconds by default, minimum 30), bounded
by any shorter remaining turn deadline. Older simple-HTTP builds used a fixed
60 seconds. Check the running consumer commit before changing modes. This
setting cannot extend an upstream server or proxy timeout and is not a
recommendation to migrate runtimes.

After an ordinary foreground text CLI subprocess reaches that hard timeout,
supported Codex, Claude, and Pi commands get one fresh, reply-only recovery
attempt. The recovery has its own 120-second deadline (configurable with
`FEEDLING_FOREGROUND_TIMEOUT_RECOVERY_SEC`, minimum 30), removes user/project
tool surfaces, and discards executable actions from the result. It does not
undo anything the timed-out turn may already have completed; the isolation is
there to prevent the automatic recovery from repeating it. Attachment turns,
HTTP/custom drivers, and background/proactive work retain the existing visible
timeout fallback.

For direct `POST /v1/chat/response`, authenticate with the account's API key and
send a valid envelope matching `whoami.content_encryption_effective`. A whoami public key
is an encryption recipient, not an API credential. Plain-text-only chat messages
(carried inside an envelope) may omit `reply_to_message_id`; file/image
**followups** require it. Authentication, bootstrap, and envelope validation
still apply. A 400 response alone does not identify which validation failed.

The server may also return HTTP 200 with `status: ignored` and one of
`voice_call_finalized`, `voice_call_cancelled`, or `voice_call_finalizing` as
`reason`. These closed voice dispositions settle the turn without counting a
posted reply or delivery success; they do not block later messages.

The official resident consumer requires a JSON success receipt containing a
nonempty string reply `id` before counting a response write as accepted. An
unreadable or missing receipt outside the terminal dispositions above leaves
delivery unconfirmed. For a foreground
turn with no accepted reply or terminal rejection, the consumer retains the
checkpoint and releases the turn for normal redelivery. A lost receipt can
follow a real commit; existing server idempotency and terminal conflict handling
still apply. Receipt acceptance proves server acknowledgment, not client display.


Unrelated untracked files do not block self-update, but tracked edits still do.
Checkout refuses to overwrite conflicting untracked or ignored files and logs
their paths under `self-update checkout failed`; dependency installation and
restart do not proceed. Older consumers also count untracked files as dirty.
When an update is blocked, first privately back up
`consumer.env`, `identity.json`, and local state outside the checkout, then inspect
`git status`. Do not use `git stash -u`, `git stash -a`, or `git clean` to clear
the warning, and never commit secrets. Plain `git stash` leaves untracked files
in place. Agents must not move, stash, or delete operator files without permission.

### Server deployment isolation

The HTTP backend is multi-user and API-key scoped. That is not the same as strong
tenant isolation for code execution.

| Deployment | Appropriate use | Security boundary |
| --- | --- | --- |
| Local development | One developer with test data | Processes on one trusted host |
| Single-operator self-host | One person, family, or organization that trusts the host operator and connected agents | Host/VM boundary plus application authorization |
| Public multi-tenant service | Unrelated users and untrusted prompts | Requires an independent isolation design and security review; the reference self-host stack does not provide this by default |

The reference Runtime V2 worker uses bounded turn slots on the same host. Those
processes do not constitute a strong adversarial tenant boundary. Do not put
unrelated users' untrusted code on one worker and call the result isolated. Use a
separately reviewed container, microVM, or confidential-VM boundary with
per-tenant secrets and storage, or keep the deployment single-tenant.

On a generic VPS, the local enclave service is software/process separation. It
does not provide Intel TDX attestation or protection from the machine operator.
Existing encrypted envelopes still protect backups and accidental storage
exposure, but the host operator controls the processes that can request
decryption. With `FEEDLING_PLAINTEXT_WRITES_ACCEPTED=1`, all known accounts use
plaintext for new shared content, even if they have a legacy stored `on`
preference. They cannot opt new content into encryption through the settings API.
Inline bodies are readable in the database, and heavy Chat image/file objects
are stored as raw bytes in object storage. Database backups, object-storage
backups, and operators with either form of storage access are plaintext
recipients. The ASGI backend reads those accounts' memory cards as plaintext to
rank keyword memory search; their legacy sealed cards are not searched. Decide whether to enable the deployment gate with that trust boundary
in mind. The gate remains fail-closed by default; this policy does not convert
existing ciphertext, and `local_only` still requires device-only encryption.

A managed migration may preserve a historical ciphertext envelope verbatim
when its enclave recipient can no longer decrypt it. That is a data-retention
mechanism, not key recovery: it does not grant the host or enclave new plaintext
access, and device readability still depends on a valid user recipient key.
Migration tooling must keep this state distinct from unresolved replication and
must not silently change an account's encryption preference. Self-hosted
operators adopting an equivalent workflow should require exact source/target
digests, an explicit write approval, and a tested pre-cutover rollback boundary.

### Managed enclave-domain access is a separate trust model

The managed custom domain is available only when the endpoint is behind
`dstack-ingress` inside a measured TDX CVM. Its route is client TLS to ingress,
then Docker-internal HTTP to `enclave-domain`; this internal plaintext hop is
within the measured CVM boundary, not a substitute for an additional TLS hop.
Cloudflare manages the DNS-01 records only and does not proxy the connection.

For a custom-domain client, validate WebPKI, the ingress certificate evidence,
and the enclave attestation as separate evidence. Do not call WebPKI alone
pinning-equivalent. The older Phala `-5003s` passthrough endpoint remains the
compatibility and audit route: it uses the enclave's live self-signed
certificate, whose fingerprint must be checked against attestation
`REPORT_DATA`. A generic self-host cannot reproduce either hardware-attested
trust chain merely by copying the Compose layout.

A resident consumer can also re-run identity extraction (a "redistill") directly
from a local terminal conversation, without going through the app's plaintext
upload flow. This path reuses the existing sealed-import lane: the resident
consumer itself seals the material into an encrypted envelope on the same host
before making any network call, so the backend and the network in between never
receive that material as plaintext, independent of which deployment profile
above you chose. The backend still serializes these jobs per account — a second
redistill request while one is already `awaiting_resident` or `processing`
is rejected with `409 redistill_job_active` (and the in-flight job's id) rather
than starting a second concurrent job or silently clobbering the first.

## Component map

A functional deployment can include:

| Component | Required for | Notes |
| --- | --- | --- |
| TLS reverse proxy | Any Internet-facing API | Terminate HTTPS and forward only intended ports. |
| ASGI backend | All API operations | Runs FastAPI under gunicorn/Uvicorn worker; public HTTP default is port 5001. |
| PostgreSQL | All persistent user state | `DATABASE_URL` is mandatory; there is no current file-persistence fallback. |
| Enclave service | Encrypted read-side and decrypt workflows | Local mode is not hardware-attested. Keep its private port off the public Internet except for a deliberately designed attestation path. With optional hybrid recall enabled it also loads the local embedding model and receives the caller's plaintext derived card vectors from the backend; size its memory and CPU for that. |
| Runtime V2 worker pool | Hosted `/v1/model_api/chat/send` | Shares PostgreSQL and runtime-token configuration with the backend and publishes worker-capacity heartbeats. |
| Resident consumer | Independent agent Chat | Alternative to hosted Chat; polls and posts encrypted replies. |
| WebSocket ingest | Screen/broadcast ingestion | The ASGI background service binds the configured ingest port, normally 9998. |
| APNs credentials | Apple push and Live Activity | Optional; Chat storage works without push delivery. |
| Object storage configuration | Large frames, chat files, and onboarding archives where enabled | Inventory and back up this data separately from PostgreSQL. |
| Enclave diagnostic log collector | Optional operational history | Only validated content-free request logs and fixed worker events from the two enclave containers; local volume 30 days, optional operator R2 with a 90-day bucket lifecycle. |
| CPU history recorder | Optional private operational history | Provide a protected, path-allowlisted Docker socket proxy and a dedicated persistent volume; expose neither service publicly. |

Database operators can read the `provider_attempts` operational ledger, including
Runtime V2 Capture/Dream job correlation, provider/model, retry counts, wire
timings, HTTP status, and closed timeout/error categories. These plaintext
measurements exclude prompts, replies, URLs, headers, credentials, and raw error
text. Protect database access and backups accordingly; this does not enable
export to another service.

The production/test log collector uses a protected socket proxy, a dedicated
persistent volume, and a separate outbound bridge for R2. It does not join the
business-service network or mount the Docker socket. Compose bridges do not
enforce a destination-domain firewall. Leaving `R2_LOGS_BUCKET` empty keeps logs
in the local volume and disables external uploads. To enable delivery, provide
that dedicated bucket and existing R2 credentials, grant bucket access, and set
its **90-day lifecycle expiration** yourself. Content-free diagnostics, including
route templates and truncated user prefixes, then leave the CVM for operator
storage. Arbitrary container output is rejected, not exported. Docker logs lost
before collection cannot be reconstructed; local retention also limits offline
upload recovery to 30 days. See [the trust boundary](/docs/architecture#enclave-operational-logs-leave-the-vm-only-when-configured).

The managed Phala CPU-history topology is optional operational infrastructure,
not an application API. A self-hosted operator who adopts it must provide and
secure their own Docker socket proxy and persistent volume, keep the recorder
off public networks, and define retention appropriate to that deployment.
Copying this topology does not create tenant isolation or make a generic host a
confidential-computing boundary.

The resident consumer requires an `openssl` binary on `PATH` if any
user-configured [MCP server](/docs/workflows/mcp) is registered over HTTPS with a
certificate that does not chain to a public root. To trust such a server without
disabling verification, the consumer shells out to `openssl s_client` to fetch
and pin the server's own trust anchor. The managed runner image ships OpenSSL
3.0; a self-hosted host without it **degrades silently**. The anchor fetch fails
open, no CA is materialized, and the agent's connection to that MCP server fails
with an ordinary certificate-verification error and no log line naming the
missing binary. MCP servers reached over plain `http://`, or presenting a
publicly trusted certificate, do not need it.

Self-hosted `codex`-driven residents have one further requirement: a
self-signed MCP server must present a **certificate chain** (a CA certificate
plus a separate leaf certificate it signs), not a lone self-signed
certificate — `codex`'s TLS stack rejects a CA used directly as the server's
own certificate, even though `claude` accepts it. See
[MCP servers](/docs/workflows/mcp) for the `openssl` recipe.

A backend that returns `/healthz` can still be unable to decrypt Memory, process
hosted Chat, or persist data. Build readiness from component checks rather than
using `/healthz` alone.

## Deployment profiles

### API and ciphertext storage only

Run the backend, PostgreSQL, TLS, and optional WebSocket ingest. Account and
ciphertext storage routes can work, but enclave-backed reads and hosted Chat are
not complete. Use this only for development or a deliberately limited product.

### Single-operator functional stack

Add a local enclave service and either:

- an independent resident consumer connected to an agent entry point; or
- the pooled Runtime V2 worker required by hosted model API routes.

This profile can exercise end-to-end workflows but is not equivalent to a
hardware-attested deployment. Prefer one trusted tenant per host.

### Managed-production parity

Parity requires more than starting the same Python modules: confidential-VM
attestation, measured images/configuration, enclave key lifecycle, separated
runner capacity, secret distribution, database TLS, object-store policy,
monitoring, backups, incident response, and tested restore/rollback. The public
repository does not currently offer this profile as a supported turnkey
self-hosting product.

## Configuration inventory

Review the current source at the exact commit you deploy. At minimum, account for
these settings:

| Setting | Requirement |
| --- | --- |
| `DATABASE_URL` | Required. Use a dedicated PostgreSQL role and database. External connections must use TLS, such as `sslmode=require`, and should verify the server certificate where the environment supports it. |
| `FEEDLING_DATABASE_SCHEMA` | Defaults to `rds`, which applies the repository's normal Alembic chain at startup. `tee` is reserved for an independently owner-migrated managed database: startup becomes a read-only `alembic_tee_version` head assertion and fails closed on drift. Do not set it merely because PostgreSQL happens to run in a TEE, and never change it without switching every backend/worker DSN in the same maintenance window. |
| `PLAINTEXT_SHADOW_DATABASE_URL` | Managed-only optional target for the decrypted all-content shadow. It must identify a different TLS PostgreSQL database from `DATABASE_URL` and use a dedicated least-privilege app role. Supplying this credential makes the database, its WAL, replicas, snapshots, and backups plaintext recipients; it is not a failover or read target. Do not distribute the DSN to hosted workers or resident runners. |
| `FEEDLING_PLAINTEXT_SHADOW_ENABLED` | Defaults to `0` and accepts only literal `0` or `1`. Enable only on the elected main backend after the TEE primary, target schema, backup/restore evidence, full backfill, and strict verification are green. This gate is independent from `FEEDLING_PLAINTEXT_WRITES_ACCEPTED`: an explicit encrypted-tier account is still decrypted before entering the all-plaintext shadow. |

The project cannot measure how many route ③ self-hosted users depend on a
private provider URL, because their backend and logs never reach the managed
service. It therefore also cannot detect when a later compatibility change
breaks that configuration. Treat the private-base-URL switch as an explicit,
locally tested trust decision rather than a zero-cost compatibility promise,
and test provider setup, model listing, Chat, and usage at the exact commit you
deploy.

The resident reports the commit loaded by its running process in
`X-Feedling-Consumer-Commit`. Do not infer that identity by reading the current
checkout after startup: an operator may change the files without restarting the
process. When the built-in updater intentionally skips a backend target because
the diff is irrelevant to the resident runtime, it reports that target in
`X-Feedling-Consumer-Compat-Commit`. This suppresses stale-consumer reminders
only while the optional compatibility value matches the backend's current
target; it does not substitute for a missing running commit.

Worker count must be sized against PostgreSQL connection capacity. Each backend
worker owns a pool plus listener/election connections; increasing workers without
raising the database limit can turn an apparent capacity improvement into an
outage.

Runtime V2 conversation maintenance is always metadata-only: it advances exact
sequence/count coverage with local sentinels and never sends conversation
history to a model provider. MEMORY/STYLE is the long-term semantic layer, while
encrypted Chat rows remain the durable source ledger. Existing model-authored
summary segments remain readable until a metadata-only checkpoint replaces
them in the canonical frontier.

Runtime V2's parent PostgreSQL pool is capped at 8 connections and every
single-slot child at 2, for an approximate 24-connection budget with eight
children. Monitor per-pool healthy/busy/restarting slots, queue age and claim
latency, Enclave wait, database pool wait/timeouts, Profile stage progress, and
watchdog recovery before increasing any slot count. Recover a bad deployment by
redeploying the previously verified image or commit; there is no legacy mode
switch. Leave additive schema migrations installed and verify fresh Foreground
capacity and exact-claim recovery after recovery.

## Apple push without the official key (notify relay)

A self-hosted backend cannot push to the official iOS app: the APNs `.p8`
signing key belongs to the app developer and is never distributed. The hosted
service exposes a **notify relay** instead:

1. In the app (self-hosted mode), the user enrolls once; the app calls the
   official `POST /v1/notify-relay/register` and receives a relay auth token
   (`nrt_…`).
2. Your backend or agent calls the official `POST /v1/notify-relay/push` with
   the `X-Relay-Token` header to deliver alert notifications (`type: 1`) and
   Live Activity start/update/end (`type: 3/2/4`). Live Activity tokens rotate
   per activity — your deployment receives them via `POST
   /v1/push/register-token` and must forward the newest one on each call.

Operational notes: calls are rate limited per token (`429` + `Retry-After`),
and every relay call is logged on the hosted service with the push content
truncated to 512 characters for triage. Do not route content through the relay
that must not be retained there; a terse generic alert text avoids the
concern entirely. See the API reference (Notify Relay tag) for the full
request schemas.

## Building requires egress to GitHub Releases

The memory judgment kernel is an external package (`memgarden`, Apache-2.0) that
is installed at image build time from a version-pinned, hash-locked GitHub
Release wheel. A cold build therefore needs outbound access to `github.com` and
`release-assets.githubusercontent.com`. Builds fail loudly if the asset is
unreachable; there is no silent fallback.

Install from `backend/requirements.lock` with `pip install --require-hashes`, as
the reference Dockerfile does. Resolving the dependency loosely — or pointing it
at a branch instead of the pinned Release — makes your build unreproducible and
breaks the guarantee that your image contains the reviewed bytes. If your build
environment has no egress, mirror the two pinned wheels internally and keep the
same hashes.

## Bring-up sequence

1. Provision PostgreSQL, create a least-privilege application role, enforce TLS
   when traffic leaves the host, and record a tested backup/restore procedure.
2. Provision the persistent data and optional object-storage locations with
   ownership matching the non-root container user.
3. Generate runtime-token, enclave, TLS, provider, and push secrets in a secret
   manager. Keep tenant/provider credentials out of the runner's global
   environment where possible.
4. Build or pull images pinned to a reviewed commit/digest. Do not deploy a
   mutable `latest` tag.
5. Start PostgreSQL connectivity and the enclave path before the backend. The
   gunicorn startup hook applies Alembic migrations and fails if required hosted
   configuration is missing.
6. Start the backend, then the Runtime V2 worker or an independent resident
   consumer. Verify that worker capacity and heartbeats are fresh before testing
   hosted Chat.
7. Put the API behind HTTPS. Expose 443 publicly; expose the screen WebSocket
   port only if the client requires it and its authentication path has been
   reviewed. Keep PostgreSQL, runner control, and internal enclave ports private.
8. Register a test account with a real generated content public key and store the
   returned API key in a credential manager.
9. Exercise the readiness checks below with non-production test data.

## Readiness checks

`GET /healthz` is only the first check. A deployment should not receive user
traffic until all enabled capabilities pass:

- Backend process responds over the public TLS hostname.
- An authenticated `/v1/users/whoami` succeeds.
- A write followed by a read proves PostgreSQL persistence, then still succeeds
  after a backend restart.
- The enclave reports expected key/attestation information for the chosen trust
  model and completes a test envelope decrypt.
- Memory `index` and `fetch` complete instead of returning
  `enclave_unavailable`.
- Hosted Chat has a fresh runtime heartbeat for the user's fenced runtime (a
  Runtime V2 worker heartbeat, or a V1 resident supervisor heartbeat during the
  dual-runtime window) and a test turn produces an encrypted assistant
  response; or the resident consumer polls with fresh
  `X-Feedling-Decrypt-Status: ok` (enclave path) or `backend_ready`
  (effective-off backend path), with fresh
  `X-Feedling-Decrypt-Checked-At` headers, passes `POST /v1/chat/verify_loop`,
  and replies to an ordinary test turn in the account's effective content mode.
- Provider cache telemetry reports the expected route and usage fields. Where
  prompt caching matters operationally, run a two-turn cache-hit canary against
  the exact provider/model; do not infer a live hit from unit tests. The
  checked-in canary currently targets OpenRouter, not native Bedrock.
- If E2B artifact parsing is enabled, an uncached synthetic artifact is parsed
  through the configured template and emits one sandbox usage event. If it is
  disabled, the same cache miss fails as `sandbox_unavailable` without parsing
  in the backend or shared worker.
- Screen WebSocket ingest works if enabled.
- Push delivery works if APNs is configured; otherwise the operator has
  explicitly accepted that push is disabled.
- Backup restore has been tested in a separate environment, not merely scheduled.

Use synthetic accounts for probes. A health check must not mutate or decrypt a
real user's data.

## Backups and key lifecycle

Back up PostgreSQL and every enabled object store as one recovery set. Database
snapshots without large ciphertext objects can restore references that no longer
resolve. Protect the content/enclave key material separately: losing it can make
otherwise healthy ciphertext permanently unreadable, while leaking it changes
the privacy impact of a database backup.

PostgreSQL also holds encrypted Runtime V2 workspace bodies and
trajectory/review payloads. Conversation compaction does not authorize deletion
of raw Chat rows, and the 5,000-message constant is only a process hot-window
limit. Trajectory rows currently have no automatic time-based retention job, so
operators must choose and document an explicit retention/export/deletion policy
before enabling provider-backed failure review broadly.

Document recovery point and recovery time targets for your deployment; Feedling
does not supply them for self-hosted systems. Test restores after schema and key
changes. Encrypt backup media, restrict restore credentials, and audit access.

The public API has no individual API-key revocation endpoint. See [API key
lifecycle](/docs/api-keys#rotation-and-revocation-status) before deciding how an
operator will respond to a leaked client credential.

## Upgrade and rollback

- Read the [public changelog](/docs/changelog) and repository migration notes.
- Back up the database and object storage before applying a new image.
- Review Alembic migrations for forward and rollback implications; do not assume
  every data migration is automatically reversible.
- With RDS selected as primary, the Gunicorn master runs `db.init_schema()` and
  `alembic upgrade head` before it forks request-serving workers. Deploying a
  new image therefore applies the initial RDS schema migration automatically
  and fails startup if the configured database credential cannot migrate it;
  the separate trace-partition workflow is for rolling maintenance after the
  initial migration.
- If the managed decrypted shadow is enabled, apply every new `alembic_tee`
  head to that target before, or in the same maintenance window as, the TEE
  primary. The exact-head gate deliberately stops replication on a mismatch,
  even when a new primary-only table is not itself shadow-replicated.
- Stage the exact image and configuration against a restored copy of production
  data with credentials disabled or replaced.
- Keep the prior image and configuration, but do not roll application code back
  across an incompatible database migration without an explicit plan.
- Re-run every enabled readiness check after upgrade and restore drills.

The managed `test`, `pre`, and `main` push workflow compares deployment paths
against the last proven complete main-CVM and runner release, including required
compose authorization. A later documentation fix therefore retains code that a
failed or partial release never deployed. Resident consumer changes count in all
three environments. The generated image-pin commit is validated before it is used
as a comparison baseline; an arbitrary image edit is still a deployment change.

Only a known baseline with unchanged deployment content may skip deployment.
Missing or incomplete release history requires the normal deployment gates;
unreadable GitHub metadata or a superseded event stops the detection job with
`UNMEASURED`. History lookup is bounded to 20 earlier push runs from the latest
50 entries; reruns conservatively require reconciliation. This CI evidence is not
an independent measurement of live health or out-of-band changes. Existing HOLD,
image/topology checks, release compare-and-swap, authorization, and single-attempt
publisher claims still apply. No failed transaction is automatically re-signed
or resent by the change detector.

## Recovering a stopped test compose authorization

A failed compose authorization does not prove that a transaction was never sent.
The normal publisher refuses automatic retries after a prior intent or an
ambiguous broadcast. Operators must reconcile the original run, archived intent,
final journal, transaction and receipt, nonce, live compose hash, and on-chain
authorization before approving a recovery.

Before merging recovery tooling, an operator must set the repository variable
`TEST_COMPOSE_RECOVERY_HOLD=true`. The normal test API and runner deployment jobs
then fail explicitly at their first step, before any mutation; their results
must not be reported as successful deployment. This avoids a tooling merge
automatically replacing the frozen recovery target. Only the coordinating
operator may clear the hold after the recovery decision and deployment review.
The operator must read back the variable and drain existing running or queued
deployments before merging: older workflow revisions do not contain this guard.
HOLD is necessary for this recovery entrypoint but never substitutes for the
separate explicit authorization.

The CI manual operation `reconcile-test-compose` is restricted to the test runner
on Sepolia. It accepts an exact, reviewed authorization document and its SHA-256,
binding the original artifacts and transaction, the execution commit, a unique
recovery ID, and an expiry no more than one hour after issuance. It only accepts
the original pre-send `frozen_limits_insufficient` stop with no attempt markers.
Both the original two-file intent/failure archive and an archive containing its
optional `frozen-limits-check.json` diagnostic are supported. The diagnostic must
match the publisher's exact schema, integer and boolean types, pre-send phase,
zero-send result, frozen gas/fee values, and failed comparison arithmetic. It is
supporting evidence only: original intent bytes, source authorization, current
preflight checks, and the persistent claim remain required. Unknown extra files,
malformed or inconsistent diagnostics, and attempt markers are rejected.
An already-authorized compose returns without signing or sending. Otherwise,
recovery keeps the original transaction hash, nonce, gas limit, and fee; drift or
unknown evidence stops execution. Recovery does not deploy or restart a CVM.

The operation shares the normal test runner deployment lock, which does not
cover all users of the signing account. Recovery therefore refuses any other
active or queued repository workflow, incomplete workflow history, or a changed
test branch head, and repeats these checks before signing and broadcasting.
The coordinating operator must prevent new deployment admissions throughout the
recovery window, including other branches and external uses of the signing key.
The read checks are not an atomic lock against an administrator starting a new
workflow. If exclusive use cannot be assured, stop recovery.
Before loading the signer, it archives non-secret evidence in GitHub annotated tags and atomically
creates a claim for the original chain/contract/compose target. This claim is
shared across directories and recovery IDs and is never automatically removed.
A claimed or ambiguously sent transaction cannot be retried by this entrypoint.
Repository administrators must preserve the `compose-recovery-*` evidence and
claim tags; deleting or rewriting them invalidates the recovery safety evidence.
The execution token therefore needs repository contents-write and Actions-read
permissions. Dispatch permission and operator approval remain trust boundaries:
the document digest verifies exact approved bytes, not the identity of a human
approver. Private keys and raw signed transactions are never archived.

After authorization, independently verify the actual API and worker release and
health before declaring the deployment complete. An absent naturally occurring
diagnostic event remains unmeasured; do not generate paid or user-facing work to
fill that gap.

## Memory index request timing

Authenticated ASGI `POST /v1/memory/index` requests emit the best-effort operator
trace `memory.index.timing` under existing trace controls. Its `trace_id` uses the
existing access-log request ID when available. `detail.lane` is `index` or
`search`; top-level `status` is `ok`, `error`, or `cancelled`, and
`detail.http_status` is null when no route response status was obtained.

Top-level `dur_ms` measures dispatch through response construction, after
authentication and body parsing, and before telemetry emission. The bounded
`detail.segments` object contains:

- `queue_ms`: dispatch until the worker callable starts.
- `core_ms`: elapsed execution of the existing index core, including enclave
  calls. `core_state` is `not_started`, `running`, `completed`, or `failed`.
- `upstream_ms`: summed elapsed synchronous enclave calls within that core;
  `upstream_calls` counts calls started. `upstream_state` is `not_called`,
  `running`, `completed`, or `failed`.

Upstream time overlaps core time; do not add them. Return scheduling and response
construction can make `dur_ms` exceed queue plus core. Missing, uncalled, or
unfinished durations are null, not zero. Cancellation records the snapshot at
route exit; a worker may still finish later. A completed core can return a handled
error, so use the route status as well as segment states.

These events contain no request content, credentials, URLs, or exception text.
They do not change results, authentication, retries, timeouts, or worker limits.
Trace delivery can be disabled or dropped; missing events do not imply no traffic
or zero latency. The event does not establish the cause or frequency of historical
slow requests and does not backfill them.

## Runtime V2 provider call errors

V2 model-call `start`, `done`, and `error` events include the owning `job_id`
when available. Correlate using user, job, runtime actor, and lane; a shared
`trace_id` alone can mix separate jobs. This applies to newly emitted events,
including retained tail events, and does not backfill older records.

For an already approved, bounded local snapshot, run
`python tools/wake_failure_attribution.py snapshot.json`. Its JSON input has
`jobs` (`user_id`, `job_id`, `status`, `lane`) and flat `events`
(`user_id`, `job_id`, `actor`, `lane`, `type`, `provider`, `model`).
It counts distinct failed heartbeat jobs, accepts only matching `hosted_v2`
observations, and returns aggregate observation and route-coverage counts.
Duplicate events do not add jobs. Conflicting candidate job snapshots are counted
separately and excluded from confirmed failures; candidate counts equal confirmed
failures plus conflicts. Multiple observed routes remain explicit. It performs no database or provider calls and prints no
identifiers or model names. Snapshot completeness and acquisition remain the
operator's responsibility.

A start records a logical attempt, not proof of an HTTP request. A done or error
event describes one call, not the job's terminal cause or outcome. Missing or
sampled-out events remain unknown; this tool cannot establish a no-call count,
reconstruct historical failures, or change the legacy open-rate denominator.

The operator event `agent.model.call.error` retains the configured provider and
model, including failures during a wake direct-text correction. Its duration is
elapsed time for the current logical provider call, not the whole wake. Transport
retry counts are included only when the private attempt envelope records HTTP
attempts; absent evidence remains unknown, even when the correction allows only
one attempt. Error categories remain closed and exclude response bodies,
credentials, endpoints, and unpublished drafts.

These best-effort events preserve available job and trace linkage. An earlier
`agent.model.call.done` can precede a correction failure; it does not mean the
job completed. Analyses that join only completed model calls cannot attribute
all failures. This metadata change does not add calls, retries, or fallbacks,
and does not backfill historical traces.

## Runtime V2 exception observations

The operator trace event `v2.failure.observed` records exceptions caught by chat,
wake, turn setup, compaction, and trajectory-review workers. It links the job
and available trace ID to closed exception-family and error-code categories.
Only a valid HTTP status from a provider exception and its immediate explicit
cause are retained; unknown categories stay unknown. Messages, class names,
tracebacks, URLs, credentials, and provider response bodies are excluded from
this event. Capture-specific failure handling is outside this event’s scope.

These events follow existing trace controls and best-effort delivery. An event
can precede a retry or a lost-lease transition, so it is an exception observation,
not a terminal job outcome. Missing events do not prove success. Use durable
job outcomes for completion rates; this event neither backfills historical
failures nor changes public errors, retry policy, or model calls.

Capture and Dream attach a separate `provider_failure` object to their existing
restricted `turn_exception` trajectory when a provider exception becomes the
returned extraction failure. The object retains only the same closed exception
families, immediate explicit cause, and valid provider HTTP status. It is bound
to the exact exception raised for that returned failure; a later health or usage
error with the same error code does not inherit it. Provider messages, payloads,
and implicit exception context are excluded.

This adds no trace event or storage lookup. Existing trajectory access controls,
encryption, enablement, and best-effort delivery still apply. Refusal, output
truncation, recoverable output-budget fallback, and Dream's shared deadline keep
their existing diagnostics. `observation_only` does not prove a durable failure
transition or an upstream root cause, and a missing object is not proof that no
local exception occurred. This does not backfill old failures or change requests,
retries, budgets, public errors, or memory-write behavior.

## Minimum security checklist

- Run containers as non-root and keep the Docker socket out of application
  containers.
- Use exact CORS origins, HTTPS, security headers at the proxy, and request-body
  limits at both proxy and application boundaries.
- Redact API keys, runtime tokens, provider keys, link tokens, and recovery
  answers from logs and traces.
- Separate database, enclave, runner, and backup credentials; rotate them through
  a secret manager.
- Do not expose admin/debug routes or internal ports through the public proxy.
- Monitor authentication failures, `5xx`, database pool exhaustion, stale
  Runtime V2 per-pool heartbeats, slot restarts, Enclave waits, queue age, disk
  use, backup age, and trace-partition health. Treat a non-empty
  `trace_events_default` partition as degraded even when writes still succeed;
  the initial migration creates 29 past and 60 future Beijing-day partitions,
  so schedule maintenance before that horizon expires. Run
  `python -m admin.trace_events_partitions` outside the request-serving path
  with a migration-capable credential in
  `TRACE_EVENTS_MIGRATION_DATABASE_URL` (the existing TEE workflow may continue
  to use `TEE_MIGRATION_DATABASE_URL`); never grant DDL to the application role
  solely for partition repair. Repository operators can invoke the guarded
  **RDS trace partition maintenance** workflow for `test`, `pre`, or `prod`;
  production execution remains a separate, explicit operator action.
- Keep unrelated tenant code and secrets out of a shared process runner.
- Commission an isolation and abuse review before offering the deployment to
  untrusted public users.

## Resident proactive failure claims

The resident consumer can attach an optional `failure_diagnostic` to an existing
`POST /v1/proactive/jobs/{job_id}/status` failure report. The request contains
`v: 1` and one `reported_error_class` from the documented closed vocabulary.
The backend records `source: consumer_reported` only after checking the original
consumer identity against the current job row. This checks association, not the
truth of a provider diagnosis: a client can report a valid category incorrectly,
and a consumer identifier is not an execution-attempt token.

Old clients need no changes. Missing diagnostics stay unknown; malformed claims,
unknown versions/classes, extra keys and unavailable bindings degrade without
changing the original status operation. Persisted objects contain only `v`,
`reported_error_class`, `source` and `state`. States are `reported`, `missing`,
`invalid`, `binding_unavailable` and `conflicting_reports`; all states other than
`reported` have class `unknown` and source `none`. A later non-failure state clears
the field to null. Repeated conflicting claims are retained as a conflict rather
than choosing a cause. No exception bodies or credentials enter this new field.
Existing job responses can expose it under the same tenant authorization.

Operators can summarize an already authorized, bounded snapshot with
`python tools/resident_failure_diagnostics.py snapshot.json`. Input has
`schema_version: 1` and a `jobs` array whose entries contain `user_id`, `job_id`
and the stored job `doc`. The tool never queries a service or database, and does
not authenticate snapshot provenance. It limits input to 16 MiB and 100,000 rows,
deduplicates by user/job, excludes conflicting job states from confirmed failures,
and emits only fixed aggregate counts. These are reported categories, not verified
causes or opening/delivery rates. Missing historical evidence is not reconstructed.
The projection follows the existing proactive-job retention and deletion lifecycle.


### Plaintext automatic recall boundaries

For an authenticated effective-off account, automatic recall has no enclave
content fallback, including rollout `off`/`shadow`, old sealed input and local
failure. Required turn content and subject ownership are validated separately
from optional candidate payloads. An invalid same-owner candidate makes the
whole recall result unavailable; an ownership, authorization, required-content
or unknown shared-read failure stops the turn. See the [memory workflow](./workflows/memory)
for fixed-frontier, unavailable-count and deadline behavior. Whoami public
attestation metadata remains compatible and may still make network requests.

### Attestation release and policy metadata

`/attestation` includes declared `enclave_release` and `app_auth` metadata.
These fields are configuration claims, not independent proof of the loaded
image digest or the effective platform KMS/AppAuth binding. The quote's
REPORT_DATA binds the content public key, TLS fingerprint and version; it does
not directly bind these metadata fields. Verify platform policy separately.

The test compose explicitly declares the test AppAuth contract on Sepolia
(chain 11155111) for both enclave listeners. Its compose URL names the mutable
`test` branch for navigation; it is not an immutable release proof. Use the
measured compose hash and recorded release/pin evidence for that purpose.
Missing or malformed `enclave_release.image_digest` and `app_auth.deploy_tx`
are JSON `null`, including empty values and development placeholders. Consumers
must handle null and must not create a transaction link without a transaction.
A configured digest or transaction remains a declaration, not verification.

The existing deployment attestation gate compares the content public key with
its baseline. The canary compares that key with the backend advertisement and
checks an encrypt/decrypt round trip. Neither verifies AppAuth contract/chain,
image digest, compose URL, or DCAP quote validity. A successful gate or canary
must not be presented as complete policy verification.
