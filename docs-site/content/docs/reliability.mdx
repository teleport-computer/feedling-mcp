---
title: Reliability and request behavior
description: Pagination, limits, timeouts, retries, and idempotency rules for Feedling clients.
---

Feedling does not have one global pagination, rate-limit, timeout, or idempotency
contract. Apply the operation-specific schema in the API reference. The rules
below describe the public behavior that clients can safely share.

## Pagination

There is no universal opaque cursor. Timestamp formats and ordering differ by
resource.

| Endpoint family | Parameters | Ordering and continuation |
| --- | --- | --- |
| `GET /v1/chat/history` | `limit` 1–200; preferred `after_seq` / `before_seq`; legacy `since` / `before` Unix seconds | No cursor returns the latest page. Sequence cursors are exact even when messages share a timestamp. Use `oldest_seq`, `latest_seq`, `has_more_older`, and `has_more_newer`. |
| `GET /v1/memory/list` | `limit` up to 200, `since` ISO-8601 | Newest `occurred_at` first. The implementation keeps records whose `occurred_at >= since`, so de-duplicate by memory ID at page boundaries. `total` is the filtered count before slicing. |
| `GET /v1/perception/photos` and `/items/{kind}` | `limit` 1–200, default 20 | Returns the most recent items. These endpoints do not currently return a continuation cursor. |
| Event and receipt streams | Usually `since` plus `limit` | `since` is endpoint-specific; inspect the operation contract before assuming Unix time or ISO-8601. |

For Chat, use sequence cursors in new clients. A robust older-page loop is:

1. Request the latest page without a cursor.
2. Render and de-duplicate by `message.id`.
3. While `has_more_older` is true, request `before_seq=<oldest_seq>`.
4. Stop if the returned page is empty or its `oldest_seq` does not advance.

For forward Chat synchronization, persist `latest_seq` only after the page has
been processed. Request `after_seq=<latest_seq>` and continue while
`has_more_newer` is true. IDs remain the final de-duplication key. Timestamp
cursors stay available for older clients, but cannot distinguish messages that
share a timestamp and therefore are not the lossless contract.

## Rate limits and capacity responses

The public API does not currently publish one account-wide request quota, and it
does not guarantee standard rate-limit headers on every response. Do not hardcode
a requests-per-minute value that is absent from the endpoint documentation.

`429` is endpoint-specific. For example, Memory reflection creation can use it
for a relationship-age business cap; retrying that response seconds later will
not help. A provider-backed operation can also surface upstream capacity
pressure. Inspect the response `error` and `detail` before classifying a `429` as
transient.

When `Retry-After` is present, honor it. When it is absent and the error is
clearly temporary, use exponential backoff with full jitter. A reasonable client
starting sequence is approximately 1, 2, 4, 8, then 16 seconds, randomized from
zero to the current cap. This is client guidance, not a server SLA.

## Timeouts and long polling

Both Chat and proactive job polls accept a `timeout` in seconds, default to 30,
and cap it at 60. A long poll that reaches that timeout normally returns `200`
with an empty collection and `timed_out: true`. Start the next poll; do not log
that response as an outage.

Hosted Chat waits briefly for a runtime response but still returns `202` whether
the assistant message is ready or not. The current server-side wait window is
about eight seconds; it is an implementation detail, not a latency commitment.

Suggested client timeout starting points:

| Request type | Client timeout |
| --- | --- |
| TCP/TLS connect | 10 seconds |
| Ordinary JSON operation | 30 seconds |
| Hosted Chat send | At least 20 seconds |
| Long poll | Requested `timeout` plus at least 10 seconds for network overhead |
| Large upload | Size- and network-aware; do not reuse the ordinary JSON timeout blindly |

These values are defensive defaults, not availability or latency guarantees.
Applications should make them configurable for self-hosted deployments.

## Provider health and proactive retries

Feedling tracks whether an account's configured model provider is producing
usable replies. If an account has no successful provider response for 48 hours
and its latest failures have continuously required user action for at least one
hour, such as an invalid API key, exhausted quota, or unavailable model name,
Feedling pauses model-backed proactive work for that account. This covers
automatic heartbeat, screen-watch, capture, and dream work in both resident
Runtime V1 and hosted Runtime V2.

Foreground Chat remains callable and is never blocked by this proactive gate.
User-initiated manual wakes also remain callable. While automatic proactive work
is paused, one automatic proactive probe is allowed every 24 hours.
Any usable provider reply, including a foreground Chat reply, or a successful
provider validation in Settings restores normal proactive work immediately.
Temporary provider failures such as rate limits and upstream `5xx` responses do
not put an account into this state.

Resident runtimes report provider outcomes through
`POST /v1/model_api/runtime_error`. The optional `provider_result` field is
`success` or `failure`; failures should include the classified `error_class`.
An error fallback generated without a usable provider reply must not be
reported as a success.

Runtime V2 treats output containing only whitespace, punctuation, or separator
characters as a truncated provider reply rather than assistant content.
Foreground Chat replaces that fragment with the standard visible fallback and
attributes it to a temporary upstream-provider failure. Automatic wake lanes
fail silently instead: they write neither a chat bubble nor an error chip.
Letters, numbers, CJK text, and emoji count as usable reply content.

A relay that cuts the provider stream can also split one internal control
envelope across the reasoning and content channels, leaving a bare JSON tail
(for example `…"reason":"…"}]}`) in the visible reply while its head sits in the
reasoning channel. Such torn fragments are never delivered as assistant content:
when the two channels rejoin to a complete control envelope, or the reasoning
channel independently carries the envelope's head, the visible fragment and its
paired reasoning are both dropped. Foreground Chat then uses the standard visible
fallback; automatic wake lanes fail silently and record the suppression. The
reconstructed control action is used only to confirm the split — it is never
executed, since a turn corrupted in transit is not a trustworthy instruction. A
message that merely looks JSON-like on its own (a user discussing code or
configuration) is preserved in Foreground Chat.

For a custom or otherwise unaudited model route without an explicit context
window, Runtime V2 uses a 65,536-token default. With the standard 4,096-token
output reserve and 5% safety margin (3,277 tokens), 58,163 tokens remain for
input.
Self-hosted operators can override the default with
`FEEDLING_V2_UNAUDITED_DEFAULT_CONTEXT_WINDOW_TOKENS`; setting it to `0`
restores fail-closed configuration. Explicit route metadata, audited model
families, and deployment overrides keep precedence over this fallback.

Runtime V2 takes one temporal snapshot for each chat or wake turn.
The prompt receives the current UTC time, the user's local IANA timezone and
local time, the age of the latest genuine user message, and timestamp metadata
for the verbatim conversation tail. The registered account timezone takes
precedence over the latest stable device-perception timezone; users without
either value fall back to UTC. Temporal metadata is appended as untrusted
application data and does not change the original conversation messages.

Runtime V2 selects recent context in complete user-seeded turns rather than a
raw message count. Foreground Chat targets up to 40 turns; heartbeat,
agent-scheduled, manual, and screen-watch wakes target up to 16. A smaller
provider window may reduce the replay to the largest newest suffix that fits,
but only after those rows are durably represented by the encrypted summary.
The summary, every uncovered source row, the current request or wake nudge, and
the provider-native tool transcript remain required and are never clipped.
This keeps the union of summary coverage and exact rows complete even when
optional replay shrinks between provider rounds.

The previous wake window was 20 messages, approximately 10 ordinary
user/assistant turns. A 16-turn wake can therefore replay about 60% more
conversation in the common two-message shape. Relative to the 40-turn Chat
target, it replays 60% fewer turns. Provider and compaction calls use the
account's configured BYOK credential, so the account owner bears those token
costs. Actual usage depends on message size, summary size, tools, and the
provider's context limit.

## Genesis plaintext processing

New clients use a two-step flow. `POST /v1/genesis/imports/plaintext/estimate`
parses and encrypted-stages the upload without making an LLM call, then returns
per-material `windows` / `est_tokens`, `est_total_tokens`, and an optional
`recommended_model`. `POST /v1/genesis/imports/plaintext/commit` accepts the
returned `staged_id` and an optional `distill_model`. The override applies only
to that Genesis job; the configured chat model is unchanged. Missing, consumed,
and expired stages return distinct `staged_import_not_found`,
`staged_import_consumed`, and `staged_import_expired` errors.

`POST /v1/genesis/imports/plaintext` allows one processing plaintext import per
account. A second submission returns `409 import_job_active` and the existing
`active_job_id`; clients should display or poll that job rather than retrying
the unchanged upload. Done and failed jobs release the account slot.

The worker uses the first real model request as a canary with a default
60-second timeout. A timed-out canary ends the job with
`distill_model_too_slow`; changing to a faster model is required before retry.
Other provider configuration failures retain their specific error class and
remediation guidance.
Later provider timeout failures make at most two attempts. This timeout cap does
not reduce the existing three-attempt budget for provider `429` and retryable
`5xx` responses.

Each successful map window is checkpointed before its public progress count is
advanced. The checkpoint's candidates are stored as an encrypted shared
envelope, not plaintext workflow metadata. Re-submitting the same failed
`client_job_id` or input resumes that job, skips checkpointed map windows, and
starts again from the unfinished map or reduction work. Status and onboarding
validation retain the durable `processed_chunks` count and per-material
`windows_done` / `windows_total` values after failure; only a completed job
reports 100 percent.

Job status also exposes `identity_ready` and material entries ordered as AI
persona, user profile, memory summary, then chat history. Material status uses
`queued`, `processing`, `failed`, or `done`; `cards` reports the durable mapped
candidate count instead of a placeholder.

Automatic Runtime V2 heartbeat and agent-scheduled wake failures use a
persistent per-user exponential retry delay. The delay starts at 60 seconds
and is capped at one hour; a successful automatic wake clears it. A new
genuine user message invalidates an older delay immediately. Manual wakes and
screen-watch events bypass this short-horizon guard. Sustained provider
failures remain the responsibility of the separate provider health circuit.

## Retry safety

Classify by operation semantics, not only by HTTP method. In particular,
`GET /v1/perception/app_open` and `GET /v1/perception/app_close` record an
event and are not read-only.

| Situation | Safe default |
| --- | --- |
| A read-only `GET` or `HEAD` fails before a response | Retry with bounded backoff. |
| A long poll returns `timed_out: true` | Poll again immediately. |
| `429` or `503` on a read | Honor `Retry-After` if present; otherwise retry only when the error is documented as temporary. |
| A mutating request fails before any bytes are sent | It can be retried if the HTTP library can prove that condition. |
| A mutating request times out after transmission | Treat the result as unknown. Read current state or reconcile by a stable resource ID before retrying. |
| `409` | Resolve the represented state conflict; do not retry unchanged. |
| `400`, `401`, `403`, or `404` | Fix the request, credential, permission, or resource reference first. |

Cap retry attempts and total elapsed time. Preserve the same logical operation ID
in client logs, but never log credentials or encrypted body material. Retain a
server `request_id` when present.

## Idempotency

Feedling does not currently implement a service-wide `Idempotency-Key` header.
Sending one does not make a write idempotent unless an individual operation says
otherwise.

Common consequences:

- Retrying `/v1/chat/response`, `/v1/memory/add`, a Perception collection
  upload, `app_open`, or `app_close` can create duplicate effects.
- A client-generated envelope or memory ID helps reconciliation but is not a
  documented create-if-absent guarantee.
- `POST /v1/model_api/chat/send` and `POST /v1/chat/message` accept an optional
  UUID `client_msg_id`. Persist it before sending and reuse it after an ambiguous
  timeout. For the same user and UUID, retries during the 600-second window
  return the first stored row and do not enqueue another turn. Omitting the
  field retains the legacy non-idempotent behavior.
- Repeating a one-time link-token claim returns a conflict rather than the raw
  API key again.
- Repeating a delete can return `404` after the first request succeeded.
- Account reset invalidates the credential used to call it. A lost success
  response followed by `401` requires state-aware handling, not an automatic
  second reset.

Where exactly-once user experience matters outside those two Chat operations,
assign a client operation ID in your own state, persist it before the call, then
reconcile against the resulting resource stream. The Chat guarantee is bounded
to its 600-second server window; it is not unbounded exactly-once delivery.

## Payload and response evolution

Enforce documented request limits before encoding base64; base64 increases wire
size. Unknown response fields must be ignored so additive API changes do not
break clients. Do not depend on object key order or human-readable error text.
See [versioning and deprecation](/docs/versioning) for the current compatibility
policy.
