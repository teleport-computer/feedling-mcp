---
title: MCP servers
description: Connect your agent to remote MCP tool servers, including plain HTTP, private-network, and self-signed endpoints.
---

Feedling lets each account register up to 10 remote [MCP](https://modelcontextprotocol.io)
servers (streamable HTTP transport). The active agent runtime calls the tools
those servers expose: a self-hosted runtime dials from your machine, while
Hosted Runtime V2 dials from its cloud worker. The management API stores the
configuration and does not connect at save time; its explicit `/test` operation
is the only control-plane probe.

Every `/v1/chat/poll` response includes a `user_mcp.fingerprint` that changes
whenever your server list changes, so a resident consumer can re-materialize
its local MCP config without polling `/v1/mcp/servers` on every turn. See the
[Chat workflow](/docs/workflows/chat) for that poll shape.

**Trust boundary:** Connecting and enabling a server lets its tool names and
retained structural input schemas enter the model-facing tool catalog, where
they can influence tool selection. Only connect servers operated by people or
organizations you trust. Feedling strips prompt-bearing catalog prose and
treats MCP tool output as untrusted external content that write-taints later
rounds; a server's `readOnlyHint` also grants no parallel-read privilege unless
the exact current catalog fingerprint has been explicitly approved.

## Add or update a server

```http
POST /v1/mcp/servers HTTP/1.1
Host: api.feedling.app
Content-Type: application/json
X-API-Key: YOUR_FEEDLING_API_KEY

{
  "name": "search",
  "url": "https://mcp.example.com/mcp",
  "headers": {
    "Authorization": "Bearer sk-..."
  },
  "enabled": true
}
```

`name` (`^[a-z0-9_-]{1,32}$`) is the update key — posting an existing name
replaces that server's config. `headers` are sent with every MCP request (max
20 entries, 8192 bytes combined across names and values); `Host` is a
forbidden header name.

```json
{
  "id": "srv_1a2b3c4d",
  "name": "search",
  "enabled": true,
  "url_hint": "mcp.example.com",
  "header_names": ["Authorization"],
  "has_ca": false,
  "created_at": "2026-07-16T00:00:00Z",
  "updated_at": "2026-07-16T00:00:00Z"
}
```

The response never echoes back the URL, header values, or CA certificate.
`url_hint` is the hostname only; `header_names` lists header keys only;
`has_ca` reports whether a CA certificate is currently stored.

`GET /v1/mcp/servers` returns `{"servers": [...]}` with the same shape.
`PATCH /v1/mcp/servers/{name}` with `{"enabled": false}` toggles a server
without resending the URL, headers, or CA. The same PATCH also updates encrypted
read-only approvals as described below. `DELETE /v1/mcp/servers/{name}` removes
the server.

## Network requirements

`url` accepts `http://` and `https://`, including loopback (`127.0.0.1`,
`localhost`), private-network (`10.x`, `192.168.x`, `172.16–31.x`), and raw IP
literal hosts. Saving the config does not connect to the URL, so none of those
forms are rejected at `POST /v1/mcp/servers`. `POST .../test` does connect from
the API backend when explicitly requested. Hosted Runtime V2 also contacts every
enabled server at the start of each chat turn for `tools/list`, before any later
tool calls.

What reaches the server at call time depends on where your agent runs:

- **Self-hosted / local agent** (you run the resident consumer or CLI agent
  yourself): it can reach anything your machine can reach, including
  `localhost` and your LAN.
- **Hosted agent runtime** (Feedling runs your agent for you, in a managed
  confidential VM — see [architecture](/docs/architecture)): it runs in the
  cloud and **cannot reach machines on your home or office network**, the
  same as any other cloud workload. This is a routing fact, not a permission
  the backend is withholding.

If you're on the hosted runtime and want to expose a local MCP server, put a
tunnel in front of it — [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/),
[Tailscale Funnel](https://tailscale.com/kb/1223/funnel), or [ngrok](https://ngrok.com/) —
and register the tunnel's public HTTPS address instead of `http://localhost:...`
or a LAN IP. Registering the raw local address will save without error and
then simply never be reachable by the hosted agent. **This is the most common
cause of "I added my MCP server and it doesn't work" for hosted users** — the
config saved correctly; the cloud agent just has no path to your machine.

### Plaintext `http://`

Choosing `http://` sends every configured header — including any API key in
`Authorization` — unencrypted over the network to reach your server. This is
supported as an explicit, informed choice (for example, a server that only
exists on a network you already trust), not a default recommendation. Prefer
`https://` whenever the server can offer it.

## Self-signed certificates and private CAs

Self-signed MCP servers work with **no configuration**: register the URL and
nothing else. When your agent — hosted or self-hosted — connects to a server
whose certificate doesn't chain to a public root, it fetches that server's
certificate chain, picks the anchor, and adds that anchor to its own local
trust store before making the real TLS connection.

**This adds trust; it does not disable verification.** TLS verification
stays on throughout: the server still has to present a certificate that
chains to the anchor it fetched, and it still has to prove it holds the
matching private key during the handshake. A server that merely claims to be
yours, without that key, still fails. This is the same trust model as
installing a corporate or personal CA in a browser; it is not "skip
certificate checking." We deliberately rejected the alternative of skipping
verification: `claude` can only turn TLS verification off for its whole
process — which would also stop it from verifying its own calls to
Anthropic — and `codex` has no such switch at all.

### This is trust-on-first-use (TOFU) — say it plainly

The automatic anchor is pinned at the moment your agent *first* connects to
that server. If that specific first connection is intercepted — before your
agent has ever reached the real server — it will pin the interceptor's
certificate instead, and every later connection will trust the wrong party.
This is the same exposure as SSH's "the authenticity of host '...' can't be
established" prompt the first time you connect to a new machine. It is a
real window, and it is the price of the zero-configuration default: nobody
has to find an out-of-band channel to hand you a CA. When you paste `ca_pem`
yourself (see below), the paste itself — you getting the certificate from
wherever you got the server, not through the connection being secured — is
that out-of-band anchor; the automatic path has no equivalent, and doesn't
claim to.

**Be precise about what a bad pin exposes.** The anchor doesn't land in a
store scoped to that one server — it lands in your agent runtime's global
trust store. `SSL_CERT_FILE` governs *every* outbound TLS connection `codex`
makes, including its own calls to `api.openai.com`; `NODE_EXTRA_CA_CERTS`
governs every one `claude` makes, including its calls to
`api.anthropic.com`. So if the first-connection intercept succeeds, the
attacker's CA is trusted for anything that agent talks to afterward, not
just the MCP server you configured — this is a global trust escalation for
that agent, not a scoped one.

That global scope isn't new here: neither runtime offers per-server trust
scoping, so the pre-existing "paste `ca_pem` yourself" path carries the same
global exposure once a certificate is stored, and always has. What automatic
fetching adds is narrower — it moves the moment of trust from a manual,
out-of-band paste to a connection your agent's code initiates on its own,
which is a connection an attacker could in principle be positioned to
intercept. Put together: **attacker-specific TOFU window, on a global trust
store** — a real, non-trivial exposure, but still far narrower than the
alternative of disabling TLS verification for the whole process (which is
open to every attacker, at every moment, with no window to miss). That
trade-off is why this design proceeds with TOFU rather than either pasting
being mandatory or verification being disabled.

### `ca_pem` is now optional, and manual always wins

Pasting the CA certificate yourself is no longer required, but it's still
supported — it's the escape hatch for anyone who wants stronger-than-TOFU
assurance. Fetch the CA certificate out-of-band (from wherever you obtained
the server in the first place) and paste it into `ca_pem` in PEM format:

```json
{
  "name": "search",
  "url": "https://mcp.internal.example.com/mcp",
  "ca_pem": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----"
}
```

`ca_pem` is limited to 32,768 bytes and is validated as parseable PEM at save
time (`invalid_ca` if it doesn't parse, `ca_too_large` if it's over the
limit). Send an empty string to clear a previously stored CA.

**A manually-pasted `ca_pem` always takes priority over the automatic
fetch.** If one is stored for a server, your agent uses it as-is and never
attempts to fetch and pin an anchor for that server. Clearing it doesn't
turn the automatic fetch off — it just means that server goes back to relying
on TOFU instead of your pasted anchor.

### Publicly-trusted servers are never touched

If your server presents a certificate that already verifies against the
public root store (Let's Encrypt, a commercial CA, etc.), your agent detects
that and pins nothing for it — the connection just uses the ordinary system
trust store, like any other HTTPS client. This was verified directly against
a real Let's Encrypt-issued server: it produces no pinned CA file at all.

Pinning a publicly-trusted certificate anyway wouldn't actually break on
rotation — both delivery mechanisms are additive (`NODE_EXTRA_CA_CERTS` adds
to Node's trust store rather than replacing it; `SSL_CERT_FILE`'s content is
the public CA bundle *plus* whatever gets pinned), so the public roots stay
trusted either way. The real reason to skip it is narrower and more
important: every automatic pin is a moment of exposure, described in detail
in the "trust-on-first-use" section above — and pinning a server that
already verifies normally would open that window for zero benefit.
Auto-fetching is reserved for the servers that actually need it — the
self-signed ones — to keep that exposure as small as possible.

Both first-party agent runtimes verified the self-signed path end-to-end
against a real self-signed server (a real TLS handshake against a real
certificate, not a mock):

| Runtime | Self-signed CA support |
| --- | --- |
| `claude` | Supported and verified. |
| `codex` | Supported and verified. |

`has_ca` on the server record reports whether a **manually pasted** CA is
currently stored — it does not reflect anchors your agent fetched and pinned
automatically, since those live only in your agent's local runtime and are
never sent to this backend. The certificate content itself is never returned
by any endpoint.

### Hosted-runtime users: this does not change reachability

Automatic trust-anchor fetching only removes a certificate-pasting step; it
does not open a network path. If your MCP server only exists on your home or
office network, the hosted agent runtime still cannot reach it — see
[Network requirements](#network-requirements) above. Put a tunnel in front of
it and register the tunnel's public address, same as before.

## Verify a server

```http
POST /v1/mcp/servers/{name}/test HTTP/1.1
Host: api.feedling.app
X-API-Key: YOUR_FEEDLING_API_KEY
```

```json
{
  "ok": true,
  "tool_count": 2,
  "tool_names": ["search", "fetch"],
  "read_only_tool_fingerprints": {
    "search": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  }
}
```

This runs a best-effort `initialize` → `tools/list` probe **from this
backend's own network**, as a convenience for validating servers that are
publicly reachable over `http://` or `https://`. It is not required before your
agent can use a server, and it is not authoritative for servers your agent can
reach but this backend cannot.

**A `400 unreachable_from_backend` response does not mean the server failed to
save.** The server was already saved successfully by `POST /v1/mcp/servers`.
It only means this backend process could not reach the host — typically
because it's a loopback/private-network address, or a tunnel endpoint that
only your agent's environment is allowed to reach. Do not surface this as a
configuration failure. For those servers, skip this probe and instead ask
your agent to call the MCP server directly in a chat turn to verify it.

Other `400` kinds from this endpoint:

| Kind | Meaning |
| --- | --- |
| `unreachable_from_backend` | Saved successfully; this backend's network can't reach the host. Verify from your agent instead. |
| `dns` | The hostname did not resolve. |
| `dns_busy` | The backend resolver is at capacity; retry later. |
| `tls` | Certificate/TLS handshake failure — check `ca_pem` if the server uses a private CA. |
| `transport` | The connection failed before a valid HTTP response arrived. |
| `timeout` | Connect or read timeout. |
| `response_too_large` | An MCP response exceeded the 1 MiB probe limit. |
| `http_401` / `http_403` / `http_404` / `http_4xx` / `http_5xx` | The server responded with an HTTP error status. |
| `protocol` | The response wasn't a valid MCP handshake (bad JSON-RPC envelope, redirect, or empty SSE stream). |
| `decrypt_failed` | The stored config could not be decrypted for this caller. |

This probe runs from this backend's own network and only ever trusts a
**manually-pasted** `ca_pem` — it does not perform the automatic
trust-on-first-use fetch described above, because that fetch happens inside
your agent's own runtime, not here. A self-signed server with no manually
pasted `ca_pem` will fail this probe with `tls`; that's expected, and it
still works fine for your agent once your agent connects to it.

`404 not_found` means no server with that name exists.

## Approve safe parallel reads

Runtime V2 runs platform reads and approved MCP reads concurrently within a
model-issued tool batch. MCP mutations remain serialized with platform writes
in model order. A remote server's `readOnlyHint` is only a claim, so it does not
grant parallel execution by itself.

After a successful `/test`, show the user the read-only candidates and require
an explicit choice. The probe returns at most 64 candidates and omits tool names
that PATCH cannot accept (control characters or more than 256 characters).
Then PATCH only the selected name/fingerprint pairs:

```http
PATCH /v1/mcp/servers/search HTTP/1.1
Host: api.feedling.app
Content-Type: application/json
X-API-Key: YOUR_FEEDLING_API_KEY

{
  "read_only_tool_fingerprints": {
    "search": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  }
}
```

The PATCH decrypts and re-seals the existing server config, preserving its URL,
headers, and CA; clients do not need to retain or resend those secrets. Runtime
V2 grants read-only execution only when the live tool still has strict
`readOnlyHint: true` and the fingerprint of its current name/schema/hint exactly
matches the encrypted approval. Catalog drift or a missing approval fails closed
to serialized mutation handling. Send an empty object to revoke every approval:

```json
{"read_only_tool_fingerprints": {}}
```

## Write-time error kinds

`POST /v1/mcp/servers` returns `400` with one of these `error.kind` values
when the payload is rejected, or `409 cannot_encrypt` if the server-side
envelope could not be built (retry):

| Kind | Meaning |
| --- | --- |
| `invalid_name` | `name` doesn't match `^[a-z0-9_-]{1,32}$`. |
| `invalid_url` | `url` isn't `http://` or `https://`, or has no host. |
| `invalid_request` | The body isn't an object or contains an unknown field. |
| `invalid_headers` | `headers` isn't an object or contains a non-string value. |
| `invalid_enabled` | `enabled` isn't a JSON boolean. |
| `too_many_headers` | More than 20 header entries. |
| `headers_too_large` | Combined header names and values exceed 8192 bytes. |
| `forbidden_header` | A header name is `Host` (case-insensitive). |
| `invalid_ca` | `ca_pem` isn't a string containing parseable PEM. |
| `ca_too_large` | `ca_pem` exceeds 32,768 bytes. |
| `invalid_read_only_tool_fingerprints` | `read_only_tool_fingerprints` isn't an object. |
| `too_many_read_only_tool_fingerprints` | More than 64 approval entries were supplied. |
| `invalid_read_only_tool_name` | A tool name is empty, longer than 256 characters, or contains a control character. |
| `invalid_read_only_tool_fingerprint` | A fingerprint isn't a lowercase 64-character SHA-256 hex string. |
| `too_many_servers` | The account already has 10 servers and `name` doesn't match an existing one. |

`PATCH /v1/mcp/servers/{name}` rejects an empty or non-object body, unknown
fields, or unsupported values with `invalid_patch` / `invalid_enabled`; approval
validation uses the same four `read_only_tool_fingerprints` errors above.
`decrypt_failed` has no internal exception detail. A re-encryption failure
returns `409 cannot_encrypt` and leaves the old config unchanged.

See the [MCP tag in the API reference](/docs/api-reference) for the full
request/response schema of every operation.
