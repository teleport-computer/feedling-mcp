Feedling exposes two chat paths with different responsibilities.

| Path | Use it when | Who encrypts the user message? |
| --- | --- | --- |
| `POST /v1/model_api/chat/send` | A user-facing client sends a turn to a configured hosted agent runtime. | Feedling builds the envelope for the registered user. |
| `/v1/chat/message` → `/v1/chat/poll` → `/v1/chat/response` | You operate an independent resident consumer. | The posting client and resident consumer build envelopes. |

The hosted path is asynchronous. A successful send is always `202`, even when
the assistant ciphertext is already available. It never returns a plaintext
assistant reply.

## Hosted chat

Before sending, the account needs a content public key, a configured model route,
and a live Hosted Runtime V2 worker pool. Runtime-control, worker-liveness,
kill-switch, and admission failures are returned before the user message is
stored.

The account's selected onboarding route is the execution-ownership switch.
Hosted Runtime V1 is eligible only when that selector is positively
`model_api`; Runtime V2's `v2`/`draining` ownership fence excludes V1
independently. Switching the selector to `resident` or `official_import`
atomically deactivates the active V1 model route. Switching back to `model_api`
restores the most recently updated tested-ok route when one exists. Missing or
legacy selector state fails closed for V1, so it cannot silently run beside an
independent resident.

### 1. Send the turn

At least one of `message`, `image_b64`, or `file_b64` is required. `message` is
limited to 12,000 characters. `context_refs` accepts at most eight references;
currently memory references are the useful public form.

```http
POST /v1/model_api/chat/send HTTP/1.1
Host: api.feedling.app
Content-Type: application/json
X-API-Key: YOUR_FEEDLING_API_KEY

{
  "client_msg_id": "76ba05cf-d6ee-45af-a1e6-091dbd8c1f0a",
  "message": "Use the selected memory to help me plan tomorrow.",
  "context_refs": [
    {
      "type": "memory",
      "id": "mom_7f20d39af321",
      "title": "Morning routine"
    }
  ]
}
```

Generate and persist one UUID as `client_msg_id` before the first send. If the
request times out or its `202` response is lost, retry with the same UUID. For
600 seconds from the first accepted row, the server returns that row's original
`user_message` reference and does not store, wake, or run a second turn. The key
is scoped to the authenticated user and works across both Chat ingest paths.
Omitting it preserves the legacy non-idempotent behavior.

For an image turn, add `image_b64` and `image_mime`. The decoded image limit is
2,000,000 bytes and the supported MIME types are JPEG, PNG, WebP, and GIF.

```json
{
  "message": "What should I notice in this image?",
  "image_b64": "BASE64_IMAGE_BYTES",
  "image_mime": "image/jpeg",
  "context_refs": []
}
```

### Image model selection

On Hosted Runtime V1 or V2, and on a VPS with the current IO resident, an
account can either keep its existing main-model image path or select a separate
saved model route as an image observer. Read the current choice with `GET
/v1/vision/config`, and change it with `PUT /v1/vision/config`:

```json
{
  "mode": "dedicated",
  "route_id": "a0a51b3f-35e0-4335-bf46-fac40bff3789"
}
```

IO sends the candidate a generated image whose answer is not known in advance
and records whether the returned observation proves image understanding.
Selection and capability are separate: a reachable text-only model may remain
selected with `effective_status: "unsupported"` as settings feedback, but image
sends are not blocked by probe state. `mode: "follow_main"` preserves the
existing main-model image path, while a selected dedicated route is pinned for
delivery even if its latest probe is stale or unsuccessful.

Use `POST /v1/vision/config` when adding a dedicated image model. It creates or
reuses the saved route, runs the generated-image check, and selects the route
as one server-owned operation. A reachable model that proves text-only remains
saved and selected with an `unsupported` warning, while authentication,
provider, quota, and other operational failures remove only the route or
credential created by that request.

When a dedicated route is configured, IO records that exact route before the
image turn is stored. Runtime V2 or the official resident then sends pixels only
to that route, asks for a neutral visual observation, marks the result as
untrusted data, and passes only that text to the main agent. A vision-call
failure does not fall back to sending the raw image to the main model.

`POST /v1/vision/routes/{route_id}/test` repeats the capability check without
changing the selection. Each accepted image turn records the dedicated route it
preflighted, so changing Settings cannot reroute an already queued image. The
consumer reads that exact route and decrypts its credential through the enclave.
If the pinned route was deleted, the turn fails instead of exposing raw pixels
to the main model.

Runtime V1 and VPS report whether a fresh official resident poll advertises
`vision_observer_v1`, but that capability signal does not block image ingestion.
Follow-main keeps the existing image path unchanged; a selected dedicated route
stays pinned rather than silently falling back to the main model. `POST
/v1/vision/observe` is the authenticated resident-facing observer exchange for
the message's pinned route.

For a document, use `file_b64`, `file_name`, and `file_mime` instead. The decoded
file limit is 25 MiB. PDF, DOCX, XLSX, supported images, and UTF-8 text/source
files are accepted. Send only one binary attachment per turn.

```json
{
  "message": "Summarize this contract.",
  "file_b64": "BASE64_FILE_BYTES",
  "file_name": "contract.pdf",
  "file_mime": "application/pdf",
  "context_refs": []
}
```

### 2. Handle the asynchronous response

The send endpoint does not wait for inference. It returns immediately after the
encrypted user row and durable V2 job commit atomically, so the response has no
`assistant_message`:

```http
HTTP/1.1 202 Accepted
Content-Type: application/json

{
  "status": "processing",
  "reply_ready": false,
  "user_message": {
    "id": "msg_user_123",
    "ts": 1783978500.125
  },
  "runtime": {
    "engine": "feedling_agent_runtime",
    "mode": "hosted_agent",
    "driver": "codex",
    "version": 1
  }
}
```

Do not look for a `reply` text field. Advance the transcript with the durable
append sequence returned by the previous page. Sequence cursors remain exact
when several messages share a client timestamp:

```http
GET /v1/chat/history?after_seq=1041&limit=50&include_image_body=false HTTP/1.1
Host: api.feedling.app
X-API-Key: YOUR_FEEDLING_API_KEY
```

```json
{
  "messages": [
    {
      "v": 1,
      "id": "msg_assistant_456",
      "role": "openclaw",
      "sender": "assistant",
      "source": "model_api",
      "content_type": "text",
      "seq": 1042,
      "ts": 1783978502.75,
      "body_ct": "BASE64_CIPHERTEXT",
      "nonce": "BASE64_NONCE",
      "K_user": "BASE64_WRAPPED_KEY",
      "K_enclave": "BASE64_WRAPPED_KEY",
      "visibility": "shared",
      "owner_user_id": "usr_0123456789abcdef",
      "content": "",
      "is_from_openclaw": true
    }
  ],
  "total": 42,
  "oldest_ts": 1783978502.75,
  "latest_ts": 1783978502.75,
  "oldest_seq": 1042,
  "latest_seq": 1042,
  "has_more_older": true,
  "has_more_newer": false,
  "bodies_omitted": 0,
  "image_bodies_omitted": 0,
  "body_omit_inline_max": 262144
}
```

Decrypt `body_ct` on the authorized client. When a history item has
`body_omitted: true`, fetch `/v1/chat/messages/{message_id}/body` instead of
assuming the message is empty.

Hosted Runtime V2 can return a generated document as a native attachment. The
model first creates or replaces editable UTF-8 source in an encrypted
`/workspace/...` entry with `workspace_write`. After that write succeeds, it
calls `send_file` with the same virtual path in a later tool round. Text formats
are delivered directly; `.docx` and `.pdf` targets are rendered into real Word
and PDF bytes at delivery time. Semantic file intent without a named format is
handled by the model prompt and never blocks an ordinary conversational reply.
An explicitly requested format such as `.docx` gets one bounded completion
recovery and cannot be satisfied by a Markdown substitute. If delivery still
fails, the worker records `required_file_missing` and publishes a non-empty
terminal reply instead of failing the chat turn. The worker resolves only the
current user's entry, then commits the final assistant text followed by its
download cards as one idempotent reply bundle. It stores `content_type: "file"`
plus a bounded filename, MIME, and byte count. The worker never scans a runtime
directory, and `send_file` rejects host paths and non-`/workspace` namespaces.
Both editable source and rendered output are limited to 1,000,000 bytes.

### 3. Read confirmed V1 or V2 activity

Use the accepted user message id as `turn_id` while waiting for either a
resident V1 or hosted V2 reply:

~~~http
GET /v1/chat/turn-activity/msg_user_123 HTTP/1.1
Host: api.feedling.app
X-API-Key: YOUR_FEEDLING_API_KEY
~~~

~~~json
{
  "turn_id": "msg_user_123",
  "runtime": "v1",
  "complete": false,
  "phase": "processing",
  "jobs": [{ "job_id": "v1:msg_user_123", "status": "running" }],
  "events": [
    {
      "id": "v1:4be4dce72b0a4f76bff3ec2c601598ce",
      "kind": "tool",
      "name": "memory_index",
      "status": "success",
      "job_id": "",
      "call_id": "v1:4be4dce72b0a4f76bff3ec2c601598ce",
      "duration_ms": 18.4,
      "result_code": "ok",
      "memory_count": 4,
      "memory_categories": [
        { "key": "relationship", "count": 3 },
        { "key": "family", "count": 1 }
      ]
    }
  ]
}
~~~

This is a runtime-neutral projection, not a reconstruction of assistant text.
V2 uses backend-owned job and tool-dispatch records. V1 accepts fixed-shape
events from the authenticated shipped resident runtime and binds them to an
existing user turn. Neither path returns tool arguments, tool result bodies, or
reasoning. Durable V2 effects may add `effect_id`, `effect_type`, and
`effect_status` only after the dispatcher has confirmed their disposition.

For successful `memory_index`, `memory_search`, and `memory_fetch`,
`memory_count` is derived
from the actual V2 capability result or V1 `io_cli` response before any
provider-facing truncation. `memory_categories` is optional: it is present only when every
returned item has one of the canonical bilingual memory buckets and its counts
sum to `memory_count`. If any bucket is custom or unknown, the category list is
omitted and clients should show the total only. Raw bucket labels, summaries,
memory content, and query text never enter activity metadata.

Every executed Runtime V2 platform, MCP, `reply`, and `send_file` call uses the
same started/result/error activity boundary. Repeated memory-discovery calls
that are deterministically rejected by the loop are recorded as confirmed
results too. Zero-result discovery is retained, and each turn returns at most
100 projected events.

Completed tool events are also attached to the assistant history item's
`activity_events` metadata, so clients can render the execution record below
the final reply. A separately encrypted `thinking_*` envelope remains the only
source for display-safe reasoning and must not be merged with tool activity.

## Independent resident loop

The resident path is a queue-and-reply protocol. It does not accept plaintext
message bodies.

Select the account's `resident` route before operating this loop. That route is
also the hosted-V1 kill switch; changing it away from `resident` transfers
execution ownership to the selected path. Poll claims remain database-atomic, so
two healthy poll consumers cannot both claim the same parent turn.

CLI residents (Claude, Codex, and Pi) can also generate native download cards.
The agent writes UTF-8 Markdown-like source inside its private
`$FEEDLING_HOME/outbound-files` directory and calls the resident `send-file`
command with a user-visible filename. `.docx` and `.pdf` names are rendered into
real Word and PDF bytes; an explicitly requested suffix cannot be replaced by
Markdown. Named formats get one bounded completion retry if the first agent
response omits the file. Requests without a named format remain prompt-level
semantic guidance. If the retry still omits the file, the resident keeps the
original model reply instead of replacing it with a file-failure response. The
resident seals the primary text and every file separately, then sends them
through `file_followups` on `POST /v1/chat/response`; the parent CAS and all
message inserts commit in one transaction, preserving text-first/card-below
ordering without partial success.
Source and rendered output are each limited to 1,000,000 bytes, and staging
rejects paths outside the per-user outbound directory.

### 1. The client stores a user message

Encrypt the user text or attachment and post the complete envelope:

```http
POST /v1/chat/message HTTP/1.1
Host: api.feedling.app
Content-Type: application/json
X-API-Key: YOUR_FEEDLING_API_KEY

{
  "client_msg_id": "76ba05cf-d6ee-45af-a1e6-091dbd8c1f0a",
  "envelope": {
    "v": 1,
    "id": "env_user_123",
    "body_ct": "BASE64_CIPHERTEXT",
    "nonce": "BASE64_NONCE",
    "K_user": "BASE64_KEY_WRAPPED_TO_USER",
    "K_enclave": "BASE64_KEY_WRAPPED_TO_ENCLAVE",
    "enclave_pk_fpr": "ENCLAVE_PUBLIC_KEY_FINGERPRINT",
    "visibility": "shared",
    "owner_user_id": "usr_0123456789abcdef"
  },
  "content_type": "text"
}
```

On an ambiguous network failure, retry with the same `client_msg_id`. The
envelope may have a new encrypted `id`; within the 600-second window the server
still returns the first stored row in the same `{id, ts, v}` response shape and
does not wake the resident consumer again. An invalid UUID returns
`400 client_msg_id_invalid`.

For `content_type: "file"`, `file_name` and `file_mime` are optional metadata.

To send **text alongside an image or file** (a caption), encrypt that text as its
own envelope and pass it as `caption_envelope` — the same E2E `EncryptedEnvelope`
shape as the main `envelope`, wrapped to the enclave (`K_enclave`) so it can be
decrypted into the message's plaintext content. Without it, an image/file message
carries no accompanying text and the agent sees only the attachment.

```json
{
  "envelope": { "...": "encrypted image bytes" },
  "content_type": "image",
  "caption_envelope": {
    "v": 1,
    "id": "env_caption_123",
    "body_ct": "BASE64_CIPHERTEXT_OF_CAPTION_TEXT",
    "nonce": "BASE64_NONCE",
    "K_user": "BASE64_KEY_WRAPPED_TO_USER",
    "K_enclave": "BASE64_KEY_WRAPPED_TO_ENCLAVE",
    "enclave_pk_fpr": "ENCLAVE_PUBLIC_KEY_FINGERPRINT",
    "visibility": "shared",
    "owner_user_id": "usr_0123456789abcdef"
  }
}
```

```json
{
  "id": "msg_user_123",
  "ts": 1783978500.125,
  "v": 1
}
```

### 2. The resident consumer long-polls and claims work

Use a stable consumer ID on every poll and response. `claim=true` is the default
and prevents healthy consumers from processing the same turn concurrently.

```http
GET /v1/chat/poll?since=1783978400&timeout=30&claim=true HTTP/1.1
Host: api.feedling.app
X-API-Key: YOUR_FEEDLING_API_KEY
X-Feedling-Consumer: feedling-chat-resident
X-Feedling-Consumer-Id: resident-macbook-01
X-Feedling-Consumer-Version: 1.4.0
X-Feedling-Consumer-Commit: abc1200
X-Feedling-Consumer-Compat-Commit: abc1234
X-Feedling-Decrypt-Status: ok
X-Feedling-Decrypt-Checked-At: 1783978499.500
```

```json
{
  "messages": [
    {
      "v": 1,
      "id": "msg_user_123",
      "role": "user",
      "source": "chat",
      "content_type": "text",
      "ts": 1783978500.125,
      "body_ct": "BASE64_CIPHERTEXT",
      "nonce": "BASE64_NONCE",
      "K_user": "BASE64_WRAPPED_KEY",
      "K_enclave": "BASE64_WRAPPED_KEY",
      "visibility": "shared",
      "owner_user_id": "usr_0123456789abcdef"
    }
  ],
  "runtime_v2": {},
  "client_release": {
    "expected_consumer_commit": "abc1234"
  },
  "user_mcp": {
    "fingerprint": "..."
  },
  "timed_out": false,
  "consumer_id": "resident-macbook-01",
  "claimed": true
}
```

An empty long poll is a successful `200` with `messages: []` and
`timed_out: true`. Immediately start the next poll; do not treat it as an error.
The requested timeout is capped at 60 seconds.

`X-Feedling-Consumer-Commit` identifies the code loaded by the current process,
not merely the checkout currently on disk. The standard resident captures this
value at process start. If its relevance check intentionally skips an advertised
release because no loaded resident file changed, it may additionally report that
target with `X-Feedling-Consumer-Compat-Commit`. The backend treats an older
running commit as compatible only while this optional value matches the current
`expected_consumer_commit`; a missing running commit is never masked, and a later
backend release makes the old compatibility claim stale automatically. Both
values are self-reported by the authenticated self-hosted consumer and therefore
have the same trust level.

#### Decrypt-health heartbeat and onboarding

An official resident reports decrypt-source health on poll requests only:

| Status | Meaning |
| --- | --- |
| `ok` | A real message decrypted successfully, or the configured enclave reachability probe succeeded. This phase-one signal is operational self-reporting, not cryptographic proof of a challenge decrypt. |
| `degraded` | Consecutive claimed messages could not be recovered as non-empty plaintext. The standard consumer changes to this status after two consecutive read failures by default; `FEEDLING_DECRYPT_DEGRADE_AFTER` changes that threshold (minimum 1). Only a later real, ordinary user-message decrypt clears this state. A server-generated maintenance turn is not recovery evidence. |
| `unconfigured` | `FEEDLING_ENCLAVE_URL` is absent. |
| `unreachable` | The configured enclave decrypt source could not be reached. |

`X-Feedling-Decrypt-Checked-At` is the Unix epoch time of the confirmation. The
backend accepts a report as fresh for 300 seconds. The standard resident
refreshes an idle report every 210 seconds; use
`FEEDLING_DECRYPT_HEALTH_REFRESH_SEC` to tune that interval, with a minimum of 5
seconds. Missing, malformed, future, or stale reports normalize to `unknown`.
Every official poll is authoritative: omitting the two headers clears any
previous cached green report instead of inheriting it. Response requests do not
update this poll-heartbeat state.

For a resident-route account that has not completed one ordinary user/agent
exchange, every non-`ok` result blocks onboarding validation, live-loop
verification, and visible Chat with `409 bootstrap_incomplete` and
`stage: "needs_decrypt_source"`. `GET /v1/onboarding/validate` exposes the
ordered `decrypt_source` step, and `GET /v1/bootstrap/status` exposes
`decrypt_source_ready`, `decrypt_health`, and `decrypt_health_policy`.

After an account has a durable successful first Chat exchange, explicit
`degraded`, `unconfigured`, or `unreachable` still blocks onboarding completion
and a new sticky verification, but does not add a new hard block to ordinary
Chat. An `unknown` report receives a seven-day warning-only onboarding grace;
it cannot mint a sticky verification during the grace, and after the grace it
blocks onboarding while ordinary Chat remains available.

Maintenance notification follows the same cohort policy. `unknown` means the
consumer report is old, absent, or stale; it can emit a
`resident_decrypt_health_unreported` in-app notice but never selects
decrypt-source repair copy and never injects a Chat turn. A new account's
explicit `degraded`, `unconfigured`, or `unreachable` report can inject a repair
turn immediately because onboarding is already blocked. For an established
account, the explicit failure emits an in-app notice first and must remain
continuous for 30 minutes before it can inject a repair turn; operators can
change this persistence window with
`FEEDLING_RESIDENT_DECRYPT_FAILURE_GRACE_SEC`.

`POST /v1/chat/verify_loop` inserts a private `source: "verify_ping"` user row.
The resident's hidden ack must post `source: "verify_ping"` and set
`reply_to_message_id` to that exact ping ID. An unrelated or stale agent reply
does not satisfy the probe. The verify response distinguishes `loop_alive`
(the exact ack arrived) from `passing` (the ack arrived and decrypt policy also
allows verification); only `passing: true` records the sticky live-loop green.

If a self-hosted resident consumer appears stale while it is still polling, the
server may claimably inject a user-role maintenance message with
`source: "resident_maintenance"`. It is a shared envelope with `K_enclave`, so
decrypt it through the same enclave history/MCP path as normal chat and pass the
plaintext to the agent. Replies to that parent should use
`source: "resident_maintenance"` and should not trigger user-visible push. Treat
this source as system repair traffic, not as user-authored activity. The prompt
identifies itself as a Feedling server notification, points to the matching App
notice for verification, limits requested work to the resident environment,
and separates consumer-update steps from decrypt-source diagnostics.

Maintenance Chat turns use a global reminder interval (24 hours by default).
Changing heartbeat timestamps, decrypt check timestamps, or the backend's
expected commit does not bypass that interval. A changed expected commit starts
the mismatch grace timer again, while the reminder interval remains in force.
The reminder gate is persisted with PostgreSQL compare-and-swap across backend
workers: a conflicting poll reloads current state and recomputes the decision
instead of overwriting another worker's reminder timestamp. The generated
maintenance message ID is also appended through the cross-worker idempotency
path, so repeated attempts for the same user, interval bucket, and prompt keep
one Chat row, preserve any existing claim/reply metadata, and let only the
insert winner wake consumers. These two guards are independent: stale state
cannot turn one logical maintenance prompt into a rapid injection loop, and
switching between maintenance reasons does not reset the global reminder
interval.
The resident-job fallback scan is throttled by
`FEEDLING_RESIDENT_FALLBACK_CHECK_SEC` (default 300 seconds).

`user_mcp.fingerprint` changes whenever the account's MCP server list changes;
see the [MCP servers workflow](/docs/workflows/mcp) for how to manage that list
and re-materialize local config when the fingerprint moves.

### 3. The consumer posts the encrypted reply

Decrypt the claimed user turn through the authorized enclave path, invoke the
agent, then encrypt its reply. `reply_to_message_id` connects the two records and
enables duplicate-reply protection.

Preserve the final reply's Markdown, blank lines, and leading indentation before
encryption. Transport logs and reasoning leakage may be filtered, but formatting
such as headings, list markers, nested-list indentation, blockquotes, and fenced
code is part of the user-visible reply and must reach the client unchanged.

```http
POST /v1/chat/response HTTP/1.1
Host: api.feedling.app
Content-Type: application/json
X-API-Key: YOUR_FEEDLING_API_KEY
X-Feedling-Consumer: feedling-chat-resident
X-Feedling-Consumer-Id: resident-macbook-01
X-Feedling-Consumer-Version: 1.4.0
X-Feedling-Consumer-Commit: abc1234

{
  "envelope": {
    "v": 1,
    "id": "env_assistant_456",
    "body_ct": "BASE64_CIPHERTEXT",
    "nonce": "BASE64_NONCE",
    "K_user": "BASE64_KEY_WRAPPED_TO_USER",
    "K_enclave": "BASE64_KEY_WRAPPED_TO_ENCLAVE",
    "enclave_pk_fpr": "ENCLAVE_PUBLIC_KEY_FINGERPRINT",
    "visibility": "shared",
    "owner_user_id": "usr_0123456789abcdef"
  },
  "content_type": "text",
  "source": "chat",
  "reply_to_message_id": "msg_user_123"
}
```

```json
{
  "id": "msg_assistant_456",
  "ts": 1783978502.75,
  "v": 1
}
```

Reply exclusivity is atomic across backend workers: marking the parent answered
and inserting its encrypted assistant reply commit together. If another
consumer wins that parent first, the endpoint returns `409 already_answered`
and does not store or deliver the losing reply. Treat that response as a lost
race and do not post a second assistant turn. Messages with `role: "system"`
remain outside reply exclusivity because they are technical notices, not
answers to the claimed user turn. A network failure after sending is ambiguous
because Chat does not support `Idempotency-Key`; check history or the parent
message's reply metadata before deciding whether to retry.

### Runtime V2 terminal failures

When a Runtime V2 foreground turn fails or expires, Chat stores an encrypted
assistant failure reply instead of leaving the user message unanswered. The
reply is linked through `reply_to_message_id` and carries
`turn_failure_error_class`, `turn_failure_blame`, and
`turn_failure_user_text`. Provider-configuration failures use actionable text
from the shared error catalog; transient provider and system failures use the
standard retry-later fallback while preserving the classified metadata.
If an internal conservative context-window default rejects a turn, Chat treats
that as a system failure rather than blaming the user's provider configuration.

The failure obligation is committed with the terminal job transition and
replayed independently, so a worker crash or lease timeout cannot lose it.
Delivery uses a deterministic message identity and advances the Runtime V2
reply cursor in the same transaction as the encrypted row and parent metadata.
If a newer successful reply already advanced that cursor, the delayed failure
is acknowledged without inserting a stale bubble. Background wake, Capture,
Dream, and maintenance failures do not write Chat messages.

## Destructive transcript clear

Clearing Chat requires an explicit body even though the method is `DELETE`:

```http
DELETE /v1/chat/history HTTP/1.1
Host: api.feedling.app
Content-Type: application/json
X-API-Key: YOUR_FEEDLING_API_KEY

{
  "confirm": "clear-chat-history"
}
```

This atomically clears the authenticated user's raw transcript plus its live
Runtime V2 summary, chat-derived artifact views, pending effects/status, and
reply cursor. It advances the runtime generation so an in-flight pre-clear turn
cannot recreate a reply or derived context after the endpoint returns.

It does not delete Memory Garden, Identity, API keys, user-authored
`/workspace`, `/memory/WORKING.md`, skills, schedules, content-free billing/token
metrics, or the account. Encrypted trajectory/review telemetry is retained under
its separate retention policy and never re-enters the live prompt. Use account
reset/deletion when the intended operation is complete data erasure.
