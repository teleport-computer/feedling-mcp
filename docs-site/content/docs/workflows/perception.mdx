---
title: Perception workflow
description: Report current context, read the freshness-gated snapshot, and upload encrypted photos.
---

Perception accepts sparse device context. A report can contain one or more of
`context_snapshot`, `items`, or `config`; at least one must be non-empty.

Use `X-API-Key` for `POST /v1/perception/report`, especially when a report
contains encrypted sensitive signals. The generic authentication layer can
recognize a runtime token on this route, but a runtime-token-only call does not
currently provide the API-key material used by the sensitive-signal decrypt
adapter. An `accepted` status in that case is not proof that the decrypted value
was written. Until that path is changed, treat sensitive report ingestion as
API-key-only.

## 1. Report non-sensitive operation context

For operation signals, `data` is a JSON-encoded string, not a nested JSON value.
Use the literal string `"null"`, an empty string, or JSON `null` when a signal is
authorized but unavailable. `client_ts` is Unix time in seconds and applies to
the report; a timestamp too far in the future is clamped to server time.

```http
POST /v1/perception/report HTTP/1.1
Host: api.feedling.app
Content-Type: application/json
X-API-Key: YOUR_FEEDLING_API_KEY

{
  "client_ts": 1783978500.125,
  "context_snapshot": [
    {
      "key": "time",
      "data": "{\"local_time\":\"2026-07-13T14:15:00-04:00\",\"timezone\":\"America/New_York\",\"locale\":\"en-US\"}",
      "message": "device clock"
    },
    {
      "key": "battery",
      "data": "{\"level\":0.72,\"charging\":false}",
      "message": "battery snapshot"
    },
    {
      "key": "focus",
      "data": "{\"authorization_status\":\"authorized\",\"focused\":true}",
      "message": "focus presence"
    }
  ]
}
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "results": {
    "time": "accepted",
    "battery": "accepted",
    "focus": "accepted"
  }
}
```

An older observation can return `stale_ignored`. Other per-signal values include
`unavailable`, `ignored`, `unknown_signal`, and validation-specific errors. A
`200` report means the request was processed; inspect every signal result rather
than treating all entries as stored.

## 2. Report an encrypted sensitive signal

Sensitive keys such as `location_signal`, `motion_state`, calendar, playback,
weather, reminders, and health signals must use an envelope. Plaintext `data`
for one of these keys is classified as `invalid_plaintext_sensitive_signal`.
`changed` must be a JSON boolean.

The encrypted plaintext uses a `values` wrapper:

```json
{
  "values": {
    "place_hint": "home",
    "wifi_anchor_id": "anchor_7d7f"
  },
  "message": "coarse location context"
}
```

After encrypting that object, send:

```http
POST /v1/perception/report HTTP/1.1
Host: api.feedling.app
Content-Type: application/json
X-API-Key: YOUR_FEEDLING_API_KEY

{
  "client_ts": 1783978500.125,
  "context_snapshot": [
    {
      "key": "location_signal",
      "changed": true,
      "envelope": {
        "v": 1,
        "id": "perception_location_123",
        "body_ct": "BASE64_CIPHERTEXT",
        "nonce": "BASE64_NONCE",
        "K_user": "BASE64_KEY_WRAPPED_TO_USER",
        "K_enclave": "BASE64_KEY_WRAPPED_TO_ENCLAVE",
        "enclave_pk_fpr": "ENCLAVE_PUBLIC_KEY_FINGERPRINT",
        "visibility": "shared",
        "owner_user_id": "usr_0123456789abcdef"
      },
      "message": "encrypted location signal"
    }
  ]
}
```

```json
{
  "results": {
    "location_signal": "accepted"
  }
}
```

The response confirms classification and processing, not that a proactive wake
was emitted. Wake policy, user settings, activation state, freshness ordering,
and debounce can suppress downstream notification independently.

Runtime V2 keeps a durable baseline for each wake-producing signal. The first
accepted observation establishes that baseline and does not wake the model.
Updates are compared and recorded atomically; an older or replayed source event
is ignored, so it cannot produce a delayed arrival or unlock message later.
Only a fresh allowlisted transition is eligible for a wake.

Legacy compatibility producers use the same dedicated wake controls as Runtime
V2: photos map to `photo_added`, location/Wi-Fi/region arrival signals map to
`arrived_at_anchor`, and a return after a long device lock maps to
`unlock_after_absence`. These are controlled by the photo, arrival, and unlock
wake switches respectively; disabling Heartbeat does not disable them. Motion
state remains available in the snapshot but never creates a proactive wake.
Global DND and Away suppression still apply.

Screen broadcast state is also a durable, significant Runtime V2 signal. After
the first report establishes a baseline, recognized off-to-on and on-to-off
transitions produce `broadcast_opened` and `broadcast_closed` wake events. Both
use the screen-watch switch and one shared 60-second capability debounce, so a
rapid open/close/open flap admits at most one wake. An opened edge additionally
requires a recent encrypted frame; a closed edge does not, because frame
production has ended. The user action of starting sharing is the consent signal
for this always-available source, but it does not bypass proactive activation,
the screen-watch switch, or delivery controls. DND may allow the runtime to
consider the edge while still blocking a visible proactive message.

## 3. Read the current snapshot

```http
GET /v1/perception/snapshot HTTP/1.1
Host: api.feedling.app
X-API-Key: YOUR_FEEDLING_API_KEY
```

```json
{
  "local_time": "2026-07-13T14:15:00-04:00",
  "timezone": "America/New_York",
  "locale": "en-US",
  "battery_level": 0.72,
  "charging": false,
  "broadcast_state": null,
  "broadcast_active": null,
  "place_label": "home",
  "wifi_label": null,
  "country": null,
  "locality": null,
  "wifi_anchor_id": "anchor_7d7f",
  "motion_state": null,
  "calendar_next_event": null,
  "calendar_events": null,
  "calendar_events_truncated": null,
  "now_playing": null,
  "focus_authorization_status": "authorized",
  "in_focus": true,
  "app_name": null,
  "app_category": null,
  "app_state": null,
  "user_state": "default",
  "recent_apps": [],
  "recent_app_events": []
}
```

Snapshot values are freshness-gated by signal-specific TTLs. `null` means the
value is unavailable, unauthorized, or stale; clients must not infer which one
without a separate user-controlled permission state. New context fields can be
added, so decoders should ignore unknown keys.

### How the agent receives perception

In a foreground conversation, ordinary current perception readings are not
inserted into the initial model prompt. The agent uses perception tools when a
question depends on current device, environment, activity, health, calendar,
reminder, or photo data. Live screen sharing is the narrow exception: when its
newest encrypted frame is at most 90 seconds old, foreground Chat may attach up
to the latest four frames from the current continuous sharing session, and
explicitly marks the newest as the current screen. A follow-up turn with no new
frame still receives that latest frame. Hosted Runtime V2 admits an untested or
missing route verdict optimistically and blocks only an explicit
image-unsupported verdict; a
confirmed provider rejection is learned after a successful text-only retry and
prevents pixel attachment on later turns. The official resident path admits
pixels only after its propagated setup probe reports `ok`.

During an ordinary proactive heartbeat, the runtime may provide a low-resolution
glance made only of availability and change booleans. Exact readings and private text
remain tool-only. A perception-triggered heartbeat adds only the triggering event type;
it does not attach an unrelated device, weather, or health report. Scheduled reminders
remain reminder-only, and the proactive screen-watch lane remains isolated to
safe screen metadata; foreground Chat's bounded pixel attachment does not change
what screen watch receives.

Proactive runtime and temporal context is labeled as application data rather
than presented as a new user message. An ordinary heartbeat does not call the
model until the account has genuine conversation history. Once history exists,
heartbeat and screen-watch moments leave speaking and staying silent as equal
model choices; scheduled reminders remain explicit delivery requests.

## Collection items

The `items` branch accepts collection uploads for `workout`, `sleep`, and
`vitals`. Each collection value is an array.

```http
POST /v1/perception/report HTTP/1.1
Host: api.feedling.app
Content-Type: application/json
X-API-Key: YOUR_FEEDLING_API_KEY

{
  "items": {
    "sleep": [
      {
        "item_id": "sleep_2026_07_13",
        "ts": 1783951200,
        "doc": {
          "asleep_minutes": 425,
          "deep_minutes": 72
        },
        "expires_at": 1786543200
      }
    ]
  }
}
```

```json
{
  "results": {
    "items": {
      "sleep": {
        "written": 1
      }
    }
  }
}
```

Photos are deliberately not accepted through `items`; use the dedicated
encrypted photo flow below.

The collection branch is a legacy compatibility surface and stores each `doc`
as provided rather than as a v1 encrypted envelope. Do not upload raw health or
other sensitive content through it unless that storage exposure is acceptable
for your threat model. New sensitive-signal integrations should use encrypted
`context_snapshot` envelopes.

## App-open / app-close shortcuts

`GET /v1/perception/app_open` and `GET /v1/perception/app_close` are
compatibility endpoints with a write side effect. This is an important
exception to the usual assumption that GET is read-only. They correspond to
the "is opened" and "is closed" trigger options on the same iOS Shortcuts App
automation; a user can configure only one of the two automations, and the
other being absent is a benign degradation (you simply lose that half of the
signal, nothing errors).

```http
GET /v1/perception/app_open?app=Notes&category=productivity&ts=1783978500.125 HTTP/1.1
Host: api.feedling.app
X-API-Key: YOUR_FEEDLING_API_KEY
```

```json
{
  "status": "ok",
  "app": "Notes",
  "category": "productivity",
  "ts": 1783978500.125
}
```

```http
GET /v1/perception/app_close?app=Notes&ts=1783980000.125 HTTP/1.1
Host: api.feedling.app
X-API-Key: YOUR_FEEDLING_API_KEY
```

```json
{
  "status": "ok",
  "app": "Notes",
  "ts": 1783980000.125
}
```

Do not retry either one blindly after an ambiguous timeout; a retry can append
a second usage event.

A close only updates the current-app state when the closed app is the one
currently recorded as in the foreground. An older app that was killed in the
background by the OS — and reports its close after a newer app has already
opened — is recorded in the app-close history but does not clobber whichever
app is actually current.

### Reading app usage back

Each call writes to two places: the current-app snapshot fields (`app_name` /
`app_category` / `app_state`, which expire 15 minutes after the reported open
or close) and an append-only history — opens and closes each append to their
own stream. `app_state` is `"foreground"` after an open and `"closed"` after a
matching close; it is `null` when no open has been reported yet.

The shortcut reports opens and closes, so `app_name` means "the app named in
the most recent open-or-matching-close event observed within the TTL" — check
`app_state` if you need to distinguish "still in it" from "just left it".

`GET /v1/agent/perception/recent_apps` merges the app-open and app-close
histories into one trajectory. Each entry has an `event` value of `"open"` or
`"close"`; either kind can appear on its own when a user configured only one
Shortcut automation or when the other event was not delivered.

The regular and pull snapshots also expose `recent_app_events`, containing the
same merged event shape for the app signal's 15-minute freshness window. This
field is additive; the older `recent_apps` snapshot field remains available for
compatibility.

```http
GET /v1/agent/perception/recent_apps?limit=20&hours=24 HTTP/1.1
Host: api.feedling.app
X-API-Key: YOUR_FEEDLING_API_KEY
```

```json
{
  "ok": true,
  "apps": [
    {"app": "Notes", "category": "productivity", "ts": 1783980000.125, "event": "close", "minutes_ago": 1.0},
    {"app": "Notes", "category": "productivity", "ts": 1783978500.125, "event": "open", "minutes_ago": 3.5}
  ],
  "count": 2,
  "window_hours": 24
}
```

Entries are newest first across both streams, and `limit` applies after the
merge. `hours` is optional and unbounded by default, so check `minutes_ago`
before treating an entry as recent. Both this endpoint and the current-app
fields are gated by the single `app` capability: when the user turns it off,
the response is `{"ok": true, "disabled": true, "reason": ...}` with an empty
`apps` list — which is deliberately distinguishable from a genuine empty
history.

## Encrypted photo flow

Photo pixels must be encrypted before upload. The main API stores ciphertext and
metadata; it does not decode the image.

```http
POST /v1/perception/photo/evaluate HTTP/1.1
Host: api.feedling.app
Content-Type: application/json
X-API-Key: YOUR_FEEDLING_API_KEY

{
  "metadata": {
    "has_faces": false,
    "face_count": 0,
    "scene_hint": "food",
    "scene_confidence": 0.93,
    "time_of_day": "evening",
    "is_burst": false,
    "is_indoor": true,
    "has_text_block": false,
    "is_screenshot": false
  },
  "content_envelope": {
    "v": 1,
    "id": "photo_01J2PHOTO123",
    "body_ct": "BASE64_IMAGE_CIPHERTEXT",
    "nonce": "BASE64_NONCE",
    "K_user": "BASE64_KEY_WRAPPED_TO_USER",
    "K_enclave": "BASE64_KEY_WRAPPED_TO_ENCLAVE",
    "enclave_pk_fpr": "ENCLAVE_PUBLIC_KEY_FINGERPRINT",
    "visibility": "shared",
    "owner_user_id": "usr_0123456789abcdef"
  },
  "meta_envelope": {
    "v": 1,
    "id": "photo_meta_01J2PHOTO123",
    "body_ct": "BASE64_PRIVATE_METADATA_CIPHERTEXT",
    "nonce": "BASE64_NONCE",
    "K_user": "BASE64_KEY_WRAPPED_TO_USER",
    "K_enclave": "BASE64_KEY_WRAPPED_TO_ENCLAVE",
    "visibility": "shared",
    "owner_user_id": "usr_0123456789abcdef"
  }
}
```

```json
{
  "photo_id": "photo_01J2PHOTO123",
  "metadata": {
    "has_faces": false,
    "face_count": 0,
    "scene_hint": "food",
    "scene_confidence": 0.93,
    "time_of_day": "evening",
    "is_burst": false,
    "is_indoor": true,
    "has_text_block": false,
    "is_screenshot": false,
    "place_label": null
  },
  "usable": true,
  "sensitive": false,
  "status": "stored"
}
```

`scene_hint` and `is_screenshot` influence the returned `sensitive` metadata;
they are not a storage-denial gate. The request parser still accepts
`exif_gps` for legacy compatibility, but new clients should not upload raw EXIF
coordinates. If location context is needed, use the encrypted sensitive-signal
flow instead.

List confirmed photo metadata:

```http
GET /v1/perception/photos?limit=20 HTTP/1.1
Host: api.feedling.app
X-API-Key: YOUR_FEEDLING_API_KEY
```

```json
{
  "photos": [
    {
      "photo_id": "photo_01J2PHOTO123",
      "metadata": {
        "has_faces": false,
        "face_count": 0,
        "scene_hint": "food",
        "scene_confidence": 0.93,
        "time_of_day": "evening",
        "is_burst": false,
        "is_indoor": true,
        "has_text_block": false,
        "is_screenshot": false,
        "place_label": null
      }
    }
  ]
}
```

```json
  "frame_id": "photo_01J2PHOTO123",
  "metadata": {
    "has_faces": false,
    "face_count": 0,

  "meta_envelope": {
    "v": 1,

```

The `decrypt_path` is user-scoped and must be called with an authorized
credential. It is not a public object URL.
