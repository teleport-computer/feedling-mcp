Memory separates ciphertext storage from enclave-authorized read projections.

Runtime V2 permits memory-card deletion only during foreground Chat, when the
user is present in the turn. Background heartbeat, scheduled, and manual-wake
turns can add or update cards but cannot delete them; the delete operation is
omitted from their tool schema and independently refused by the execution gate.

An unattended screen-watch turn that carries a fresh screen frame is narrower
still: from 2026-08-21 it is offered no platform mutation tools at all, so it
can neither add nor update a card. The only instruction source in that turn is
text that happened to appear on the user's screen, and the model cannot
reliably separate it from something the user asked for. Reading memory,
inspecting the screen, and replying remain available. Screen-watch turns
without a fresh frame, and foreground Chat turns where the user did send a
message, keep the usual write surface.

## Hosted profile refresh execution

Runtime V2 generates its bounded Memory/User profile as low-priority Heavy-pool
work, separate from foreground Chat. It first verifies the complete lightweight
Garden index, then fetches card bodies in stable batches of 64 and fails closed
if any batch is incomplete. At most one Profile Job runs in a serve-worker
instance; the second Heavy slot remains available for Dream, Capture, and other
maintenance. Provider and write stages report progress so a slow but advancing
profile is not mistaken for a hung Job.

For a healthy or empty profile, the next existing post-turn check schedules a
refresh when the Garden's content-free row count or maximum `updated_at` differs
from the profile's recorded source. It no longer waits for the profile to be
three days old. This is a background full-Garden refresh, not incremental
generation on every write or a guarantee that the current reply uses the update.
Repeated enqueue requests coalesce; disabled profiles, provider-repair gates,
and scheduled retry backoff remain in force. An unchanged witness does not
trigger a refresh. Writes that leave both witness values unchanged cannot be
detected by this check. More frequent source changes can increase provider work
and invalidate the profile's stable prompt-cache prefix more often.

On Chat and proactive wake turns, non-empty MEMORY and STYLE fields enter the
trusted system prefix after the current identity card (or transitional Genesis
persona fallback) and before general behavior rules. They are presented as the
companion's own memory and learned speaking style, while the verbatim
conversation remains authoritative on conflict. World Book and changing runtime
context stay in non-privileged application-data messages. A successful profile
refresh changes that user's provider prompt-cache prefix once.

Genesis onboarding and identity redistillation do not wait for the later
maintenance refresh to create this profile. They use only valid cards,
persona, and voice material produced from the current upload; Genesis never
reads the existing encrypted Garden. The fields share Runtime V2's validation
and encrypted CAS contract, and an untouched side keeps its existing envelope
byte-for-byte. Profile publication remains required for these two paths.
Add-memory imports do not write a profile at all: they write cards, changing
the Garden fingerprint that causes the ordinary profile lane to perform the
later full-Garden refresh.

| Operation | Returns |
| --- | --- |
| `POST /v1/memory/add` | The stored v1 encrypted record. |
| `GET /v1/memory/list` | Raw encrypted records for client synchronization. |
| `POST /v1/memory/index` | Lightweight decrypted summaries for discovery. |
| `POST /v1/memory/fetch` | Full decrypted content for selected IDs. |
| `GET /v1/dream/status` | Dream and Capture counts for Memory Garden banners. |

`local_only` records can be stored and synchronized, but the enclave has no
wrapped key for them, so they are unavailable from `index` and `fetch`.

`memory/fetch` resolves IDs against the full Garden rather than an index or
ranking window. Its response separates `missing_ids` from `unavailable_ids` and
always includes a `truncation` object with requested, processed, and omitted
counts. Do not treat a shorter `items` array as proof that every requested ID was
processed. `include_archived` and `include_superseded` expose those lifecycle
states when explicitly requested. All shared cards otherwise use the same read
contract for direct fetch, ambient recall, profile refresh, Dream, and Capture.
Legacy card-classification keys in stored envelopes are ignored and are not
returned by `index` or `fetch`.

The read-side `score` and default candidate ordering no longer add a bonus for
legacy `is_open_thread=true` metadata. That field has no maintained open/closed
lifecycle; cards carrying it are scored with the same importance and recency
decay as other cards. Existing records are not rewritten. Query relevance
ranking and ambient importance-times-pulse weighting are unchanged.

Runtime V2's `memory_index` tool accepts `bucket` and `thread` filters in
addition to `limit`, matching the resident CLI's partitioned browsing path.
The V2-only `memory_index` and `memory_search` views contain compact items
(`id`, event `date`, `bucket`, and the first sentence of `summary`). `total` is
the available Garden count before filtering, `matched` is the number returned
by the underlying read, and `returned` is the number of complete items retained
for the model. `omitted`, `source_truncated`, and `truncated` distinguish the
model budget from upstream limits. The 6000-character result budget drops
whole lower-ranked items, never part of a JSON object. Specific questions should use `memory_search` followed by
`memory_fetch`; broad reviews should reconcile partition counts against
`total`, without indiscriminately loading every card. Bulk cleanup requests
belong to `memory_organize`, not a chat-loop sequence of single-card edits.

V2 `memory_fetch` has a 12000-character result budget and preserves each retained
card's complete read-side content (up to 5000 characters). Cards that do not fit
are omitted as whole items and counted explicitly. These memory results reserve
their full budget in addition to the ordinary tool batch's 8000 characters, so
mixed batches cannot silently slice their JSON. A turn still limits the number
of tool calls. Existing primary-card fields remain compatible; optional recall
metadata is described below. Index discovery is allowed once per V2
loop; after a bounded overview, fetch visible IDs or use a more specific search.

Recall diagnostics distinguish card selection from actual prompt injection.
Each V2 chat/wake turn can read enclave-selected cards from a sequence-bounded
history window. The selection query includes the last four conversation messages,
including assistant replies. The runtime adds a non-system “相关记忆” data block
before conversation replay: card ID, the summary, and the selection reason. It
never substitutes the card body for a missing summary and never truncates a
summary: summaries up to 300 characters appear whole, and a longer one is
replaced by its ID and reason plus a fetch hint, because a half sentence is the
input shape that most invites a model to complete it. The block is limited to
2500 characters; overflow drops whole lower-ranked cards. Explicitly quoted IDs
are excluded. A card whose verbatim summary already appears in the profile keeps
its ID with an empty summary and a “profile already covers this, details can be
fetched” reason, so the fuller body stays fetchable. This is conservative text
deduplication, not semantic coverage detection. Models must fetch details and
must not invent facts absent from their evidence.

V2 also requests a recent-card supplement on each turn. Up to three readable,
active cards created in the last seven days take priority within the same
eight-card selection and 2500-character block. This uses creation time, not
last-fetch/update time, and is bounded by the existing candidate window. Unknown,
timezone-less or future dates are not treated as recent. The reason label says
“recent” rather than claiming a query match. This supplements a potentially stale
profile; it does not regenerate it. Quoted/profile deduplication still applies,
so three candidates do not imply three actual injections. Older enclave versions
may ignore the optional `context_recent` request flag.

Cards may carry `retrieval_cues`: up to five short, grounded keywords, aliases,
answerable questions or known event-time hints, at most 120 characters each.
The read side includes them in BM25 search and lightweight index projections;
V2's index also retains up to three thread pointers for navigation. Cues are
search hints, not independent factual evidence. The pinned memgarden 0.19.0
producer does not generate this new field; absent cues remain compatible. New
Capture/Dream cue generation and five-level importance guidance require a later
reviewed dependency release. No existing user cards are backfilled by this IO change.

`memory_fetch` preserves requested full cards and adds `related_items`, at most
six one-hop pointers (`id`, summary excerpt, `source_id`, `relation`, `status`).
Relations are shared threads or explicit `anchor_memory_ids`/`supersedes` links.
Only same-user readable candidates are considered; local-only, deleted and
archived cards are excluded. A superseded card is included only through an
explicit link and is marked `superseded`, not presented as current. Expansion
does not recurse or mark neighbors as fetched. `related_status` is `ok` when
the bounded search is complete, `bounded` when the candidate/result window or
decryption limits coverage, `unavailable` when relation lookup cannot be measured,
or `not_needed` when fetched cards have no links. In the V2 tool budget, primary
bodies take precedence and optional pointers may be omitted (`related_omitted`
when metadata fits). Missing optional metadata is not proof of no relations.

`memory.select.traced` does not claim the selected cards reached the model.
`memory.recall.completed` records per-execution recall counts, with unknown
values marked explicitly; automatic injection and user-quoted cards are separate.
V2 events carry turn/job/attempt coordinates so retries and wake work need not
be mistaken for additional foreground turns. Search diagnostics record a bounded
sample of returned card IDs and an omitted-ID count, never the query or card text.
V2 `memory.context.applied` events report which rendered card entries were found
in the final provider-request messages and whether profile context was included.
An entry counts as present when it appears verbatim (whitespace-normalized) or as
an equal JSON object, so an adapter that re-formats, re-flows or splits content
into parts does not read as a missing injection, while an edited entry does.
`injected_chars` is the normalized size of the rendered block reduced to the
entries that were found, including its frame lines — not the character count of
the provider payload. When a bound stops that check or it fails, the affected
IDs are reported in `unverified_ids` with `injected_is_lower_bound` set and any
`arrival_errors` named: unverified is not the same as absent, and only a complete
check reports `missing_ids`. Separate
`memory.recall.tool_result` events record final normalized tool-result
JSON completeness, returned/omitted counts, result characters, and fetch call-ID
to requested/returned card-ID bindings, joined by turn/job/attempt. The terminal
`memory.recall.completed` event contains aggregate counts. These are content-free operational fields,
not proof of semantic relevance or provider-token usage. The full provider-request
messages remain in the encrypted trajectory under its existing access controls.
On the pinned memgarden 0.19.0 release, selection still uses its historical buckets;
the opt-in relevance-gated soft-quota policy is used only when a reviewed, released
dependency upgrade supplies it. A missing or failed selection remains unknown,
not a measured empty Garden.

`memory_search` uses request-local BM25 token ranking over the complete authorized
readable Garden. Chinese segmentation uses pinned jieba 0.42.1 (precise mode,
HMM disabled); ASCII words and whole identifiers such as `NP-4286` and `CR2450`
are case-insensitive tokens, not substring prefixes. Query terms need not be
adjacent; any matching term can contribute. No synonyms, translation, stemming,
time interpretation, embedding or model is involved. A nonblank query with no
searchable tokens returns no matches. Empty results do not prove memory absence;
try different wording or browse a bucket/thread. Only identical repeated
arguments are refused within a turn. The V2 compact result preserves `ranking`
and `unavailable_count`, including the explicit `substring-legacy` mode during
rolling upgrades.

`GET /v1/dream/status` also returns `capture_cards_added` and
`capture_completed_at`. The count is a monotonic total of cards actually added
across Capture runs. Clients subtract the total saved when the user last
dismissed the banner to show the unconfirmed count. A Capture run that adds no
cards does not change the total or refresh the timestamp.

Hosted Dream maintenance reads complete decrypted candidate cards, stopping
before the next whole card when the configured prompt budget is reached. Every
proposed consolidation must explain its rationale. Text overlap is not
required: cards may be consolidated when they describe the same event or the
evolution of one plan, while cards that merely share a broad topic remain
separate. The model's consolidation judgment is not second-guessed by another
model call: Dream applies only deterministic exit gates. A proposal is rejected
when its result text contains an internal card id or a tombstone-style note
(for example "superseded by \<id\>") instead of real memory content — those
rejections are bounced back to the model once for a rewrite. A run that would
retire more than 80% of the active garden (and at least 10 cards) fails as a
whole without applying anything; both thresholds are deployment-configurable.

Dream does not impose a per-run consolidation count, a per-proposal retired-card
count, a cross-run cooldown, or any content-quality judgment on rewrites. It
still rejects repeated use of one source card within a run and proposals that
target unknown cards. Every proposal is bound to the card snapshot captured
before the run and all accepted actions are applied afterward, so a card
created by the current run cannot be fed back into that same run. Rejected
operations leave every original card active, and accepted operations supersede
rather than hard-delete source cards. Automatic scheduling continues to advance
only when new non-Dream cards are added; new conversation turns alone do not
schedule another Dream run.

Dream diagnostics correlate scheduling, model execution, and the final write
outcome without exposing memory content. The admin trace distinguishes a clean
no-op, an applied run, a partial write, provider or parse failure, deterministic
mapping or blast-radius rejection, and a failed write. It reports only closed
outcome enums, booleans, duration, and fixed integer counts. A failed or
budget-truncated full-card read is recorded separately and marks the terminal
run as using degraded context, so it cannot be mistaken for a model choosing to
make no changes from a complete input. Card ids, prompts, replies, summaries,
raw errors, and other memory text are never part of this diagnostic shape.

In Runtime V2 chat, the model-facing `memory_organize` tool can force-enqueue a
Dream run when the user explicitly asks to organize or consolidate their
memories. It bypasses the automatic scheduler's night window, minimum interval,
and new-material gates, but not Dream's deterministic exit gates and
soft-deletion safeguards.
Repeated requests coalesce with an active Dream job. If the deployment-wide or
user-level Dream switch is off, the tool returns an explainable disabled result.
Resident V1 agents have the equivalent `io_cli.py memory-organize` command,
which calls the existing `POST /v1/dream/tick` endpoint with `force: true`.

## 1. Build and store a card

The card's meaningful text is an encrypted JSON object. A typical plaintext
before encryption is:

```json
{
  "summary": "The user prefers a quiet start to the morning.",
  "content": "Coffee after 08:30, no meetings in the first half hour.",
  "bucket": "preferences",
  "threads": ["morning-routine", "work-style"]
}
```

Do not send this plaintext object to `/v1/memory/add`. Encrypt its serialized
bytes and send the resulting envelope. Ordering and lifecycle metadata is
intentionally visible outside the ciphertext.

```http
POST /v1/memory/add HTTP/1.1
Host: api.feedling.app
Content-Type: application/json
X-API-Key: YOUR_FEEDLING_API_KEY

{
  "envelope": {
    "v": 1,
    "id": "mom_7f20d39af321",
    "body_ct": "BASE64_CIPHERTEXT",
    "nonce": "BASE64_NONCE",
    "K_user": "BASE64_KEY_WRAPPED_TO_USER",
    "K_enclave": "BASE64_KEY_WRAPPED_TO_ENCLAVE",
    "enclave_pk_fpr": "ENCLAVE_PUBLIC_KEY_FINGERPRINT",
    "visibility": "shared",
    "owner_user_id": "usr_0123456789abcdef",
    "type": "fact",
    "occurred_at": "2026-07-13T12:30:00Z",
    "source": "live_conversation"
  }
}
```

`type` is required and must be one of `moment`, `quote`, `fact`, `event`,
`insight`, or `reflection`. An `insight` must include at least one existing
`anchor_memory_ids` value in the envelope; a `reflection` needs at least two.
The authenticated user must own every anchor. Reflection creation also has an
endpoint-specific relationship-age cap and can return `429`; that response is
not a generic service-wide rate limit.

For new cards, datetime-valued `occurred_at` metadata is normalized to the same
instant in UTC with a `Z` suffix. A date-only `YYYY-MM-DD` value remains
date-only. The server stamps `created_at` in UTC with a `Z` suffix. Existing
cards keep their stored timestamp strings when they are retyped, rewrapped, or
otherwise updated; this does not backfill historical records.

```http
HTTP/1.1 201 Created
Content-Type: application/json

{
  "status": "created",
  "moment": {
    "v": 1,
    "id": "mom_7f20d39af321",
    "type": "fact",
    "occurred_at": "2026-07-13T12:30:00Z",
    "created_at": "2026-07-13T12:31:02Z",
    "source": "live_conversation",
    "body_ct": "BASE64_CIPHERTEXT",
    "nonce": "BASE64_NONCE",
    "K_user": "BASE64_KEY_WRAPPED_TO_USER",
    "K_enclave": "BASE64_KEY_WRAPPED_TO_ENCLAVE",
    "enclave_pk_fpr": "ENCLAVE_PUBLIC_KEY_FINGERPRINT",
    "visibility": "shared",
    "owner_user_id": "usr_0123456789abcdef"
  },
  "v": 1
}
```

The server can generate `moment.id` if it is absent, but a stable unique
client-generated ID is easier to reconcile after an ambiguous network failure.
It is not an idempotency guarantee: posting the same payload again can append
another record, and clients must not rely on the ID to deduplicate requests.

## 2. Discover cards with the lightweight index

`index` sends authorized candidates to the enclave and returns summaries rather
than complete content.

```http
POST /v1/memory/index HTTP/1.1
Host: api.feedling.app
Content-Type: application/json
X-API-Key: YOUR_FEEDLING_API_KEY

{
  "limit": 100,
  "ambient": false,
  "ambient_top_n": 20,
  "bucket": "preferences",
  "thread": "morning-routine"
}
```

`bucket` is an exact match; `thread` must be present in the card's thread list.
`ambient_top_n` applies when `ambient` is true. A missing or zero `limit` asks
for the full lightweight index up to a deployment safety cap; inspect the
response's effective `limit` and `truncated` values.

```json
{
  "items": [
    {
      "id": "mom_7f20d39af321",
      "summary": "The user prefers a quiet start to the morning.",
      "bucket": "preferences",
      "threads": ["morning-routine", "work-style"],
      "importance": 0.5,
      "pulse": 0.3,
      "status": "active",
      "occurred_at": "2026-07-13T12:30:00Z",
      "created_at": "2026-07-13T12:31:02.125000",
      "updated_at": "",
      "last_referenced_at": "",
      "score": 0.5
    }
  ],
  "limit": 100,
  "truncated": false,
  "user_card_count": 1
}
```

A nonblank `query` searches the existing readable summary/content/thread/bucket
projection plus retrieval cues using **BM25** (`k1=1.2`, `b=0.75`, nonnegative
IDF). In the enclave, plaintext-tier and sealed cards share one corpus and one
set of statistics. Exact `bucket` / `thread` filters select from that ranking;
`limit` is applied only afterwards. Scores tie by `occurred_at` descending, then
ID ascending. The existing per-item `score` remains importance/recency, **not**
BM25. Full content, tokens, postings and BM25 scores are not added to the response.
Final evidence selection still belongs to your client or agent.

Query responses additionally carry `ranking: "bm25-jieba-0.42.1-v1"` and
`unavailable_count` (candidate cards that could not be read, excluded from
statistics). A recognized older enclave response instead reports
`ranking: "substring-legacy"`: this temporary rolling-upgrade mode uses the old
case-insensitive whole-query substring match and importance order. Authentication
errors, timeouts, and unknown protocols do not silently fall back. Blank or
omitted `query` retains the existing index browsing path; fetch is unchanged.

Search is bounded to 4096 candidate cards, 32 MiB of encoded internal JSON request,
and 16 MiB of searchable UTF-8 projection text. Crossing any bound fails the
whole search with HTTP 413 `memory_search_resource_limit`; no partial-corpus rank
or false empty result is returned. Reducing `limit` does not reduce the corpus.
`FEEDLING_MEMORY_READSIDE_HARD_MAX` bounds result count and enclave decrypt chunks,
not search corpus size. Within the bounds, a query's `truncated: false` means no
candidate-window truncation, not that every match was returned or every card
was decryptable; inspect `limit` and `unavailable_count`. These resource bounds
are not a deployed latency guarantee.

## 3. Fetch selected content

Pass the IDs selected from the index. Results preserve the requested ID order.

```http
POST /v1/memory/fetch HTTP/1.1
Host: api.feedling.app
Content-Type: application/json
X-API-Key: YOUR_FEEDLING_API_KEY

{
  "ids": ["mom_7f20d39af321", "mom_missing"],
  "limit": 20,
  "include_archived": false,
  "include_superseded": false
}
```

```json
{
  "items": [
    {
      "id": "mom_7f20d39af321",
      "summary": "The user prefers a quiet start to the morning.",
      "content": "Coffee after 08:30, no meetings in the first half hour.",
      "bucket": "preferences",
      "threads": ["morning-routine", "work-style"],
      "importance": 0.5,
      "pulse": 0.3,
      "status": "active",
      "source": "live_conversation",
      "occurred_at": "2026-07-13T12:30:00Z",
      "created_at": "2026-07-13T12:31:02.125000",
      "updated_at": "",
      "last_referenced_at": ""
    }
  ],
  "missing_ids": ["mom_missing"],
  "unavailable_ids": []
}
```

`missing_ids` are not owned by the user or do not exist. `unavailable_ids` are
known records that cannot be returned under some archive, supersession, or
encryption rules. Compare requested IDs with returned item IDs and treat any
unaccounted-for ID as not available.

## 4. Apply a batch of memory actions

After selecting with `index` and reading the necessary cards with `fetch`, use
`POST /v1/memory/actions` for an ordered write batch. The public action types are
`memory.add`, `memory.supersede`, `memory.retype`, and `memory.delete`. Submit
between 1 and 20 actions. The implementation processes only the first 20, so a
client must reject an oversized batch before sending it.

The server executes every item independently and does not stop after one item
fails. Full success and partial applied success return HTTP `200`. When no
action was applied and at least one failed, the batch returns HTTP `400`; its
top-level `error` and optional `detail` come from the first failed item, while
the complete `results`, `effects`, and counts remain available. An all-skipped
batch returns HTTP `200`; skipped actions do not count as failures. Read every
`results` entry and the batch `applied_count`, `skipped_count`, and
`failed_count`; top-level `status` is `ok`, `partial`, or `failed`. Each result
includes its own `http_status`.

`source` and `capture_mode` are closed enums. Unknown values produce an
item-level failure (`source_invalid` or `capture_mode_invalid`) rather than
being stored or rewritten, while later valid actions in the same batch still
run. Use the values published in the OpenAPI schema; omit optional metadata
when none applies.

Plaintext card text is validated for obviously-wrong content. A plaintext
`memory.add`, upgrade, or `memory.supersede` whose summary or content is a
tombstone-style bookkeeping note — the phrase "已被 … 取代" or "superseded by"
followed by an internal hex id — fails with an item-level
`memory_card_tombstone` (HTTP 400 for that item) instead of being stored, and a
rejected supersede leaves every targeted card active. Card fields must carry
the memory content itself; card retirement bookkeeping is recorded by the
server, never written into visible text. Ordinary prose about something being
replaced is unaffected: the rejection requires an internal-id-like hex string
next to the phrase.

A `memory.supersede` action accepts one source ID or an array of at most 20
source IDs. An oversized array fails that action with
`too_many_supersedes` before any card is changed; it is never truncated to a
successful prefix. On success, `superseded_ids` lists the cards the mutation
actually retired rather than echoing the requested IDs. Every requested source
must still be active when the mutation commits. If a source is already
unavailable, the action fails with `supersede_targets_unavailable`; if one
changes between validation and commit, it fails with
`supersede_targets_changed`. Either failure leaves all source cards unchanged
and does not write the successor. After either conflict, search or index memory
again for the current active source IDs before retrying; do not repeat the stale
IDs. Clients consolidating more than 20 cards should continue in a later
request, including the returned successor ID among that request's at most 20
source IDs.

This example adds one encrypted card, retypes an existing card, supersedes an
outdated card with a new encrypted card, and deletes a fourth card:

```http

Content-Type: application/json

      "type": "memory.add",

        "v": 1,
        "id": "mom_new_preference",
        "body_ct": "BASE64_CIPHERTEXT",
        "nonce": "BASE64_NONCE",
        "K_user": "BASE64_KEY_WRAPPED_TO_USER",
        "K_enclave": "BASE64_KEY_WRAPPED_TO_ENCLAVE",
        "enclave_pk_fpr": "ENCLAVE_PUBLIC_KEY_FINGERPRINT",

    },
    {
      "type": "memory.supersede",
      "supersedes": ["mom_old_city"],
      "reason": "The user's city changed.",
      "source_chat_message_ids": ["msg_user_123"],
      "envelope": {
        "v": 1,
        "id": "mom_current_city",
        "body_ct": "BASE64_CIPHERTEXT",
        "nonce": "BASE64_NONCE",
```

A successful batch returns HTTP `200`; the per-action result records the create
or update details, and `effects` is the flattened change summary:

```json
{
  "status": "ok",
  "results": [
    {
      "status": "ok",
      "action": "memory.add",
      "memory": {
        "id": "mom_new_preference",
        "type": "fact",
        "occurred_at": "2026-07-13T12:30:00Z",
        "status": "active"
      },
      "change": {
        "id": "0123456789abcdef",
        "ts": "2026-07-13T12:31:02.125000",
        "action": "insert",
```

The batch is ordered but not transactional. Execution stops on the first failed
action and returns that action's HTTP status. Earlier results and effects remain
committed; they are included in the error response and are not rolled back.
Split independent writes when partial completion would be hard to reconcile.

There is no `Idempotency-Key` support and the server does not scan existing
cards for duplicate content. Every accepted add creates a new memory ID and
emits a write effect, even when its title and content match an active card.
Prebuilt envelopes are validated from their plaintext metadata and envelope
shape without decrypting their body during the add. Read `index` or `fetch`,
reconcile stable memory IDs, and construct a new batch instead of replaying the
original blindly.

`memory.upgrade` exists for controlled legacy migration, but it is not part of
the public Memory workflow and should not be emitted by ordinary clients.

## Synchronize encrypted records

Use the list endpoint when the client needs raw envelopes rather than an enclave
projection:

```http
GET /v1/memory/list?limit=50&since=2026-07-01T00%3A00%3A00Z&include_archived=false HTTP/1.1
Host: api.feedling.app
X-API-Key: YOUR_FEEDLING_API_KEY
```

```json
{
  "moments": [
    {
      "v": 1,
      "id": "mom_7f20d39af321",
      "type": "fact",
      "occurred_at": "2026-07-13T12:30:00Z",
      "created_at": "2026-07-13T12:31:02.125000",
      "source": "live_conversation",
      "body_ct": "BASE64_CIPHERTEXT",
      "nonce": "BASE64_NONCE",
      "K_user": "BASE64_WRAPPED_KEY",
      "K_enclave": "BASE64_WRAPPED_KEY",
      "visibility": "shared",
      "owner_user_id": "usr_0123456789abcdef"
    }
  ],
  "total": 73,
  "next_cursor": "eyJoIjp0cnVlLCJpIjoibW9tXzdmMjBkMzlhZjMyMSIsInQiOiIyMDI2LTA3LTEzVDEyOjMwOjAwKzAwOjAwIiwidiI6MX0"
}
```

`since` and card `occurred_at` values are parsed as ISO-8601 instants before
comparison, so equivalent `Z`, offset, and legacy naive datetime strings sort
consistently. Date-only values are interpreted at UTC midnight. Invalid card
timestamps sort after valid timestamps and are excluded when a valid `since`
filter is active. Results are newest first with memory ID as a stable tie-break.
The default `limit` is 50 and the server caps a page at 500. `total` is the
number matching the filters before any cursor or page slice, so it stays
constant while paging. Pass each opaque `next_cursor` back as `cursor` until the
response returns `next_cursor: null`. Existing clients may continue to omit the
cursor and receive the same first-page filtering and ordering behavior. See the
[pagination rules](/docs/reliability#pagination).

## Retype an existing card

Retyping changes plaintext classification metadata without changing the
encrypted body. Anchors are required when changing to `insight` or `reflection`.

```http
POST /v1/memory/retype HTTP/1.1
Host: api.feedling.app
Content-Type: application/json
X-API-Key: YOUR_FEEDLING_API_KEY

{
  "id": "mom_7f20d39af321",
  "type": "insight",
  "anchor_memory_ids": ["mom_0123456789ab"]
}
```
