This public changelog starts with this developer-documentation work. Entries stay
under **Unreleased** until a production deployment is confirmed. It does not
reconstruct the repository's internal engineering history, and an omitted older
change must not be interpreted as an API guarantee.

## Unreleased

- **The `identity_patch` tool can recalibrate the relationship day count.** Put a
  non-negative integer `relationship_days` inside the `patch` object (e.g. `patch:
  {"relationship_days": 300}`) and the persona's `days_with_user` is recalibrated by
  moving its start anchor to `today − relationship_days`. The day count is always
  derived from that anchor, so this rides the same compare-and-swap write as every
  other profile field. Notes on the contract:
  - **Absolute anchor is frozen at request time.** The relative day count is
    resolved to a fixed calendar date when the change is accepted, not when it is
    later applied, so a delayed/retried apply cannot drift the count and re-applying
    the same recalibration is a no-op.
  - **Priority.** An explicit `relationship_days` is treated as a deliberate user
    calibration and wins over both an auto-inferred count (earliest memory / session)
    and a duration stated in uploaded persona material; a persona re-derivation will
    not overwrite a count the user calibrated.
  - **New error codes.** `relationship_days_must_be_non_negative_int` (not an
    integer, or negative) and `relationship_days_out_of_range` (exceeds the ~100-year
    cap) are returned as a stable `400` before any write. Invalid values are rejected
    up front rather than failing at apply time.
  - `POST /v1/identity/relationship_anchor` and the `identity.relationship_days_set`
    action keep their existing request/response shapes but now share this same
    compare-and-swap write and integer validation (a boolean/string day count is now
    rejected instead of coerced).

- **Received AI messages no longer expand the Dynamic Island.** Chat replies and
  proactive messages now deliver via the system alert notification only (it stacks
  in Notification Center instead of the Live Activity briefly expanding). The
  Live Activity / Dynamic Island push for these messages is gated off by default;
  set `FEEDLING_AI_MSG_LIVE_ACTIVITY=1` to restore the previous dual delivery. The
  explicit `/v1/push/dynamic-island`, `/v1/push/live-activity`, and
  `/v1/push/live-start` routes are unchanged and remain available for other uses.
  No request/response shape change.

### API

- Automatic `heartbeat_*` calls to `POST /v1/proactive/tick` now use a
  server-clock cadence gate per account. After a heartbeat job is successfully
  queued, the response's `decision.heartbeat_next_tick_at` advances by the
  normalized wake interval; another automatic heartbeat before that epoch is
  rejected with `decision.reason: "heartbeat_throttled"` and recorded as a
  skipped job. Rejections do not move the deadline. Reducing
  `wake_interval_sec` shortens an existing deadline immediately. Manual,
  event-driven, scheduled, screen-watch, and self-wake jobs neither read nor
  update this scheduler field.

- **The Runtime V2 `identity_nudge` tool now actually applies personality-dimension
  changes.** The tool was exposed in the model-visible catalog but had no effect
  wiring, so any call failed the turn. Its full produce → encrypt → replay-validate
  → sink path is now implemented (dimension nudges land on the identity card), with
  unknown effect operations failing closed. No request/response shape change.

- **`web_fetch` now returns the beginning of a large page instead of failing.**
  A response over the raw-body cap was discarded whole, so the tool errored on
  essentially every real site (Wikipedia is 360 KB, a weather page 86 KB, the
  Python docs 41.8 KB) and a model that only ever saw failures would tell the
  user it had no web access. It now keeps what it read, raises the retained-body
  cap to 300 KB, and reports a new `truncated` boolean that is true whenever any
  content was left out — either the body cut or the text cap. An unterminated
  `<script>`/`<style>` tail is dropped rather than handed over as page text.
- **`web_fetch` now extracts the readable article from a page.** With only a
  plain tag-strip, most of the model's per-page budget went to the navigation
  menu ("Jump to content / Main menu / Donate" fills the first 2257 characters
  of a Wikipedia article; a weather page opened with "首页 预报 预警 雷达").
  HTML pages now go through an article extractor first, so a weather page reads
  "中雨 24℃ 晴转多云" and an article starts at its first sentence. Non-HTML
  responses (JSON, plain text, source) are untouched. Extraction runs in an
  isolated, time- and memory-bounded child process and falls back to the plain
  strip on any failure; the `FEEDLING_WEB_EXTRACT_ARTICLE` env var disables it.

- **Web search is now user-controlled.** `web_search` / `web_fetch` are only
  offered to the model when the account's toggle is on; before this change they
  were always available. The switch covers **every** turn — foreground chat, the
  proactive companion's background turns, and any subagent spawned from either —
  so there is one answer to "can my companion go online", not a per-lane matrix.
  Accounts whose persisted runtime target was already the V2 runtime are
  backfilled to "on" once, so existing users keep exactly what they had; new
  accounts start off and enable it in the app.
- New `GET`/`POST` `/v1/web/settings` (api-key only; runtime tokens are
  refused). The response keeps the user's saved preference separate from what is
  actually possible right now:
  `{"enabled", "runtime_supported", "status", "effective", "tools"}`.
  `enabled` is written only by the user — an operator halt never rewrites it.
  `runtime_supported` is false for self-hosted accounts, whose consumer does not
  run the tool loop these tools live in. `status` is `available` / `degraded` /
  `unavailable`, where `degraded` means one of the two tools is halted and the
  other still works. `effective` is derived, and covers every lane. `POST` requires a real JSON boolean under `enabled`; strings such as
  `"no"` are rejected with `400` rather than coerced.

- `GET /v1/content/export` now includes a `world_book` array alongside `chat`,
  `memory`, `identity` and `frames`. World book entries are user-authored
  content that account deletion removes, so an export that omitted them handed
  back an incomplete copy. Entries are returned as stored v1 envelopes,
  ciphertext verbatim for client-side decryption, exactly like the other
  sections — the server still never decrypts. The export is not filtered by
  `visibility`; every stored entry is returned. The export's
  `schema_version` goes from 2 to 3 so a reader can distinguish an
  export taken before world book coverage from one where the user simply had no
  entries.
- The resident consumer's idle decrypt-health probe interval
  (`FEEDLING_DECRYPT_HEALTH_REFRESH_SEC`) default changes from 120 to 210
  seconds. The probe is one of the more expensive periodic calls a resident
  makes, and its reporting contract is unchanged: the backend still accepts a
  report as fresh for 300 seconds. Because the probe only runs on an idle poll
  cycle, the usable interval is that window minus one poll round trip; values
  near 300 report stale health and block onboarding verification.
- Chat poll and Chat history now confirm an answer against the database before
  reporting that nothing newer exists, instead of only when their cached page
  is empty. A message committed by another backend worker is therefore served
  on the next poll rather than after the cache TTL.
- A chat message that was claimed for reply and abandoned (its claim lease
  expired with no reply) is no longer treated as superseded by a later
  answered turn, so the redelivery backstop can still serve it inside the
  redelivery window. The age bound is unchanged.
- `POST /v1/identity/actions` profile-patch writes now cover the full identity
  card: 9 string fields (`user_preferred_name`, `agent_role`, `tone_style`,
  `custom_persona_prompt`, `language_preference`, `relationship_anchor`, and
  others, alongside the existing `agent_name`/`self_introduction`/`category`),
  plus explicit `add_*`/`remove_*`/`replace_*` operations on the four list
  fields (signatures, boundaries, do-not-say, stable definitions) instead of
  only whole-list replacement. Renaming the agent (`agent_name`) must now
  include `self_introduction` in the same patch or the write is rejected with
  `400 rename_requires_self_introduction`; this pairing requirement only
  applies to agent-originated (runtime-token) writes, not user/app writes made
  with an API key, which are unchanged. New error codes on this endpoint:
  `list_op_conflict` (a field targeted by more than one list-operation shape
  in one patch), `list_op_blank` (an add/replace entry is blank after
  cleanup), `list_op_too_many_items` (an `add_*` or `replace_*` op's final
  item count would exceed the 12-item cap — the whole op is rejected, not
  silently truncated; only the legacy direct-list-assign shape still
  truncates for back-compat), and `identity_write_conflict` (`409`, a
  concurrent writer won after retries under lock were exhausted).
- `POST /v1/identity/actions` dimension nudges are now capped per request:
  same-name deltas are normalized and summed, and any dimension whose summed
  `|delta|` exceeds 10 is rejected with `400 nudge_delta_exceeds_cap` instead
  of being silently clamped.
- Resident-sealed identity redistill imports
  (`POST /v1/genesis/imports/plaintext`, `mode=update_identity`) are now
  serialized per account: starting a redistill while one is still
  `awaiting_resident` or `processing` for that account is rejected with
  `409 redistill_job_active` and the in-flight job's id, instead of starting a
  second concurrent job. Retrying the same `client_job_id` is unaffected and
  still returns the existing job. Resident distill now merges its output into
  the identity card's **latest** state field-by-field at write time (it
  previously replaced the whole card from the pre-distill snapshot), so a
  `profile_patch`/`dimension_nudge` made while a redistill is in flight is no
  longer silently discarded. Distill prompts also now treat instruction-like
  text found in uploaded material purely as persona content to analyze, never
  as instructions to follow. Both resident redistill and the onboarding
  Genesis import can now also derive `user_preferred_name`,
  `custom_persona_prompt`, `language_preference`, `relationship_anchor`, and
  `stable_definitions` from uploaded material when it explicitly states them
  (previously these five fields were settable only via chat profile-patch);
  each stays empty, never invented, when the material gives no explicit
  signal for it.
- Resident maintenance reminder state now uses cross-worker PostgreSQL
  compare-and-swap instead of process-local read-modify-write persistence.
  Concurrent Chat poll, claim, and pending-work requests therefore preserve one
  another's heartbeat, decrypt-health, and reminder fields. Maintenance Chat
  appends also use the existing atomic `client_msg_id` idempotency path: repeated
  attempts for the same user, reminder bucket, and prompt retain one row and
  preserve its claim/reply metadata, while only the insert winner wakes
  consumers. Reason changes remain subject to the same global reminder interval.
- Official self-hosted resident polls can now include
  `X-Feedling-Consumer-Compat-Commit` when the updater intentionally keeps an
  older running image because the advertised release changes no resident-loaded
  files. A non-empty running commit plus a compatibility value matching the
  current backend target suppresses commit-mismatch maintenance warnings. A
  missing running commit, an absent compatibility value, or a compatibility
  value for an older backend target retains the existing grace and reminder
  behavior. `X-Feedling-Consumer-Commit` now identifies the commit captured by
  the running process rather than a checkout changed underneath it.
- Official resident consumers now report decrypt-source health on
  `GET /v1/chat/poll` with `X-Feedling-Decrypt-Status`
  (`ok`, `degraded`, `unconfigured`, or `unreachable`) and
  `X-Feedling-Decrypt-Checked-At`. Missing, invalid, future, or reports older
  than 300 seconds normalize to `unknown`. Resident onboarding exposes a new
  `decrypt_source` validation step; unfinished accounts require a fresh `ok`
  report before Chat or live-loop verification can pass. Existing accounts keep
  ordinary Chat available and receive a seven-day warning-only grace for
  `unknown`. Unknown/absent health now produces only an in-app stale-consumer
  notice and never injects decrypt-source repair copy. An established resident's
  explicit decrypt failure must persist for 30 minutes before a repair turn can
  be injected; new onboarding remains immediately actionable. Verify-ping
  replies must now use `source: "verify_ping"` and point
  `reply_to_message_id` at the exact pending ping; `loop_alive` can therefore be
  true while `passing` is false when decrypt policy blocks sticky verification.
- Self-hosted resident polls may now receive server-generated maintenance turns
  with `role: "user"` and `source: "resident_maintenance"` when the resident
  consumer appears stale or is not claiming resident-only distill jobs. These
  rows use shared envelopes so enclave-backed consumers can decrypt the repair
  prompt. Prompts now identify their server origin, provide an App-notice trust
  anchor, avoid requesting user data, and use reason-specific update or decrypt
  diagnostics. Heartbeat timestamps and backend deploy commit changes no longer
  bypass the global 24-hour reminder interval. Notices and API errors can use
  `blame: "user_environment"` for issues in the user's VPS/runtime environment.
  The resident-only distill job fallback scan is throttled by
  `FEEDLING_RESIDENT_FALLBACK_CHECK_SEC` (default 300 seconds).
- Resident decrypt health now changes to `degraded` only after consecutive
  claimed-but-unreadable messages (two by default, configurable with
  `FEEDLING_DECRYPT_DEGRADE_AFTER`). A real ordinary user-message decrypt resets
  the streak; a server-generated maintenance turn does not count as recovery.
- New `GET /v1/agent/perception/recent_apps` returns recent app-open history
  (`app`, `category`, `ts`, `minutes_ago`), newest first, with optional `limit`
  (1–100, default 20) and `hours` query parameters. It reads the same app-open
  history written by `GET /v1/perception/app_open`; no new storage. It is gated
  by the same `app` capability as the current-app snapshot fields — when the
  user has disabled that capability the response is
  `{"ok": true, "disabled": true, "reason": ...}` with an empty `apps` list,
  which is distinguishable from a genuine empty history.
- The `app_name` / `app_category` snapshot fields now expire 15 minutes after
  the reported open instead of 5 minutes. Because the shortcut reports opens and
  never closes, these fields mean "last open observed within the window", not
  "currently on screen".
- `POST /v1/content/rewrap-to-current-key` now also normalizes the **identity
  card plaintext** while rewrapping: dimension values are coerced onto the
  documented 0–100 integer contract (0–1-scale floats such as `0.95` rescale to
  `95`; a `score` key is adopted as `value`; malformed dimensions are repaired
  instead of dropped). The identity record is probed (decrypted) even when its
  envelope is already sealed to the current key, and re-sealed only if
  normalization changed the card — reported as `rewrapped` with reason
  `identity_plaintext_normalized`. A probe decryption failure on an
  already-current envelope reports `skipped_sanitize_probe_failed` instead of
  an error, so clients do not retry a record that needs no rewrap. Server-side
  identity writes (genesis import, init, profile patch, dimension nudge) apply
  the same normalization before sealing.

- New **Notify Relay** endpoints for self-hosted deployments, which cannot hold
  the official APNs signing key. Anonymous `POST /v1/notify-relay/register`
  enrolls a device's APNs token and mints a relay auth token (`nrt_…`), returned
  only on first enrollment (or when you re-enroll while presenting the token you
  already hold); re-registering an already-enrolled device returns
  `already_enrolled` without disclosing the token, since an APNs device token is
  not a secret. `POST /v1/notify-relay/push` (authenticated by the new
  `X-Relay-Token` header) delivers alert notifications and Live Activity
  start/update/end through the hosted service's APNs credentials. Alert
  pushes (type 1) are scoped to the enrolled device; types 2-4 pass the
  rotating Live Activity target token per call. Both endpoints are
  rate limited (`429` with `Retry-After`); pushes are logged server-side with
  content truncated (default 512 chars) for triage, as disclosed in the
  self-hosting guide.
- `POST /v1/model_api/chat/send` and `POST /v1/chat/message` now accept an
  optional UUID `client_msg_id`. Reusing the same value for the same user within
  600 seconds returns the first stored user row without appending or waking a
  second agent turn, including when a retry switches between the two ingest
  paths. Invalid values return `400 client_msg_id_invalid`; requests that omit
  the field retain their previous behavior.
- Encrypted envelopes now carry an optional `content_pk_fpr` label (first
  16 hex chars of SHA-256 of the user public key `K_user` was sealed to);
  server- and consumer-built envelopes set it automatically. `POST
  /v1/chat/message` and `POST /v1/chat/response` reject a labeled envelope
  whose fingerprint no longer matches the user's registered content key with
  a new `409 content_pk_fpr_mismatch` error (response includes
  `current_public_key_fpr` and `envelope_content_pk_fpr`) — a writer holding
  a stale key cache should re-fetch `whoami`, re-seal, and retry once.
  Unlabeled envelopes are accepted unchanged, so existing clients are
  unaffected. This closes the failure mode where a writer with a stale key
  seals messages the owner's device can never decrypt.
- Expand `GET /healthz` from a fixed liveness stub into a structured
  liveness-and-dependency probe. Responses now carry a top-level `status`
  (`healthy`, `degraded`, or `unhealthy`), a `checks` object with per-component
  detail, and release/uptime metadata, while preserving the legacy `ok` /
  `mode` / `ready` fields. The backend checks PostgreSQL (`SELECT 1`),
  connection-pool saturation, the in-memory user registry, and the cross-worker
  wake-bus listener, and returns HTTP 503 when PostgreSQL is unreachable. The
  enclave reports readiness, release, and TLS posture from cached boot state
  without performing any cryptography. The documented response schema is
  unchanged (a generic JSON object).
- `POST /v1/mcp/servers` now accepts `http://` URLs and loopback/private-network
  and raw-IP hosts — this backend never dials the URL itself, only your agent
  does when it calls a tool, so none of those forms were ever a new attack
  surface on this backend. Add `ca_pem` (PEM, up to 32,768 bytes) to trust a
  self-signed or private-CA server; the returned server record now includes
  `has_ca`. This is "add trust," not "skip verification" — the server still
  has to present a certificate chaining to that CA and prove it holds the
  matching private key. Both first-party runtimes (`claude`, `codex`) were
  verified end-to-end against a real self-signed server.
  **Hosted-runtime users:** the managed agent runs in a cloud confidential VM
  and cannot reach machines on your home or office network; put a tunnel
  (Cloudflare Tunnel, Tailscale Funnel, ngrok) in front of a local MCP server
  and register its public address instead. See the
  [MCP servers workflow](/docs/workflows/mcp) for the full guide.
- Self-signed and private-CA MCP servers no longer require pasting a CA
  certificate. Your agent now fetches and pins the server's own trust anchor
  automatically the first time it connects (trust-on-first-use), then
  verifies against it on every connection after that — TLS verification
  stays on throughout, and the server still has to hold the matching private
  key. `ca_pem` is now optional: paste one yourself (out-of-band) for
  stronger-than-TOFU assurance, and a manually-pasted `ca_pem` always takes
  priority over the automatic fetch. Servers with a publicly-trusted
  certificate (Let's Encrypt, etc.) are never pinned — auto-fetching is
  reserved for servers that can't verify against the public roots, which keeps
  the trust-on-first-use window as small as possible.
  **Self-hosted residents:** the fetch shells out to `openssl`; a host without
  that binary on `PATH` silently materializes no CA, leaving such a server
  unreachable exactly as it was before — see [self-hosting](/docs/self-hosting).
  See the [MCP servers workflow](/docs/workflows/mcp) for the full explanation,
  including the TOFU exposure window.
- Rename the `POST /v1/mcp/servers/{name}/test` error kind previously returned
  for non-public hosts from `blocked_url` to `unreachable_from_backend` — the
  backend still refuses to probe non-global addresses itself (that refusal is
  unrelated to the storage change above), but the old name read as a
  rejection when the server had, in fact, already saved successfully. Clients
  matching on the literal string `blocked_url` for this case must update to
  `unreachable_from_backend`.
- **`codex` + self-signed MCP servers:** `codex`'s TLS stack (rustls) rejects
  a CA certificate used directly as a server certificate, so a single
  self-signed cert works with `claude`/`pi` but not `codex`. Configure such
  servers with a certificate chain (a CA cert plus a separate server cert it
  signs). `POST /v1/mcp/servers/{name}/test` now returns
  `codex_cert_chain_required` (instead of a generic `tls` result) when a
  `codex`-driven account tests a server presenting a lone self-signed cert.
  See [MCP servers workflow](/docs/workflows/mcp).

### Behavior

- Runtime V2 now persists an immutable encrypted turn trajectory alongside its
  aggregate token telemetry. Provider prompts and responses, late input folds,
  tool calls and results, planned replies, and failure details are compressed
  and sealed to the user's and trusted-decrypt keys before database storage.
  Provider-backed failure review is off by default; when explicitly enabled,
  a database-serialized fleet ceiling admits a bounded `trajectory_review`
  lane whose provider call has no tools and whose handler has no reply, effect,
  MCP, Memory, schedule, or workspace dispatch surface. Disabled/overflow
  failures still retain capture but enqueue no provider runner, and encrypted
  analysis is never added to live conversation context automatically. This is
  bounded offline analysis, not deterministic replay; automatic trajectory
  retention/GC and restricted operator inspection/export remain open.

- Runtime V2 now treats encrypted Chat rows and referenced object-storage bodies
  as the durable source ledger. Conversation compaction advances only the
  summary prompt view: it does not delete source messages, and the 5,000-message
  limit now bounds only each process's hot cache. Conversation summaries now use
  immutable encrypted exact-range leaves and retained higher-level checkpoints;
  a versioned canonical-ID binding keeps the model-facing view bounded and
  complete. Existing single-blob summaries migrate lazily, including oversized
  accounts with no new messages.

- Explicit Chat clear now advances the runtime generation and atomically removes
  raw messages, summary, chat-derived artifacts, effects/status, and reply
  cursor. Paused old workers cannot resurrect cleared context. Independent
  Memory/workspace state and encrypted trajectory telemetry retain their own
  policies; account deletion remains the complete-erasure operation.

- Runtime V2 adds an encrypted virtual workspace foundation with read-only
  `/artifacts` and `/skills`, editable `/workspace`, and a persistent editable
  `/memory/WORKING.md` that is distinct from Memory Garden. Native file writes
  use optimistic revisions and the existing encrypted, generation-fenced effect
  outbox. Sandbox acquisition is lazy: stored text views and Markdown edits do
  not start one, while physical artifact materialization, untrusted binary
  parsing, and any future shell/code execution require a registered sandbox
  provider. Generic shell/code tools are not currently model-visible.
  Upload persistence is unchanged, but on a deployment without an audited CVM
  or E2B adapter an uncached attachment is reported as `sandbox_unavailable`
  instead of falling back to in-process parsing. Successful acquisitions append
  content-free billing/usage events; cached text reads do not. Disjoint
  workspace writes can commit concurrently in conflict-free waves, while
  same/ancestor/descendant paths and external mutations remain ordered.

- The model-visible Runtime V2 catalog now contains 24 built-in tools: 22
  platform tools plus `task` and `reply`. `task` runs bounded read-only child
  loops with isolated transcripts and can parallelize independent work without
  exposing reply, recursive-task, MCP mutation, platform-effect, or
  workspace-write surfaces.

- Provider-aware prompt caching now keeps deterministic tool/system/trusted-
  skills blocks ahead of dynamic conversation/tool data, including Bedrock
  Converse cache points and provider-neutral cache usage telemetry. Editable
  `WORKING.md` is deliberately pull-only; after it or another private workspace
  entry is read, later outbound web/MCP/`task` tools are unavailable for that
  turn. The existing Pre canary proves an OpenRouter cache hit; native Bedrock
  and live trusted-`/skills` mutation still need post-deploy proof.

- Eager perception grounding now contains only fixed numeric/boolean/null
  fields. Calendar/reminder/app/place/weather strings and screen/photo content
  are pull-only; once explicitly read, later web, MCP, and `task` tools are
  removed for that turn. Numeric health reads remain composable with outbound
  tools.

- Self-hosted resident consumers now only execute embedded agent actions whose
  type is on an explicit allowlist, and the reply sent to the user is rewritten
  to match what actually happened — a reply is no longer sent as if an
  identity/memory change applied when the action payload was empty, unknown,
  or rejected. Default mode is shadow (log-only, nothing blocked); set
  `FEEDLING_ACTION_ALLOWLIST=enforce` to actually reject non-allowlisted action
  types, or `off` to disable the check entirely.
- Self-hosted resident consumers now report why the built-in auto-updater is
  stuck — a dirty working tree, `FEEDLING_AUTO_UPDATE=0`, or a failed `git
  fetch` — alongside their regular poll. The periodic stale-consumer reminder
  now names the specific cause and remedy instead of a generic "update your
  resident" notice.
- The standard resident consumer now answers an offline backlog with one
  merged agent turn. When a processing batch contains at least
  `FEEDLING_BACKLOG_COLLAPSE_MIN` (default 3) stale plain-text user messages
  whose oldest entry is older than `FEEDLING_BACKLOG_COLLAPSE_AGE_SEC`
  (default 1800 seconds), the pile is presented to the agent as one
  timestamped timeline with an instruction to reply once. The merged reply
  anchors to the newest message; older parents stay superseded and are never
  redelivered. A purely fresh burst from an online user never merges and keeps
  per-message replies; once a stale pile has triggered, fresh eligible messages
  in the same batch join that single merged turn. Probe, maintenance, media,
  and unreadable rows keep their own pipelines, the merged prompt is bounded
  (newest lines win when trimming), and a transient reply-write failure keeps
  the checkpoint with the whole pile retryable as one turn.
- Genesis imports now use the person's saved preferred name in distilled
  memory prose. When no name is known, generated cards omit the subject where
  possible or use the neutral “the person”/“对方”; they no longer expose the
  system labels `user`/`用户`, second-person address, or guessed gender for the
  person. Product terms such as `用户增长`, `用户画像`, and `用户留存` remain
  unchanged. An explicit preferred name found in uploaded User Profile material
  is also retained on the encrypted Identity Card.
- The resident consumer's default per-turn agent timeout
  (`FEEDLING_AGENT_TURN_TIMEOUT_SEC`) is raised from 120 to 300 seconds. Slow
  self-hosted stacks (official Claude Code cold starts, heavy MCP, long-thinking
  models) can legitimately take 100–120s+ per turn, and the old default was
  terminating those turns right at the wire so real replies were dropped. The
  minimum floor (30s) and the operator env override are unchanged, and the cap
  still exists so a hung agent can never wedge the single-flight chat lane.
- Resident agent replies now preserve Markdown markers, paragraph breaks, and
  list indentation when the consumer filters runtime noise. Headings, unordered
  lists, nested lists, blockquotes, thematic breaks, and fenced code therefore
  reach clients unchanged instead of being flattened before encryption.
- Concurrent `POST /v1/chat/response` calls for the same parent are now resolved
  by one PostgreSQL compare-and-swap across all backend workers. Exactly one
  request marks the parent answered and inserts its encrypted reply; later
  contenders receive the existing `409 already_answered` response and emit no
  reply-side wake, capture, push, or trace effects. `role: "system"` notices
  continue to bypass reply exclusivity.
- User MCP servers now support the legacy **HTTP+SSE** transport in addition to
  streamable HTTP. Some providers (e.g. Chinese map services) still ship their
  MCP endpoint only as an `…/sse` URL; those now connect end-to-end. The
  transport is detected automatically — from the URL path at save time and,
  authoritatively, from the server's handshake when a connectivity test runs —
  and reported on each server record as a new `transport` field (`"http"` or
  `"sse"`). The hosted runtime and the `claude` self-hosted runtime speak both
  transports; the `codex` self-hosted runtime remains streamable-HTTP only, so
  a legacy-SSE server is left out of its generated config with a note to use the
  provider's `/mcp` URL instead.
- `POST /v1/mcp/servers/{name}/test` now enforces a 45-second wall-clock
  ceiling over the whole probe and returns `400 timeout` when it is exceeded.
  Previously a server that answered the handshake with a never-ending event
  stream (a legacy HTTP+SSE endpoint, e.g. `…/sse` URLs) could hold the
  request open indefinitely — the app sat on "saving…" with no reply. Saving
  the server (`POST /v1/mcp/servers`) was never affected and still succeeds
  first; only the connectivity probe is bounded.
- Proactive wake bubbles no longer post on top of an active conversation: right
  before delivery, the consumer re-checks the latest chat rows and skips the
  wake (recorded as `skipped` / `chat_collision`) when a user message or an
  agent chat reply landed within the last 90 seconds. One-shot introduction
  greetings and scheduled-wake reminders still deliver. This closes the "one
  message, two near-identical replies" duplication seen when a wake and the
  chat turn answer the same moment.
- Memory Garden cards no longer refer to the person as "用户"/"user": the
  capture, dream, and history-import pipelines use the known identity name
  (history import can also resolve an explicitly self-stated name from User
  Profile material before writing cards). Capture and dream transcripts label
  lines with the known identity names
  (falling back to internal TA/我 markers only when unknown) instead of
  literal `user:`/`agent:` markers, the card-writing prompts require the
  person's name; when it is unknown, prompts prefer subject-free prose and use
  the neutral 「对方」 only when a subject is necessary,
  placeholder "names" such as 用户/user/TA stored on the identity card are
  treated as unknown, and the hardcoded fallback line "用户在对话中明确提到"
  is now subject-free. Dream consolidation also rewrites the old wording out
  of existing cards over time. Wrapped chat-history files whose `.json` body
  is actually plaintext now fall back to plaintext parsing instead of dropping
  the entire wrapped block.

### Storage and deployment

- Hosted model-API execution is now Runtime V2-only in local, test, pre, and
  production deployment manifests. The resident supervisor, per-user CLI
  processes/homes/leases, rollback selectors, and hosted resident admin flip
  have been removed. The independently operated `/v1/chat/*` resident consumer
  remains available and is not a hosted fallback.
- Test, pre, and production deploys now treat their pooled Runtime V2 worker CVM
  as mandatory. Hosted sends fail before persistence when no fresh worker
  heartbeat or capacity is available; the worker image contains only the Python
  V2 runtime, not agent CLIs or resident data volumes.
- Heavy Chat **image** bodies are now offloaded to object storage alongside file
  bodies, under a separate `chatimages/` key prefix so image retention and usage
  can be governed on their own. The message row keeps envelope metadata plus a
  pointer; the ciphertext is re-fetched only at the exits that deliver a body.
  The request and response shapes are unchanged.
- Operator impact: the chat object-storage bucket now backs image bodies too.
  Disabling it, repointing it, or scoping its credential too narrowly **after**
  pointer rows exist makes those image bodies unreadable, not just file bodies.
  It is part of the primary data set and must be backed up with the database.
- Image bodies written before this change remain inline in the database and keep
  working. An offline backfill moves them; it is idempotent and safe to re-run.
- Object reads and deletes are constrained to the requesting account's own key
  prefix, so a malformed or hand-repaired pointer cannot reach another account's
  ciphertext.

### Security

- Browser API access is limited to the documentation site's exact configured
  origin. CORS does not bypass API-key or runtime-token authorization.
- Require a long-lived API key for link-token creation, destructive account
  reset, and Perception report ingestion; runtime tokens are rejected on these
  control-plane boundaries.
- Permit the documented resident, range, cache-validation, and Genesis chunk
  headers through that exact-origin CORS policy without enabling credentials or
  wildcard origins.
- The playground warns that Production requests operate on the authenticated
  account's live data and persists credentials in browser local storage.

### Behavior

- Resident consumers no longer surface an agent's control-protocol JSON as a
  chat message. When a reply wraps its `{"actions":…,"messages":…}` envelope in
  prose or a ```json fence, the consumer now parses out the payload — executing
  the actions and sending only the natural-language messages — instead of
  posting the raw JSON. Malformed, conflicting, or ambiguous payloads fail
  closed (nothing is posted) rather than leaking. No public API shape changed.

### Deprecations

- None in the public OpenAPI contract.

## Reading this changelog

“Added” normally means backward-compatible surface area. “Changed” can require a
client review even when the `/v1` path remains stable. “Deprecated” begins the
process described in [versioning and deprecation](/docs/versioning); it does not
imply a removal date unless the entry states one explicitly.
