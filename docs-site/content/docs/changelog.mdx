---
title: Changelog
description: User-visible changes to the public Feedling API contract and developer documentation.
---

This public changelog starts with this developer-documentation work. Entries stay
under **Unreleased** until a production deployment is confirmed. It does not
reconstruct the repository's internal engineering history, and an omitted older
change must not be interpreted as an API guarantee.

## Unreleased

- **MCP tool schemas now load on demand by default.** MCP server records expose
  a `resident` boolean on `GET /v1/mcp/servers`; `POST` and `PATCH` accept the
  same field, defaulting to `false`. Hosted Runtime V2 keeps folded tool names
  and short descriptions available, then uses the new `mcp_tool_search`
  platform tool to inject complete schemas for matching tools on the next model
  round. `resident=true` retains the previous full-catalog behavior. Changing
  the setting updates `user_mcp.fingerprint`, and search cannot add names beyond
  the bounded catalog already admitted for that turn.

- **Screen-share start and end are now first-class proactive events.** Runtime
  V2 recognizes durable `broadcast_opened` and `broadcast_closed` edges behind
  proactive activation and the screen-watch switch, with one shared 60-second
  debounce for rapid toggles. Both edges are ordinary proactive wake facts,
  remain actionable without a new frame, and let the model decide whether to
  speak from the current conversation and attention state. DND continues to
  block visible delivery. Foreground Chat, heartbeat, manual wake, Runtime V1,
  and the `screen_read` tool now share an explicit `screen_share_ended` state:
  earlier conversation frames remain discussable, but current-screen access requires
  restarting sharing or sending a screenshot. Pixel-free default reads report
  `screen_share_not_active`, `screen_share_ended`, or `screen_share_stalled`
  with a suggested action instead of the misleading `not_requested` reason.

- **Model API settings no longer serialize unrelated accounts.** Concurrent
  provider validation for different users can now proceed through separate,
  bounded database advisory-lock sessions. Mutations for the same account
  remain serialized, and excess concurrent requests still fail with the
  existing bounded `model_api_config_busy` response instead of exhausting the
  database connection budget.

- **Hosted Runtime V2 now starts proactive screen watching for every eligible
  account.** New Runtime V2 transitions arm the screen-watch schedule alongside
  heartbeat, and worker startup repairs existing schedule rows whose
  screen-watch clock was left empty. Existing non-empty wake clocks are
  preserved, so the repair cannot pull a future heartbeat or screen check
  forward.

- **Account deletion now removes Runtime V2 rollout controls.** Account reset,
  administrator deletion, and application-managed registry removals clear the
  deleted user's Runtime V2 allowlist record regardless of whether it came from
  automatic new-user routing or an administrator pin. Other users and resident
  routing behavior are unchanged.

- **MCP server lists can include recent Hosted Runtime V2 readiness.**
  `GET /v1/mcp/servers` now adds an optional, content-free `runtime` object to
  each server that Runtime V2 has observed. It reports the latest stable outcome
  and successful/total observations across a bounded window of at most 10 Chat
  turns. The field is omitted when no observation exists, including current
  Runtime V1 users, and omission is not evidence that the server is healthy.
  URLs, headers, exception text, tool arguments, remote responses, and individual
  turn history are never exposed.

- **Foreground Chat now stays grounded in an active screen share.** When the
  newest encrypted screen frame is no more than 90 seconds old, each foreground
  turn attaches the latest four frames from the current continuous sharing
  session, capped to the most recent ten minutes. A durable cursor avoids
  repeating an entire batch, while a turn with no newer frame still receives the
  latest current-screen frame. Each attached frame is explicitly labelled as
  either the current screen or earlier in the same session. Hosted Runtime V2
  sends raw pixels unless the active
  model route is explicitly known to be image-unsupported; an untested or
  missing probe is no longer treated as evidence that the model is text-only.
  The official resident path retains its setup-probe requirement. Screen frames are
  explicitly untrusted application data, and any turn that receives pixels has
  outbound web, MCP, and child-task access fenced from its first model call. If
  the provider rejects those frames, Chat retries once without them and records
  that route as image-unsupported instead of failing the user's text turn.
  Runtime operations now also report screen-watch turns, turns that produced a
  visible reply, their speaking rate, frames pushed, and input tokens by lane.
  The `screen_read` tool now uses the same live-share clock: during an active
  share, omitting `include_image` includes real pixels, while inactive reads
  remain text-only by default. Pixel-free successful reads identify whether an
  image was not requested or was absent from the decrypted plaintext.

- **Screen-share diagnostics now expose metadata-only frame health.** The admin
  user detail view reports encrypted frame count, newest-frame time and age, and
  inline-versus-object-storage distribution without reading screen content.
  When a fresh device report still says broadcasting but the newest frame is
  over five minutes old, the API, Runtime V1, Runtime V2, and admin view now
  agree that the connection is stalled. Chat asks the user to stop and restart
  sharing instead of presenting the old frame as current or merely saying it
  cannot be read. The stalled state never defaults to decrypting old pixels.
  Enclave logs now identify missing plaintext images on both screen read routes
  and AEAD verification failures using stable event names and identifiers only.

- **Runtime V2 wake turns can persist memories with their server-frozen event
  time.** The encrypted-effect validator now accepts the current memory payload,
  including optional bucket, thread, importance, and pulse metadata, instead of
  rejecting it as a legacy shape immediately before the memory sink.

- **New Model API users can enter Runtime V2 through a cutoff-based default.**
  Only newly registered accounts with a successfully tested and active Model API
  route are eligible; the default does not migrate older accounts or users on a
  resident route. Invalid or absent rollout configuration keeps the account
  resident.

- **Runner health probe keeps reserved capacity under backend load.**
  `GET /healthz/runner` now runs its blocking heartbeat database query outside
  the ordinary ASGI thread pool, with bounded connection and SQL timeouts plus
  a three-second route deadline. A deadline failure returns a structured HTTP
  503 instead of leaving external monitors to time out.

- **Runtime V1 Fable 5 chat no longer requires visible chain-of-thought.**
  Fable 5 routes running through pi, including OpenRouter and compatible relays,
  now skip the mandatory `<think>` response format that the model refuses. Pi's
  native reasoning setting is unchanged, and other models keep the existing
  self-thinking behavior.
- **Memory extraction no longer mistakes model thinking for its JSON result.**
  Capture, Dream, legacy-card migration, and resident identity distillation now
  remove well-formed thinking blocks before locating the result object while
  retaining the previous raw-text fallback for malformed output. Hosted
  Capture and Dream may re-ask once after a JSON decoding error; truncated or
  prose-only responses remain non-retryable parse failures.

- **A base URL that is not an API endpoint no longer reports as an API-key
  failure.** When the configured relay base URL points at a web page rather than
  the API (an HTTP 200 that returns the site's homepage, or a **404** HTML error
  page), `provider_test_failed` now returns `"status_code": null` and a
  bilingual `detail` telling the operator the endpoint usually needs to end with
  `/v1` and that the API key is not the problem. Clients should display that
  `detail` directly. HTML error pages carrying any other status
  (401/402/429/5xx — relay auth, payment, throttle and gateway pages) keep their
  original status code and detail unchanged.

- **Runtime V2 Chat can search its own older conversation history on demand.**
  Two chat-only agent tools let the agent keyword-search messages beyond its
  visible context and read a small window around a match. Original messages
  remain the retrieval source of truth (summaries only prioritize scanning);
  decryption and matching stay inside the enclave under strict row/byte/time
  budgets; attachment binaries are never read for search. A turn that reads
  history loses outbound web/MCP/task tools for the next round, proactive wake
  lanes never see these tools, and a deployment kill switch (default on) can
  remove the capability without touching the normal chat path.
- **Genesis plaintext retries reuse completed persona-voice mapping.** The
  estimate/commit flow now retains its opaque staged-upload pointer in trusted
  job metadata until completion, and both fact-map and voice-map window results
  are stored in the encrypted checkpoint. Manual retries skip those completed
  model calls without duplicating memory cards. Interrupted workers also emit
  content-free cause, progress, elapsed-time, model, tier, and checkpoint-size
  diagnostics; interruption and retry policy itself is unchanged.
- **A large MCP server can no longer starve a smaller one.** When the connected
  servers together expose more tools than one turn can carry, the tools kept are
  now allocated round-robin across servers instead of taken in server-name order,
  so every connected server keeps a share; only the largest ones are trimmed.
  Previously a single big server could consume the whole budget and a server
  later in the alphabet would contribute no tools at all — its connection test
  passed while the companion genuinely could not see any of its tools. This now
  applies to both runtimes: the self-hosted bridge and Hosted Runtime V2, whose
  catalog was still filled in server-name order. The self-hosted bridge's
  per-turn cap is also raised from 50 to 100.
- **A self-hosted `claude` agent now receives the MCP servers you enabled in the
  app.** A hand-written `AGENT_CLI_CMD` without the `{mcp}` placeholder — the
  form the operator documentation previously showed — never passed
  `--mcp-config`, so no app-configured server reached the agent even though its
  connection test passed. Chat turns now get the server list and a matching
  pre-approval for its tools. A command that already sets `--mcp-config` is left
  untouched, and one that pins its own `--allowed-tools` keeps it and is told in
  the log which `mcp__<name>__*` rules to add. Other self-hosted runtimes
  (`codex`, hermes, OpenClaw) were unaffected: they read MCP from their own
  config files.

- **Voice calls no longer end with a protocol error when a turn produces no
  speech.** A turn that is deliberately silent — transport noise, a call that
  already ended, an ASR revision that superseded it — now returns a valid
  completion instead of one with no content at all, which ElevenLabs rejected
  as a Custom LLM failure and used to terminate the whole call.

- **A finished call stays in ordinary conversation context.** Its preview card
  is replayed as a labelled call-record block that names the speakers and
  states the transcript is not the companion's own speech, rather than being
  removed from the prompt entirely. Memory distillation is unchanged and still
  reads the archived full transcript.

- **Thinking-leak gate.** A model's own `<think>` block could reach the user's
  chat bubble on three delivery paths: Runtime V2 chat stripped only the first
  block of a reply, resident V1 required a matched open/close pair and passed an
  orphaned closing tag through verbatim, and proactive messages had no stripping
  at all. All four delivery points and the assistant history replayed to the
  model now share one strip step that fails closed when a block cannot be
  cleanly resolved. New `FEEDLING_THINK_GATE` environment variable, on by
  default, documented in Self-hosting. Turning off `FEEDLING_V2_SELF_THINKING`
  no longer disables this gate.
- **Runtime V2 now supports stricter Anthropic-compatible models during chat and
  multi-step tool use.** Fable 5 is allowed to answer without the optional
  self-thinking bubble instead of being forced into a visible chain-of-thought
  format that it refuses. Native tool definitions also remain visible while
  their matching `tool_use` / `tool_result` history is in the turn, so models
  such as Opus 4.8 can continue a real tool workflow without treating earlier
  results as fabricated. Repeated memory discovery is still executed at most
  once per mode.

- **Runtime V1 now pins and verifies the selected Claude model family.** Managed
  Claude Code commands pass the configured route through `--model`, and model
  changes rotate resident sessions. A Claude Code fallback to another Claude
  model is allowed and logged with both configured and actual model IDs;
  structured output that proves a non-Claude model served a Claude route is
  rejected as `model_mismatch`.

- **The companion now decides when to generate an image.** Image generation is
  no longer triggered by keyword matching on the user's message, and a dedicated
  image route no longer bypasses the main model. The companion calls an image
  tool itself — `generate_image` on Runtime V2, `io_cli.py generate-image` on
  Runtime V1 and self-hosted CLI residents — writes its own prompt, and its
  accompanying words are delivered together with the picture in one reply
  instead of being discarded. It may also generate an image without an explicit
  request. Generation failures are returned to the companion as a tool result so
  it can explain them in its own words rather than ending the turn; a reply that
  claims an image was produced when none was is returned once for correction,
  and is then delivered as written. `POST /v1/image-generation/generate` and the
  existing encrypted image-delivery path are unchanged.

- **Image-model setup failures remain actionable without replacing the
  companion's reply.** Runtime V1, Runtime V2, and CLI residents now preserve an
  allowlisted `image_generation_*` code on the failed `generate_image` activity
  event. Clients can use the final image-generation attempt in a completed turn
  to offer model setup while still displaying the companion's own words. A later
  successful attempt or a temporary provider failure does not request setup.

- **Failed voice calls now have an explicit, idempotent cancellation path.**
  `POST /v1/voice/cancel` installs a durable per-call tombstone, clears
  unarchived turn/result rows, and suppresses late resident or Hosted Runtime
  V2 replies before chat insertion. Finalize and cancel claim one lifecycle
  winner before archive writes, so cancellation cannot downgrade a call whose
  archive already won.

- **Runtime V2 Chat now applies matching World Book entries.** Matches use the
  current user turn and enter the prompt as a standalone, untrusted setting-data
  block rather than changing the user's message. Oversized matched context is
  deterministically truncated with a visible marker.

- **World Book now also reaches the turns your companion starts.** Previously
  only foreground chat saw it, so the companion could describe the world one way
  in conversation and another way when it reached out on its own. Entries marked
  *always on* — the world's constants — now enter every lane where the companion
  speaks in its own voice: heartbeat, scheduled reminders, manual wakes and
  screen-watch, on Runtime V2 and on your own server alike. Keyword entries
  still need a fresh text signal to trigger, so only scheduled reminders match
  them, and only against the reminder's own text; heartbeat and screen-watch do
  not trigger keyword entries from stale conversation or from on-screen text.
  Memory distillation, profile and maintenance turns receive no World Book
  context. On your own server the block now carries the same untrusted-data
  header, total-size cap and visible truncation marker that Runtime V2 already
  used.

- **Dream more clearly keeps merely related memories separate.** Its shared V1
  and Runtime V2 consolidation guidance now gives a concrete example that a
  cycling habit and recent insomnia remain independent memories even though
  both concern health; genuine evolution of one plan remains mergeable.

- **Runtime V2 no longer treats an intentional silent heartbeat as a failed
  response.** A model response containing a complete self-thinking block and no
  public text now completes ordinary heartbeat, manual-wake, and screen-watch
  jobs without publishing a bubble or arming proactive failure backoff.
  Scheduled reminders still require public text, while malformed or truncated
  thinking markup remains a fail-closed error.

- **Voice calls are now archived in full, and memory is distilled from the
  whole call.** At hang-up `POST /v1/voice/finalize` archives the complete
  transcript (permanent, sealed to the account's content key) and leaves ONE
  bounded preview card in chat; the per-turn rows are deleted only after the
  archive is durable. Memory then runs through the ordinary capture pipeline
  over the archived full text. This replaces the earlier behaviour where a
  model-written 1–3 sentence summary was both the chat artifact and the only
  thing memory ever saw — anything not in those sentences was lost. The
  response now returns `transcript_message_id`; `summary_message_id` is still
  sent as a deprecated alias for one release. Idempotent replays are judged on
  the archive; rows already folded by Runtime V2 compaction are retained and
  reported as `retained_covered`.

- **New public endpoints for reading archived calls.**
  `GET /v1/voice/transcripts` lists a caller's calls (metadata only — no
  words), and `GET /v1/voice/transcripts/{call_id}` returns one call's sealed
  envelope for the client to decrypt locally. The server never returns
  transcript plaintext. Calls are retained until the account is deleted;
  clearing chat history does not remove them.

- **Voice call length raised from 5 minutes to 1 hour.** The previous cap was
  shorter than the voice provider's own default and had no product rationale.
- **`POST /v1/chat/message` now accepts `context_refs`, carrying Garden
  "talk in chat" memory references on the resident line.** Same plaintext
  routing contract as the hosted send: only `type: "memory"` entries are
  honored, ids only are persisted as `quoted_memory_ids` (capped at eight),
  and the enclave expands them into decrypted memory context for the
  resident consumer. Requests without `context_refs` are unchanged.

- **Hosted Genesis no longer silently completes a non-empty long-term-memory
  import with zero cards.** Keep-all imports now fail with
  `distill_empty_output` and remediation copy directing the user to switch
  models. The job output retains up to six discarded map diagnostics with a
  reason and a 500-character model-output excerpt. Compatible-relay model
  recommendations temporarily exclude Gemini Flash IDs while leaving Gemini
  Pro and non-Gemini Flash names eligible. Admin data-track Genesis jobs now
  include the selected `distill_model`.

- **Hosted Genesis retries no longer reuse completed imports that produced no
  durable memories or identity artifact.** Retrying identical staged material
  after such an incomplete historical result now creates a new processing job
  instead of returning the empty result as successfully completed.

- **Do Not Disturb now suppresses Runtime V2 heartbeat and screen-watch
  scheduling.** Due-query polling excludes accounts whose proactive settings
  have `dnd` enabled and resumes automatically when DND is turned off.

- **Hosted Runtime V2 exposes finer-grained perception and memory tools.** The
  model can now read the permission-gated recent app open/close trajectory,
  request ambient or sensitive memory-index views, include archived or
  superseded cards when fetching, and attach audit reasons to memory writes.
  Tool guidance also distinguishes a recent app event from current app usage,
  explains rolling perception baselines, accepts relative scheduled-wake times,
  and routes requested screen pixels through the native visual observer.

- **Hosted Runtime V2 now carries the complete genesis persona into every Chat
  and proactive wake turn.** The encrypted persona is decrypted just in time
  for the turn and placed in the trusted system prefix without profile or
  context truncation. Accounts that have not completed genesis keep the generic
  companion prompt, and a persona update takes effect on the next turn.

- **Hosted Runtime V2 restores the proactive-presence semantics used by Runtime
  V1.** Automatic wake context is no longer serialized as a synthetic user
  message, and speaking and staying silent are treated as equally valid for
  heartbeat and screen-watch moments. Those turns now receive content-free
  attention facts for the last user-message age, recent-tail freshness, and the
  number of visible proactive messages in the preceding 24 hours. Scheduled
  reminder text is supplied as labeled application data and retains its
  must-deliver semantics, while an ordinary heartbeat for an account with no
  genuine conversation history completes without calling the model.

- **Runtime V2 perception wakes now use durable per-signal baselines.** The
  first observation establishes a baseline without waking the model, and stale
  or replayed source events cannot manufacture a later change. Only a fresh,
  allowlisted transition can enqueue its corresponding proactive wake, which
  prevents delayed arrival or unlock notices from old sensor data. Exact
  network/device anchor identifiers and home/work labels are excluded from
  durable wake metadata. Baseline fingerprints record an opaque key ID and
  support a one-generation previous-secret bridge so rolling secret rotation
  cannot manufacture a location change. A separate post-rollout convergence
  switch can rebaseline dormant unknown-key rows without waking, but remains
  disabled by default and must not be used while old workers are running.

- Changed Hosted Runtime V2 perception grounding to keep foreground chat
  readings tool-only and give proactive wake a boolean-only glance.
  Perception-triggered wake messages no longer receive unrelated exact battery,
  weather, activity, sleep, or health values in their initial prompt.

- **Empty provider replies are now attributed to the provider, not the
  system.** When a model or relay returns a successful response with no usable
  text (empty terminal reply, mid-stream cut, quota-pressure fake success), the
  failure notice now uses the `provider_empty_reply` class with
  provider-transient blame and copy that points at the user's model channel,
  instead of the system-blame "something went wrong on our side" message.
  Replies that contained real text but were emptied by protocol-leak
  sanitization keep the system attribution, as does exhausting the server's own
  tool-call budget without producing a reply. Applies to the resident V1 agent
  path and to Runtime V2 chat, wake, and memory-extraction lanes.

- **Runtime V2 can recover once from a reasoning-only provider response.** A
  successful foreground response with reasoning or a normal stop reason but no
  visible text or client tool call gets one bounded correction while preserving
  the currently allowed tool catalog. A relay response with no text, tool call,
  reasoning, or stop reason now fails immediately as `provider_empty_reply`
  instead of repeating the same billed request or reporting a network outage.
  Intentional Runtime V2 wake silence is unchanged.

- **Plaintext memory writes reject tombstone-style notes.** A plaintext
  `memory.add`, upgrade, or `memory.supersede` whose summary or content is a
  bookkeeping note — "已被 … 取代" or "superseded by" followed by an
  internal-id-like hex string — now fails with an item-level
  `memory_card_tombstone` instead of being stored, and a rejected supersede
  leaves every targeted card active. This closes the freehand agent-tool path
  that bypassed the structured extraction gates; ordinary prose about
  replacement without a hex id is unaffected.

- **Hosted Dream maintenance now applies deterministic exit gates instead of
  content-quality judgment.** Runtime V2 fetches complete candidate card bodies
  instead of reconstructing them from one-line summaries. Every consolidation
  must include a rationale, may not reuse a source card within a run, and may
  not target unknown cards. Consolidation content itself is not second-guessed:
  the earlier per-proposal semantic-review call and the substantive-increment
  requirement for one-card rewrites were removed, so low-overlap evolution such
  as a travel plan becoming a booked ticket merges without an extra model
  judgment, and a shorter-but-more-accurate rewrite is accepted. In their place
  Dream rejects (and bounces back for one rewrite) any result whose visible
  fields contain an internal card id or a tombstone-style note, and a run that
  would retire more than a configurable share of the active garden (default
  80% and at least 10 cards) fails as a whole without applying anything. All
  actions remain soft supersedes bound to the pre-run card snapshot, and
  Dream's durable automatic trigger advances only on new non-Dream cards.

- **Users can explicitly wake a full Memory Dream organization from chat.**
  Runtime V2 exposes `memory_organize` only for an explicit user request and
  force-enqueues a single-flight Dream job without granting direct merge access
  to the chat turn. It bypasses automatic timing and new-material gates but
  retains the rationale requirement, deterministic exit gates, soft
  supersedes, and the deployment/user Dream switches; a disabled switch returns
  a clear disabled state. Resident V1 has
  the equivalent `memory-organize` CLI verb over `POST /v1/dream/tick` with
  `force: true`.

- **Runtime V2 can browse large Memory Gardens by partition without increasing
  its tool-result cap.** `memory_index` now exposes the existing `bucket` and
  `thread` filters, restoring resident CLI parity without adding offset-based
  full-library pagination. Index and search results report content-free
  `total` and `returned` counts, and truncated results tell the model to browse
  bucket or thread partitions. Tool guidance keeps targeted questions on
  `memory_search` then `memory_fetch`, while user-requested bulk cleanup is sent
  to `memory_organize` rather than many chat-loop card edits.

- **Scheduled reminders can repeat daily or weekly.** The model-facing
  `schedule_wake` tool accepts `repeat: "daily"` or `repeat: "weekly"` and uses
  fixed 24-hour or 7-day intervals. Identical pending reminders are deduplicated
  by trigger instant and repeat mode, each successful trigger publishes a new
  pending `wake_id`, and `cancel_wake` stops the complete repeating series.
  One-time reminders remain unchanged.

- **Hosted Genesis memory imports no longer fail provenance validation or
  complete after every card was rejected.** `genesis_import` is now a published
  `capture_mode` for `POST /v1/memory/actions`, matching the existing memory
  source value used by plaintext and long-term-memory imports. If an import
  batch writes no cards and reports any failed item, the Genesis job is marked
  `failed` with the underlying action error instead of completing with a zero
  memory count; partial batches that write at least one card still complete.

- **Genesis onboarding supports estimate then commit.** Managed clients can
  encrypted-stage onboarding material and receive per-material window/token
  estimates without an LLM call, then commit the `staged_id` with an optional
  job-only model override. Fast-model recommendations cover Anthropic,
  DeepSeek, Gemini, OpenAI, and OpenRouter, with a three-second catalog probe
  for compatible relays. Job status immediately exposes every material as
  queued, followed by ordered progress and real candidate-card counts,
  `identity_ready`, and cause-aware failure fields. Processing frames preserve
  the complete material list while individual items advance, so counters do
  not disappear between stages. Missing, consumed, and expired stages have
  distinct 4xx errors. Genesis V2 now remains processing
  after foreground identity readiness and reaches done only after all material
  windows complete, including combined-map imports. Malformed provider JSON is
  reported as `model_bad_json` instead of an internal error. Plaintext workers
  now maintain an independent, instance-fenced lease. Status and submission
  requests immediately recover a same-host job whose owner process has exited;
  remote or legacy owners retain a two-minute heartbeat cutoff so a rolling
  deploy cannot kill a worker that is still running on another host.

- **Genesis plaintext processing now fails fast and resumes completed windows.**
  `POST /v1/genesis/imports/plaintext` permits only one processing plaintext
  job per account. A concurrent submission returns `409 import_job_active`
  with `active_job_id`; the guard is enforced in PostgreSQL across API workers.
  The first real model call is a bounded canary, provider timeouts make at most
  two attempts while `429`/`5xx` retain their existing retry budget, and a
  timed-out canary is reported as `distill_model_too_slow` with copy directing
  the user to a faster model. Other provider configuration failures retain their
  specific cause-aware guidance. Each successful material window is durably
  checkpointed in an encrypted envelope before progress advances. Retrying the
  same failed import skips completed windows and resumes at reduction, and
  failed onboarding validation now reports the durable window percentage and
  per-material progress instead of `progress: 100`.

- **Web search and fetch now work on Runtime V1 too (managed runtime only).**
  The user-controlled `web_search` / `web_fetch` tools were previously a Runtime
  V2 capability only; V1 accounts on the **managed (cloud) runtime** can now use
  them through new backend endpoints `POST /v1/agent/web/search` and
  `POST /v1/agent/web/fetch`. These endpoints require a hosted per-user runtime
  token carrying the `web` scope and refuse long-term api-key auth with 403, so
  **self-hosted deployments do not receive Feedling's web tools** — a
  self-hosted operator's model reaches the internet through its own provider's
  built-in web capability instead. Authorization is re-checked on every call
  (user switch, operator halt, per-user rate limit), so a static V1 tool prompt
  cannot bypass it. On the managed runtime the model relies on these tools for
  web access, so the user's "off" switch is effectively a full cut.

- **Attested custom enclave domains can accompany the direct audit endpoint.**
  The production, test, and pre-production deployment definitions stage
  `enclave.feedling.app`, `test-enclave.feedling.app`, and
  `pre-enclave.feedling.app` through `dstack-ingress`; each URL becomes available
  only after that environment is deployed and its evidence is validated.
  Existing `-5003s` clients remain compatible and retain the direct audit route.
  New clients must verify WebPKI plus both the ingress certificate-evidence and
  enclave-attestation bundles before claiming pinning-equivalent security;
  WebPKI alone is insufficient.

- **Memory Garden status now reports a monotonic captured-card total.**
  `GET /v1/dream/status` adds `capture_cards_added` and
  `capture_completed_at`. Resident and Runtime V2 Capture runs add only cards
  actually inserted, never reset the total at a calendar boundary, and leave
  the banner fields unchanged after a zero-card run. Clients derive the
  unconfirmed count from the total saved when the user last dismissed it.

- **Background agent turns can no longer rewrite the identity card.** Runtime
  V2 now visibly refuses `identity_patch` and `identity_nudge` during proactive
  wake turns while preserving identity reads, foreground Chat identity changes,
  and wake-time Memory writes.

- **Visual-model setup now treats a real image probe as authoritative.** Every
  selected model receives one small, randomized image challenge even when its
  provider catalog declares image support, declares text-only input, omits the
  model, or is unavailable. Catalog modalities are advisory and are preserved
  only from explicit official per-model fields; model-name tables and provider
  defaults are no longer used. Catalog/probe disagreements produce
  content-free diagnostics. Empty visible replies from reasoning models are a
  retryable failure rather than proof of image incompatibility, while a
  non-empty reply with contradictory colors remains unsupported. Stable visual
  error codes still distinguish incompatible image input, invalid credentials,
  quota, rate limits, and temporary provider failures.

- **VPS image generation is now capability-based.** A resident can advertise
  `agent_image_generation_v1` when its configured agent entry actually exposes
  a callable image tool. Dedicated image routes still take precedence; without
  one, capable residents receive the request directly, while residents that do
  not advertise the capability continue to receive image-model setup guidance.
  When a dedicated route succeeds, its prepared image is delivered immediately
  through the existing atomic reply path instead of waiting for a second main-
  model turn.

- **Generated images can now appear directly in Chat.** Runtime V2 normalizes
  inline image results from supported provider responses, while CLI residents
  can stage PNG, JPEG, or WebP output with `send-image`. Images are validated,
  size-bounded, encrypted separately, and committed atomically with the reply as
  native `content_type=image` rows. The public resident response contract adds
  `image_followups`; remote provider URLs and local filesystem paths are never
  exposed as image delivery.

- **Hosted visual failures are easier to diagnose without exposing user
  content.** Per-user admin detail now includes bounded model-route runtime
  error metadata and the newest 20 notice summaries through explicit
  content-free field allowlists; provider endpoint URLs, notice text, notice
  detail, and copyable prompts are excluded. Visual observation also emits
  metadata-only debug trace events for image-read failures and provider-call
  outcomes, without image data, observations, or raw provider responses.

- **Hosted visual observation now works for zero-roster Runtime V1 users.**
  The authenticated request's short-lived, user-bound runtime token is
  forwarded through both the exact image-body read and visual provider-key
  decrypt, instead of being discarded and replaced by an empty API key. Image
  retries now fetch the requested message directly rather than searching only
  the newest 20 Chat rows. Requests with neither credential still fail closed.

- **Runtime V2 can replace its legacy summary with a bounded Memory/User
  profile.** The default-off `FEEDLING_V2_PROFILE_ENABLED` switch now gates
  both generation and turn-time selection. Only an `ok`, non-disabled profile
  whose two encrypted fields both validate and decrypt is injected, as one
  early user-role block explicitly labeled model-derived untrusted data.
  Missing, pending, degraded, disabled, invalid, or undecryptable profiles keep
  the rollback-compatible summary. Verbatim replay wins on conflict, coverage
  gaps remain a separate late data notice, and OpenAI Chat and Anthropic cache
  breakpoints prioritize the stable profile ahead of an older recent-user
  boundary.

- **Runtime V2 stages bounded profile generation and restores the pooled
  worker's Memory lanes.** A new low-priority `profile` job reads the complete
  eligible Memory Garden with a scoped runtime token, rejects truncated views,
  generates Memory/User fields with a bounded provider-call budget, and writes
  them through the encrypted profile CAS. Runtime V2 cutover, successful dream
  writes, and best-effort post-Chat freshness checks can enqueue the job;
  degraded profiles respect exponential retry metadata, and the seven-day
  stale floor runs independently of the dream setting. Profile failures remain
  background-only and never create a Chat bubble or terminal turn error.
  Managed production, pre-production, and test Compose configurations now
  explicitly enable capture and dream in `serve-worker`. Profile generation
  and injection stay default-off under the same worker switch.

- **Runtime V2 restores proactive presence and memory maintenance.** Ambient
  heartbeats no longer require screen broadcasting to be active: an enabled,
  activated companion may wake for a presence turn while screen sharing is
  off, while the ambient consent switch still blocks the lane. Perception
  events such as photo, arrival, and unlock changes now enter the pooled V2
  job queue instead of the resident-only legacy queue, and their bounded
  trigger context follows the wake as untrusted runtime data so the turn can
  respond to the actual change. The pooled worker also runs the independently
  consent-gated Memory Capture and Dream producers; each fleet lane remains
  independently reversible through deployment configuration.
- **Encrypted Runtime V2 profile storage is staged for the bounded
  Memory/User rollout.** Both fields share one `v2_agent_profile` CAS document
  but remain separate shared encrypted envelopes. PostgreSQL and the TEE shadow
  receive the same ciphertext document; only state, character counts, source
  counts, and generation/retry timestamps remain plaintext metadata.

- **Runtime V2 can advance conversation coverage without steady-state
  background model calls.** The default-off
  `FEEDLING_V2_PROFILE_COVERAGE_DETERMINISTIC` worker switch replaces
  provider-backed maintenance and inline catch-up folds with exact,
  content-free count leaves. Deterministic fan-out checkpoints keep the
  canonical frontier and encrypted materialized head bounded. Synthetic
  `verify_ping` and `resident_maintenance` rows remain excluded from both the
  source bounds and immutable coverage witnesses; encrypted Chat rows remain
  the durable source ledger. Disabling the switch restores the existing
  provider-backed summary path. Enable it only after the bounded Memory/User
  prompt path is deployed and verified. Existing legacy model-written frontier
  nodes can still require a provider-backed rollup during migration, so zero
  background calls is the steady state.

- **Memory action batches now isolate item failures.** A structurally valid
  `POST /v1/memory/actions` batch processes every item and returns per-item
  `http_status` plus `applied_count`/`skipped_count`/`failed_count`. Full and
  partial applied success return HTTP `200`; a batch with zero applied actions
  and at least one failure returns HTTP `400`, promotes the first failed item's
  `error` and optional `detail`, and still includes every item result and all
  counts. An all-skipped batch remains HTTP `200`. Older clients that treated
  every HTTP `200` as full success must still inspect the item fields. Capture
  clients record applied, skipped, and failed items separately; partial success
  no longer marks the whole capture job failed. Resident capture may re-ask the
  model once after either a format or semantic validation failure, using one
  shared per-job retry budget so the two layers cannot multiply retries.

- **Memory writes now fail closed on invented metadata and skip exact active
  duplicates.** `POST /v1/memory/actions` rejects unknown `source` and
  `capture_mode` values with HTTP `400`. Before `memory.add`, the server
  compares Unicode-NFKC/case/whitespace-normalized title and content with
  readable active shared cards; an exact match returns a successful
  `duplicate_active` no-op with the existing card ID and emits no write effect.
  The published source enum includes existing bootstrap, history-import,
  resident-write, and Ombre sync provenance values.
  Capture clients no longer rewrite `merge` or `supersede` cards that lack a
  target into `memory.add`.
- **The thinking chain is now io's own first-person reasoning, not raw provider
  chain-of-thought.** When the thinking display is enabled, io is prompted to open
  each reply with a short self-authored `<think>` block (its own train of thought,
  in the user's language, with no tool/internal names); the runtime prefers that
  block and shows the model's native reasoning only as a fallback when no block was
  written. The model still reasons natively for answer quality — only what is
  *displayed* changes. This spans both Runtime V2 and resident V1. It is on by
  default and controlled by a single kill switch, `FEEDLING_V2_SELF_THINKING`
  (unset/`1` = on; `0`/`false`/`no`/`off` = revert to showing native reasoning
  verbatim). Because the displayed thinking may now be this self-authored summary,
  `include_reasoning` requests "the assistant's per-turn thinking," which may be
  either the self-authored block or native reasoning, rather than strictly the
  provider's raw chain-of-thought.

- **Image turns rejected by a text-only main model now return actionable
  failure metadata.** Resident V1, Runtime V2, and current VPS residents classify
  the provider rejection as `vision_model_required` and direct the user to add
  or select a vision-capable model instead of showing the generic retry-later
  reply. Hosted V1 and Runtime V2 also record that exact active provider/model
  binding as `unsupported`, so later `GET /v1/vision/config` responses can show
  the non-blocking client hint without requiring a separate Settings probe.
  Image sends remain ungated: probe status does not block delivery.

- **Main-model image validation now uses one runtime-neutral endpoint.**
  `POST /v1/vision/main/test` trusts only explicit provider catalog modalities;
  when metadata is missing, it performs a real two-image capability probe.
  Every successful `POST /v1/model_api/setup` now starts that same probe in the
  background, so `GET /v1/vision/config` can expose an unsupported main model
  before the user opens visual settings or sends an image. Setup and image
  delivery never wait for the probe, and a route-version fence discards a
  result if the user reconfigures the route while provider I/O is in flight.
  Model API routes return a terminal `ok`, `unsupported`, `failed`, or
  `untested` result. Resident runtimes return `202 testing` while an isolated,
  hidden probe runs; clients then refresh `GET /v1/vision/config`.
  VPS residents with the probe capability now enqueue that same hidden check
  automatically when their consumer/entry/provider/model binding first appears
  or changes. Matching pending or completed bindings are not re-probed, and
  explicit modality metadata still avoids the model call. Polling and image
  delivery remain non-blocking. Explicit resident rejections
  (`vision_model_required` or `vision_model_incompatible`) normalize to the
  same cached `unsupported` verdict, while authentication, quota, rate-limit,
  timeout, upstream, and empty-response failures remain `failed`. Known
  `unsupported` verdicts are non-blocking signals for client guidance: image
  sends still follow the user's configured main or dedicated route unchanged.
  Runtime failures expose stable visual error codes and the exact provider/model
  without putting probe traffic into Chat history or activity.

- **Hosted Runtime V2 chat sends can request provider reasoning per turn.**
  `POST /v1/model_api/chat/send` accepts the optional boolean
  `include_reasoning`; omission preserves the previous disabled behavior. The
  request applies only to the accepted V2 user turn. Resident runtimes ignore
  it, and provider/tool-loop fallbacks remain text-only when reasoning is not
  supported or tools have been disabled for the terminal round.

- **Access-mode changes no longer bypass the Hosted Runtime V2 rollout
  reconciler.** Selecting `model_api` records the user's route choice but does
  not directly move the execution fence to V2; the `v2_user_allowlist` desired
  state and reconciler remain the only authority for the resident-to-V2
  transition. Selecting `resident` still demotes immediately, and a failed
  runtime-control update now restores both the prior runtime mode and the prior
  onboarding route.

- **ElevenLabs calls can now use the same Chat model and context as typed
  messages.** An authenticated client creates a short-lived, call-bound voice
  session, then ElevenLabs sends transcribed turns to an OpenAI-compatible
  streaming endpoint. Feedling routes each turn through the user's current
  resident or Hosted Runtime V2 path, preserving persona, memory, tools, and
  chronological Chat history. ElevenLabs continues to handle transcription,
  interruption, and speech synthesis, but never receives the user's model API
  key. Voice reply handoff state is encrypted and expires automatically.
  Deployments must set `FEEDLING_VOICE_GATEWAY_PUBLIC_URL` to the public HTTPS
  API origin; missing, private, or non-HTTPS values cause voice-session
  creation to fail closed with `503 voice_gateway_not_configured`.

- **A new `GET /v1/perception/app_close` endpoint reports app closures,
  mirroring the existing `app_open` shortcut.** It accepts the same `app`
  (required, `bundle_id` remains a deprecated alias), `category`, and `ts`
  (`client_ts` remains a deprecated alias) parameters, and — like
  `app_open` — is a GET with a write side effect: it records an event and
  is not read-only. A close only updates the current-app state when the
  closed app matches the app currently recorded as foreground, so an older
  app killed in the background cannot clobber whichever app is actually
  current. The two endpoints correspond to the "is opened" / "is closed"
  trigger options on the same iOS Shortcuts automation; a client can wire up
  only one of them, and the other being absent is a benign degradation.
  The Perception snapshot gains a corresponding `app_state` field, valued
  `"foreground"` or `"closed"`, and `null` when no open has been reported yet.

- **Chat route selection now fences Hosted Runtime V1 from independent
  residents.** The onboarding route is the execution-ownership source of truth:
  V1 discovery requires an explicit `model_api` selector in addition to a
  tested active model route and the existing Runtime V2 fence. Switching to
  `resident` or `official_import` deactivates the V1 route atomically; switching
  back restores the most recently updated tested-ok route. Missing selector
  state fails closed. Operations telemetry now keeps recent polls per consumer
  identity, reports the effective responder and its evidence, and marks
  route/lease/poll conflicts instead of treating the last poller as proof that
  another process stopped.

- **Runtime V2 Chat failures no longer leave the sender waiting silently.**
  A failed or expired foreground turn now commits a parent-linked encrypted
  failure reply carrying the same `turn_failure_error_class`,
  `turn_failure_blame`, and `turn_failure_user_text` metadata as the resident
  path. Actionable provider configuration failures show their specific recovery
  text; transient provider and system failures use the standard retry-later
  fallback. A conservative internal context-window default is attributed to the
  system, not misreported as the user's model limit. Delivery is replayed from a
  durable outbox after worker crashes and lease timeouts, while a newer
  successful reply atomically suppresses a stale failure bubble. Proactive and
  maintenance lanes remain silent.


- **V1 CLI residents can now return generated documents as native download
  cards.** Claude, Codex, and Pi residents receive a `send-file` command backed
  by a private per-user staging directory. Word and PDF requests render real
  `.docx`/`.pdf` bytes, and explicit formats cannot fall back to Markdown. Named
  formats receive one bounded completion retry; no-format requests remain
  semantic prompt guidance, and a missing file no longer replaces or fails the
  model's text reply. When a file is delivered, the text primary and its encrypted
  `file_followups` commit atomically through `POST /v1/chat/response`, preserving
  text-first/card-below ordering.

- **Memory cards are no longer written with unfilled template placeholders.**
  Capture and Dream now validate card *content*, not just field presence: a
  `summary` or `content` that is a bracketed placeholder (`[thickened summary]`),
  a bare ellipsis, a copied instruction fragment, or empty is rejected, and both
  fields must carry real text. A reply containing any such card is returned to
  the model once with an explicit note about which field was unfilled; the second
  attempt keeps whatever cards are clean. If nothing usable survives the retry,
  the extraction job fails and its conversation window is left for a later
  attempt instead of being silently consumed. Substantive-character detection is
  language-neutral (Arabic, Cyrillic, Hebrew, accented Latin, and CJK all count),
  so non-Latin cards are unaffected.
- **Memory cards are less likely to refer to the account holder as "user".** The
  conversation transcript given to the Capture and Dream models now labels
  speakers with the person's own name — or the neutral `对方` when no name is
  known — instead of the raw `user` / `assistant` roles, which is what taught
  models to copy the system label into cards. The prompts also ask for the
  `用户` / `user` prefix to be dropped from product vocabulary, so a card says
  `界面` rather than `用户界面`. Card text is deliberately **not** post-edited by
  a rewriter: only the model can tell whether a given "user" means the account
  holder or that person's own customers, and guessing wrong would silently
  rewrite a true memory into a false one.
- **Runtime V2 now selects recent conversation context in complete turns.**
  Foreground Chat targets the newest 40 user-seeded turns and proactive wake
  lanes target 16. Before every provider round, smaller model windows can
  reduce only summary-covered verbatim replay to the largest newest suffix that
  fits; the summary, uncovered exact rows, current request or wake nudge, and
  native tool transcript are never clipped. Budget pressure can first compact
  a safe answered prefix and then rebuild from the new durable watermark, so
  every stored row remains represented by either summary coverage or exact
  prompt content. New turn-based environment settings control the two targets;
  the legacy message-count setting keeps its old compaction meaning.
- **Runtime V2 chat and wake turns now receive explicit temporal context.**
  Each turn gets one snapshot containing UTC and user-local time, the latest
  genuine user-message age, and timestamps for the verbatim conversation tail.
  Account timezone, stable device timezone, and UTC are used in that order.
- **Runtime V2 now gives unaudited model routes a 65,536-token default context
  window.** The existing environment override remains available, and setting it
  to `0` still restores fail-closed configuration. Explicit route metadata,
  audited model families, and deployment overrides continue to take
  precedence.
- **Runtime V2 now applies a persistent per-user retry delay after automatic
  wake failures.** Consecutive heartbeat or agent-scheduled wake failures back
  off from 60 seconds to a maximum of one hour, and a successful automatic
  wake clears the streak. A new user message resumes automatic wakes
  immediately. Manual wakes and screen-watch events remain available, while
  the longer-horizon provider health circuit continues to handle sustained
  provider outages.
- **Runtime V2 no longer publishes punctuation-only provider fragments as
  assistant messages.** A foreground Chat turn replaces a truncated fragment
  such as `.` or `。` with the standard visible fallback and classifies it as a
  temporary upstream-provider failure. Background wake lanes record the failed
  turn silently and do not create a chat bubble or error chip. Emoji, letters,
  digits, and CJK text remain valid replies.
- **Runtime V2 now carries forward the incident-hardened proactive interruption
  guards from Runtime V1.** After three consecutive AI-authored follow-up wake
  schedules without genuine user input, the fourth schedule is suppressed until
  the user speaks; heartbeat and screen/event wakes do not consume this budget.
  Heartbeat, manual, and screen-watch replies also perform a final 90-second
  chat-collision check inside publication, so a user message or foreground
  agent reply that lands while the wake model call is running makes that wake
  sleep instead of posting or folding and retrying. User-requested scheduled
  reminders remain deliverable during active chat.
- **New `POST /v1/model_api/models` lists a provider's live model catalog (BYOK
  setup).** Supply the credential exactly one of two ways — a fresh `api_key`, or
  a stored `credential_id` whose provider/base_url are the source of truth (any
  `provider`/`base_url` sent alongside a `credential_id` is ignored). Supplying
  both, neither, an empty string, or a null is a `400 api_key_or_credential_id_required`.
  The response returns `models` (each `{id, display_name}`), `complete`, and
  `catalog_supported`. `complete: false` with `warnings` means the list was
  truncated (page/size/time budget). `catalog_supported: false` means the
  provider has no listable catalog (e.g. Bedrock, or a custom endpoint with no
  `/models` route) and the client should fall back to manual model entry.
  Provider auth failures are mapped to `400`/`429`/`503` catalog slugs — never
  `401` — so an expired Feedling login is never confused with a bad provider key.
- **V1 resident and Hosted Runtime V2 chat now expose confirmed execution activity.**
  `GET /v1/chat/turn-activity/{turn_id}` returns a user-scoped, read-only
  projection of backend job and tool-dispatch records while a turn runs. The
  projection contains only bounded identifiers, state, timing, result
  classification, and confirmed durable-effect disposition; it excludes tool
  arguments, result bodies, assistant prose, and reasoning. Completed events
  also appear as `activity_events` on the assistant history item. Confirmed
  memory-index/search/fetch results include a total count and include canonical
  category counts only when the complete classification is reliable; custom or
  unknown buckets fall back to total-only. The shipped V1 resident `io_cli`
  records the same fixed-shape invocation transitions through an authenticated,
  turn-scoped write boundary; tool arguments and result bodies are never sent.
  Zero-result discovery remains visible, and Runtime V2 protocol calls such as
  `reply` and `send_file` use the same activity boundary. A turn exposes at
  most 100 projected activity events.
- **Separate vision models now work on Hosted Runtime V1 and VPS residents as
  well as Runtime V2.** The official resident advertises a fresh
  `vision_observer_v1` capability, accepted image turns pin the selected route,
  and only a neutral untrusted observation reaches the main model. Resident
  capability and probe state remain settings feedback and do not block image
  ingestion; follow-main keeps the existing image path.

- **Runtime V2 now honors the Dream and screen-watch consent switches at
  execution time.** Disabling Dream prevents queued Dream work from making a
  provider call even when the deployment-wide Dream feature flag is enabled.
  Disabling screen watch prevents its producer from enqueueing background work;
  Heartbeat and the other proactive controls remain independent. Runtime V1
  behavior is unchanged.
- **Legacy perception wakes now honor the same dedicated controls as Runtime
  V2.** Photo, arrival, and unlock events map to their canonical triggers and
  are governed only by their corresponding switches; disabling Heartbeat no
  longer suppresses them. Motion-state changes remain readable perception
  context but no longer create proactive wakes. DND and Away remain global
  suppressors.

- **Long-term provider configuration failures now pause proactive model work.**
  When an account has gone 48 hours without a usable provider response and its
  latest failures have continuously required user action for at least one hour,
  Feedling pauses automatic heartbeat, screen-watch, capture, and dream calls
  instead of retrying every few minutes. Foreground Chat and user-initiated
  manual wakes remain available, one automatic proactive recovery probe is
  allowed every 24 hours, and any successful provider response or Settings
  validation restores normal operation immediately. Temporary rate limits and
  upstream `5xx` failures do not trigger the pause. Resident runtimes can report
  the outcome through the new optional
  `provider_result: "success" | "failure"` field on
  `POST /v1/model_api/runtime_error`.

- **`POST /v1/chat/message` now persists an optional `caption_envelope`.** To send
  text alongside an image or file, pass the caption as its own E2E
  `EncryptedEnvelope` in `caption_envelope` (same shape as `envelope`, wrapped to
  the enclave). The enclave decrypts it into the message's plaintext content so the
  agent receives the caption. Previously an image/file sent with typed text
  dropped the text on this endpoint (the agent saw only the attachment). Image/file
  sends without a caption are unchanged; `content_type: "text"` ignores the field.

- **The `identity_patch` tool can recalibrate the relationship day count.** Put a
  whole number `relationship_days` inside the `patch` object (for example
  `patch: {"relationship_days": 300}`) and the persona's relationship start anchor is
  recalibrated so the app shows that day count. `relationship_days` is the **1-based,
  user-facing** count — the "day N" the client displays, where the day you met is
  day 1 (not day 0); the anchor is moved to `today − (relationship_days − 1)`. (The
  stored `days_with_user` remains the elapsed 0-based count and the client adds 1 for
  display, so "set it to 45" shows 45.) Onboarding, which derives the elapsed count
  from a relationship date rather than a user-stated number, is unaffected. The day
  count is always derived from the anchor, so this rides the same compare-and-swap
  write as every other profile field. Notes on the contract:
  - **Absolute anchor is frozen at request time.** The relative day count is
    resolved to a fixed calendar date when the change is accepted, not when it is
    later applied. When the change is applied, that frozen date is consumed verbatim
    as long as it is a valid calendar date not in the future and its day count is
    within the ~100-year cap; the apply step never re-ages it against the day it
    happens to run. A delayed or retried apply — including one that crosses midnight
    or lands at the maximum day count — therefore uses the exact date computed at
    request time, so it cannot drift and re-applying the same recalibration is a
    no-op.
  - **Priority.** An explicit `relationship_days` is treated as a deliberate user
    calibration and wins over the auto-inferred count (earliest memory / session);
    a persona re-derivation will not overwrite a count the user calibrated.
  - **New error codes.** `relationship_days_must_be_non_negative_int` (not an
    integer, or negative) and `relationship_days_out_of_range` (exceeds the ~100-year
    cap) are returned as a stable `400` before any write. Invalid values are rejected
    up front rather than failing at apply time.
  - `POST /v1/identity/relationship_anchor` and the `identity.relationship_days_set`
    action keep their existing request/response shapes but now share this same
    compare-and-swap write and integer validation (a boolean/string day count is now
    rejected instead of coerced).

- **Received AI messages no longer expand the Dynamic Island.** Chat replies and
  proactive messages now deliver via the system alert notification only (it stacks
  in Notification Center instead of the Live Activity briefly expanding). The
  Live Activity / Dynamic Island push for these messages is gated off by default;
  set `FEEDLING_AI_MSG_LIVE_ACTIVITY=1` to restore the previous dual delivery. The
  explicit `/v1/push/dynamic-island`, `/v1/push/live-activity`, and
  `/v1/push/live-start` routes are unchanged and remain available for other uses.
  No request/response shape change.

### API

- `GET /v1/onboarding/validate`: when Genesis fails, the `history_import` step's
  `required` text now names the cause bilingually (zh/en), classified from the
  job's stored error — API key invalid, provider timeout (naming thinking/slow
  models and unstable relays), quota exhausted, malformed/empty model output,
  service restart, decrypt failure, or internal — and always directs the user
  to fix the cause and restart the import (uploaded materials are kept). It no
  longer suggests updating the app. User-facing copy now says "文件解读 /
  reading your onboarding materials" instead of the internal term "蒸馏 /
  distilling", including the `genesis_failed` / `genesis_partial` notice texts
  and the in-progress step line.
- Automatic `heartbeat_*` calls to `POST /v1/proactive/tick` now use a
  server-clock cadence gate per account. After a heartbeat job is successfully
  queued, the response's `decision.heartbeat_next_tick_at` advances by the
  normalized wake interval; another automatic heartbeat before that epoch is
  rejected with `decision.reason: "heartbeat_throttled"` and recorded as a
  skipped job. Rejections do not move the deadline. Reducing
  `wake_interval_sec` shortens an existing deadline immediately. Manual,
  event-driven, scheduled, screen-watch, and self-wake jobs neither read nor
  update this scheduler field.

- **The Runtime V2 `identity_nudge` tool now actually applies personality-dimension
  changes.** The tool was exposed in the model-visible catalog but had no effect
  wiring, so any call failed the turn. Its full produce → encrypt → replay-validate
  → sink path is now implemented (dimension nudges land on the identity card), with
  unknown effect operations failing closed. No request/response shape change.

- **`web_fetch` now returns the beginning of a large page instead of failing.**
  A response over the raw-body cap was discarded whole, so the tool errored on
  essentially every real site (Wikipedia is 360 KB, a weather page 86 KB, the
  Python docs 41.8 KB) and a model that only ever saw failures would tell the
  user it had no web access. It now keeps what it read, raises the retained-body
  cap to 300 KB, and reports a new `truncated` boolean that is true whenever any
  content was left out — either the body cut or the text cap. An unterminated
  `<script>`/`<style>` tail is dropped rather than handed over as page text.
- **`web_fetch` now extracts the readable article from a page.** With only a
  plain tag-strip, most of the model's per-page budget went to the navigation
  menu ("Jump to content / Main menu / Donate" fills the first 2257 characters
  of a Wikipedia article; a weather page opened with "首页 预报 预警 雷达").
  HTML pages now go through an article extractor first, so a weather page reads
  "中雨 24℃ 晴转多云" and an article starts at its first sentence. Non-HTML
  responses (JSON, plain text, source) are untouched. Extraction runs in an
  isolated, time- and memory-bounded child process and falls back to the plain
  strip on any failure; the `FEEDLING_WEB_EXTRACT_ARTICLE` env var disables it.

- **Web search is now user-controlled.** `web_search` / `web_fetch` are only
  offered to the model when the account's toggle is on; before this change they
  were always available. The switch covers **every** turn — foreground chat, the
  proactive companion's background turns, and any subagent spawned from either —
  so there is one answer to "can my companion go online", not a per-lane matrix.
  Accounts whose persisted runtime target was already the V2 runtime are
  backfilled to "on" once, so existing users keep exactly what they had; new
  accounts start off and enable it in the app.
- New `GET`/`POST` `/v1/web/settings` (api-key only; runtime tokens are
  refused). The response keeps the user's saved preference separate from what is
  actually possible right now:
  `{"enabled", "runtime_supported", "status", "effective", "tools"}`.
  `enabled` is written only by the user — an operator halt never rewrites it.
  `runtime_supported` is true when the account's runtime can actually reach the
  web tools: a Runtime V2 tool loop, or — since the V1 web endpoints shipped — a
  Runtime V1 consumer (hosted runner or self-hosted resident) once a new
  consumer build advertises the web capability on a fresh poll. An old consumer
  build, a stale heartbeat, or any read error fail closed to `false`, so the
  switch stays inert for that account. `status` is `available` / `degraded` /
  `unavailable`, where `degraded` means one of the two tools is halted and the
  other still works. `effective` is derived, and covers every lane. `POST` requires a real JSON boolean under `enabled`; strings such as
  `"no"` are rejected with `400` rather than coerced.

- New `GET /v1/model_api/usage`. Queries the caller's active model_api
  provider for balance/usage live on every call — never cached, never stored.
  Response shape: `{"provider", "adapter", "status", "as_of", "metrics", "error"?}`,
  where `metrics` always has all five fixed keys (`balance`, `remaining`,
  `usage_total`, `usage_today`, `usage_month`), each with its own `status`
  (`ok` / `unsupported` / `failed`). Field support depends on the configured
  provider/adapter: DeepSeek and OpenRouter are queried through their official
  APIs; an `openai_compatible` relay (中转站) is queried through its
  dashboard-style endpoints when reachable. `400` when there is no usable
  route to query (`model_api_not_configured`, `model_api_not_tested`, and
  related slugs).

- `GET /v1/content/export` now includes a `world_book` array alongside `chat`,
  `memory`, `identity` and `frames`. World book entries are user-authored
  content that account deletion removes, so an export that omitted them handed
  back an incomplete copy. Entries are returned as stored v1 envelopes,
  ciphertext verbatim for client-side decryption, exactly like the other
  sections — the server still never decrypts. The export is not filtered by
  `visibility`; every stored entry is returned. The export's
  `schema_version` goes from 2 to 3 so a reader can distinguish an
  export taken before world book coverage from one where the user simply had no
  entries.
- The resident consumer's idle decrypt-health probe interval
  (`FEEDLING_DECRYPT_HEALTH_REFRESH_SEC`) default changes from 120 to 210
  seconds. The probe is one of the more expensive periodic calls a resident
  makes, and its reporting contract is unchanged: the backend still accepts a
  report as fresh for 300 seconds. Because the probe only runs on an idle poll
  cycle, the usable interval is that window minus one poll round trip; values
  near 300 report stale health and block onboarding verification.
- Chat poll and Chat history now confirm an answer against the database before
  reporting that nothing newer exists, instead of only when their cached page
  is empty. A message committed by another backend worker is therefore served
  on the next poll rather than after the cache TTL.
- A chat message that was claimed for reply and abandoned (its claim lease
  expired with no reply) is no longer treated as superseded by a later
  answered turn, so the redelivery backstop can still serve it inside the
  redelivery window. The age bound is unchanged.
- `POST /v1/identity/actions` profile-patch writes now cover the full identity
  card: 9 string fields (`user_preferred_name`, `agent_role`, `tone_style`,
  `custom_persona_prompt`, `language_preference`, `relationship_anchor`, and
  others, alongside the existing `agent_name`/`self_introduction`/`category`),
  plus explicit `add_*`/`remove_*`/`replace_*` operations on the four list
  fields (signatures, boundaries, do-not-say, stable definitions) instead of
  only whole-list replacement. Renaming the agent (`agent_name`) must now
  include `self_introduction` in the same patch or the write is rejected with
  `400 rename_requires_self_introduction`; this pairing requirement only
  applies to agent-originated (runtime-token) writes, not user/app writes made
  with an API key, which are unchanged. New error codes on this endpoint:
  `list_op_conflict` (a field targeted by more than one list-operation shape
  in one patch), `list_op_blank` (an add/replace entry is blank after
  cleanup), `list_op_too_many_items` (an `add_*` or `replace_*` op's final
  item count would exceed the 12-item cap — the whole op is rejected, not
  silently truncated; only the legacy direct-list-assign shape still
  truncates for back-compat), and `identity_write_conflict` (`409`, a
  concurrent writer won after retries under lock were exhausted).
- `POST /v1/identity/actions` dimension nudges are now capped per request:
  same-name deltas are normalized and summed, and any dimension whose summed
  `|delta|` exceeds 10 is rejected with `400 nudge_delta_exceeds_cap` instead
  of being silently clamped.
- Resident-sealed identity redistill imports
  (`POST /v1/genesis/imports/plaintext`, `mode=update_identity`) are now
  serialized per account: starting a redistill while one is still
  `awaiting_resident` or `processing` for that account is rejected with
  `409 redistill_job_active` and the in-flight job's id, instead of starting a
  second concurrent job. Retrying the same `client_job_id` is unaffected and
  still returns the existing job. Resident distill now merges its output into
  the identity card's **latest** state field-by-field at write time (it
  previously replaced the whole card from the pre-distill snapshot), so a
  `profile_patch`/`dimension_nudge` made while a redistill is in flight is no
  longer silently discarded. Distill prompts also now treat instruction-like
  text found in uploaded material purely as persona content to analyze, never
  as instructions to follow. Both resident redistill and the onboarding
  Genesis import can now also derive `user_preferred_name`,
  `custom_persona_prompt`, `language_preference`, `relationship_anchor`, and
  `stable_definitions` from uploaded material when it explicitly states them
  (previously these five fields were settable only via chat profile-patch);
  each stays empty, never invented, when the material gives no explicit
  signal for it.
- Resident maintenance reminder state now uses cross-worker PostgreSQL
  compare-and-swap instead of process-local read-modify-write persistence.
  Concurrent Chat poll, claim, and pending-work requests therefore preserve one
  another's heartbeat, decrypt-health, and reminder fields. Maintenance Chat
  appends also use the existing atomic `client_msg_id` idempotency path: repeated
  attempts for the same user, reminder bucket, and prompt retain one row and
  preserve its claim/reply metadata, while only the insert winner wakes
  consumers. Reason changes remain subject to the same global reminder interval.
- Official self-hosted resident polls can now include
  `X-Feedling-Consumer-Compat-Commit` when the updater intentionally keeps an
  older running image because the advertised release changes no resident-loaded
  files. A non-empty running commit plus a compatibility value matching the
  current backend target suppresses commit-mismatch maintenance warnings. A
  missing running commit, an absent compatibility value, or a compatibility
  value for an older backend target retains the existing grace and reminder
  behavior. `X-Feedling-Consumer-Commit` now identifies the commit captured by
  the running process rather than a checkout changed underneath it.
- Official resident consumers now report decrypt-source health on
  `GET /v1/chat/poll` with `X-Feedling-Decrypt-Status`
  (`ok`, `degraded`, `unconfigured`, or `unreachable`) and
  `X-Feedling-Decrypt-Checked-At`. Missing, invalid, future, or reports older
  than 300 seconds normalize to `unknown`. Resident onboarding exposes a new
  `decrypt_source` validation step; unfinished accounts require a fresh `ok`
  report before Chat or live-loop verification can pass. Existing accounts keep
  ordinary Chat available and receive a seven-day warning-only grace for
  `unknown`. Unknown/absent health now produces only an in-app stale-consumer
  notice and never injects decrypt-source repair copy. An established resident's
  explicit decrypt failure must persist for 30 minutes before a repair turn can
  be injected; new onboarding remains immediately actionable. Verify-ping
  replies must now use `source: "verify_ping"` and point
  `reply_to_message_id` at the exact pending ping; `loop_alive` can therefore be
  true while `passing` is false when decrypt policy blocks sticky verification.
- Hosted Runtime V2 can now publish a generated `/workspace` document as a
  native download card through the explicit `send_file` tool. Text formats are
  delivered directly, while `.docx` and `.pdf` requests produce real Word and
  PDF bytes instead of Markdown with a renamed suffix. Explicit formats get one
  bounded completion recovery and cannot be replaced with a different suffix;
  requests without a named format remain prompt-level semantic guidance. If
  delivery still fails, Runtime V2 records `required_file_missing` and preserves
  a non-empty terminal reply instead of failing the turn. The entry remains
  user-scoped and encrypted; final assistant text and its file cards commit as
  one ordered, idempotent reply bundle; host filesystem paths are never scanned
  or accepted.
- Add account-scoped vision-model routing for Hosted Runtime V2 model-API
  users. `GET/PUT /v1/vision/config` reads or changes
  whether images use the main model or a dedicated saved route; `POST
  /v1/vision/config` atomically creates, image-tests, and selects a candidate.
  Reachable text-only candidates remain selectable with an `unsupported`
  status, while operationally invalid new routes and credentials are removed; `POST
  /v1/vision/routes/{route_id}/test` verifies real image understanding. Dedicated vision output is passed to the
  main model as untrusted observation text, while follow-main preserves the
  pre-existing image path without requiring a dedicated-route probe. Image
  ingestion is not blocked by probe or resident-capability state; those values
  remain settings feedback. Concurrent selection changes cannot reroute an accepted image; a
  deleted pinned route fails closed instead of falling back to the main model.
  Runtime V1 and self-hosted VPS preserve their existing image delivery paths;
  mutation endpoints return `409 vision_runtime_v2_required` outside Hosted
  Runtime V2.
- Self-hosted resident polls may now receive server-generated maintenance turns
  with `role: "user"` and `source: "resident_maintenance"` when the resident
  consumer appears stale or is not claiming resident-only distill jobs. These
  rows use shared envelopes so enclave-backed consumers can decrypt the repair
  prompt. Prompts now identify their server origin, provide an App-notice trust
  anchor, avoid requesting user data, and use reason-specific update or decrypt
  diagnostics. Heartbeat timestamps and backend deploy commit changes no longer
  bypass the global 24-hour reminder interval. Notices and API errors can use
  `blame: "user_environment"` for issues in the user's VPS/runtime environment.
  The resident-only distill job fallback scan is throttled by
  `FEEDLING_RESIDENT_FALLBACK_CHECK_SEC` (default 300 seconds).
- Resident decrypt health now changes to `degraded` only after consecutive
  claimed-but-unreadable messages (two by default, configurable with
  `FEEDLING_DECRYPT_DEGRADE_AFTER`). A real ordinary user-message decrypt resets
  the streak; a server-generated maintenance turn does not count as recovery.
- `GET /v1/agent/perception/recent_apps` now returns a merged app open/close
  trajectory (`app`, `category`, `ts`, `event`, `minutes_ago`), newest first,
  with optional `limit` (1–100, default 20) and `hours` query parameters. It
  reads the existing streams written by `GET /v1/perception/app_open` and
  `GET /v1/perception/app_close`; no new storage. Regular and pull snapshots
  now include the same event shape as `recent_app_events` for the app signal's
  15-minute freshness window. The endpoint remains gated by the same `app`
  capability as the current-app snapshot fields — when the user has disabled
  that capability the response is
  `{"ok": true, "disabled": true, "reason": ...}` with an empty `apps` list,
  which is distinguishable from a genuine empty history.
- The `app_name` / `app_category` snapshot fields now expire 15 minutes after
  the reported open or matching close instead of 5 minutes. These fields mean
  "last app event observed within the window", not "currently on screen";
  inspect `app_state` to distinguish a foreground app from a matching close.
- `POST /v1/content/rewrap-to-current-key` now also normalizes the **identity
  card plaintext** while rewrapping: dimension values are coerced onto the
  documented 0–100 integer contract (0–1-scale floats such as `0.95` rescale to
  `95`; a `score` key is adopted as `value`; malformed dimensions are repaired
  instead of dropped). The identity record is probed (decrypted) even when its
  envelope is already sealed to the current key, and re-sealed only if
  normalization changed the card — reported as `rewrapped` with reason
  `identity_plaintext_normalized`. A probe decryption failure on an
  already-current envelope reports `skipped_sanitize_probe_failed` instead of
  an error, so clients do not retry a record that needs no rewrap. Server-side
  identity writes (genesis import, init, profile patch, dimension nudge) apply
  the same normalization before sealing.

- New **Notify Relay** endpoints for self-hosted deployments, which cannot hold
  the official APNs signing key. Anonymous `POST /v1/notify-relay/register`
  enrolls a device's APNs token and mints a relay auth token (`nrt_…`), returned
  only on first enrollment (or when you re-enroll while presenting the token you
  already hold); re-registering an already-enrolled device returns
  `already_enrolled` without disclosing the token, since an APNs device token is
  not a secret. `POST /v1/notify-relay/push` (authenticated by the new
  `X-Relay-Token` header) delivers alert notifications and Live Activity
  start/update/end through the hosted service's APNs credentials. Alert
  pushes (type 1) are scoped to the enrolled device; types 2-4 pass the
  rotating Live Activity target token per call. Both endpoints are
  rate limited (`429` with `Retry-After`); pushes are logged server-side with
  content truncated (default 512 chars) for triage, as disclosed in the
  self-hosting guide.
- `POST /v1/model_api/chat/send` and `POST /v1/chat/message` now accept an
  optional UUID `client_msg_id`. Reusing the same value for the same user within
  600 seconds returns the first stored user row without appending or waking a
  second agent turn, including when a retry switches between the two ingest
  paths. Invalid values return `400 client_msg_id_invalid`; requests that omit
  the field retain their previous behavior.
- Encrypted envelopes now carry an optional `content_pk_fpr` label (first
  16 hex chars of SHA-256 of the user public key `K_user` was sealed to);
  server- and consumer-built envelopes set it automatically. `POST
  /v1/chat/message` and `POST /v1/chat/response` reject a labeled envelope
  whose fingerprint no longer matches the user's registered content key with
  a new `409 content_pk_fpr_mismatch` error (response includes
  `current_public_key_fpr` and `envelope_content_pk_fpr`) — a writer holding
  a stale key cache should re-fetch `whoami`, re-seal, and retry once.
  Unlabeled envelopes are accepted unchanged, so existing clients are
  unaffected. This closes the failure mode where a writer with a stale key
  seals messages the owner's device can never decrypt.
- `GET /healthz` is now a pool-independent process-liveness probe. It keeps the
  structured status, release/uptime metadata, legacy fields, in-memory user
  registry check, and cross-worker wake-bus check, but no longer executes
  `SELECT 1`, inspects the business connection pool, returns DB-related 503s, or
  includes `checks.db` / `checks.db_pool`. This prevents saturated user traffic
  from delaying the health probe or creating a false outage. PostgreSQL
  readiness now requires a separate authenticated synthetic read/write probe.
  The documented response schema remains a generic JSON object.
- `POST /v1/mcp/servers` now accepts `http://` URLs and loopback/private-network
  and raw-IP hosts — this backend never dials the URL itself, only your agent
  does when it calls a tool, so none of those forms were ever a new attack
  surface on this backend. Add `ca_pem` (PEM, up to 32,768 bytes) to trust a
  self-signed or private-CA server; the returned server record now includes
  `has_ca`. This is "add trust," not "skip verification" — the server still
  has to present a certificate chaining to that CA and prove it holds the
  matching private key. Both first-party runtimes (`claude`, `codex`) were
  verified end-to-end against a real self-signed server.
  **Hosted-runtime users:** the managed agent runs in a cloud confidential VM
  and cannot reach machines on your home or office network; put a tunnel
  (Cloudflare Tunnel, Tailscale Funnel, ngrok) in front of a local MCP server
  and register its public address instead. See the
  [MCP servers workflow](/docs/workflows/mcp) for the full guide.
- Self-signed and private-CA MCP servers no longer require pasting a CA
  certificate. Your agent now fetches and pins the server's own trust anchor
  automatically the first time it connects (trust-on-first-use), then
  verifies against it on every connection after that — TLS verification
  stays on throughout, and the server still has to hold the matching private
  key. `ca_pem` is now optional: paste one yourself (out-of-band) for
  stronger-than-TOFU assurance, and a manually-pasted `ca_pem` always takes
  priority over the automatic fetch. Servers with a publicly-trusted
  certificate (Let's Encrypt, etc.) are never pinned — auto-fetching is
  reserved for servers that can't verify against the public roots, which keeps
  the trust-on-first-use window as small as possible.
  **Self-hosted residents:** the fetch shells out to `openssl`; a host without
  that binary on `PATH` silently materializes no CA, leaving such a server
  unreachable exactly as it was before — see [self-hosting](/docs/self-hosting).
  See the [MCP servers workflow](/docs/workflows/mcp) for the full explanation,
  including the TOFU exposure window.
- Rename the `POST /v1/mcp/servers/{name}/test` error kind previously returned
  for non-public hosts from `blocked_url` to `unreachable_from_backend` — the
  backend still refuses to probe non-global addresses itself (that refusal is
  unrelated to the storage change above), but the old name read as a
  rejection when the server had, in fact, already saved successfully. Clients
  matching on the literal string `blocked_url` for this case must update to
  `unreachable_from_backend`.
- **`codex` + self-signed MCP servers:** `codex`'s TLS stack (rustls) rejects
  a CA certificate used directly as a server certificate, so a single
  self-signed cert works with `claude`/`pi` but not `codex`. Configure such
  servers with a certificate chain (a CA cert plus a separate server cert it
  signs). `POST /v1/mcp/servers/{name}/test` now returns
  `codex_cert_chain_required` (instead of a generic `tls` result) when a
  `codex`-driven account tests a server presenting a lone self-signed cert.
  See [MCP servers workflow](/docs/workflows/mcp).

### Behavior

- Torn control-envelope JSON no longer leaks into chat. When a relay cuts the
  provider stream and splits one internal control envelope across the reasoning
  and content channels, the bare JSON tail left in the visible reply is
  suppressed across all runtimes (resident consumer, Proactive Runtime V2, and
  Model API Runtime V2) instead of being posted as an assistant bubble. Detection
  rejoins the two channels — or uses a protocol head observed independently in
  the reasoning channel, or a reported stream cut — as evidence; the
  reconstructed action is used only to confirm the split and is never executed.
  Foreground Chat substitutes the standard visible fallback and preserves a
  message that merely looks JSON-like on its own; automatic wake lanes stay
  silent and record the suppression.

- Runtime V2 now persists an immutable encrypted turn trajectory alongside its
  aggregate token telemetry. Provider prompts and responses, late input folds,
  tool calls and results, planned replies, and failure details are compressed
  and sealed to the user's and trusted-decrypt keys before database storage.
  Provider-backed failure review is off by default; when explicitly enabled,
  a database-serialized fleet ceiling admits a bounded `trajectory_review`
  lane whose provider call has no tools and whose handler has no reply, effect,
  MCP, Memory, schedule, or workspace dispatch surface. Disabled/overflow
  failures still retain capture but enqueue no provider runner, and encrypted
  analysis is never added to live conversation context automatically. This is
  bounded offline analysis, not deterministic replay; automatic trajectory
  retention/GC and restricted operator inspection/export remain open.

- Runtime V2 now treats encrypted Chat rows and referenced object-storage bodies
  as the durable source ledger. Conversation compaction advances only the
  summary prompt view: it does not delete source messages, and the 5,000-message
  limit now bounds only each process's hot cache. Conversation summaries now use
  immutable encrypted exact-range leaves and retained higher-level checkpoints;
  a versioned canonical-ID binding keeps the model-facing view bounded and
  complete. Existing single-blob summaries migrate lazily, including oversized
  accounts with no new messages.

- Explicit Chat clear now advances the runtime generation and atomically removes
  raw messages, summary, chat-derived artifacts, effects/status, and reply
  cursor. Paused old workers cannot resurrect cleared context. Independent
  Memory/workspace state and encrypted trajectory telemetry retain their own
  policies; account deletion remains the complete-erasure operation.

- Runtime V2 adds an encrypted virtual workspace foundation with read-only
  `/artifacts` and `/skills`, editable `/workspace`, and a persistent editable
  `/memory/WORKING.md` that is distinct from Memory Garden. Native file writes
  use optimistic revisions and the existing encrypted, generation-fenced effect
  outbox. Sandbox acquisition is lazy: stored text views and Markdown edits do
  not start one, while physical artifact materialization, untrusted binary
  parsing, and any future shell/code execution require a registered sandbox
  provider. Generic shell/code tools are not currently model-visible.
  Upload persistence is unchanged, but on a deployment without an audited CVM
  or E2B adapter an uncached attachment is reported as `sandbox_unavailable`
  instead of falling back to in-process parsing. Successful acquisitions append
  content-free billing/usage events; cached text reads do not. Disjoint
  workspace writes can commit concurrently in conflict-free waves, while
  same/ancestor/descendant paths and external mutations remain ordered.

- The model-visible Runtime V2 catalog now contains 24 built-in tools: 22
  platform tools plus `task` and `reply`. `task` runs bounded read-only child
  loops with isolated transcripts and can parallelize independent work without
  exposing reply, recursive-task, MCP mutation, platform-effect, or
  workspace-write surfaces.

- Provider-aware prompt caching now keeps deterministic tool/system/trusted-
  skills blocks ahead of dynamic conversation/tool data, including Bedrock
  Converse cache points and provider-neutral cache usage telemetry. Editable
  `WORKING.md` is deliberately pull-only; after it or another private workspace
  entry is read, later outbound web/MCP/`task` tools are unavailable for that
  turn. The existing Pre canary proves an OpenRouter cache hit; native Bedrock
  and live trusted-`/skills` mutation still need post-deploy proof.

- Eager perception grounding now contains only fixed numeric/boolean/null
  fields. Calendar/reminder/app/place/weather strings and screen/photo content
  are pull-only; once explicitly read, later web, MCP, and `task` tools are
  removed for that turn. Numeric health reads remain composable with outbound
  tools.

- Self-hosted resident consumers now only execute embedded agent actions whose
  type is on an explicit allowlist, and the reply sent to the user is rewritten
  to match what actually happened — a reply is no longer sent as if an
  identity/memory change applied when the action payload was empty, unknown,
  or rejected. Default mode is shadow (log-only, nothing blocked); set
  `FEEDLING_ACTION_ALLOWLIST=enforce` to actually reject non-allowlisted action
  types, or `off` to disable the check entirely.
- Self-hosted resident consumers now report why the built-in auto-updater is
  stuck — a dirty working tree, `FEEDLING_AUTO_UPDATE=0`, or a failed `git
  fetch` — alongside their regular poll. The periodic stale-consumer reminder
  now names the specific cause and remedy instead of a generic "update your
  resident" notice.
- The standard resident consumer now answers an offline backlog with one
  merged agent turn. When a processing batch contains at least
  `FEEDLING_BACKLOG_COLLAPSE_MIN` (default 3) stale plain-text user messages
  whose oldest entry is older than `FEEDLING_BACKLOG_COLLAPSE_AGE_SEC`
  (default 1800 seconds), the pile is presented to the agent as one
  timestamped timeline with an instruction to reply once. The merged reply
  anchors to the newest message; older parents stay superseded and are never
  redelivered. A purely fresh burst from an online user never merges and keeps
  per-message replies; once a stale pile has triggered, fresh eligible messages
  in the same batch join that single merged turn. Probe, maintenance, media,
  and unreadable rows keep their own pipelines, the merged prompt is bounded
  (newest lines win when trimming), and a transient reply-write failure keeps
  the checkpoint with the whole pile retryable as one turn.
- Genesis imports now use the person's saved preferred name in distilled
  memory prose. When no name is known, generated cards omit the subject where
  possible or use the neutral “the person”/“对方”; they no longer expose the
  system labels `user`/`用户`, second-person address, or guessed gender for the
  person. Product terms such as `用户增长`, `用户画像`, and `用户留存` remain
  unchanged. An explicit preferred name found in uploaded User Profile material
  is also retained on the encrypted Identity Card.
- The resident consumer's default per-turn agent timeout
  (`FEEDLING_AGENT_TURN_TIMEOUT_SEC`) is raised from 120 to 300 seconds. Slow
  self-hosted stacks (official Claude Code cold starts, heavy MCP, long-thinking
  models) can legitimately take 100–120s+ per turn, and the old default was
  terminating those turns right at the wire so real replies were dropped. The
  minimum floor (30s) and the operator env override are unchanged, and the cap
  still exists so a hung agent can never wedge the single-flight chat lane.
- Resident agent replies now preserve Markdown markers, paragraph breaks, and
  list indentation when the consumer filters runtime noise. Headings, unordered
  lists, nested lists, blockquotes, thematic breaks, and fenced code therefore
  reach clients unchanged instead of being flattened before encryption.
- Concurrent `POST /v1/chat/response` calls for the same parent are now resolved
  by one PostgreSQL compare-and-swap across all backend workers. Exactly one
  request marks the parent answered and inserts its encrypted reply; later
  contenders receive the existing `409 already_answered` response and emit no
  reply-side wake, capture, push, or trace effects. `role: "system"` notices
  continue to bypass reply exclusivity.
- User MCP servers now support the legacy **HTTP+SSE** transport in addition to
  streamable HTTP. Some providers (e.g. Chinese map services) still ship their
  MCP endpoint only as an `…/sse` URL; those now connect end-to-end. The
  transport is detected automatically — from the URL path at save time and,
  authoritatively, from the server's handshake when a connectivity test runs —
  and reported on each server record as a new `transport` field (`"http"` or
  `"sse"`). The hosted runtime and the `claude` self-hosted runtime speak both
  transports; the `codex` self-hosted runtime remains streamable-HTTP only, so
  a legacy-SSE server is left out of its generated config with a note to use the
  provider's `/mcp` URL instead.
- `POST /v1/mcp/servers/{name}/test` now enforces a 45-second wall-clock
  ceiling over the whole probe and returns `400 timeout` when it is exceeded.
  Previously a server that answered the handshake with a never-ending event
  stream (a legacy HTTP+SSE endpoint, e.g. `…/sse` URLs) could hold the
  request open indefinitely — the app sat on "saving…" with no reply. Saving
  the server (`POST /v1/mcp/servers`) was never affected and still succeeds
  first; only the connectivity probe is bounded.
- Proactive wake bubbles no longer post on top of an active conversation: right
  before delivery, the consumer re-checks the latest chat rows and skips the
  wake (recorded as `skipped` / `chat_collision`) when a user message or an
  agent chat reply landed within the last 90 seconds. One-shot introduction
  greetings and scheduled-wake reminders still deliver. This closes the "one
  message, two near-identical replies" duplication seen when a wake and the
  chat turn answer the same moment.
- Memory Garden cards no longer refer to the person as "用户"/"user": the
  capture, dream, and history-import pipelines use the known identity name
  (history import can also resolve an explicitly self-stated name from User
  Profile material before writing cards). Capture and dream transcripts label
  lines with the known identity names
  (falling back to internal TA/我 markers only when unknown) instead of
  literal `user:`/`agent:` markers, the card-writing prompts require the
  person's name; when it is unknown, prompts prefer subject-free prose and use
  the neutral 「对方」 only when a subject is necessary,
  placeholder "names" such as 用户/user/TA stored on the identity card are
  treated as unknown, and the hardcoded fallback line "用户在对话中明确提到"
  is now subject-free. Dream consolidation also rewrites the old wording out
  of existing cards over time. Wrapped chat-history files whose `.json` body
  is actually plaintext now fall back to plaintext parsing instead of dropping
  the entire wrapped block.

### Storage and deployment

- Hosted model-API execution now runs a dual-runtime topology: the pooled
  Runtime V2 serve-worker runs inside the main confidential VM alongside the
  backend, while the V1 resident supervisor (per-user CLI processes, homes, and
  leases) stays available in its own CVM behind a per-user runtime fence.
  `FEEDLING_HOSTED_RUNTIME_POLICY` defaults to `dual`; the reference
  self-hosting Compose pins the fail-closed `v2_only` override. The
  independently operated `/v1/chat/*` resident consumer remains available and
  is not a hosted fallback.
- For accounts on Runtime V2 (and any `v2_only` deployment), hosted sends fail
  before persistence when no fresh worker heartbeat or capacity is available;
  the V2 runtime is pure Python and does not use agent CLIs or resident data
  volumes.
- Heavy Chat **image** bodies are now offloaded to object storage alongside file
  bodies, under a separate `chatimages/` key prefix so image retention and usage
  can be governed on their own. The message row keeps envelope metadata plus a
  pointer; the ciphertext is re-fetched only at the exits that deliver a body.
  The request and response shapes are unchanged.
- Operator impact: the chat object-storage bucket now backs image bodies too.
  Disabling it, repointing it, or scoping its credential too narrowly **after**
  pointer rows exist makes those image bodies unreadable, not just file bodies.
  It is part of the primary data set and must be backed up with the database.
- Image bodies written before this change remain inline in the database and keep
  working. An offline backfill moves them; it is idempotent and safe to re-run.
- Object reads and deletes are constrained to the requesting account's own key
  prefix, so a malformed or hand-repaired pointer cannot reach another account's
  ciphertext.

### Security

- Browser API access is limited to the documentation site's exact configured
  origin. CORS does not bypass API-key or runtime-token authorization.
- Require a long-lived API key for link-token creation, destructive account
  reset, and Perception report ingestion; runtime tokens are rejected on these
  control-plane boundaries.
- Permit the documented resident, range, cache-validation, and Genesis chunk
  headers through that exact-origin CORS policy without enabling credentials or
  wildcard origins.
- The playground warns that Production requests operate on the authenticated
  account's live data and persists credentials in browser local storage.

### Behavior

- Resident consumers no longer surface an agent's control-protocol JSON as a
  chat message. When a reply wraps its `{"actions":…,"messages":…}` envelope in
  prose or a ```json fence, the consumer now parses out the payload — executing
  the actions and sending only the natural-language messages — instead of
  posting the raw JSON. Malformed, conflicting, or ambiguous payloads fail
  closed (nothing is posted) rather than leaking. No public API shape changed.

### Deprecations

- None in the public OpenAPI contract.

## Reading this changelog

“Added” normally means backward-compatible surface area. “Changed” can require a
client review even when the `/v1` path remains stable. “Deprecated” begins the
process described in [versioning and deprecation](/docs/versioning); it does not
imply a removal date unless the entry states one explicitly.
