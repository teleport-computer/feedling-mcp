This public changelog starts with this developer-documentation work. Entries stay
under **Unreleased** until a production deployment is confirmed. It does not
reconstruct the repository's internal engineering history, and an omitted older
change must not be interpreted as an API guarantee.

## Unreleased

### API

- Self-hosted resident polls may now receive server-generated maintenance turns
  with `role: "user"` and `source: "resident_maintenance"` when the resident
  consumer appears stale or is not claiming resident-only distill jobs. These
  rows use shared envelopes so enclave-backed consumers can decrypt the repair
  prompt. Notices and API errors can now use `blame: "user_environment"` for
  issues in the user's VPS/runtime environment. The resident-only distill job
  fallback scan is throttled by `FEEDLING_RESIDENT_FALLBACK_CHECK_SEC` (default
  300 seconds).
- New `GET /v1/agent/perception/recent_apps` returns recent app-open history
  (`app`, `category`, `ts`, `minutes_ago`), newest first, with optional `limit`
  (1–100, default 20) and `hours` query parameters. It reads the same app-open
  history written by `GET /v1/perception/app_open`; no new storage. It is gated
  by the same `app` capability as the current-app snapshot fields — when the
  user has disabled that capability the response is
  `{"ok": true, "disabled": true, "reason": ...}` with an empty `apps` list,
  which is distinguishable from a genuine empty history.
- The `app_name` / `app_category` snapshot fields now expire 15 minutes after
  the reported open instead of 5 minutes. Because the shortcut reports opens and
  never closes, these fields mean "last open observed within the window", not
  "currently on screen".
- `POST /v1/content/rewrap-to-current-key` now also normalizes the **identity
  card plaintext** while rewrapping: dimension values are coerced onto the
  documented 0–100 integer contract (0–1-scale floats such as `0.95` rescale to
  `95`; a `score` key is adopted as `value`; malformed dimensions are repaired
  instead of dropped). The identity record is probed (decrypted) even when its
  envelope is already sealed to the current key, and re-sealed only if
  normalization changed the card — reported as `rewrapped` with reason
  `identity_plaintext_normalized`. A probe decryption failure on an
  already-current envelope reports `skipped_sanitize_probe_failed` instead of
  an error, so clients do not retry a record that needs no rewrap. Server-side
  identity writes (genesis import, init, profile patch, dimension nudge) apply
  the same normalization before sealing.

- New **Notify Relay** endpoints for self-hosted deployments, which cannot hold
  the official APNs signing key. Anonymous `POST /v1/notify-relay/register`
  enrolls a device's APNs token and mints a relay auth token (`nrt_…`), returned
  only on first enrollment (or when you re-enroll while presenting the token you
  already hold); re-registering an already-enrolled device returns
  `already_enrolled` without disclosing the token, since an APNs device token is
  not a secret. `POST /v1/notify-relay/push` (authenticated by the new
  `X-Relay-Token` header) delivers alert notifications and Live Activity
  start/update/end through the hosted service's APNs credentials. Alert
  pushes (type 1) are scoped to the enrolled device; types 2-4 pass the
  rotating Live Activity target token per call. Both endpoints are
  rate limited (`429` with `Retry-After`); pushes are logged server-side with
  content truncated (default 512 chars) for triage, as disclosed in the
  self-hosting guide.
- `POST /v1/model_api/chat/send` and `POST /v1/chat/message` now accept an
  optional UUID `client_msg_id`. Reusing the same value for the same user within
  600 seconds returns the first stored user row without appending or waking a
  second agent turn, including when a retry switches between the two ingest
  paths. Invalid values return `400 client_msg_id_invalid`; requests that omit
  the field retain their previous behavior.
- Encrypted envelopes now carry an optional `content_pk_fpr` label (first
  16 hex chars of SHA-256 of the user public key `K_user` was sealed to);
  server- and consumer-built envelopes set it automatically. `POST
  /v1/chat/message` and `POST /v1/chat/response` reject a labeled envelope
  whose fingerprint no longer matches the user's registered content key with
  a new `409 content_pk_fpr_mismatch` error (response includes
  `current_public_key_fpr` and `envelope_content_pk_fpr`) — a writer holding
  a stale key cache should re-fetch `whoami`, re-seal, and retry once.
  Unlabeled envelopes are accepted unchanged, so existing clients are
  unaffected. This closes the failure mode where a writer with a stale key
  seals messages the owner's device can never decrypt.
- Expand `GET /healthz` from a fixed liveness stub into a structured
  liveness-and-dependency probe. Responses now carry a top-level `status`
  (`healthy`, `degraded`, or `unhealthy`), a `checks` object with per-component
  detail, and release/uptime metadata, while preserving the legacy `ok` /
  `mode` / `ready` fields. The backend checks PostgreSQL (`SELECT 1`),
  connection-pool saturation, the in-memory user registry, and the cross-worker
  wake-bus listener, and returns HTTP 503 when PostgreSQL is unreachable. The
  enclave reports readiness, release, and TLS posture from cached boot state
  without performing any cryptography. The documented response schema is
  unchanged (a generic JSON object).
- `POST /v1/mcp/servers` now accepts `http://` URLs and loopback/private-network
  and raw-IP hosts — this backend never dials the URL itself, only your agent
  does when it calls a tool, so none of those forms were ever a new attack
  surface on this backend. Add `ca_pem` (PEM, up to 32,768 bytes) to trust a
  self-signed or private-CA server; the returned server record now includes
  `has_ca`. This is "add trust," not "skip verification" — the server still
  has to present a certificate chaining to that CA and prove it holds the
  matching private key. Both first-party runtimes (`claude`, `codex`) were
  verified end-to-end against a real self-signed server.
  **Hosted-runtime users:** the managed agent runs in a cloud confidential VM
  and cannot reach machines on your home or office network; put a tunnel
  (Cloudflare Tunnel, Tailscale Funnel, ngrok) in front of a local MCP server
  and register its public address instead. See the
  [MCP servers workflow](/docs/workflows/mcp) for the full guide.
- Self-signed and private-CA MCP servers no longer require pasting a CA
  certificate. Your agent now fetches and pins the server's own trust anchor
  automatically the first time it connects (trust-on-first-use), then
  verifies against it on every connection after that — TLS verification
  stays on throughout, and the server still has to hold the matching private
  key. `ca_pem` is now optional: paste one yourself (out-of-band) for
  stronger-than-TOFU assurance, and a manually-pasted `ca_pem` always takes
  priority over the automatic fetch. Servers with a publicly-trusted
  certificate (Let's Encrypt, etc.) are never pinned — auto-fetching is
  reserved for servers that can't verify against the public roots, which keeps
  the trust-on-first-use window as small as possible.
  **Self-hosted residents:** the fetch shells out to `openssl`; a host without
  that binary on `PATH` silently materializes no CA, leaving such a server
  unreachable exactly as it was before — see [self-hosting](/docs/self-hosting).
  See the [MCP servers workflow](/docs/workflows/mcp) for the full explanation,
  including the TOFU exposure window.
- Rename the `POST /v1/mcp/servers/{name}/test` error kind previously returned
  for non-public hosts from `blocked_url` to `unreachable_from_backend` — the
  backend still refuses to probe non-global addresses itself (that refusal is
  unrelated to the storage change above), but the old name read as a
  rejection when the server had, in fact, already saved successfully. Clients
  matching on the literal string `blocked_url` for this case must update to
  `unreachable_from_backend`.
- **`codex` + self-signed MCP servers:** `codex`'s TLS stack (rustls) rejects
  a CA certificate used directly as a server certificate, so a single
  self-signed cert works with `claude`/`pi` but not `codex`. Configure such
  servers with a certificate chain (a CA cert plus a separate server cert it
  signs). `POST /v1/mcp/servers/{name}/test` now returns
  `codex_cert_chain_required` (instead of a generic `tls` result) when a
  `codex`-driven account tests a server presenting a lone self-signed cert.
  See [MCP servers workflow](/docs/workflows/mcp).

### Behavior

- Runtime V2 now persists an immutable encrypted turn trajectory alongside its
  aggregate token telemetry. Provider prompts and responses, late input folds,
  tool calls and results, planned replies, and failure details are compressed
  and sealed to the user's and trusted-decrypt keys before database storage.
  Provider-backed failure review is off by default; when explicitly enabled,
  a database-serialized fleet ceiling admits a bounded `trajectory_review`
  lane whose provider call has no tools and whose handler has no reply, effect,
  MCP, Memory, schedule, or workspace dispatch surface. Disabled/overflow
  failures still retain capture but enqueue no provider runner, and encrypted
  analysis is never added to live conversation context automatically. This is
  bounded offline analysis, not deterministic replay; automatic trajectory
  retention/GC and restricted operator inspection/export remain open.

- Runtime V2 now treats encrypted Chat rows and referenced object-storage bodies
  as the durable source ledger. Conversation compaction advances only the
  summary prompt view: it does not delete source messages, and the 5,000-message
  limit now bounds only each process's hot cache. Conversation summaries now use
  immutable encrypted exact-range leaves and retained higher-level checkpoints;
  a versioned canonical-ID binding keeps the model-facing view bounded and
  complete. Existing single-blob summaries migrate lazily, including oversized
  accounts with no new messages.

- Explicit Chat clear now advances the runtime generation and atomically removes
  raw messages, summary, chat-derived artifacts, effects/status, and reply
  cursor. Paused old workers cannot resurrect cleared context. Independent
  Memory/workspace state and encrypted trajectory telemetry retain their own
  policies; account deletion remains the complete-erasure operation.

- Runtime V2 adds an encrypted virtual workspace foundation with read-only
  `/artifacts` and `/skills`, editable `/workspace`, and a persistent editable
  `/memory/WORKING.md` that is distinct from Memory Garden. Native file writes
  use optimistic revisions and the existing encrypted, generation-fenced effect
  outbox. Sandbox acquisition is lazy: stored text views and Markdown edits do
  not start one, while physical artifact materialization, untrusted binary
  parsing, and any future shell/code execution require a registered sandbox
  provider. Generic shell/code tools are not currently model-visible.
  Upload persistence is unchanged, but on a deployment without an audited CVM
  or E2B adapter an uncached attachment is reported as `sandbox_unavailable`
  instead of falling back to in-process parsing. Successful acquisitions append
  content-free billing/usage events; cached text reads do not. Disjoint
  workspace writes can commit concurrently in conflict-free waves, while
  same/ancestor/descendant paths and external mutations remain ordered.

- The model-visible Runtime V2 catalog now contains 23 built-in tools: 21
  platform tools plus `task` and `reply`. `task` runs bounded read-only child
  loops with isolated transcripts and can parallelize independent work without
  exposing reply, recursive-task, MCP mutation, platform-effect, or
  workspace-write surfaces.

- Provider-aware prompt caching now keeps deterministic tool/system/trusted-
  skills blocks ahead of dynamic conversation/tool data, including Bedrock
  Converse cache points and provider-neutral cache usage telemetry. Editable
  `WORKING.md` is deliberately pull-only; after it or another private workspace
  entry is read, later outbound web/MCP/`task` tools are unavailable for that
  turn. The existing Pre canary proves an OpenRouter cache hit; native Bedrock
  and live trusted-`/skills` mutation still need post-deploy proof.

- Eager perception grounding now contains only fixed numeric/boolean/null
  fields. Calendar/reminder/app/place/weather strings and screen/photo content
  are pull-only; once explicitly read, later web, MCP, and `task` tools are
  removed for that turn. Numeric health reads remain composable with outbound
  tools.

- Concurrent `POST /v1/chat/response` calls for the same parent are now resolved
  by one PostgreSQL compare-and-swap across all backend workers. Exactly one
  request marks the parent answered and inserts its encrypted reply; later
  contenders receive the existing `409 already_answered` response and emit no
  reply-side wake, capture, push, or trace effects. `role: "system"` notices
  continue to bypass reply exclusivity.
- User MCP servers now support the legacy **HTTP+SSE** transport in addition to
  streamable HTTP. Some providers (e.g. Chinese map services) still ship their
  MCP endpoint only as an `…/sse` URL; those now connect end-to-end. The
  transport is detected automatically — from the URL path at save time and,
  authoritatively, from the server's handshake when a connectivity test runs —
  and reported on each server record as a new `transport` field (`"http"` or
  `"sse"`). The hosted runtime and the `claude` self-hosted runtime speak both
  transports; the `codex` self-hosted runtime remains streamable-HTTP only, so
  a legacy-SSE server is left out of its generated config with a note to use the
  provider's `/mcp` URL instead.
- `POST /v1/mcp/servers/{name}/test` now enforces a 45-second wall-clock
  ceiling over the whole probe and returns `400 timeout` when it is exceeded.
  Previously a server that answered the handshake with a never-ending event
  stream (a legacy HTTP+SSE endpoint, e.g. `…/sse` URLs) could hold the
  request open indefinitely — the app sat on "saving…" with no reply. Saving
  the server (`POST /v1/mcp/servers`) was never affected and still succeeds
  first; only the connectivity probe is bounded.
- Proactive wake bubbles no longer post on top of an active conversation: right
  before delivery, the consumer re-checks the latest chat rows and skips the
  wake (recorded as `skipped` / `chat_collision`) when a user message or an
  agent chat reply landed within the last 90 seconds. One-shot introduction
  greetings and scheduled-wake reminders still deliver. This closes the "one
  message, two near-identical replies" duplication seen when a wake and the
  chat turn answer the same moment.
- Memory Garden cards no longer refer to the person as "用户"/"user": the
  capture and dream transcripts label lines with the known identity names
  (falling back to internal TA/我 markers only when unknown) instead of
  literal `user:`/`agent:` markers, the card-writing prompts require the
  person's name (or a natural relationship referent when unknown — never a
  system label),
  placeholder "names" such as 用户/user/TA stored on the identity card are
  treated as unknown, and the hardcoded fallback line "用户在对话中明确提到"
  is now subject-free. Dream consolidation also rewrites the old wording out
  of existing cards over time.

### Documentation and contract

- Add `GET /v1/dream/status` — read-only dream (memory distillation) banner
  status for the authenticated user, exposing scheduler state and counts for
  client status banners.
- Change plaintext role-card imports (`mode=update_identity`) to create an
  identity when none exists or update the existing card while preserving its
  relationship anchor by default. Reusing a completed `client_job_id` still
  returns the existing job without a duplicate write.
- Add explicit JSON, multipart, query, path, and non-authentication header
  contracts to the generated public OpenAPI document.
- Add complete Chat, Memory, and Perception workflow examples.
- Add a system architecture and trust-boundary guide covering managed and
  self-hosted topology, encryption, tenant isolation, and capability readiness.
- Document API key registration, additional-device issuance, keypair recovery,
  and the absence of public per-key rotation and revocation.
- Document endpoint-specific pagination, rate-limit, timeout, retry, and
  idempotency behavior.
- Add scoped API-playground credential cleanup instructions and a button that
  removes only `fumadocs-openapi-auth-*` local-storage entries.
- Add the current versioning, deprecation, and experimental self-hosting status.

These documentation additions describe existing behavior; they do not by
themselves add a backend endpoint or change production request handling.

### Storage and deployment

- Hosted model-API execution is now Runtime V2-only in local, test, pre, and
  production deployment manifests. The resident supervisor, per-user CLI
  processes/homes/leases, rollback selectors, and hosted resident admin flip
  have been removed. The independently operated `/v1/chat/*` resident consumer
  remains available and is not a hosted fallback.
- Test, pre, and production deploys now treat their pooled Runtime V2 worker CVM
  as mandatory. Hosted sends fail before persistence when no fresh worker
  heartbeat or capacity is available; the worker image contains only the Python
  V2 runtime, not agent CLIs or resident data volumes.
- Heavy Chat **image** bodies are now offloaded to object storage alongside file
  bodies, under a separate `chatimages/` key prefix so image retention and usage
  can be governed on their own. The message row keeps envelope metadata plus a
  pointer; the ciphertext is re-fetched only at the exits that deliver a body.
  The request and response shapes are unchanged.
- Operator impact: the chat object-storage bucket now backs image bodies too.
  Disabling it, repointing it, or scoping its credential too narrowly **after**
  pointer rows exist makes those image bodies unreadable, not just file bodies.
  It is part of the primary data set and must be backed up with the database.
- Image bodies written before this change remain inline in the database and keep
  working. An offline backfill moves them; it is idempotent and safe to re-run.
- Object reads and deletes are constrained to the requesting account's own key
  prefix, so a malformed or hand-repaired pointer cannot reach another account's
  ciphertext.

### Security

- Browser API access is limited to the documentation site's exact configured
  origin. CORS does not bypass API-key or runtime-token authorization.
- Require a long-lived API key for link-token creation, destructive account
  reset, and Perception report ingestion; runtime tokens are rejected on these
  control-plane boundaries.
- Permit the documented resident, range, cache-validation, and Genesis chunk
  headers through that exact-origin CORS policy without enabling credentials or
  wildcard origins.
- The playground warns that Production requests operate on the authenticated
  account's live data and persists credentials in browser local storage.

### Deprecations

- None in the public OpenAPI contract.

## Reading this changelog

“Added” normally means backward-compatible surface area. “Changed” can require a
client review even when the `/v1` path remains stable. “Deprecated” begins the
process described in [versioning and deprecation](/docs/versioning); it does not
imply a removal date unless the entry states one explicitly.
