Feedling separates ciphertext persistence from authorized decryption and agent
execution. Managed production uses a main confidential VM for the public API and
trusted-decrypt service, separate confidential-VM capacity for hosted agents,
and external persistence and delivery services.

This page describes the stable logical boundaries. Exact instance counts,
regions, image digests, and provider choices are deployment details rather than
part of the public API contract.

## System at a glance

<ArchitectureDiagram />

The managed main deployment runs TLS ingress, the ASGI API, and the attested
decrypt service as separate services inside one measured confidential-VM
boundary. Hosted runners can scale in separate confidential VMs and reach the
main API and decrypt service with short-lived, user-bound runtime tokens.

Self-hosted deployments can place the same logical components on one machine,
but process separation on a generic host is not equivalent to a hardware-backed
confidential-VM boundary. See [self-hosting](/docs/self-hosting) before choosing a
deployment topology.

## Components and responsibilities

| Component | Primary responsibility | Data it can handle |
| --- | --- | --- |
| Client app or integration | Own the user credential and content keypair; call HTTP or WebSocket operations | Plaintext created or displayed by that client, plus encrypted envelopes |
| TLS ingress | Terminate the public API certificate and route configured traffic | Transport plaintext inside the managed confidential-VM boundary |
| ASGI API | Authenticate, enforce user ownership, validate requests, coordinate workflows, and persist state | Envelopes and metadata; transient plaintext for operations that explicitly accept plaintext |
| Attested decrypt service | Own the content private key and authorize envelope decryption or read-side projection | Plaintext while servicing an authorized operation |
| PostgreSQL | Persist account, workflow, queue, and user-scoped state | Encrypted protected bodies plus plaintext IDs, timestamps, types, status, and other operational metadata |
| Object storage | Offload enabled large-object flows | Screen and Chat objects are normally ciphertext; diagnostics and compatibility uploads can be stored as provided |
| Hosted runner | Poll work, assemble authorized context, invoke an agent, and return an encrypted result | Plaintext selected for an agent turn, the provider credential, and encrypted API traffic |
| Model or push provider | Perform user-selected inference or device delivery | The plaintext and delivery material required by that external service |
| ElevenLabs voice service | Transcribe and segment speech, manage interruption, and synthesize the selected voice | Call audio, transcript text, and the assistant text returned for speech |

The component that stores a record is therefore not always the component that
can interpret its protected body. Conversely, “encrypted at rest” does not mean
that every identifier, status field, compatibility payload, normalized signal,
or diagnostic upload is encrypted.

## Core data flows

### Hosted Chat

1. The client sends a message or attachment over HTTPS to
   `POST /v1/model_api/chat/send`.
2. Inside the managed main VM, the API validates the request, creates a shared
   encrypted envelope, appends the user turn, and wakes the hosted queue.
3. A bounded Runtime V2 worker pool claims the durable job and mints a scoped
   runtime token for that turn. It requests only the Chat, Memory, and Perception
   context authorized for that user.
4. The decrypt service opens the required shared envelopes. The runner sends the
   plaintext prompt and selected context to the configured model provider.
5. The runner encrypts the assistant result into a new user-owned envelope before
   it is persisted. The original send remains asynchronous and returns `202`.

The model provider is an external plaintext recipient. Envelope encryption
protects persisted content and the storage path; it does not hide the prompt
from the model selected to process it. When visible push text is enabled, that
notification text also passes through the external push provider.

Runtime V2 builds each turn from an encrypted hierarchical summary frontier plus
every uncovered source message verbatim. The trusted runner decrypts that
selected view in memory before sending ordinary plaintext messages to the
configured model. It can additionally replay a newest suffix of complete,
user-seeded turns that the summary already covers: Chat targets 40 turns and
proactive wake lanes target 16. Before each provider round, the runner admits
the largest newest complete-turn suffix that fits the resolved model window
after the fixed prompt, summary, uncovered exact core, and provider-native tool
transcript. Only summary-covered replay is optional; uncovered rows are never
clipped. If the required core is too large, the runner first compacts only a
safe answered prefix and rebuilds the prompt from the new durable watermark.

Proactive wake turns may read the agent identity card but cannot mutate it:
Runtime V2 visibly refuses `identity_patch` and `identity_nudge` in background
turns. Foreground Chat identity changes and wake-time Memory writes retain their
existing authorization.

Exact immutable leaf segments carry source-range/count
witnesses; immutable higher-level checkpoints retain and name their ordered
children, while one encrypted materialized view keeps ordinary turns to a
single summary decrypt. The durable encrypted `chat_messages` rows and
referenced object-storage bodies remain the source ledger: compaction never
deletes them, and the 5,000-message constant bounds only a process-local hot
window. Only explicit Chat clear or account deletion removes this conversation
data.

Runtime V2 chat turns may retrieve older ledger content on demand through two
chat-only agent tools (`history_search`, `history_fetch`). Retrieval is
search-first: summary leaves serve only as scan-priority hints, matching runs
against decrypted original messages inside the enclave in bounded batches, and
attachments contribute caption text only — object-storage bodies are never
decrypted for search. Every call is bounded by row, byte, and deadline budgets
with an authenticated resumable cursor, and an incomplete scan is reported as
incomplete rather than as an empty result. These tools are never offered to
proactive wake lanes or subagents; a turn that reads history drops outbound
web/MCP/task tools for the following round, and a deployment kill switch
removes the capability entirely without touching the normal chat path.

Deployments may opt into deterministic Runtime V2 coverage accounting as an
independent precursor to the bounded Memory/User profile rollout. In that mode,
maintenance and synchronous prompt catch-up advance the same exact source
witnesses using content-free count sentinels, and deterministic fan-out
checkpoints keep the frontier bounded without sending historical Chat plaintext
to a model provider. The source ledger and rollback-compatible summary storage
remain unchanged.

The bounded Memory/User profile storage contract uses one
`v2_agent_profile` document so both fields advance under one compare-and-swap.
The two field bodies are separate shared encrypted envelopes; PostgreSQL and
the TEE shadow see the same ciphertext document. Field character counts,
state, disabled status, source-card counts, and generation/retry timestamps
remain plaintext routing and observability metadata. A stale CAS loser must
re-read and recompute rather than replaying its earlier result.

When the default-off profile switch is enabled, a turn strictly reads that
document and decrypts both fields together. Only an `ok`, non-disabled document
whose two fields both validate replaces the rollback-compatible summary. The
Memory and User fields are serialized into one early user-role block, labeled
as model-derived untrusted data; they are never system instructions, and later
verbatim conversation replay wins on conflict. Missing, pending, degraded,
disabled, invalid, or undecryptable profiles retain the existing summary path.
Any bounded-tail coverage-hole count is a separate late user-role data block,
so it cannot perturb the stable profile prefix.

Profile generation is a separate low-priority Runtime V2 job, alongside
maintenance, capture, and dream rather than foreground Chat or wake work. The
worker reads the complete eligible Memory Garden through a user-bound runtime
token and fails loudly if the read-side response is truncated or incomplete.
It sends that plaintext Garden view to the user's configured model provider,
then seals the generated Memory/User fields before the compare-and-swap write.
Generation failure only updates bounded retry metadata and fails the background
job; it does not publish a Chat bubble or terminal turn error.

The staged worker refreshes after a successful dream write, after Runtime V2
cutover, and best-effort after Chat when a profile is missing, eligible for
retry, or at least seven days old and the Garden's content-free source witness
has changed. The seven-day floor is independent of the user's dream setting.
The profile switch remains off by default and gates both generation and prompt
selection. Managed Compose now explicitly enables capture and dream in the
pooled `serve-worker`; their user-level consent gates remain independent.

An [independent resident consumer](/docs/workflows/chat#independent-resident-loop)
uses the same encrypted queue-and-reply protocol but runs in infrastructure the
user or integrator controls instead of Feedling's hosted runner.

### Genesis plaintext imports

The plaintext compatibility endpoint accepts onboarding material inside the
managed confidential-VM boundary and sends only the required prompt to the
user-selected model provider. PostgreSQL serializes processing plaintext jobs
per account, so separate API workers cannot start two provider pipelines for
the same account concurrently.

After each successful map window, the API creates a shared encrypted envelope
containing the resumable candidate output. PostgreSQL stores that envelope plus
plaintext operational metadata such as job ID, material kind, window counts,
status, and hashes. Candidate text is not written into the job JSON or progress
fields. An authorized retry decrypts the checkpoint inside the trusted boundary
and skips completed windows; successful completion deletes the checkpoint.
Resident-sealed imports and their local plaintext boundary are unchanged.

Managed clients can first call the plaintext estimate endpoint. The API parses
the material without an LLM call, stores the original payload in a short-lived
shared encrypted envelope, and returns only material kinds, window counts,
conservative token estimates, and an optional model recommendation. Commit
decrypts that account-bound stage inside the trusted boundary and starts the
same plaintext pipeline. A commit-time model override is copied into job
metadata and changes only that job's model string; it does not mutate the
account's chat route, provider URL, or credential.

### ElevenLabs voice calls

1. An authenticated client creates a short-lived voice session with
   `POST /v1/voice/sessions`. The response contains a call-bound token and the
   public HTTPS Custom LLM endpoint; it does not expose the user's model
   credential.
2. ElevenLabs transcribes and segments the caller's speech, then sends each text
   turn to `POST /v1/voice/chat/completions` with that session token.
3. Feedling resolves the user's current Chat route and processes the transcript
   through the same resident or Hosted Runtime V2 path used by typed messages,
   including the same conversation history, persona, memory, and tools.
4. Assistant text streams back over an OpenAI-compatible SSE response for
   ElevenLabs to synthesize. During the call the user and assistant turns are
   persisted as ordinary Chat rows in their original order.
5. At hang-up the client posts the call transcript to
   `POST /v1/voice/finalize`. The full transcript is archived — permanently,
   sealed to the account's content key — and the chat stream keeps ONE bounded
   preview card (`voice_call_transcript`, deterministic id, idempotent
   retries). Only after the archive is durable are the call's per-turn rows
   deleted, so the raw back-and-forth stops occupying chat history and model
   context. Memory then runs the ordinary capture pipeline, which renders the
   ARCHIVED FULL transcript into its window in place of that card — a call is
   distilled from everything that was said, not from a précis of it. Rows
   already folded into the Runtime V2 conversation summary are retained
   (deleting them would desync compaction's frozen ledger); they no longer
   feed future context reads. If the archive or the card cannot be persisted,
   nothing is deleted and the client may retry. In ordinary conversation
   context the card is replayed as a labelled call-record block, not as
   assistant speech: its preview holds both speakers' lines, so presenting it
   as something the companion said would misattribute the user's words to it.
   The block states who is who and that the transcript is not the companion's
   own speech.
6. If a failed or empty call will not be archived, the client calls
   `POST /v1/voice/cancel` with its `call_id` and a bounded reason. The
   idempotent cancellation tombstone removes unarchived turn rows and stops
   late resident or Runtime V2 replies before they can enter ordinary Chat.
   Finalize claims its lifecycle state before writing the archive, so a
   concurrent cancel cannot downgrade or partially delete a successful call.
7. Archived calls stay readable: `GET /v1/voice/transcripts` lists them and
   `GET /v1/voice/transcripts/{call_id}` returns the sealed envelope for the
   client to open locally. The agent reaches the same archive through the
   `voice_transcript_list` / `voice_transcript_read` tools, and memory cards
   distilled from a call carry that call's id so it can go back to the source.
   The server stores and serves ciphertext; it never holds the transcript
   after the finalize request that archived it. Transcript trust
   boundary: the transcript is client-supplied plaintext (chat rows are
   ciphertext the server cannot read); an authenticated user can therefore
   only shape their own summary and delete their own call rows. Known
   limitation: a resident (self-hosted) runtime's persistent agent session may
   still remember in-call content until its session naturally rotates.

Deployment prerequisite: the API service must set
`FEEDLING_VOICE_GATEWAY_PUBLIC_URL` to the externally reachable HTTPS origin
that serves `/v1/voice`. Feedling returns this origin to ElevenLabs as the
Custom LLM endpoint; a private, non-HTTPS, missing, or otherwise invalid value
causes `POST /v1/voice/sessions` to fail closed with
`503 voice_gateway_not_configured` instead of returning an unusable internal
address.

ElevenLabs is an external plaintext recipient for call audio, transcripts, and
assistant speech text. It does not receive the user's model API key. Voice
session tokens are short-lived, signed, bound to one user and call, and are not
valid as general Feedling API credentials. Incremental reply handoff state is
encrypted and expires automatically.

### Memory

1. A client writes a Memory envelope. `shared` records wrap the content key for
   both the user and the trusted decrypt service; `local_only` records omit the
   enclave-wrapped key.
2. PostgreSQL stores the encrypted body and the plaintext ordering and
   classification metadata required by the API.
3. `memory/index` and `memory/fetch` send authorized candidate envelopes to the
   decrypt service and return only the requested projection.
4. A `local_only` body remains client-readable but is unavailable to agent-side
   index and fetch operations.

See the [Memory workflow](/docs/workflows/memory) for the complete envelope,
selection, fetch, and action contracts.

### Perception and screen content

Sensitive Perception signals and photo bodies use encrypted envelopes. Ordinary
operational context fields can be submitted as plaintext. Encrypted sensitive
signals are opened for authorized processing, after which normalized state and
metadata can be persisted separately from the original body. The legacy
collection branch stores each `doc` as provided.

Screen pixels use encrypted frame envelopes; large frame ciphertext can be
offloaded to object storage without giving that store the content key. The
authenticated screen WebSocket is an ingest path only—Chat uses HTTP send,
history, and long polling.

Foreground Chat may decrypt a bounded live-screen batch after the newest-frame
metadata proves the share is no more than 90 seconds old. Admission follows the
active route's real randomized image-control verdict rather than provider
catalog metadata. At most six frames newer than the runtime's Chat cursor are
sampled uniformly and labelled as untrusted application data with capture time
and age. A small frame-ID cache avoids repeated enclave decrypts, while the
shared decrypt proxy remains concurrency-limited. Aggregate frame counts and
cache counters contain neither pixels nor visible text.

Heavy Chat bodies—image and file ciphertext—can be offloaded the same way. The
message row keeps its envelope metadata plus a pointer, and the ciphertext is
re-fetched from object storage only at the exits that actually deliver a body.
The object store receives ciphertext and never receives the content key, so this
does not move the decrypt boundary. It does make the object store part of the
read path: a body that is unreachable there degrades that one message rather
than the conversation.

The [Perception workflow](/docs/workflows/perception) identifies the encrypted,
plaintext, and legacy compatibility branches. Clients should choose the
encrypted branch for new sensitive integrations rather than assuming every
Perception payload has the same privacy properties.

## Envelope and decrypt boundary

A protected v1 envelope separates one encrypted body from two possible readers:

| Field | Meaning |
| --- | --- |
| `body_ct` and `nonce` | Authenticated ciphertext and its nonce |
| `K_user` | Per-record content key wrapped to the user's content public key |
| `K_enclave` | The same content key wrapped to the trusted decrypt service; required for `shared` visibility |
| `owner_user_id` | Plaintext tenant binding checked against the authenticated caller |
| `enclave_pk_fpr` | Identifies the content public key used for the enclave wrap |

`K_user` lets an authorized device decrypt without the service. `K_enclave` lets
the measured decrypt service open only the records needed by shared agent
workflows. Attestation-aware clients can verify that the live content public key
and measured deployment match the service they intend to trust.

This is dual-recipient envelope encryption, not a claim that no server-side
component ever sees plaintext. Hosted Chat, enclave-backed read projections,
normalized Perception processing, user-approved diagnostics, and external
inference each have an explicit plaintext boundary.

## Authentication and credential roles

| Credential | Scope and lifetime | Where it is used |
| --- | --- | --- |
| User API key | Long-lived, full access to one user's public control and data plane | User-owned apps, integrations, and control-plane operations |
| Runtime token | Short-lived, user-bound, and scope-limited | Hosted runner processes and background workers |
| Voice session token | Short-lived and bound to one user and call | ElevenLabs Custom LLM requests to the voice gateway only |
| Provider credential | Belongs to the configured external inference provider | Encrypted at rest, then decrypted for the authorized Runtime V2 turn that calls the provider |

Runtime tokens do not replace API keys. Key issuance, account reset, MCP
management, and other designated control-plane operations require the user API
key even when a valid runtime token exists. See [authentication](/docs/authentication)
and [API key lifecycle](/docs/api-keys) for the current issuance and revocation
limitations.

## Tenant and execution isolation

The public API resolves each credential to one user, scopes storage queries by
that user, and checks envelope ownership before protected reads and writes. This
is the primary multi-tenant boundary for API and persistence access.

Managed Hosted Runtime V2 uses a bounded worker pool. Durable jobs, conversation
state, reply cursors, deadlines, and terminal errors live in PostgreSQL; there is
no resident process, per-user home, CLI checkpoint, or lease to keep alive. A
turn can run in a watchdog-controlled child process, but that is a failure and
resource boundary rather than a strong sandbox for mutually hostile code.

Newly registered Model API accounts can be admitted directly to this pooled V2
runtime after a provider route has been successfully tested and activated. The
cutoff-based admission is fail-closed: accounts outside the configured cohort,
without an eligible route, or on an invalid rollout configuration remain on the
separate resident execution path.

Feedling does not represent this as per-user microVM or per-user hardware-enclave
isolation. Keep hosted execution restricted to supported agent entry points, and
use a separately reviewed container or microVM boundary before offering
arbitrary untrusted code execution to unrelated tenants.

### Runtime V2 virtual workspace

Runtime V2 exposes a virtual, backend-pluggable workspace to its native agent
loop. `/artifacts` and `/skills` are read-only; `/workspace` is task-editable;
and `/memory/WORKING.md` is editable agent working state distinct from
user-facing Memory Garden cards. Writes use exact revisions, so stale same-file
writes fail instead of silently overwriting one another.

Independent reads and bounded child tasks can execute concurrently. Disjoint
workspace mutations are grouped into conflict-free waves and may commit in
parallel at the database CAS boundary; same-path and ancestor/descendant paths
serialize. Platform effects, schedules, Memory Garden writes, and mutating MCP
calls remain in provider order, and tool results are reconstructed in that same
order.

Workspace bodies are stored as shared encrypted envelopes. PostgreSQL still sees
the user ID, virtual path, kind, MIME type, source reference, revision, and
timestamps as plaintext routing metadata. An authorized hosted runner asks the
decrypt service to open content and sends plaintext—not ciphertext—to the model
when the turn uses that file.

Reading an already-derived text view or editing a virtual Markdown file does not
start a sandbox. Physical artifact materialization, untrusted binary parsing,
shell commands, and code execution cross a separate, lazily acquired sandbox
provider boundary. The provider is deployment-pluggable; a shared runner process
or access to a host Docker socket is not treated as a sandbox. A remote provider
also becomes a plaintext recipient for any decrypted artifact bytes sent to it.
The E2B adapter is source-wired but active only when the deployment selects it
and supplies its API key and template. If the provider is disabled,
misconfigured, or unavailable, uploads remain stored but an artifact cache miss
is explicitly unavailable rather than parsed inside the API or runner process.
Successful provider acquisition emits a content-free usage event for billing;
cached text-view reads do not. The current catalog does not expose generic shell
or arbitrary code execution.

The native `task` tool runs a bounded child loop with the same provider route
and an isolated transcript. Children receive approved read tools but no user
reply, recursive task, mutating MCP, platform-effect, or workspace-write
surface. Multiple independent children may run in parallel and return bounded
results to the parent.

Runtime V2 layers perception by lane. Foreground Chat starts with perception
tools but no current readings. Ordinary heartbeat and manual-wake prompts may
receive only a fixed boolean glance describing domain availability and whether
that glance changed. Scheduled wake remains reminder-only. Screen watch retains
only its isolated safe screen-count metadata, while a perception-triggered
heartbeat receives only its allowlisted event type. Raw change digests,
presence hints, origin references, and internal glance fingerprints never
enter model-visible runtime data. Exact readings and private text do not enter
the initial prompt; they become model-visible only through an authorized tool
read.

Wake-producing perception signals use a durable per-user, per-signal baseline.
The comparison and baseline update occur atomically, so the first observation
and stale or replayed source events do not enqueue a wake. Only a fresh
allowlisted transition can append wake context to the durable job. Exact
Wi-Fi, Bluetooth, and connectivity anchor identifiers are HMAC-fingerprinted
at this boundary; durable wake metadata keeps only the signal category and a
boolean change marker. Each row also records an opaque fingerprint-key ID.
During a runtime-secret rotation, a new worker can compare with the configured
previous secret and migrate an equal row without waking; a worker that does not
recognize the row's key ID fails closed instead of rewriting it. After every
old worker has drained, an explicit operator-only convergence mode can replace
a dormant unknown-key row on its next fresh observation, always as a non-waking
baseline.

Foreground Chat serializes application-data blocks with a user role. Proactive
turns use an assistant role for the same explicitly untrusted blocks, preventing
platform wake control or scheduled reminder payloads from masquerading as a
new user request. An ordinary heartbeat requires an authoritative genuine-user
row in Chat history before any workspace, compaction, or provider-capable prompt
work begins. A summary or assistant-only artifact is not sufficient. Scheduled
and manual wakes remain valid without prior history.

Exact device, environment, activity, health, calendar, reminder, and photo data
cross the decrypt boundary only through an authorized tool read. Shared-screen
pixels normally follow that rule too, with one foreground-Chat exception:
Hosted Runtime V2 may contribute the bounded new-frame block unless the exact
active route is explicitly marked image-unsupported. Untested and absent probe
states are admitted optimistically; a confirmed rejection is learned by the
screen-only text fallback. The official resident path still requires a setup
probe `ok` signal. Screen content is evidence only and
cannot supply requirements or instructions. A turn receiving screen pixels has
web, MCP, and `task` removed before its first provider call; an image-rejection
retry stays behind the same fence. After any other explicit text-bearing private
read, those outbound tools are removed for the remainder of the turn. Numeric
health snapshot/trend reads remain compatible with outbound work.

### Runtime V2 prompt caching

Tool schemas, runtime policy, and canonical-path-sorted trusted `/skills` are
serialized deterministically before dynamic summary, tail, runtime context, and
tool results. Provider adapters use route-bound cache affinity or provider-native
cache controls/checkpoints where supported and normalize cache read/write/miss
usage into whole-turn telemetry.

An enabled, usable Memory/User profile forms a deterministic early prompt
prefix after editable working memory. OpenAI Chat and Anthropic cache
breakpoints prioritize that profile ahead of an older recent-user boundary;
dynamic runtime context and coverage-hole notices are excluded from the stable
profile checkpoint.

Editable `/memory/WORKING.md` is encrypted persistent state, but it is pull-only
through `workspace_read`, not silently injected into future prompts or cache
prefixes. After private workspace state is read, later outbound web, MCP, and
`task` tools are unavailable for the remainder of that turn.

The current Pre canary proves an OpenRouter cache read over a stable synthetic
conversation prefix. Native Bedrock and the deployed trusted-skills boundary
still require their own live post-deploy evidence; unit and wire tests
are not presented as that proof.

### Runtime V2 encrypted trajectories and offline review

Runtime V2 keeps an append-only flight recorder for each job in addition to
aggregate token and latency telemetry. Rendered provider requests, provider
responses, late-message folds, tool calls and results, planned replies,
exceptions, and terminal state are serialized inside the trusted runner,
bounded and compressed, then stored as shared encrypted envelopes. PostgreSQL
sees the user and job IDs, event index, event kind, ciphertext size, truncation
bit, and timestamps, but not the conversation or tool payload. Event updates
are rejected; explicit account or job deletion still removes associated rows.

A failed or expired turn can enqueue a separate low-priority offline review,
but provider-backed review is off by default and requires the managed runner's
explicit enable variable. Admission is serialized in PostgreSQL against a
fleet-wide pending-plus-running ceiling; disabled, invalid, and overflow cases
retain capture but create no review runner. The same flag is checked before
provider boundaries as an operational cost kill switch. If that fence stops an
in-flight runner, its durable request returns to pending; after re-enable, the
parent reconciler idempotently recreates one runner per pending-review user in
bounded batches. The review worker decrypts only a bounded trajectory frontier,
calls the user's
configured model once with no tool schemas, and encrypts the analysis before
storage. This is not a production retry or deterministic replay and cannot
resend a reply or invoke a platform, MCP, Memory, schedule, or workspace
mutation: the review handler does not receive those dispatch surfaces. Review
output is not inserted into Chat or agent context automatically. Its lease and
process-watchdog progress remain live across decrypt/provider work, and
completion is fenced to the exact event frontier: any late event discards or
reopens stale analysis.

Explicit event truncation, changing external reads, and fresh model sampling
also mean the flight recorder cannot promise byte-for-byte historical
re-execution. Trajectory and review rows currently have no automatic retention
job; they are removed by explicit owning job/account deletion. Keep provider
review opt-in until a BYOK budget and retention/GC policy are chosen. Turning
review off never turns trajectory capture off.

## Managed and self-hosted trust models

| Deployment | Confidential-compute guarantee | Appropriate boundary |
| --- | --- | --- |
| Managed production | Main and hosted-runner workloads can run in measured confidential VMs; the decrypt service exposes attestation evidence | Multi-user API with the documented runner isolation limitations |
| Single-operator self-host | Depends on the operator's host and configuration | One user, family, or organization that trusts the operator |
| Generic local development | Software processes on one developer machine | Test identities and non-production data |

Running the decrypt service on an ordinary VPS preserves the envelope format but
does not protect its private key from that machine's operator. Achieving managed
production parity also requires measured deployment, key lifecycle, network
policy, secret distribution, backups, monitoring, and incident response.

### Enclave transport trust chains

Managed deployments expose two supported transports to the enclave service. They
are not interchangeable evidence models:

> Custom-domain path: client TLS -> dstack-ingress inside the measured TDX CVM
> -> Docker-internal HTTP -> enclave-domain. Verify WebPKI, ingress certificate
> evidence, and enclave attestation.

> Direct audit path: client TLS -> Phala -5003s passthrough -> enclave. Verify the
> live self-signed certificate fingerprint against enclave attestation REPORT_DATA.

The custom-domain route has a deliberately disclosed plaintext hop between
`dstack-ingress` and `enclave-domain`. It is Docker-internal traffic inside the
measured TDX CVM, not a public-network hop; its protection relies on that CVM
boundary rather than a second TLS layer. Cloudflare manages DNS-01 records only
and does not proxy this traffic.

Clients using the custom domain must verify both the ingress certificate-evidence
bundle and the enclave attestation bundle, in addition to ordinary WebPKI, before
claiming security equivalent to direct fingerprint pinning. The existing
`-5003s` endpoint remains the compatibility and audit route for clients that
perform the direct certificate-fingerprint-to-`REPORT_DATA` check.

## Health and capability readiness

`GET /healthz` returns a structured process-liveness snapshot. It carries a
top-level `status` of `healthy` or `degraded`, a `checks` object with
process-local detail, and release/uptime metadata. The backend probe reports the
in-memory user registry size and cross-worker wake-bus listener, but deliberately
does not borrow a PostgreSQL connection or inspect the business connection pool;
pool saturation therefore cannot delay the probe or turn it into an outage. The
backend returns HTTP 200 whenever its worker can serve the request. The enclave
probe reports readiness, release, and TLS posture from cached boot state without
doing any cryptography. A `degraded` result still returns HTTP 200.

`GET /healthz/runner` runs its blocking heartbeat database query on a
per-backend-worker executor with two worker threads and a four-call outstanding
admission cap, separate from ordinary ASGI blocking work. Connection acquisition
and health SQL each have a one-second bound, and the route has a three-second
deadline, so business-thread saturation cannot leave the runner probe queued
until an external monitor times out.

`/healthz` still does not, by itself, complete an enclave decrypt, verify a live
runner, call a model provider, test object storage, start the screen WebSocket,
or deliver a push notification. Readiness for those must be evaluated per
enabled capability:

| Capability | Minimum end-to-end readiness evidence |
| --- | --- |
| Account and storage API | Authenticated request plus a successful write/read round trip through PostgreSQL |
| Memory index and fetch | Storage round trip plus a successful authorized decrypt projection |
| Hosted Chat | Database, decrypt service, a fresh runtime heartbeat for the user's fenced runtime (Runtime V2 worker heartbeat and capacity, or V1 resident supervisor heartbeat during the dual-runtime window), queue processing, provider call, and encrypted assistant result |
| Independent resident Chat | Fresh official poll plus a fresh `ok` decrypt-health report, an exact-parent verify-ping reply, and an encrypted ordinary reply |
| Screen ingestion | Authenticated WebSocket ingest plus frame persistence and, when needed, decrypt retrieval |
| Push delivery | Valid device token and a confirmed provider delivery attempt |

There is no single public `/readyz` endpoint that proves all of these
dependencies. Operators should compose synthetic, non-production probes for the
capabilities they enable; `/healthz` covers process liveness plus the registry
and wake bus, but not PostgreSQL, the business connection pool, or the
capability-level checks above.

The resident decrypt-health headers are an operational self-report used to
prevent live-loop-only false greens. They do not move the decrypt trust boundary
and are not attestation: phase one may report `ok` after a successful
reachability probe. A future encrypted challenge can provide stronger proof
that the resident opened ciphertext for the account.

## Security boundary summary

Feedling's architecture is designed to provide:

- user-scoped API and storage access;
- ciphertext-at-rest protected bodies for the documented envelope workflows;
- an attested trusted-decrypt boundary in the managed deployment;
- short-lived, scoped credentials for hosted execution; and
- explicit handoff to user-selected external inference and delivery services.

It does not claim that every field or compatibility upload is encrypted, that a
Runtime V2 turn process is a hostile-code sandbox, that external model
providers cannot see inference plaintext, or that process liveness proves full
service readiness.
