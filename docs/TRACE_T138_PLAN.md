## 一句话结论

**换存储只解决 10 道验收题里的 3 道。** 其余 5 道要逐条补探针（存储换了也照样答不出），

## ⚠️ 两件必须 Seven 先拍的（挡在开工前）

### 决策 1：「全量保存」的边界划在哪

换成 append-only 表**只解决存进去以后被挤掉/过期**。写进去**之前**的三条丢失路径原样存在：

| 丢在哪 | 代码 | 何时发生 |
|---|---|---|
| 队列满即丢 | `debug_trace.py:_QUEUE_MAX=5000`，`queue.Full → _record_drop` | 突发写入高于刷盘速度 |
| 刷盘失败只记数 | 同文件 flush 异常路径 | DB 抖动 |
| 进程崩溃丢队列 | daemon 线程，未 flush | 重启/OOM |

所以**不改这三条就不能对 Seven 说「全量保存」**。三个选项，代价递增：

- **(甲) 承认边界**：保证「入库即不丢」，队列/刷盘/崩溃的丢失**计数并显式暴露**在面板上。
  代价最小，但 Seven 的原话是"能够全量保存下来"，这是打折。
- **(乙) durable spool**：先落本地磁盘再异步入库。丢失窗口缩到磁盘故障。
  代价：新增一套 spool 的运维与故障模式。
- **(丙) 阻断业务**：trace 写不进去就让业务请求失败。零丢失，但**用调试数据的失败拖垮用户请求**——我不建议。

**这是 Runtime 架构级选择，我不替 Seven 定。** 我的建议是 (甲)，理由：trace 是调试数据，
拿它去阻断用户请求不划算；而"丢了多少"只要**是可见的**，就不会变成"以为有其实没有"——
后者才是这次要治的病。

### 决策 2：保留期与「删不删旧数据」

Seven 要"全量保存"。若字面执行 = **永不删**，那么：
- 分区形态（日/月/不分区）、索引策略、维护成本全都跟着变
- 长期项里的"删过期分区"就**不成立**，要改成"永久保留 + 容量规划"

⚠️ **这条必须在建表之前定**（原稿把"按天分区"写在了"速率答不了"的前面，
顺序反了，codex2 指出，成立）。

## 二、分块、大小、依赖

### 0. 先量再定（挡在 A 前面）

### A. 存储层：blob 环 → append-only 表 ★ 地基
含四件，不能只算建表：
1. migration + 写函数改写 + admin 读点改写（47 个调用点不改，是**省下的成本**，
   但见 A3 —— 它同时意味着**单点改坏一次会一次性丢全部 47 处**）

   enable+verbose 开关、clear、销号语义；新 writer 与 union reader 对同一 fixture 等价。
   Seven 明说"基础记录尤其现有的不许丢"，这条是**底线的可执行形式**，不是加分项
4. **存储拓扑先定**：test 已是 TEE primary。T133 刚为此做了 RDS+TEE 双链迁移 +
   registry + reconciler 三处登记。trace_events 的权威库是哪个、要不要双链、
   进不进 snapshot（⚠️**永久增长表若进整表 SNAPSHOT，会反向制造 Q7**）、
   plaintext excerpt 的信任边界——**没定拓扑就写不出准确的"1 个 migration"**

## 三、⚠️ 详细内容在入库前就已经被截了

Seven 要"详细内容的时间长度更长"，但现状是**内容在写入前已被静默裁剪**：

| 限制 | 值 |
|---|---|
| detail 键数 | 最多 20 |
| detail 列表项 | 最多 20 |
| detail 字符串 | 200 字符 |
| content_excerpt 每字段 | 2048 |
| content_excerpt 每事件 | 8192 |

后果：**Q8 要的 name 级集合可能在入库前就被截成 20 个，且没有任何标记。**
新表忠实保存一份**已经悄悄残缺**的事件 —— 存得再久也没用。

所以 plan 要求：明确哪些数组必须完整、哪些允许 cap，**所有 cap 必须带
`truncated` 与 `total_count`**。没有标记的截断等于说谎。
