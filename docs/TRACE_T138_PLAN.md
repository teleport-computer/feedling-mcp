## 二、分块、大小、依赖

### A. 存储层：blob 环 → append-only 分区表 ★ 地基
- **改动面**：1 个 migration（表 + 按天分区）、`debug_trace.trace_event()` 内部改写、
  admin 唯一读点改写。**47 个调用点一行不动**（写入口是单一函数，这是这次最省的地方）
- **大小**：中。设计已定死，主要是实现 + 迁移演练
- **依赖**：无（T137 已落 test）
- **风险点**：分区滚动。**谁来建下个月的分区？漏建 = 写入直接失败**。
  这不是一次性工作，见第三节
- 解决 Q3(半)、Q4

### B. 读侧：能一路点到底
- **改动面**：新查询端点（按 user/lane/day/trace_id 过滤 + 分页 + 覆盖自报）；
  现有面板接上
- **大小**：中。判据是「聚合数字 → 按用户拆 → 单条事件 → 该条 content，
  断在任何一层都算没过」
- **依赖**：A
- 解决 Q3(另半)、Q9(半)

### C. 补探针 ×3 ★ 工作量大头
逐条独立，可并行，互不依赖：
- **C1 模型添加/测试路径（Q1）** —— 路线创建 / 测试调用 / invalid_output / 回滚删除
  全程零事件。⚠️**这条链路真金白银打中转站扣 token，失败归因目前只能靠读代码推断**

- **依赖**：无结构依赖，但**价值依赖 A**（补了探针仍存进 48 小时的环 = 白补）

## 三、⚠️ 哪些是做完就没了，哪些要一直养

Seven 要看「还有多少事」，所以这两类必须分开 —— 长期项混在一次性任务里，
会让人以为做完就结束了。

### 做完就没了（一次性）
- A 存储层改造、B 读侧端点、D 唤醒道复验、E SNAPSHOT 出口
- C1/C2/C3 三条探针本身

### 要一直养（长期机制，**做完 T138 也不会消失**）

1. **分区滚动** —— 新引入的运维负担。建下个月分区、删过期分区。
   **漏建 = 写入失败**。必须做成自动 + 有告警，不能靠人记得
2. **容量增长** —— 「全量保存」是 Seven 的硬要求，代价是无上限增长。
   现有估算 68 MB/天、约 25 GB/年，但⚠️**这个数没实测过**，且它基于「人均 200 条/天」；
   C 块补完探针后事件密度会涨。**建议 A 块落地时先量一周真实速率再定保留天数**
3. **覆盖矩阵维护** —— 新增流水线要登记，否则矩阵会慢慢变成一张过期的地图
4. **content 边界** —— Seven 已裁「以好查 bug 为准，verbose 默认开」。
   这是持续的判断：什么能进 `content_excerpt`、什么不能，每加一条探针都要过一次

## 四、建议顺序

```
E（独立，最先，倒计时在跑）
A（地基）──→ B（读侧）
              └─→ C1 / C2 / C3（可并行，但 A 之前补等于白补）
D（独立，随时，且是 Q9 的前置）
```

**先 E 后 A** 的理由：E 与 trace 存储无关、体量小、且有真实倒计时（~139 天）。
**C 放在 A 之后**：探针补了却仍存进 48 小时的环，等于没补。
