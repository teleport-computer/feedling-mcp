## 第 2 点:memory 上传要按"来源类型"分两条,不能一刀切

### 现状问题
现在的口径是**一刀切"重质不重量"**(任何文档都只出一小组精选卡)。
这对"聊天记录"是对的,但**误伤了"长期记忆"**——用户已经自己筛好的事实被丢掉了。

### 目标行为:按上传内容的**形态**分流

| 上传类型 | 判据(内容形态) | 落卡策略 |
|---|---|---|
| **聊天记录 / 对话转录** | 有对话轮次、时间戳、"我:…/他:…"、大量寒暄噪声 | **重质不重量**,克制精选,只留"一个月后还重要"的 |
| **长期记忆 / 已整理的事实档案** | 陈述句事实、条目式、个人档案、"关于我"清单 | **尽量全收,不为简洁而丢内容** |

**两个约束(避免从一个极端荡到另一个):**
1. **"全收" ≠ 逐句刷卡。** 长期记忆也要:走 bucket/thread 结构、写前查重
   (`memory-index` / server 端等价去重)、已存在的不重复 add。全收指的是
   **"不主动丢弃内容",不是"不去重/不结构化"**。
2. **混合文件按段分别处理**(一半聊天记录、一半笔记 → 分段套不同策略)。
3. **形态判不准时** → 简短问用户一句"这份是聊天记录,还是你整理好的长期记忆?"
   (成本低、比猜错强)。

### 落点
- **服务端蒸馏(工程师):** `backend/genesis/*` 蒸馏时按 import 素材类型区分抽取密度。
  目前疑似对所有导入素材用同一套抽取,需要引入"聊天记录 vs 长期记忆"的分流。
- **resident skill(Claude 改):** `skill-resident-agent.md`「吸收文件」段拆两路。

## 第 3 点:identity 上传 —— 覆盖优先 + 部分补全 + 关系时间要能覆盖

### 目标行为
用户上传新 identity,就是**想改它**。因此:

1. **整卡覆盖优先。** 冲突时(名字/性格/日期)**最新版本赢**。
2. **部分上传要补全,不清空。** 若上传只给了一部分(例:只给了性格、没给名字)
   → 先取现状卡(`identity_get` / server 读现卡)→ 覆盖上传提到的字段
   → **上传没提到的字段保留旧值** → 整卡 replace 提交。
   (机制上已支持:agent/server 构造完整明文卡再 replace。)

### ⚠️ 需要后端改动的关键点:关系时间(relationship time)
- **现状:** `identity.replace` 复用 `replace_identity_preserving_anchor`,
  **无条件保留**关系锚点(`relationship_started_at` / 认识多久)——一次重蒸馏
  改不了这个字段。
- **Seven 的决定:** 如果**上传的新 identity 里带了明确的关系时间**,
  **应当覆盖旧值**(而不是永远锚定旧值)。
- **需要工程师做:** 把"无条件保留锚点"改成:
  - 上传**含明确关系时间** → **覆盖**关系锚点(采用最新);
  - 上传**未提及关系时间** → 保留现有锚点(维持现状,防止空上传把它清掉)。
- **一个实现决策点(请工程师定并回报):** 覆盖关系锚点时是否仍要求
  证据(`relationship_anchor_evidence`)?
  建议:**明确给了就采用,但保留一层最基本的合法性校验**(避免模型把一句模糊
  提及误判成"明确关系时间"从而重置)。请工程师确认门槛怎么设。

### 落点
- **后端(工程师):** `backend/identity/actions.py`(`85afeae`)+ genesis 的
  `replace_identity_preserving_anchor` —— 增加"上传含明确关系时间则覆盖锚点"分支。
- **resident skill(Claude 改):** `skill-resident-agent.md` identity 段,从
  "谨慎、优先 nudge" 改为 "覆盖优先 + 部分补全",并说明关系时间可被明确上传覆盖。

## 第 4 点(已确认,不改,仅记录)
中转不稳/超时用户的蒸馏**接受"少记一部分"**(确实超时,重传用户也不知道漏了啥)。
