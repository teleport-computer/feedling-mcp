# 身份卡(角色卡)修改路径 — 全景图

> 2026-07-23,io_cli 能力补全重构后的最终形态(含 B2)。
> 说人话版,给 hx 存档。ASCII 图,任何客户端可读。

## 一、四条修改路径 + 一条只读消费

```
┌─ 路径 1:onboarding 蒸馏(建卡)────────────────────────────────┐
│  用户上传聊天记录/人物卡                                          │
│     ▼  genesis 蒸馏器(backend/genesis/prompts.py)               │
│  抽:名字 / 类别 / 七维 / 关系天数                                 │
│     +(B2 新增)从素材抽 5 个用户层字段:称呼/人设指令/语言/         │
│        关系锚点/稳定设定 —— 有据才写,无据留空(grounding)          │
│     ▼  identity.init 建卡                                        │
└─────────────────────────────────────────────────────────────┘

┌─ 路径 2:二次蒸馏(重新总结)────────────────────────────────────┐
│  用户上传新素材说"照这个重新总结你自己"(App 或 io_cli 终端)        │
│     ▼  读【当前最新卡】+ 新素材 → 蒸馏器只产【增量字段】            │
│     ▼  服务端键级合并到最新卡(没提的字段永不丢,CAS 防并发覆盖)     │
│     +(B2 新增)5 个用户层字段也纳入可蒸馏 → 能被重塑                 │
│     ▼  identity.replace 落库                                     │
└─────────────────────────────────────────────────────────────┘

┌─ 路径 3:对话修改(最灵活,唯一逐字段任意改的路)──────────────────┐
│  用户在聊天里说"改名老6"/"说话温柔点"/"把我当哥们"                  │
│     ▼  agent 调 identity-write / 夹带 identity.profile_patch      │
│  可改全部 13 字段 + 七维微调(±10/轮封顶)                          │
│  硬规矩:改名必须同批带自我介绍(服务端闸,防名字/介绍打架)          │
└─────────────────────────────────────────────────────────────┘

┌─ 路径 4:做梦(定期后台整理)────────────────────────────────────┐
│  服务器定期跑 memory_dream                                        │
│  【只整理记忆,不碰身份卡】—— 读 memory index/fetch,合并记忆卡      │
└─────────────────────────────────────────────────────────────┘

┌─ 只读消费:persona_backfill ──────────────────────────────────┐
│  把 custom_persona_prompt(最高优先)+ tone_style + 自我介绍       │
│  拼成 persona 材料重建人格。【只读不写】,证明系统真拿人设指令当骨架 │
└─────────────────────────────────────────────────────────────┘
```

## 三、B2 解决的落差

- **改前**:5 个"用户层"字段名义上"用户所有",却没有任何 App 入口能填,
  也没有任何蒸馏器会产 —— 全链只有"聊天里让 agent 写"这一条实际通路,
  新用户一路空到手动改。而系统(persona_backfill)却认真拿 custom_persona_prompt
  当人设骨架用。重视它、用它,却没生产它。
- **改后(B2)**:onboarding 建卡和二次蒸馏都能从素材把这 5 个抽出来,
  "人设会变、也该有初值"落地。安全靠 grounding(无据留空、绝不编造),
  防止别人塞的素材凭空捏造人设。
- **iOS 不加输入框**(hx 定):用户手写人设 = 通过对话让 agent 写,已具备。

## 三.五、自我介绍 / 第一句招呼:谁生成(两套机制,别混)

```
                       self_introduction                第一句招呼
─────────────────────────────────────────────────────────────────────
cloud v2 onboarding    deriver 建卡时一起产(9字段之一)   onboarding 任务预生成并存库
                       空则兜底句                        (_append_plaintext_onboarding_greeting
                                                          → 模型生成,失败用兜底,区分新/老关系)
                       → 不是 agent 事后写                → 用户进 App 就看到,agent 不必先开口

V1 / VPS(resident)    蒸馏器【故意不产】               agent 重生后本人第一轮说
                       → agent 重生后本人写(7.D,
                         identity-write)
```

⚠️ 常见误解:"自我介绍/招呼都是 agent 本人事后写"——**只对 V1/VPS 成立;cloud v2
是任务替它生成的。** 两套机制不同。

**设计建议(hx 地盘,待定,超出当前分支范围)**:
- 招呼:保持 cloud v2 的"直接生成"(要快、防空白主页),改进=喂更全的卡(人设/语气)让它更像本人。
- 自我介绍:倾向"deriver 先占位 + agent 上线后用本人声音重写"(它长期展示 + 喂 persona_backfill,
  真实度 > 一次性延迟;现已可 identity-write 重写)。

### ⚠️ 已知短板 / 待决(记录于 Router,2026-07-23)

**VPS 不满足"进主页即有"。** cloud v2 由系统保证进场即有(deriver 产自我介绍 +
任务预生成招呼存库);**VPS 靠 agent 在 onboarding 里自己跑 `identity-init
--self-introduction`(第5步)+ 自己发第一句问候(第8步)**——"有没有、及不及时"
取决于 agent 有没有把这两步做完,任一步失败或延迟,主页就可能空着。

**要让 VPS 也"进场即有"(选项②,hx 待拍)**:
- 自我介绍:VPS resident 蒸馏器(distill_prompt_v1)其实已产 self_introduction,
  可直接用建卡那版展示,不必非等 agent 再写;agent 之后重写只作润色。
- 第一句:在 resident distill 完成时由 consumer 兜底备一句存库(对齐 cloud v2 的
  `_append_plaintext_onboarding_greeting`),不再纯靠 agent 第8步。

**更深一层:蒸馏 authorship 模型本身不统一** —— 同一件事(自我介绍/招呼谁生成)
cloud=系统、VPS=agent,两套心智模型。长期应收敛成一致契约(系统保证进场即有 +
agent 可后续用本人声音润色),归 hx。

## 四、并发与防丢(贯穿所有写路径)

```
两个进程/两轮同时改同一张卡  → DB CAS(写前确认没被改过,变了就重读重算)
"重新总结"读卡后跑几分钟模型  → 落库时对【最新卡】合并,不覆盖期间的改动
夹带通道                     → 类型白名单(shadow→enforce),只放行认识的动作
残留未走 CAS 的写者          → relationship_days_set / init_if_absent / rewrap(已修)
                              已在代码注释里标为已知残留
```
