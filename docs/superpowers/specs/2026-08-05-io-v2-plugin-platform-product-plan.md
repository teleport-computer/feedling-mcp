# IO V2 插件化产品计划书

> 状态：产品与架构设计评审稿
> 日期：2026-08-05
> 适用对象：产品、设计、iOS、Runtime、后端与安全团队

## 一句话概括

IO V2 将从一套默认捆绑的 Personal Agent 能力，升级为一个由用户主动选择的能力系统。

账户、模型和基础聊天属于始终可用的 **IO Core**；人格、长期记忆、iOS 感知和后台思考则成为独立插件。用户可以清楚看到每个插件带来什么、会访问什么数据，并随时启用或停用。

首版只提供官方插件，但底层协议从第一天就为未来第三方插件保留清晰边界。

---

## 1. 为什么要做 IO V2

当前 IO 已经拥有 Identity Card、Memory Garden、iOS Perception、Inner Thought 等能力，但在用户眼中，它们更像一个不可拆分的整体：

- 用户不容易判断某项能力正在读取什么、什么时候运行；
- 不同用户无法组合出真正适合自己的 IO；
- 某项能力即使在界面上关闭，也缺少一套统一机制证明它不会继续注入上下文、处理事件或产生后台任务；
- 工程上各项能力共享运行时和调用链，新功能容易继续增加耦合；
- 如果未来开放第三方扩展，现有边界不足以支撑可信的授权与隔离。

V2 首先要解决的不是“增加更多功能”，而是把能力的控制权交还给用户。

本项目的优先级是：

1. **用户掌控感**：用户知道 IO 能看什么、记什么、主动做什么。
2. **产品可定制**：不同用户可以选择不同能力组合。
3. **研发解耦**：团队可以更独立地演进和回滚各项能力。

---

## 2. V2 的产品定义

### 2.1 IO Core

关闭所有插件后，IO 仍然是一套完整可用的纯聊天产品。

Core 只负责：

- 账户、设备和模型连接；
- 基础聊天与 Agent turn；
- 加密、安全和租户隔离；
- 插件注册、授权、状态和调度；
- 对插件输入与产物进行统一检查。

Core 不再默认拥有长期人格、记忆、设备感知或后台主动行为。

### 2.2 首批官方插件

| 插件 | 用户获得的能力 | 停用后的行为 |
|---|---|---|
| **Identity** | 让 IO 保持稳定的人格、关系理解、称呼和表达偏好 | 不再读取或注入身份信息；已有身份数据保留并冻结 |
| **Memory Garden** | 形成、展示、检索并引用长期记忆 | 不再读写或注入记忆；已有花园保留 |
| **iOS Perception** | 在用户允许的范围内感知屏幕、位置、运动、日历、媒体等情境 | 停止采集和消费对应信号；历史数据保留 |
| **Inner Thought** | 在没有新消息时整理想法，并在值得时主动出现 | 停止后台思考、计划唤醒和主动触达；历史产物保留 |

### 2.3 用户如何组合

V2 首版采用“选择能力”的模式，而不是工作流编辑器：

- 用户只决定开启哪些插件；
- 系统负责插件执行顺序、上下文预算和事件调度；
- 用户不需要理解节点、分支、触发器或数据管线；
- 任意插件组合都必须保持可用，包括全部关闭。

## 3. 用户体验

### 3.1 新用户

首次使用时，IO 推荐 Identity 与 Memory Garden，但不强制开启。

iOS Perception 与 Inner Thought 因为涉及设备数据或后台主动行为，需要分别解释价值与权限，再由用户确认是否启用。用户可以跳过所有插件，直接使用纯聊天。

### 3.2 插件中心

插件中心不是普通的功能开关列表，而是用户管理 IO 能力和数据访问的控制台。

每张插件卡至少说明：

- 它会为 IO 增加什么；
- 它需要访问哪些数据或系统能力；
- 为什么需要这些权限；
- 停用后会发生什么；
- 当前处于启用、停用还是异常状态。

首页展示价值、状态和简短权限摘要。用户启用高权限插件前，会进入详情页逐项确认。

首版不开放单项权限编辑。一个插件的必要权限不完整时，插件无法启用或进入受控降级，避免出现界面显示正常、实际行为随机缺失的状态。

### 3.3 启用与停用

首版只提供两种用户可见状态：启用和停用。

- **启用**：用户确认权限后，系统初始化插件并开始提供能力。
- **停用**：立即停止新的读取、写入、上下文注入、事件消费、后台任务和主动触达。
- **数据保留**：停用不会删除历史数据；重新启用后可以恢复使用。

数据导出、彻底删除和插件卸载不属于首版范围。

---

## 4. 插件如何组合

插件可以声明两类关系：

- **必需依赖 `requires`**：缺少依赖时无法运行。用户启用时，系统会说明并请求连带开启。
- **可选增强 `enhances_with`**：相关插件存在时体验更好，不存在时仍能独立运行。

例如：

- Inner Thought 只依赖 Core；
- Identity 和 Memory Garden 都是 Inner Thought 的可选增强；
- iOS Perception 可以独立服务于前台问答；
- 同时启用 Inner Thought 后，感知事件才可能触发后台思考；
- 关闭 Inner Thought 不应导致 iOS Perception 一并关闭。

停用一个被其他插件硬依赖的插件时，系统必须提前展示受影响范围。用户确认后，按依赖关系安全地关闭相关插件。

---

## 5. 权限模型

每个插件都必须在启用前声明权限。权限使用用户能理解的“资源 + 动作”表达，而不是笼统的“访问全部数据”。

示例包括：

- 读取最近聊天；
- 读取或写入该插件的数据；
- 向 Agent 上下文贡献内容；
- 订阅某类感知事件；
- 安排后台任务；
- 发送主动消息。

权限设计遵循五条原则：

1. **最小授权**：插件只申请完成核心价值所必需的权限。
2. **用途可解释**：界面不仅列权限，还说明为什么需要。
3. **运行时强制**：权限不是文案；每次访问都必须经过 Core 检查。
4. **跨插件受控**：插件不能私下读取另一个插件的数据。
5. **随时撤销**：停用或系统权限撤销后，新操作立即停止。

iOS 系统权限与 IO 插件权限是两层独立控制。例如，手机仍保留位置授权，不代表 iOS Perception 插件在停用后仍可以采集位置。

## 6. 如何实现

### 6.1 总体方案：Manifest + Capability Host

每个插件提供一份版本化 manifest，用来声明：

- 插件身份、版本、类别和用户说明；
- 必要权限与可选权限；
- 必需依赖与可选增强；
- 订阅的标准事件；
- 提供的上下文、工具、任务或 App 页面；
- 自己的数据域；
- 后台运行频率和资源预算。

Core 内新增统一的 **Capability Host**，负责：

- 读取并校验 manifest；
- 保存每个用户的插件状态和授权；
- 解析依赖关系；
- 将事件投递给有权接收的插件；
- 收集并组装插件贡献的上下文；
- 管理后台任务与资源预算；
- 在产物写入或消息发送前再次检查权限。

首版插件代码仍可与现有 Runtime V2 一起部署。插件化首先意味着权限、数据和生命周期边界成立，不意味着立即拆成微服务。

### 6.2 标准插件接口与 Input/Output

所有插件必须实现同一套生命周期与运行接口。概念接口如下：

```text
manifest()                         → PluginManifest
enable(plugin_context)            → PluginResult
disable(plugin_context)           → PluginResult
handle(plugin_input, context)     → PluginOutput[]
health()                           → PluginHealth
```

`PluginContext` 不是后端内部对象的集合。它只提供用户已授权的 capability，例如读取指定资源、申请模型执行、写入本插件数据或发送受控通知。插件不能直接获得数据库连接、模型密钥、通知服务或其他插件实例。

#### 标准 Input：固定信封 + 类型化 payload

所有运行输入共享一个固定外层：

```json
{
  "event_id": "evt_123",
  "type": "chat.turn.completed",
  "schema_version": 1,
  "occurred_at": "2026-08-05T10:00:00Z",
  "user_id": "usr_123",
  "source": "core.chat",
  "trace_id": "trace_123",
  "state_epoch": 8,
  "payload": {},
  "resource_refs": []
}
```

固定外层负责事件路由、租户归属、幂等、追踪、状态校验和协议版本；`payload` 则由 `type + schema_version` 对应的 schema 定义。例如：

- `chat.turn.completed.v1`；
- `perception.scene_changed.v1`；
- `timer.wake_due.v1`；
- `plugin.memory.created.v1`。

Input 由 Host 创建，插件不能自行指定或改写 `user_id`、`source`、`trace_id` 和 `state_epoch`。敏感内容默认通过 `resource_refs` 引用；插件只有在执行时再次通过 capability 授权，才能读取引用对应的数据。

这套设计不是把所有输入塞进一个万能 JSON。统一的是信封和运行语义，业务 payload 仍然保持强类型和独立版本。

#### 标准 Output：插件提交申请，Core 执行副作用

插件输出同样使用固定信封：

```json
{
  "output_id": "out_123",
  "type": "effect.request",
  "schema_version": 1,
  "plugin_id": "io.inner-thought",
  "caused_by": "evt_123",
  "state_epoch": 8,
  "idempotency_key": "inner-thought:evt_123:notify",
  "payload": {
    "effect": "notification.send",
    "arguments": {}
  }
}
```

首版支持四类 Output：

| Output 类型 | 用途 |
|---|---|
| `context.contribution` | 向当前 Agent turn 提供结构化上下文 |
| `effect.request` | 申请写记忆、修改身份、安排任务或发送消息 |
| `event.emit` | 产生一个可被其他插件订阅的标准事件 |
| `ui.projection` | 向 App 提供标准卡片、摘要或状态数据 |

返回空数组是合法的 `noop`：表示插件正确处理了 Input，但判断无需产生任何结果。

Output 只描述意图，不代表副作用已经发生。Host 收到 Output 后必须：

1. 校验 Output schema 和声明来源；
2. 再次检查插件状态、权限、预算和 `state_epoch`；
3. 使用 `idempotency_key` 防止重复执行；
4. 由 Core 执行获准的写入、调度或发送；
5. 将执行成功、拒绝或失败记录为结构化结果事件。

因此插件不能直接写数据库、拼接最终 prompt 或发送通知。未来插件改为独立进程或第三方沙箱时，只需把本地方法调用替换为 RPC，Input/Output 契约无需推翻。

#### 版本与错误规则

- JSON Schema 是跨运行时的协议真相；Python、Swift 等类型从 schema 生成或做一致性校验。
- `api_version` 管插件与 Host 的整体兼容性，`schema_version` 管单个 Input/Output 类型。
- 同一 schema version 只允许增加可选字段；删除字段、改变含义或改变类型必须升级版本。
- Host 遇到未知类型、未知版本、字段超限或非法资源引用时必须拒绝，不能猜测兼容。
- 标准错误至少包含 `code`、`retryable`、`user_visible` 和内部 `details_ref`；敏感 payload 不进入错误文本。
- 可重试错误必须沿用同一个 `event_id` 或 `idempotency_key`，避免重复副作用。

### 6.3 插件不能直接修改 prompt

Identity 和 Memory Garden 等插件只能返回结构化的“上下文贡献”。Core 的 Context Assembler 负责：

- 校验插件是否启用且有权读取数据；
- 对内容排序、去重和截断；
- 分配 token 预算；
- 生成最终模型上下文。

插件不能自行拼接 system prompt，也不能绕过 Core 调用其他插件。这能避免某个插件无限占用上下文，或通过隐藏路径扩大权限。

### 6.4 插件数据隔离

数据按“用户 + 插件 namespace”进行逻辑隔离：

```text
core.chat
plugin.identity
plugin.memory-garden
plugin.ios-perception
plugin.inner-thought
```

这不要求首版把现有数据全部迁入一张通用插件表。Identity、Memory、Perception 等现有专用表可以继续保留，但必须通过统一访问层标明数据所有者和插件 namespace，并接受 Capability Host 的权限检查。

### 6.5 统一事件流

前台聊天和后台事件共享同一套授权机制：

```text
触发源
  → Event Router
  → 插件状态与权限检查
  → 插件执行
  → 产物检查
  → 上下文 / 存储 / 用户触达
```

前台聊天中，Core 向已启用插件请求上下文，再执行模型 turn。

后台链路中，iOS 信号先由 Perception 归一化和降噪，再由 Event Router 决定是否投递给 Inner Thought。原始设备信号不能直接唤醒模型。

### 6.6 防止“关闭后仍然发生”

每个用户的插件状态带有递增的 `state_epoch`：

- 后台任务开始时记录当前 epoch；
- 用户启用或停用插件时递增 epoch；
- 任务提交结果前再次比较；
- epoch 不一致时，结果直接作废。

因此，即使用户停用插件时某个任务已经在模型侧运行，它也不能在稍后写入记忆或发送主动消息。

### 6.7 为未来第三方插件预留什么

首版提前稳定以下协议：

- manifest 格式及 `api_version`；
- 权限名称和能力调用方式；
- 标准事件格式；
- 插件状态与依赖语义；
- 数据 namespace；
- 资源预算和结构化审计事件。

首版不实现第三方代码执行。插件签名、审核、商店、沙箱、独立升级和恶意插件治理在协议稳定后另行设计。

## 7. 现有用户如何迁移

V2 升级保持现有用户行为，不要求重新开启所有能力。

迁移时：

- 根据当前服务端开关、实际系统权限和正在运行的能力生成插件状态与授权记录；
- 已经正常工作的能力继续工作；
- 仅有历史数据、但当前没有启用或运行证据的能力，不会被自动开启；
- 不扩大任何既有权限；
- 用户首次进入插件中心时看到迁移摘要，并可以检查或停用每项能力。

实施采用渐进收口：

1. 引入 Registry、manifest、状态和授权数据，但暂不改变现有行为。
2. 先以影子模式记录每条旧链路在新权限模型下是否会被允许。
3. 依次将上下文读取、数据写入、后台任务和主动消息接入 Capability Host。
4. 修完影子模式发现的遗漏后，开启强制检查。
5. 最后发布 iOS 插件中心和用户启停入口。

迁移不进行一次性大爆炸重写。旧路径只有在对应能力通过新 Host 运行并完成回归后才退出。

## 8. 推荐实施顺序

### 阶段 A：基础能力宿主

- 定义 manifest schema、权限词表和标准事件；
- 建立用户插件状态、授权和 `state_epoch`；
- 实现 Registry、Permission Gate 与依赖解析；
- 接入影子检查和内部审计事件。

交付标准：不改变用户行为，但能准确描述“如果现在强制权限，会允许或拒绝什么”。

### 阶段 B：插件逐个收口

建议按以下顺序迁移：

1. **Identity**：先验证上下文贡献模型；
2. **Memory Garden**：覆盖读取、写入和 Agent tool；
3. **iOS Perception**：覆盖设备权限、采集和事件归一化；
4. **Inner Thought**：最后收口后台调度、跨能力增强和主动触达。

每迁移一个插件，都要证明停用状态下不存在旁路，然后再迁移下一个。

### 阶段 C：用户控制面

- 新用户推荐套装；
- 插件中心与详情页；
- 权限确认、启停和依赖提示；
- 现有用户迁移摘要；
- 异常与受控降级状态。

### 阶段 D：全量强制与清理

- 从影子检查切换为权限强制；
- 删除已确认无调用的旧旁路；
- 完成全组合、真机和迁移回归；
- 更新公共 API、架构、工作流、信任模型和 changelog 文档。

## 9. 故障时应该发生什么

- 单个插件超时或报错时，纯聊天继续工作。
- 插件初始化失败时，启用操作原子回滚，不留下半启用状态。
- 可选增强不可用时，主插件降级运行，不被强制关闭。
- 必需依赖被停用时，系统先展示影响范围，再按依赖关系关闭。
- 系统权限被撤销时，对应能力立即停止，界面说明如何恢复。
- 插件版本与 Host 不兼容时，插件进入隔离状态，数据保持不动。
- 后台预算耗尽时，停止新的后台执行，不影响前台聊天。
- 停用后的迟到结果一律丢弃，不写库、不通知用户。

所有故障都应落入结构化内部事件，为未来的“最近活动”和用户可见诊断保留基础，但首版不建设完整审计时间线。

---

## 10. 首版不做什么

为避免 V2 演变成一个过重的平台项目，首版明确不做：

- 第三方插件安装和插件市场；
- 任意代码执行与插件沙箱；
- 用户自定义处理顺序、条件分支或工作流；
- 插件独立部署和独立发版；
- 权限逐项开关；
- 插件卸载、数据导出或彻底删除；
- 完整的用户可见活动日志；
- 插件自带任意 Swift UI。

这些能力只有在官方插件协议经过真实使用并稳定后，才进入下一阶段评估。

---

## 11. 验收标准

V2 首版必须满足：

1. 关闭全部插件后，账户、模型连接和纯聊天完整可用。
2. 四个官方插件的 16 种启停组合都能启动并完成聊天。
3. 停用插件后，不再发生该插件的数据读取、写入、上下文注入、事件消费、后台任务或用户触达。
4. 停用前已执行的后台任务无法提交迟到产物。
5. manifest 未声明的访问会被 Core 拒绝。
6. 插件不能跨用户或越权访问其他 namespace。
7. 依赖图不存在循环，硬依赖停用结果可预测。
8. 单插件故障不会让基础聊天失败。
9. 现有用户迁移后行为保持不变，迁移授权摘要准确。
10. iOS 展示的每项权限都对应真实运行时 gate。

测试包括：

- manifest、依赖图和权限矩阵单测；
- Capability Host 拒绝路径和跨租户隔离测试；
- 启停竞态、队列迟到结果和故障恢复测试；
- 16 种插件组合的集成测试；
- 现有用户迁移与回滚测试；
- iOS 真机权限撤销、后台任务、通知和插件中心 E2E；
- Runtime V2 的聊天、感知、记忆、Identity 和主动触达回归。

## 12. 如何判断 V2 是否成功

技术上线不是最终成功。V2 应同时满足以下产品结果：

- 用户能用自己的话解释每个插件会做什么；
- 用户能在不担心数据丢失的情况下停用任意能力；
- 关闭某项能力后，用户观察不到相关的“幽灵行为”；
- 新用户可以跳过插件并顺利开始聊天；
- 推荐开启 Identity 与 Memory 不会让用户误以为它们是强制项；
- 团队新增一个官方插件时，不需要修改其他插件的内部实现；
- 未来设计第三方插件时，不需要推翻现有授权、事件和生命周期模型。

建议首批观测指标包括插件启用率、停用率、授权页退出率、纯聊天成功率、插件降级率、越权拦截数、迟到产物拦截数和迁移前后行为一致性。

## 13. 关键风险与应对

| 风险 | 应对方式 |
|---|---|
| 只做 UI 开关，底层仍可绕过 | 所有读取、写入、上下文、任务和触达统一进入 Capability Host；影子检查后再强制 |
| 插件停用时仍有任务在运行 | `state_epoch` 在任务开始与结果提交时双重校验 |
| 迁移时错误扩大授权 | 只根据当前启用状态、真实权限和运行证据生成授权；历史数据存在不等于启用 |
| 插件贡献让 prompt 失控 | 插件只返回结构化贡献，由 Core 统一预算、排序和拼装 |
| 一个插件故障拖垮整个 Agent | 插件超时、隔离和降级；纯聊天路径保持独立 |
| 用户被依赖关系困惑 | 只暴露少量硬依赖；启停前明确展示连带影响；优先使用可选增强 |
| 首版过度建设平台 | 不做市场、沙箱、工作流和独立部署；先验证四个官方插件 |

---

## 14. 最终原则

IO V2 的插件化不是把现有功能换一组名字，也不是先造一个插件市场。

它要建立一条用户可以信任的产品规则：

> 我开启什么，IO 才拥有什么；我关闭什么，它就真正停止；我的数据仍由我掌控。

只要这条规则在产品说明、iOS 界面、Runtime 执行和数据边界上保持一致，V2 就具备继续扩展成开放插件平台的基础。
