# V2 测试案例库 — 从真实故障里学出来的

> 2026-08-14 建。材料来自 8 个 agent 手上正在修的**真实灰测故障**,
> 不是推演。每条都附:用户症状 / 根因位置 / **现有测试为什么没抓住** / 该写什么测试。
>
> **这份文档的用法**:改 V2 代码之前先扫第一节。
> 如果你的改动落在任何一种失效模式的形状里,照那条的"抓法"补测试再动手。

---

## 第一节:十三种失效模式(测试为什么会漏)

这十三种是从 8 位 agent 报上来的真实故障里归纳的**测试失效形状**。它们比"某个功能没测"更值钱 ——
知道形状,就能在下次写测试时提前避开。

### 模式 1:夹具比生产干净

**形状**:测试用的样本是精心构造的小样本,真实流量的样本大一个数量级、脏一个数量级,
于是闸门在测试里永远不被触发。

**真实案例**:MCP 工具全部消失(claude, usr_90184)。
用例都用**几个玩具工具**造工具面,而真实工具面是 **32,684 字节 / 69 个工具**
(34 平台 + 35 用户 MCP)。玩具样本永远越不过预算闸,测试永远绿。

**抓法**:**用真实尺寸的样本把闸逼到边界**。
拿平台 catalog 的实测字节数 + 一份典型用户 MCP 目录,在 16K/32K/40K 各档窗口下断言。

### 模式 2:单轮夹具看不见多轮退化

**形状**:第一次调用正常,第二次起被静默摘掉/降级。单轮用例永远只测第一次。

**真实案例**:MCP 一轮只能调一次(claude4,两位灰测用户报)。
`tool_loop.py` 的 `blocked_tools` 在后续轮次把工具摘掉;单轮用例看不到。
⚠️ 放大器:`_PRIVATE_READ_TOOLS` 含 `memory_index/search/fetch`,模型几乎每轮都读记忆,
所以围栏在真实流量里**几乎必然触发**,而单轮夹具里**永远不触发**。

**抓法**:凡是「本轮后续工具面」的裁剪,必须有一条
**「第一轮调 A、第二轮还能调 B」**的两轮用例,并且断言第二轮工具面
**包含**什么(而不是只断言不含什么)。

### 模式 3:if/else 里只测 if

**形状**:受控分支(模型乖乖照做)测得很全,兜底分支(模型不照做)一条用例都没有。
而真实模型经常不照做。

**真实案例**:推理过程时有时无/整段英文/反复自我推翻(claude3 + codex3,两人独立查到)。
代码是「模型没写 `<think>` 就兜底展示 provider 原生 CoT」。
两份约束差一个数量级:自撰 240 字/压成一行/有语言规则;原生 20000 字/保留换行/零约束。
**测试全都喂"模型乖乖写了 `<think>`"的样本**,兜底分支零覆盖,
反而把旧兜底当成了契约。

**抓法**:让 provider **同时返回正文 + 原生 reasoning 但不写 `<think>`**,
分别走 chat / wake 两道,断言下发 payload 不带 thinking。
通用规则:**每个 if 都要有对应的 else 用例**,尤其"模型没按预期输出"那一支。

### 模式 4:断言钉错层

**形状**:断言钉在**生产者侧**(封装前的文本),而用户看到的是**消费者侧**
(封装后解密出来的)。两者之间那条边界没人断言,于是对存量数据和跨端问题恒绿。

**真实案例**:`<think></think>` 裸标签出现在聊天气泡里(claude3)。
剥离全在封装前;封完是密文,服务端永远擦不掉存量。
`serve_worker.py:1077 _scrub_leaked_thinking_rows` 只擦"喂回模型的那一份",
docstring 自述用户那一份不管。iOS 侧零渲染期剥离。

**抓法**:需要**「脏数据落库后,用户视图还长什么样」**的端到端断言 ——
不是单元测试能抓的。凡是跨加密边界的能力,断言必须钉在解密之后。

### 模式 5:埋点测的不是要测的东西

**形状**:观测点取在链路的错误位置,于是线上和测试都显示"一切正常"。

**真实案例**:同上 MCP 消失案。唯一观测点 `mcp.turn.usage` 的 `offered_tool_count`
取自 `worker.py:11623`,是**交进 tool_loop 之前**的 specs ——
埋点测的是「解析出多少」,不是「发出去多少」。所以线上显示 35 个工具一切正常,
实际 provider 收到 0 个。(报告人自陈:这个埋点洞是他 08-12 自己留的。)

**抓法**:端到端断言 **「实际发给 provider 的数量 == 解析出的数量」**。
通用规则:**埋点必须取在最终出口,不能取在中途**;
写埋点时自问「如果这之后的代码把它清空了,我这个数字会变吗」。

### 模式 6:把旧契约当成正确答案

**形状**:测试锁住的是"当年的降级行为",而那个行为本身就是 bug。
测试越牢,bug 越难被发现。

**真实案例**:工具面预算不足时**整份丢弃**(codex)。
现有测试"只锁了整份省略的旧降级契约"——即测试在保护这个错误行为。

**抓法**:写降级/兜底类测试时,断言的应该是
**「用户还能得到什么」**(底线集合),而不是「系统会丢掉什么」。
定期问:这条测试锁住的行为,今天还是我们想要的吗?

### 模式 7:无信号故障

**形状**:故障发生时**没有任何可观测痕迹**,于是它能活很久,
且没人能定位——查不到分布 = 没人能修。

**真实案例**:推理过程异常(claude3)。拉两个用户各 1000 条 trace,
**thinking 相关 0 条**,admin 也不暴露 `thinking_kind` 分布。
另:工具面被丢弃只写进加密轨迹,外部完全看不见,
外在形状就是"配置好好的、AI 说用不了"。

**抓法**:这类不能只靠测试,要**同时补可观测性**。
规则:**任何"静默丢弃/静默降级"的分支,都必须留下 admin 可见的痕迹**;
测试里断言"丢弃发生时有对应事件被记录"。

### 模式 8:同一个出口有多种协议形态,只防了一种

**形状**:出口清洗器是**按已知泄漏形态一条条补出来**的,没有"协议残片"这个统一维度。
于是防住了 JSON,却对 XML 一无所知。

**真实案例**:气泡里出现 `<parameter name="tool_name">reply</parameter>`(claude2/codex2)。
`_on_reply` 五道处理没一道认识尖括号工具标记:
self_thinking 只认 `<think>` 族;`_is_degenerate_reply` 有字母就放行;
`core/protocol_leak` **整个模块只认 JSON**;downloadable_reply 只清文件路径。
全仓 grep `function_calls|<invoke|<parameter` **零命中**。
对照:JSON 泄漏当年专门建了 `core/protocol_leak` 这道闸,XML 这一侧从来没建过。

**抓法**:出口清洗测试要按**「非我方协议形态」这个维度**去写,而不是按已知案例逐条补。
拿真实中转/模型会吐的各种残片(XML 标记、JSON 尾巴、think 标签、命名空间前缀变体)
一起灌进出口,断言:用户可见文本里**永不出现协议标记**,且**正文不被吃掉**。

### 模式 9:手工枚举字面量 —— 每个变体都是一次独立的漏网机会

**形状**:词表/清单靠**手工列举字面量**建立(`function_calls`、`tool_call`…),
而不是从结构规律派生。于是每多一个数形/前缀/大小写变体,就是一次新的漏网,
且**补一个漏一个**永远补不完。

**真实案例**(2026-08-14,T016 审计中被连环发现):
1. 用户报的是 `<parameter name="tool_name">` 单数形态
2. codex2 按报的修好了;CI 12 绿,claude2 判 APPROVED
3. Supervisor 用独立矩阵复验,发现**复数 `<parameters>` 原样漏过**
4. claude2 把它当成一类去扫,又发现 **`tool_results` / `tool_uses` / `invokes`
   也一样漏** —— 范围远大于报上来的那一处

claude2 自认根因:上一轮审计时"只点了 `function_call(s)` / `tool_call(s)` 两个实例,
**把一个类当成两个 bug 报**,codex2 按清单补完,类还开着"。

**抓法**:
- 修法上:改成**词干 + 结构规则**(如可选 `s`、可选命名空间前缀),不要手写全表
- 测试上:**从模块的词表变量派生用例**,遍历所有数形/变体 ——
  手写测试清单会复制手写词表的同一个盲点
- 审计上:发现一个字面量漏网时,先问「**这是一个 bug 还是一个类**」;
  是类就要求结构性修法,不要按实例逐个报

### 模式 10:把「查不到」当成「没发生」

**形状**:某个动作**没有埋点**,于是它在 trace/日志里永远缺席。
排查的人看到"没有记录",推断"没有发生" —— 但**缺席不是证据**,
只说明它不被记录。这会把排查引向完全错误的方向。

**真实案例**(2026-08-14,Supervisor 自己踩的):
用户报「记忆花园搜不到内容」,我拉 trace 后写下线索:
「memory_search 一次都没出现,说明 AI 嘴上说搜了但实际没搜」。
核实后发现:
```
memory.index.called   埋点 3 处   ← 有
memory.fetch.called   埋点 3 处   ← 有
memory.search.called  埋点 0 处   ← 压根没有
memory.write.called   埋点 0 处   ← 也没有
```
**memory_search 从来就没有埋点。** 我把"没被记录"读成了"没被调用",
差点让接手的 agent 顺着错方向查一整夜。已发更正。

同一晚 claude4 独立撞到同族问题:一轮多次工具派发**在部署态没有任何可观测量**,
它拒绝把「验不了」写成「验过了」,选择标 blocked ——这是对的。

**抓法**:
- 排查时先问:**这个动作有埋点吗?** 没有埋点的缺席一律不能当证据
- 写排查线索给别人时,**标注每条证据的可信度**;
  推断和观测要分开写(我那条错在把推断写成了观测)
- 发现「某能力无信号」时,把补埋点开成独立任务 —— 它通常是**多个 bug 的共同盲区**,
  不是某一次排查的附属品

### 模式 11:只验证自己控制的那一段,不看它被拼进更大结构后的位置

**形状**:作者在自己写的那个函数里把 A 放在第一位,注释也写着「A 在前」——
但那个列表整体被拼进一个更大的结构时排在了 B 后面。**注释局部为真、整体为假。**
后来的人读注释,就继承了这个错觉。

**真实案例**(2026-08-14,一晚上骗过三个人):
`serve_worker.py:194` 注释写着 "Persona first, matching V1's persona-before-tools
ordering",代码也确实把 persona 放在 `trusted_system_blocks` 第一个。但
`context.py:563` 是 `trusted_parts = [system_prompt, _RUNTIME_CONTEXT_POLICY]`
然后才 extend 那个列表 —— **人格实际出现在 9009 字符里的第 8987 位**。
codex3 信了注释,把这条判成「已修」;claude3 跑真装配打位置才拆穿。

**抓法**:
- 验「谁前谁后」**一律用哨兵字符串跑真装配打位置**,不读注释、不只读单个函数
- 写这类测试时断言的是**最终产物里的相对位置**,不是「我把它 append 在第几个」
- 见到「X first」这类注释,先问:**first 是在哪个范围内的 first?**

### 模式 12:admin 查不到用户,第一解释是查错环境

**形状**:prod 和 test 是两套完全独立的数据。拿 prod 用户去 test 查,
得到 404 或空结果,于是推断「查不到证据」「这用户不存在」——
实际只是查错了地方。

**真实案例**(2026-08-14 一晚两次):
- codex3 写「该用户在 test 查询返回 404」并据此认为拿不到证据,
  实际那是 prod 用户,整份报告的技术链条因此建错了模型家族
- Supervisor 查 usr_15d76 时,prod 的单点接口对未知用户**返回了默认值
  `resident_cli`**(而不是报错),差点当成「他在 prod 跑 V1」——
  拿全员名单复核才发现该账号在 prod 根本不存在

**抓法**:查用户前先确认环境;**单点查询的返回值可能是默认值不是事实**,
用全量名单复核一次。

### 模式 13:「我没出事」不等于「我做得对」——先分清是纪律还是环境在保护你

**形状**:同一个操作,有人一直没出事、有人立刻中招。
如果把「没出事」当成「做法正确」的证据,就会得出两个错误结论:
①这个做法是安全的 ②出事的人比较粗心。**两个都错。**

**真实案例**(2026-08-14):mailbox 投递地址事故后,claude3 自查报告
「我今晚 13 封信零丢件」,但它接着写:

> 不是我守了规矩,是**我的执行环境每次工具调用都把 cwd 重置回主树**。
> **保护我的是环境,不是纪律。**所以我这条「一直没出事」不能作为做法正确的证据 ——
> 换成 cwd 持久的 shell(codex 那类),同样的操作立刻中招。
> 这也说明这次事故里出事的 agent 未必更粗心,可能只是环境不同。

这条直接推翻了「广播一条规矩就能防住」的想法:
对 cwd 持久的执行环境,**人记得住不代表每次都记得**。于是改成硬闸(拒绝执行),
而不是靠自觉。

**抓法**:
- 复盘时先问:**没出事的那些人,是靠纪律还是靠环境?**
  如果是环境,那这个"经验"不可复制,不能当最佳实践推广
- 同一份代码在不同执行环境下行为不同(cwd 是否持久、PATH、TTY、
  权限模式),**测试要覆盖最不利的那种环境**,不是开发者自己那种
- 事故归因不要停在「谁不小心」——先找环境差异

**同案还有一条**:第一版修复只封了**发信侧**(post.sh),
读信侧(read.sh/ack.sh)同族洞还开着,而且**读信侧的失败更阴险** ——
发信侧至少落了文件能考古;读信侧返回「no inbox」+ **退出码 0**,
连排查的起点都没有。**修一族洞时,把这条链路的两端都走一遍。**

## 第一节附:一个测试矩阵层面的系统缺口

⚠️ **V2 的 e2e 探针清一色用官方直连,而真实用户大量走中转(relay/openai_compatible)。**

模式 8 那个 bug 只有**中转把 function-calling 降级成 XML 文本模拟**时才产生 ——
也就是说**真实故障源根本不在测试矩阵里**。官方 API 再怎么测都测不出来。

建议单开一类必测场景:**低质中转的输出畸形**
- 工具调用被降级成 XML/文本模拟,解析残片落进正文
- 流被切断(半截回复)
- 空回复体但 HTTP 200
- HTML 错误页伪装成正常响应(401/402/429/504 各有先例)

`p0.py` 里已有 `relay-openai-compatible` 和 `hojimi-relay` 两个格子,
但它们验的是"能不能连通",不是"畸形输出会不会漏进用户视野"。

## 第三节:V2 的共用路径清单(该重点设防的地方)

按上表归纳,V2 上所有功能共同流经这几段。改动它们等于同时改动所有功能:

| 共用路径 | 代码 | 出过的事 |
|---|---|---|
| 上下文组装 | `v2/context.py`、`v2/prompt_frontier.py` | #1 #6 |
| 工具面裁剪 | `v2/tool_loop.py` | #2 #7 |
| 回复清洗出口 | `worker.py _on_reply`、`proactive/agent_protocol_v2.py` | #3 |
| 回复封装出口 | `worker.py` chat/wake 两处终点 | #4 |
| 加密边界 | 封装/解密两侧 | #5 |

⚠️ **注意 #4 的形状**:chat 和 wake **各写了一遍同样的逻辑**。
这类"同一逻辑两处实现"的地方,修必须两处一起,只改一处会留半个洞;
测试也必须两道都覆盖。

## 第四节:该写的测试(按优先级)

1. **真实尺寸工具面 × 各档窗口**(治 #1,模式 1+5)
   断言:各窗口下 `tool_schemas` 未被整份丢弃;发给 provider 的工具数 == 解析出的数
2. **两轮工具调用**(治 #2 #7,模式 2)
   断言:第二轮工具面**包含**平台工具与用户 MCP;一轮内可搜多个关键词
3. **provider 返回原生 reasoning 但无 `<think>`** × chat/wake 两道(治 #4,模式 3)
   断言:下发 payload 不带 thinking

## 模式 14:变异验证的基线选错了,会把真闸误判成纸糊的

**2026-08-14 我(Supervisor)在复验 T036 时踩的,而且差点据此打回一个正确的修复。**

变异验证的做法是「把修复的源码还原,测试必须变红」。问题出在**还原到哪个版本**:

```sh
# ❌ 我的做法:还原到当前 origin/test
git checkout origin/test -- backend/model_api_runtime/v2/worker.py
pytest -k tool_markup     # → 4 passed,看起来测试没守住

# ✅ 正确做法:还原到**修复提交的父节点**
git checkout <修复提交>^ -- backend/model_api_runtime/v2/worker.py
pytest -k tool_markup     # → 4 failed,真闸
```

**为什么第一种会骗人**:我做变异的那一刻,那个修复**已经通过 PR 合进 origin/test 了**
(PR#201,merge `ecd925c8`)。所以「还原到 origin/test」等于「还原到一个已经含修复的版本」——
什么都没变异掉。测试当然是绿的。

**判据(做变异时必须当场核实,不能假设)**:
变异之后立刻数一下被删掉的那个行为在不在:
```sh
git checkout <基线> -- <文件>
grep -c '<修复引入的那个调用>' <文件>     # 这个数必须比修复后少
```
今晚的实例:修复后 2 处调用,还原到 origin/test 仍是 **2** 处(说明变异无效),
还原到父节点是 **1** 处(说明变异生效)。**多花一条 grep,省掉一次误判。**

**同族**:本文件模式 10「把查不到当成没发生」、TESTING.md §6.1「先证明测量工具是好的」。
今晚这条是它们在**变异验证**这个具体动作上的化身:
`git checkout origin/x` 回答的从来不是「回到修复之前」,而是「回到 origin/x 此刻的样子」,
而 origin/x 是**会动的**。

## 模式 15:变异红了几条不重要,**红的是哪几条**才重要

**2026-08-14 claude4 在 T044 里提出的,我采纳并复现验证。**

我给的规矩是「变异基线用修复提交的父节点」(模式 14)。claude4 照做了,
结果 **12 failed** —— 数字很漂亮,但它自己指出这个数**信息量有限**:

> 里面大部分是 reader 从二元变三元的**签名噪声**,证明的是「接口变了」,不是「信号被锁住」。

**签名改动会让一大片测试红,而这些红和你要守的行为无关。**
一个只改了函数签名、根本没实现功能的假修复,同样能让那 12 条红 —— 于是变异验证被架空了。

**它的做法(比原规矩好,已成为新标准)**:把链路切成几段,**每段各做一次窄变异**:

| 变异点 | 期望 | 实得 |
|---|---|---|
| 出口处的推导强制 `False` | 只有"卡被截断"那条红 | 1 failed |
| 中间传递的 bool 强制 `False` | 两条都红 | 2 failed |
| 接线处 `tail_window=` 删掉 | 只有 lane 那条红 | 1 failed |

**三段各有独立的锁** —— 这才证明了信号从产生到落盘每一环都被钉住,
而不是"某处一改就有一堆东西红"。

我独立复现过其中一段:把 `serve_worker.py` 的 `profile_cards_truncated = any(...)`
改成 `= False and any(...)`,基线 55 passed → **1 failed**,
且失败的正是 `test_profile_card_truncation_reaches_provider_request_trace`。
**失败的测试名和被破坏的语义对得上**,这是窄变异最值钱的地方。

**判据**:
- 变异后**先看失败的是哪几条**,再看数量;名字对不上语义 = 你可能只是改坏了接口
- 一次变异红一大片 ⇒ 八成是签名噪声,**换更窄的变异点重做**
- 链路有 N 段,就做 N 次窄变异,**每次只切一段**

## 模式 16:测试自己把失败的证据删掉了

**2026-08-14 实际发生,代价是三个 agent 一晚上的工作换来"不可恢复"。**

T049 是一个约 33% 复现的 continuity 间歇失败。拿到两个红样本后想查那一轮的 trace
(有没有 `memory_write` 调用、最终进 provider 的消息里有没有目标词)——**证据没了**:

```
p0 teardown 删测试账号 → /v1/account/reset CASCADE
→ trace / trajectory / jobs 全清
→ 本地 orphan manifest 也随「成功 teardown」一起删除
```

**结构性后果**:E2E **每失败一次,就把诊断这次失败所需的一切删掉一次**。
于是:
- 间歇性失败**永远查不动** —— 只能重跑去撞下一次红,撞到时它又自杀一次
- **越罕见的失败(越可能是真 bug),证据越难留下** —— 这是最坏的偏向

**判据(写自动化测试时逐条问)**:
1. **这个测试失败时,我需要什么才能查清?那些东西在 teardown 之后还在吗?**
2. 清理逻辑是不是**无条件执行**的?失败路径应该**保留现场**,不是照常清理。
3. 失败信息里有没有告诉人**现场留在哪**?没有的话,留了也等于没留。
4. ⚠️ 反向约束:保留的现场往往含用户内容(哪怕测试账号),
   **落盘位置和清理策略必须一起定**,否则会变成无人清理的明文堆。

**同族**:模式 7「无信号故障」。区别在于 —— 模式 7 是信号从来没产生,
这一条是**信号产生了,然后被我们自己删掉**。后者更隐蔽,因为流程看起来完全正常
(teardown 成功、退出码 0、日志干净)。
