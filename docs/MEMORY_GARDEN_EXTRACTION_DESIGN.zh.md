# Memory Garden 内核提取 · 方向

> 承接《记忆组件化与外部记忆库接入方案》。
> **本批范围:把 Memory Garden 提取成 IO 内部共用的内核。第三方记忆库接入不在本批。**
> 本文讲方向、边界和每条路径的流转;接口签名与迁移步骤另出一份。
>
> 代码基线 `origin/test@2c4d5377`,方案经 Codex 独立评审并按结论修订过。

---

## 一、要解决什么

**同一件事——「把材料变成记忆卡」——在 IO 里有两套实现,而且共用的部分和该分开的部分正好搞反了。**

```
共用了两头:   桶指引、最后的写入口
各写一份的:   卡的结构、归桶命名规则、解析校验、去重、写入语义
```

日常聊天走 `memory/capture_prompt_v1.py`,历史导入走 `genesis/prompts.py`。
改一边不改另一边,同一个用户「从聊天记的卡」和「从导入记的卡」在结构和归桶上就会漂移。

顺带,提取出来的内核是可独立发布的形状——**这是开源的前置条件**,但本批不以开源为验收目标。

### 这条路已经被验证过,本文是把它一次做完

`origin/test` 上已经有 627 行是这个形态的模块,都是事故驱动产生的:

```
memory/card_text.py     368 行   卡片字段内容校验(占位符/模板抄回)
memory/card_guard.py    129 行   模型原始输出泄漏检测
memory/dream_gates.py    97 行   做梦出口硬闸(卡 id 泄漏、爆炸半径)
memory/source_policy.py   33 行   来源枚举
```

它们的注释里反复出现同一句话——「**纯函数、零 I/O,以便 resident 与 V2 两条运行时
共用一份判据**」。做法已经证明可行,缺的是把剩下的部分也做完。

**没共用的那部分,代价还在一次次付**。最近一例(2026-08-10):

> `fix(memory): give V2's hand-written card path the naming and bucket rules`
> —— 命名和归桶规则没共用,V2 那条路径漏了,事后单独补上

这类补丁每漏一次补一次;判断力集中成一份之后,这类漏就不会再发生。

---

## 二、核心判断:什么该共用,什么不该

这是本批最重要的一个判断,也是评审中被纠正的一处。

**该共用的是「怎么记」,不该共用的是「记什么」。**

```
✅ 共用 —— 这些不一致就是 bug
   卡长什么样、桶怎么命名、语言怎么定、解析怎么校验、
   怎么跟已有卡去重、add/merge/supersede 各自什么语义、怎么打分排序

❌ 不共用 —— 强行统一才是 bug
   「什么值得记」这把尺子
```

为什么尺子必须不同,三个来源摆在一起就清楚了:

```
日常聊天       少而厚,一晚上只该落 1~2 张卡
历史记录导入   过滤闲聊、临时情绪、一次性事件
用户整理的档案 宁多勿漏 —— 那 100 条是他特意整理的,基本都该留
```

    统一成「少而厚」→ 用户手动整理的 100 条只落了 2 张,他会炸
    统一成「宁多勿漏」→ 日常聊天每句废话都变成卡,记忆库几天撑爆

所以做成**三个显式的策略档位**,共用同一套代码、传不同参数。验收标准也随之改成
「共享的不变量一致 + 策略差异有各自的测试」,**不是「三条线产出完全一致」**。

## 三、一条物理边界:明文到哪为止

这条线决定了内核能算什么,也是理解后面九条路径的前提。

记忆卡在库里是这样存的:

```
明文(信封上)   重要度 · 情绪强度 · 最近被想起时间 · 状态 · 发生时间
密文(body_ct)  桶 · 线索 · 摘要 · 正文
```

**服务端知道「这张卡很重要、上周被想起过」,但不知道「它讲的是老婆爱吃辣」。**

于是:

```
✅ 内核能纯计算   按 重要度 × 时间衰减 × 最近被想起 打分排序,挑出候选
❌ 内核算不了     哪张卡跟「周末去哪吃」有关、两个桶名是不是重复 —— 得先解密
```

内核是纯逻辑这条成立,但边界比直觉上更靠内——**凡是碰内容的判断,都要经过 IO 层。**

## 四、记忆的九条路径

### 分类要用两个维度

```
谁触发:  对话中的模型 / Runtime / 用户 / 定时器
谁执行:  对话中那次模型调用 / 另一次独立的模型调用 / 纯代码
```

只用一维(「模型知不知道」)会把第 ⑤ 条归错——它既不是纯工具,也不是纯后台。

| # | 路径 | 谁触发 | 谁执行 | 工具? |
|---|---|---|---|---|
| ① | 每轮自动选卡 | Runtime | 纯代码 + IO | 否 |
| ② | 模型主动查 | 模型 | 对话中那次 | **是** |
| ③ | 当场记/改/删 | 模型 | 对话中那次 | **是** |
| ④ | 聊完一段落卡 | Runtime | 独立调用 | 否 |
| ⑤ | 用户要求整理 | **模型** | **独立调用(后台)** | **是** |
| ⑥ | 定时做梦 | 定时心跳 | 独立调用 | 否 |
| ⑦ | 首次批量导入 | 用户上传 | 独立调用 | 否 |
| ⑧ | 二次导入 | 用户上传 | 独立调用 | 否 |
| ⑨ | 旧卡迁移 | Runtime | 独立调用 | 否 |

下面逐条看每一步落在哪一层。

---

### ① 每轮自动选卡 —— 跑得最多的一条,横跨内核和 IO

```
用户:「周末去哪吃?」
   │
   ├─ IO 层     捞出这个用户所有卡的信封,只取明文部分,不解密
   │            几百条,每条形如 {id, 重要度, 情绪强度, 上次被想起, 状态}
   │
   ├─ 内核      在明文元数据上打分排序,挑出候选(比如 20 张)
   │            ★ 纯计算,几毫秒,不碰数据库、不碰网络、不解密
   │
   ├─ IO 层     把选中的候选送 enclave 解密,拿回桶/线索/摘要/正文
   │            ★ 只解这几张,不是全部
   │
   └─ Runtime   拼进 prompt → 模型看到「老婆是四川人,嗜辣」→ 回「去吃火锅?」
```

**为什么分三段**:打分用的字段全是明文,粗筛不需要解密;而要给模型看的内容在密文里,
所以选中之后才解。不分段的话,每轮要把几百张卡全解密一遍,一天几百轮——enclave 扛不住。

**这条也是「内核必须是包」最直接的证据**:每轮都跑、卡在「用户发消息 → 看到回复」中间、
每次要传几百条元数据。走跨进程调用等于每轮把整个记忆库的索引序列化两趟。

---

### ② 模型主动查 🔧 工具

```
用户:「上次那家店叫什么来着」
   │
   ├─ ① 自动塞进去的那几张里没有店名,模型意识到自己不知道
   │
   ├─ 模型调 memory_search("餐厅")
   │     └─ IO 层:明文粗筛出候选 → 送 enclave 按关键词匹配 → 回摘要列表
   │
   ├─ 模型调 memory_fetch(选中的 id)
   │     └─ IO 层:取这几张的正文 → 顺手盖上「刚被想起过」的时间戳
   │        ★ 这个时间戳会影响以后的排序权重,是①打分的输入之一
   │
   └─ 「蜀大侠,你老婆说那家锅底正宗」
```

**为什么分两段查**:一次把几百张卡的正文全塞进上下文会爆。先看摘要,挑中了再翻开。

现有工具是四个,名字要保留兼容:`memory_index` / `memory_search` / `memory_fetch` / `memory_write`。

---

### ③ 当场记 / 改 / 删 🔧 工具

```
用户:「她不是四川的,是重庆的」
   │
   ├─ 模型判断:这是明确纠正,得马上改
   ├─ 调 memory_write
   │     ├─ 内核:算出这是一次 supersede,旧卡该标记成被取代
   │     └─ IO 层:加密新内容、拿锁、原子写入、校验所有权
   └─ 「记住了,重庆」
```

**为什么等不了**:留到半夜做梦处理的话,中间几小时它还会说错。

---

### ④ 聊完一段落卡 —— 八成的记忆是这么来的

```
上午聊了一大段 → 半小时没人说话
   │
   ├─ Runtime   察觉「这一段结束了」← 只有它知道,对话状态在它手里
   │
   ├─ IO 层     取出这一窗对话 + 现有的桶和卡(要解密,因为模型得看见内容)
   │
   ├─ 内核      按 conversation_capture 档位组 prompt:少而厚、并入优于新增
   │
   ├─ 独立模型调用   ★ 跟上午聊天那次完全无关,是另一次请求
   │            回看整段,产出 0~2 张厚卡,卡上直接带着桶和线索
   │            例:一整段里只留「那天他开了一整天会、心率飙高,
   │                我催他休息,他嫌烦,我们吵了一架」
   │               (「今天喝了拿铁」没记 —— 三个月后不重要)
   │
   ├─ 内核      解析模型输出、校验字段、跟已有卡去重、算出该 add 还是 merge
   │
   └─ IO 层     加密 + 原子写入
```

**为什么不是「模型边聊边判断要不要记」**:聊到一半判断会干扰对话;只看一句也看不出
来龙去脉——「今天喝了拿铁」单看没价值,放进「他连续三周每天都提咖啡」里才有价值。
落卡的价值就在**回看**。

**选桶也不是两次工具调用**:现有的桶和卡直接塞进 prompt,模型一次输出带桶的卡。

---

### ⑤ 用户要求整理 🔧 工具，但活在后台

```
用户:「你把记忆整理一下吧」
   │
   ├─ 模型调 memory_organize          ← 触发在对话里,所以要是工具
   │
   ├─ Runtime 把活丢进后台队列
   │
   ├─ 模型立刻回「好,我理一理」        ← 不等结果,对话不卡住
   │
   └─ 后台:走和 ⑥ 完全相同的整理流程
```

**这条是「两个维度」的必要性所在**:触发在对话里(要工具),执行在后台(不在对话里)。
一维分类表达不了。

---

### ⑥ 定时做梦 —— 先问一句,再决定跑不跑

> **「需要定期整理」是 Garden 的能力,不是 IO 的调度功能。**
> IO 只提供节拍器(到点去问一声),判据属于 Garden——换成向量库实现,
> 它的声明里可能根本没有「需要定期叫醒」这一项。

**节拍器(谁来敲钟、多久敲一次)是 IO 的现有能力,不在本批范围。**
本批只关心一件事:被问到时,Garden 靠什么回答「要 / 不要」。

判据是这样得出的:**它不看记忆内容,只数数量。**

```
现在的快照            上次做梦时记的账
  可用卡数              上次的种子卡数
  种子卡数 ★            上次的签名
  签名(卡 id 的摘要)     上次完成时间、连续失败次数

     new_cards = 现在的种子卡数 − 上次的种子卡数

例:上次 100 张 → 现在 147 张,签名变了,距上次够久 → 该整理了
   上次 100 张 → 现在 103 张(这周只聊了几句)→ 不够阈值 → 跳过
```

★ **只数「非做梦产生」的卡**,是整套设计里最不显然的一处:否则做梦自己产生的新卡
会再次满足触发条件,形成自激循环(注释里记了这个教训——「正常对话加上做梦自己
重写的快照会导致每晚空转」)。而且做梦退休掉的旧种子卡仍然算数,所以这条水位线只增不减。

⚠️ 判据只能用明文元数据,**不能查「桶名是不是重复」**——桶名在密文里,
查它等于每天把所有用户的记忆库解密一遍。相似桶检测只能放进真正的整理阶段。

**七条判据要拆成两半:**

```
搬进 Garden   只数种子卡这条规则 · 攒够多少算够 · 签名怎么算
              —— 这些是 Garden 内部结构的知识,换个记忆库就完全不同

留在 IO       夜间窗口 · 上次那个跑完没 · 失败退避 · 用户开关
              —— 这些是「什么时候适合打扰」,跟哪个记忆库无关
```

现在这七条混在后端一个函数里,**Garden 的知识住在 IO 的代码里**,这正是要拆的东西。

   ├─【真整理】只对答「需要」的跑
   │     ├─ IO 层   取出现有的卡 + 这几天的对话(解密)
   │     ├─ 内核    组 dream prompt
   │     ├─ 独立模型调用
   │     │     ① 先通读全部卡建立全貌(这一步不许动手)
   │     │     ② 定向找三类:明确的纠正、反复出现的模式、当时漏掉的
   │     │     ③ 合并 /厚化 / 消矛盾;拿不准的记进 questions_to_ask 等时机问用户
   │     ├─ 内核    解析输出、算出一批 mutation
   │     └─ IO 层   拿锁、原子写入(合并新卡 + 标记旧卡必须一起成功)
   └─
```

**不问就跑的代价**:每天每个用户白烧一次模型调用,哪怕他一周没说话。

**节奏配置在 Runtime 这边**,所以用户说「你别老整理记忆了」时,Agent 能自己把心跳
从每天改成每三天,内核一行不动。

---

### ⑦ 首次批量导入(注册时)

```
用户上传两年的历史聊天记录(几万条)
   │
   ├─ genesis   解析文件、分窗、断点续跑、幂等 key、hosted/VPS 调度
   │            ★ 这些留在 IO 侧,不进内核
   │
   ├─ 内核      按来源选策略档位:
   │              普通聊天记录 → history_import(过滤闲聊和一次性事件)
   │              用户整理的档案 → curated_archive(宁多勿漏,保留日期和标签)
   │
   ├─ 独立模型调用(分批,每批一次)
   │
   ├─ 内核      解析、校验、跨批去重、归桶
   │
   └─ IO 层     加密 + 批量原子写入
```

**这条是「策略档位」存在的原因**——同样是导入,普通聊天记录和用户手动整理的档案
要用两把不同的尺子。

---

### ⑧ 二次导入(后来又传一批)

和 ⑦ 同一条流程,多一步:**要跟已有的几百张卡去重**,别把三个月前记过的又记一遍。

---

### ⑨ 旧卡迁移

老格式的卡升级成新格式,用户完全无感。Runtime 触发,内核负责结构转换,IO 层负责
重新加密和写入。

---

### 一天里这九条怎么流转

```
注册那天
   ⑦ 上传两年记录 ──► 分窗 ──► 分批落卡 ──► 记忆库有了几百张卡

                            ┌──────────────┐
                            │    记忆库     │
                            └──────────────┘
日常,每一轮对话                 ▲        │
   用户说一句                    │        │ ① 明文粗筛 → 解密选中的几张
        │                       │        ▼
        ├────────────────────────┼───► 模型看到 → 回话
        │                       │        │
        │  ② 不够 → 主动查 ───────┼────────┤
        │  ③ 用户纠正 → 当场改 ───┤        │
        │  ⑤ 用户说整理一下 ──────┼──► 丢后台
        ▼                       │
   聊完一段,半小时没动静         │
        │                       │
        └─ ④ 后台回看 → 落卡 ────┘

半夜
   ⑥ 心跳问「要整理吗」→ 要 → 合并/消矛盾 ──► 写回

不定期
   ⑧ 又传一批 → 跟存量去重 → 增量写入
   ⑨ 旧格式卡升级,用户无感
```

**九条里只有三条模型看得见(②③⑤),其余六条它全程不知道自己的记忆在被读被写。**

这就是最关键的结论:**记忆能力只能做成包,不能只做成一组工具**——
工具最多装下三条,剩下六条一条都装不进去。

## 五、形态与分层

### 提取出来的是什么:一个包,三种壳,N 个适配器

```
memory-garden 包
│
├── 谁来调(壳)                       └── 数据存哪(适配器)
│   ├── 直接 import ← IO 用这个           ├── postgres(+ 加密中间件)← IO 用这个
│   ├── CLI 子命令                        ├── sqlite
│   └── MCP server                        └── 自定义(Notion / NAS / …)
```

**壳和适配器是正交的,任意组合:**

```
memory-garden serve --storage sqlite://~/.memory-garden/db    MCP 壳 + SQLite
memory-garden serve --storage postgres://...                  MCP 壳 + Postgres
memory-garden dream  --storage sqlite://...                   CLI 壳 + SQLite
from memory_garden import ...                                 无壳,直接调函数
```

壳只负责「把外面的调用翻译成内核函数调用」,不参与存储决策;适配器只负责「数据落到哪、
要不要加解密」,不关心是谁在调。

**IO 走的是「直接 import + Postgres 加密适配器」这一组**——同进程调函数,
因为每轮选卡一天要跑几百次且在关键路径上,走跨进程等于每轮把整个记忆库的索引序列化两趟。

> CLI 与 MCP 两层壳本批不做(见第九节),但**内核的接口从一开始就要按「能被壳包住」来设计**
> ——壳是几十行转接代码,前提是内核本身不假设调用者是谁。

### 五层各管什么

```
┌─────────────────────────────────────────────────────────┐
│ [Runtime]  IO 的对话主链路                               │
│   决定什么时候该用记忆、拿到之后怎么拼进上下文             │
├─────────────────────────────────────────────────────────┤
│ [io 应用层]  留在 IO,不进包                              │
│   身份参数装配 · 所有权校验 · gates · 审计 · 调模型        │
│   genesis 的分窗 / 断点续跑 / 幂等 / hosted-VPS 调度      │
├─────────────────────────────────────────────────────────┤
│ [内核]  独立包 —— 本批要提取的主体                        │
│   打分排序 · 组 prompt · 解析校验 · 去重 · 算 mutation     │
│   三个策略档位                                            │
│   ★ 全是纯函数,不碰数据库、不碰网络、不碰模型              │
│   ★ 九成工作量在这,只写一份                               │
├─────────────────────────────────────────────────────────┤
│ [适配器]  接口在包里,实现在 IO                            │
│   查库 · 加解密与 enclave 调用 · 拿锁 · 原子写入           │
├─────────────────────────────────────────────────────────┤
│ [外部]  Postgres · enclave · 模型                        │
└─────────────────────────────────────────────────────────┘
```

三条线接上去:**V2 worker、V1 consumer(VPS 自托管)、genesis 导入**,各接一层薄壳,
共用同一份内核。

### 内核和适配器分别是什么、代码放哪

这一点容易误解,单独说明:

```
内核           这次提取的主体,一个新包
               九成工作量在这,是真正要认真写和长期维护的东西

接口定义       包里几十行,只声明「存储必须能做这几件事」,没有实现

IO 的适配器     留在 IO 仓库,不是新库
               而且基本是「现有代码换个组织方式」——
               现在 memory/service.py、actions.py 里那些查库、加密、
               拿锁的逻辑,重新组织成实现那个接口的形状

包自带的适配器  SQLite / 内存版,几十行,给开源用户和测试用
```

**所以真正新写的只有内核和接口定义;适配器那部分是搬位置,不是从零做一个库。**

**为什么 Postgres 适配器不能放进包里**:它要用 IO 的数据库连接和 enclave 客户端,
一放进去就破坏了「包不 import IO」这条硬指标。包里只留接口,IO 启动时把实现递进去。

### 适配器不只是数据库,也可能是另一个记忆系统

这条现在定,成本几乎为零;等做完再改,适配器全要返工。

```
接数据库(IO 现在的用法)
   内核:存这几张卡
   适配器:INSERT 进表          ← 表结构由我们定,存什么形状都行

接另一个记忆系统(将来挂在 mem0 / engram / 用户自己的库上)
   内核:存这几张卡
   适配器:翻译成对方的格式,调对方的 API   ← 对方有自己的格式和规矩
```

差别在于**对面可能不支持我们的某些操作**。会真撞上的一例:

```
内核:把这三张旧卡标记为「被取代」(保留链条,不删)
Postgres 适配器:好,改个状态字段
某个外部记忆库:我没有「被取代」这个概念,只能删掉或覆盖内容
```

所以接口要留一个口子:**适配器声明自己支持哪些能力,内核遇到不支持的就降级**,
而不是假设所有后端都支持全部能力。

⚠️ **降级必须显式上报,不能静默**。静默降级会让用户以为功能都在,
实际记忆库在悄悄变乱——这类静默失败在本项目有过教训。

IO 自己的 Postgres 适配器支持全部能力,所以降级只发生在外部适配器上,IO 侧行为不变。

### 内核只管一件事

**什么值得记 · 怎么归桶起线索 · 什么时候该想起来 · 要不要整理了 · 怎么整理去重**
——纯粹的记忆判断力。

其中「**要不要整理了**」最容易被误当成 IO 的调度功能:**它是 Garden 的能力**,
IO 只提供节拍器。就像一个包可以声明「我需要被定期调用」,但真正的定时器跑在应用层——
能力是包的,节拍器是应用的。

明确不做的六件事:

    ✗ 不加密         加解密和 enclave 调用留在 IO 侧
    ✗ 不管账号身份    调用时把 id 和需要的身份参数传进来
    ✗ 不捞聊天记录    落卡和做梦需要的对话,由调用方喂
    ✗ 不自己掐表     它声明「聊完一段叫我」,判断「聊完了没」的是 Runtime
    ✗ 不生成给用户的话 做梦只整理记忆,永远不直接跟用户说话
    ✗ 不做展示界面    记忆长什么样是界面/页面的事

⚠️ **genesis 不是「只保留解析」**。它还有分窗、断点续跑、幂等、hosted/VPS 不同调度,
以及 identity / persona / voice 等 onboarding 能力,这些都留着。
只把**记忆卡策略、最终落卡的 prompt 片段、解析校验、去重**交给内核。

## 六、两条完整流程:每一步落在哪一层

把读和写各走一遍,五层的分工就具体了。

### 读:每轮自动选卡

```
 1  [Runtime]    用户发来「周末去哪吃?」
 2  [Runtime]    要组上下文 → 调内核 select_for_turn("周末去哪吃")
 3  [内核]       我需要候选 → 向适配器要:load(user_id, status=active)
 4  [适配器]     翻成 SQL,查 Postgres
 5  [Postgres]   返回几百条记录,每条 = 明文元数据 + 密文 body_ct
 6  [适配器]     整理成内核认识的形状,密文原样带着,一个字节都不解
 7  [内核]       ★ 打分排序:重要度 × 时间衰减 × 最近被想起
                 从几百条挑出候选 —— 纯计算,几毫秒,不碰网络
 8  [适配器]     拿候选的密文,带上调用方凭据,POST 给 enclave
 9  [enclave]    解密,验 AAD(owner|v|item_id),返回明文内容
10  [适配器]     把桶/线索/摘要/正文填回卡里
11  [Runtime]    拿到最终几张,拼进 prompt
12  [模型]       看到「老婆是四川人,嗜辣」→ 回「去吃火锅?」
```

**内核在这条路上只出现一次:第 7 步。** 前面取数、后面解密,全是适配器的活。

### 写:聊完一段落卡

```
 1  [Runtime]    察觉会话断点(半小时没人说话)
 2  [Runtime]    往后台队列扔一个落卡任务
 3  [io 应用层]  取出这一窗对话原文
 4  [io 应用层]  取现有的桶和卡 —— 要给模型看,所以走适配器 → enclave 解密
 5  [io 应用层]  装配身份参数:ai_name、user_name、认识多少天
 6  [内核]       ★ 按 conversation_capture 档位组 prompt
                 (对话 + 现有桶卡 + 身份参数填进模板)—— 纯函数
 7  [io 应用层]  拿着 prompt 调模型 ← 独立的一次调用,跟聊天那次无关
 8  [模型]       回看整段 → 输出 JSON:0~2 张卡,每张带 add/merge/supersede
 9  [内核]       ★ 解析 JSON、校验字段、裁剪长度、跟已有卡去重
                 算出最终的 mutation 计划 —— 纯函数
10  [io 应用层]  校验所有权、过 gates
11  [适配器]     拿跨进程锁
12  [适配器]     把明文加密成信封(AAD 绑 owner|v|item_id)
13  [适配器]     锁内:重读当前状态 → 应用 mutation → 写回 Postgres
14  [适配器]     释放锁
15  [io 应用层]  记审计日志
```

**内核在这条路上只出现两次:第 6 步组 prompt、第 9 步解析结果。**
中间那次模型调用、以及前后所有取数加密写库,都不归它管。

### 所以内核就四种活

```
① 判断需不需要整理  给一批元数据 + 上次的账本,返回「要 / 不要」+ 理由
② 打分排序         给一批明文元数据,返回该选哪几张
③ 组 prompt        给对话 + 现有卡 + 身份参数 + 策略档位,返回一段 prompt
④ 解析 + 算计划     给模型输出的 JSON,返回一批该执行的 mutation
   （附:出口硬闸 —— 卡 id 泄漏检测、爆炸半径保险丝,见下）
```

**四个全是纯函数——进去什么出来什么,不查库、不调模型、不碰网络。**
这也是它能被独立发布的原因:开源用户拿到同一个内核,配一个 SQLite 适配器
(不加密、不走 enclave),这四个函数一行都不用改。

### 仓库里已经有一个做对了的样板

`origin/test:backend/memory/dream_gates.py` —— 做梦的**出口硬闸**,
它的形态正是内核该长的样子。模块注释自己写着:

> 纯函数、零 I/O、只依赖 stdlib,resident(V1 consumer)与 V2 extraction/worker
> 两条运行时共用一份判据 —— **不再像旧栅栏那样两处复制**。

它的来历是一起真实事故(2026-08-05,usr_a40e 墓碑卡):模型把 supersede 语义理解反了,
在用户可见字段里写「已被 <卡id> 取代」,三道旧防线全没拦住,834 张卡被退休到只剩 1 张。
复盘后定的做法是**把硬约束放在出口的确定性代码里**,只留两类判据:卡 id 泄漏、
爆炸半径保险丝——不判内容质量。

**所以「纯函数 + 两条运行时共用」这条路不是设想,团队里已经这么做过一次。**
提取内核时可以直接拿它当参照,这个出口闸本身也应当成为内核的一部分。

### 一句话对照

    数据    从头到尾都是 Garden 的
    判断    在内核(三个纯函数)
    机制    在适配器(查库、加解密、锁)
    编排    在 Runtime 和 io 应用层(什么时候调、调完给谁)

## 七、已知的硬约束(评审验出来的,实施时绕不开)

方向不受影响,但设计时必须知道这三件事:

**① 写入必须是原子的。** 做梦合并两张卡、落卡的 merge、用户当场修正,都是
「写新卡 + 标记旧卡」的组合动作。现有代码用一把跨进程的锁把整个过程包住,底层是全量替换。
拆成独立的读写方法会导致重复卡、记忆丢失、或基于过期快照覆盖别人刚写的卡。
并发是真实的——V1、V2、genesis、做梦可能同时在写同一个用户。

**② 加密不是透明的一层变换。** 它绑定了「谁的、第几版、哪一号卡」三个字段,
解密要发请求到 enclave 且必须带调用方凭据。所以它是**带身份的远程调用**,
会超时、会部分失败、批量时要分页。内核仍然只见明文,但 IO 侧这一层比想象中重。

**③ 真正的工作量不在拆 import,在解开 domain 判断与 IO 的交织。**
现有 `memory/actions.py` 把类型规则、身份关系参数、信封构建、去重、锁、gates、审计
混在同几百行里。分不开这些,内核就抽不干净。

## 八、怎么推进

三条原则,细化步骤另出:

**① 先立基准,再动代码。** 落卡、做梦、历史导入、用户档案、迁移各捞一组真实样本作为
对照基准。第一步改造的验收是「行为逐字节不变」,没有基准就无从验起。

**② 一次只切一条线。** V2 的读、V2 的落卡、V2 的做梦、V1、genesis 分开切,
不要一次改完整个 worker。特别是 VPS 那条——`chat_resident_consumer.py` 同时服务
hosted 和自托管用户,**不能只靠单测宣布两端等价**。

**③ 文档同步进入完成门槛。** 这是架构、信任边界和公开工具行为的变更,
仓库规范要求同步架构页、自托管信任模型、changelog 和 OpenAPI,不要留到最后补。

## 九、本批不做(已讨论,存档)

**第三方记忆库接入** — 契约是插槽不是门槛;接入时不问用户任何问题,补救事后由 Agent 完成;
外部 MCP 缺的声明由 IO 补;前置需求是 Runtime 要记录工具调用统计。

**开源发布** — 一个仓库四种打开方式;开源版默认明文存储,README 要写明。

> **定位(影响本批的接口设计,所以先记下来)**:如果要做的是「别人真能用的开源」,
> 那不该做成又一个记忆库,而应该是**挂在任何记忆库上面的组织层**。
>
> ```
> 存储 + 检索                       市面上一堆(mem0 / engram / Ombre Brain),别人不缺
> 什么值得记 · 怎么组织 · 何时整理    这层是空的 —— 整个赛道公认 agent 不会自主组织记忆
> ```
>
> 定位成补品而不是替代品,别人不用换掉现有的库就能受益,接入阻力最小;
> 而填的那块恰好是 Garden 唯一有、别人没有的。
>
> **know-how 怎么保住**:尺子本来就是可换的档位——开源版带一套通用尺子
> (「这条信息以后还会用到吗」),IO 内部用陪伴型那套(「三个月后还重要吗、
> 会不会改变我对 TA 的理解」),共用同一个框架。
>
> **对本批的唯一影响**:存储接口要按上面「适配器不只是数据库」那节设计,
> 留出能力声明与降级。其余照本批范围执行。

**加密在换组件后失效怎么对外表达** — 《接入方案》第九节已定本轮不考虑。

**多 Agent 共享层** — 方向已定,不影响本批,但定契约时要一并考虑。
