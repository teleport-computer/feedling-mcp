## 一、这个插件是什么

一句话：**给任何 agent 装上眼睛和分寸感。**

```
之前：一个普通 agent    你不说话，它永远不知道你在干嘛，也永远不会先开口
之后：装上这个插件      你走到公司，它知道；昨晚没睡好，它知道；
                        它还知道什么时候该说一句、什么时候该闭嘴
```

打个比方：**插件是「眼睛和分寸感」，agent 是「这个人本身」。**
眼睛看到什么、值不值得张嘴 —— 插件管；真张嘴说什么话、什么语气 —— agent 管。

### 为什么值得单独做一个插件

动手前扫了一圈现有生态：

```
采集 + 被动查询    一堆。health-export-mcp（190 个 HealthKit 指标）、
                   FreeReps（Apple Watch + Oura 自托管 + MCP）、apple-health-mcp……
                   全是「agent 问、它答」

主动开口           ProactiveAgent（45 星）：只看对话节奏决定该不该说话，
                                            不看任何现实世界信号
                   ContextAgent（arXiv 2505.14668）：用可穿戴数据判断该不该主动
                                            服务，是论文原型，不是能装的库

两边接起来的       没有
```

所以**采集不是卖点**（别人做得比我们全），**「信号变了 → 该不该打断人 → 怎么说才不像监控」这条链才是**。采集要带，但它的角色是「让插件开箱能跑的电池」，不是招牌。

参考：https://github.com/leomariga/ProactiveAgent ·
https://arxiv.org/abs/2505.14668 ·
https://github.com/PhilipAD/health-export-mcp ·
https://github.com/meltforce/FreeReps

## 二、插件干哪些事

三件，缺一不可。**只做第①件的库满街都是，②③才是这个插件的价值。**

### ① 感知：22 类信号

```
不用授权   现在几点 · 电量 · 有没有在共享屏幕
要授权     在哪儿 · 在动还是坐着 · 下一场日程 · 在听什么歌 · 专注模式 ·
           刚打开了哪个 app · 天气 · 刚拍的照片 · 提醒事项 ·
           睡眠 · 运动 · 心率 / 体重 / 血糖 / 经期 / 心情 / 活动量
```

每类都有**保质期**（位置 15 分钟、睡眠 24 小时）。过期就变 null，
**agent 看到 null 一律当「不知道」，不许猜**。

**原始值永不外泄**：经纬度算完「公司」两个字就当场扔掉，WiFi 名字变成「已知网络」，
app bundle id 变成「社交类」。agent 只看得到标签。

### ② 主动叫醒：判断什么时候值得打断人

不是每次上报都叫醒。目前只有这几件事算「值得打断你」：

```
到了一个新地方 · 拍了张照片 · 开始/结束共享屏幕 · 手机放了半小时以上又解锁
```

心率、走路、听歌**故意不叫醒** —— 变得太频繁，一叫就是骚扰。

叫醒之前还要过三道闸：

```
去抖冷却     1 分钟内同一件事别叫第二遍（手机抖一下不算新事）
安静时段     深夜别叫（可配置）
每日上限     一天最多打扰几次（可配置）
```

### ③ 被动查询：给 agent 一组工具

叫不叫醒是一回事，**agent 想主动查的时候得查得到**：

```
perception.now / location / weather / motion / calendar / focus / audio_route
perception.recent_apps        最近开过哪些 app（当前 app 那个字段答不了轨迹问题）
perception.sleep / workout / vitals / activity / body / metabolic / cycle / mood
perception.trend / history    最近 N 天的趋势和逐日数据
```

这条路**跟"打断"无关**——你问它答。所以就算把性格调成"闷葫芦"（永不主动开口），
这些工具照样能用。

## 三、怎么切分（核心）

### 判据：一句话

```
换一个 agent 装上去，这件事该不该跟着变？

不该变 → 插件      「从家到公司算一次变化」，换谁装上都一样
该变   → 消费方    「他正忙着跟我说话呢」，只有 agent 自己知道
```

### 插件 · 核心（不可替换）

```
能力表             有哪些信号 · 字段名 · 保质期 · 哪个字段归哪个能力
上报解析校验       字段形状、非法值、过期即 null
变没变的判据       心率跳两下不算变，从家到公司算变
去抖冷却           手机抖一下不许连叫两遍
值不值得打断       哪些事件算叫醒源
时钟上的分寸       安静时段 · 每日上限 · 距上次多久
一瞥的形状         只出是 / 否，不出数值
读法说明书         别念数字 · 一次别说太多 · 信号偏低时更轻
历史计算           rollup · 趋势 · 什么算「显著变化」
perception_* 工具  名字 · 参数与结果契约 · handler · 字段投影 · 权限判据
```

### 插件 · 电池（自带默认，可整块换掉）

```
存储      SQLite（默认）        ← IO 换成自己那套 Postgres + 加密
上游      iOS 快捷指令包 / Swift 采集 SDK / 手环适配器
性格      陪伴型（默认）/ 助手型 / 闷葫芦
上报端点  挂到宿主的 HTTP 服务上
```

### 消费方（插件完全不碰）

```
账号 · 鉴权 · 多租户
加密与 enclave                 IO 特有，插件里连这个概念都不该有
对话上的分寸                   他正在跟我说话 / 刚聊完五分钟 /
                               连着三条主动消息都没理 —— 插件看不见这些
叫醒之后的工程                 入队 · 并发 · 幂等 · 失败退避
prompt 放哪一层                V2 特意放 assistant role 防伪装成用户消息，
                               那是 runtime 协议，不是感知的事
调模型 · 说什么
界面                           设置页 · 权限引导文案
总工具目录怎么拼 · 工具预算 · 出站隐私栅栏 · trace
```

### 五个容易切错的地方

```
① 三种「别烦我」，长得像，归属不同
   插件   「1 分钟内同一个地点别重复叫」   噪声，换谁装上都不该重复
   插件   「凌晨 2 点别叫我」              时钟上的分寸，做成配置
   消费方 「他正忙着跟我说话呢」           对话状态，插件根本看不见

② 权限
   插件   「step_count 归 steps 管，不归 vitals 管」   字段归属，不该变
   消费方 「这个用户到底授权了没」                     有账号系统的是它

③ 照片
   插件   「拍照算叫醒源」「30 秒内连拍算一张」
   消费方 「照片字节存哪、谁能解密」

④ prompt
   插件   说明书写什么
   消费方 放哪一层、怎么跟其它上下文拼
   ★ 插件必须把「可信的静态说明书」和「不可信的感知事实」分成两个字段返回，
     不能拼成一段字符串让消费方直接塞进 system prompt

⑤ 工具
   插件   感知工具的名字、契约、handler、权限判据
   消费方 总目录怎么组合、预算、隐私栅栏、trace
   ★ 现在的 tool_catalog 里混着 memory / screen / send_message / schedule，
     整块搬进感知插件就违反了上面的边界
```

## 四、怎么用（核心）

### 接入长什么样

```python
from perception import Perception

p = Perception(
    preset      = "companion",          # 性格，不给就是陪伴型
    storage     = MyEncryptedStore(),   # 不给就用自带的 SQLite
    resolve_user= my_auth,              # 先鉴权、再解析用户
    on_wake     = my_wake_handler,      # 插件说「该开口了」时走这里
)

app.mount("/perception", p.routes())    # ① 上报入口，不用自己写接收逻辑

glance, howto = p.glance(user_ctx, now) # ② 每轮拿一瞥 + 读法说明书

tools += p.tools()                      # ③ 注册感知工具
```

### 三栏契约（别只说"三个钩子"）

```
① 消费方要实现的回调
   resolve_user(request) -> user_context
       先鉴权、再解析用户。插件只拿一个不透明句柄，不碰账号
   on_wake(WakeEvent) -> WakeReceipt
       插件说「该开口了」→ 你做最终对话闸、入队，然后回执

② 消费方要调用的插件 API
   glance(user_context, now) -> (一瞥, 说明书)
   tools() / 各 perception_* 工具的调用

③ 消费方必须注入的适配器
   存储适配器      读写状态 / 历史（IO 这边还要加解密）
   采集入口        上报从哪来
   配置与时区      性格 · 安静时段 · 用户的 IANA timezone
```

**为什么要回执**：插件放行之后，消费方还会因为「他正在跟我聊天」再拒一次。
如果插件在回调**之前**就把冷却和每日额度扣掉，消费方一拒、或者入队失败，
额度就白烧了。

```
WakeEvent    稳定的 wake id · 触发源 · 原因 · 发生时间 · 有界的上下文
WakeReceipt  accepted / conversation_suppressed / enqueue_failed

★ 只有回执是 accepted，插件才提交「已打扰」的冷却和每日额度
★ 同一个 wake id 重试必须幂等
```

**凭据不进插件**：IO 要解密得带调用方凭据，但那是存储适配器自己的事——
插件只传 `user_context`，适配器从请求上下文里取。插件里连「凭据」这个概念都不该有。

**关键分工**：插件说的是「**该开口了，因为他刚到公司**」，

### 流程二：你主动问它

```
你：「我最近睡得怎么样？」
   │
   ▼
【消费方】 这个得查 → 调插件的工具
   │
   ▼
【插件】   跟存储要最近两周的睡眠 → 算出趋势：比上周少了
           ★ 插件自己不带数据库，只说「帮我捞出来」

## 五、配置

### 分三层，越往下越少人碰

```
第 1 层  性格          一行定 80% 的人
         preset: companion    陪伴型（IO 用这个）
                 assistant    助手型：少打扰，只在明确有用时开口
                 silent       闷葫芦：只感知不主动开口，纯给工具查

第 2 层  全局旋钮      五六个，人人会调
         存哪儿 · 启用哪些信号 · 安静时段 · 一天最多打扰几次

第 3 层  逐信号覆盖    高级，按需
         location.debounce_sec: 300      默认 60，我这场景不想这么灵
         photos.wake: false              拍照别叫我
         health_sleep.ttl_sec: 172800    我手环两天才同步一次，别当过期
```

性格差在哪，一个例子：

```
深夜 + 在听悲伤的歌 + 昨晚没睡好
   陪伴型   「还没睡啊」
   助手型   不吭声 —— 这不算一件「有用」的事
   闷葫芦   永远不主动说，但你问它「我最近睡得怎么样」它答得出来
```

### 用户级配置是另一码事

```
部署级（接入方在配置文件里定）    性格 · 存哪 · 启用哪些信号 · 阈值
用户级（终端用户在 app 里点的）   我不想让它看健康数据 · 别在深夜叫我

★ 用户级：插件只定义「有哪些开关可点」，存在哪、界面长什么样归消费方
  —— 它得跟消费方的账号系统绑在一起
```

### 三条纪律

```
① 配置能改参数，不能改判断力
   ✅ 「到达锚点的去抖从 60 秒改成 300 秒」
   ❌ 「到达锚点这件事怎么算」—— 想改就换性格，或自己实现一个策略类
   否则判断力又散回配置里，这次提取就白做了

② 默认必须是开的
   开关是出问题时快速止血用的，不是「等人来打开的门」
   （踩过：默认关的开关，上了 prod 好几天才发现功能压根没生效）

③ 每个默认值要写清为什么是这个数
   「位置 15 分钟过期」不能是拍脑袋 —— 写不出理由的阈值就不该有
```

### 坚决不给配的四件事

一旦开放，整个设计就塌了：

```
✗ 一瞥里出不出具体数值
  给了这个开关所有人都会打开，然后 agent 开始念体检报告 —— 地基就没了

✗ 原始经纬度要不要落库
  永远不落。想存原始值的人该去用采集库，不是用这个

✗ 过期字段要不要「用旧值凑合」
  过期就是 null，null 就是不知道。给了这个开关，
  agent 会拿三天前的位置当现在

✗ 关掉说明书直接给模型看原始数据
  那正是要修的东西
```

## 六、数据怎么进来

**这是感知和记忆最大的不同**：记忆的输入是对话（本来就有），
感知的输入必须新建一条采集链路。**「装上就有」能不能成立，全看这一节。**

### 三档，难度递减

```
最省事   iOS 快捷指令包        用户导入几条自动化就开始上报
         ★ 不用写 Swift、不用过审、不用交 99 刀开发者费
         ★ 这一档决定这插件在开源界有没有人用

中等     Swift 采集 SDK        集成进自己的 app，拿到完整能力
                               （健康 / 定位 / 后台保活）

自己来   写个上游适配器        手环 API / 桌面 / Home Assistant，几十行
```

### 一个 iOS 事实：有些东西原生查不到

**iOS 不给 app 查「用户刚打开了哪个 app」** —— 没这个 API，也没这个权限。

```
定位 / 健康 / 日历 / 天气    原生权限就能查，IO 现在直接查
他在用哪个 app               查不到，只能靠用户自己配自动化上报
```

IO 现在的做法：设置页给一条 URL，用户去快捷指令 app 里建自动化，
一个 app 配两条（打开一条、关闭一条）。所以 **IO 现在只知道用户亲手配过的那几个 app**。

### 包里先带这 6 个快捷指令

主要给「没有 app 的开源用户」用 —— 他们什么都查不到，快捷指令是唯一入口。

```
到家 / 到公司        位置变化 —— 最核心，叫醒的主力
打开 / 关闭某 app    IO 现在就在用的那条
每天早上 8 点        把昨晚睡眠 + 今天天气一起送上来
专注模式开 / 关      在忙还是有空，一个信号顶很多
连上充电器           准备睡了的强信号
起床（睡眠专注结束） 一天的起点
```

挑这几个的理由：**都是 iOS 自动化能自己触发的**，用户配一次就不用再管。

> ⚠️ **待实机验证**：iOS 自动化有的能「直接运行」，有的每次都要弹窗确认。
> 每次弹窗这套就没法用。这 6 个分别属于哪一类，**必须实机试一遍再写进实现计划**。

## 七、形态与分层

```
                      感知插件（判断力，纯函数）
                                │
        ┌───────────────────────┴───────────────────────┐
        │                                               │
   上游适配器：数据从哪来                     下游适配器：状态存哪
   ├── iOS 快捷指令       ← 开源默认           ├── SQLite         ← 开源默认
   ├── Swift SDK          ← IO 用              ├── Postgres + 加密 ← IO 用
   ├── 手环 / 健康 API                         └── 内存（测试用）
   └── Home Assistant

        壳（谁来调）：直接 import ← IO 用 · CLI · MCP server
```

**IO 走「直接 import + Postgres 加密适配器 + 自己的 app 采集」**，
同进程调函数 —— 每次上报都要跑，走跨进程不划算。

**IO 走的路必须和别人完全一样** —— 不能有「IO 专用后门」，否则插件早晚腐化。
IO 只多做两件事：把存储换成加密的、把采集换成自己的 app。

## 八、为下一个大版本准备了什么

本批只是把它抽出来、行为不变。**真正的收益全在下一批**，而且这些收益
**只有在切分做对之后才可能**：

```
① 第三方感知源
   Oura / Whoop / 桌面 / Home Assistant 各写一个上游适配器接进来。
   前提：上游适配器这根轴现在就得留出来，事后补要全返工

② 感知能力插件化
   一个新信号 = 一份声明，不用改任何判断代码
   前提：判断力先收拢成一份，否则加一个信号还是要改四个文件

③ 两条线的说明书拉平
   V1 有「别念数字、状态低时更轻」，V2 有「最多一个主题、防重复打断」，
   两边内容不同。收拢之后才谈得上对齐，现在改等于改两遍

④ 开源发布
   套 CLI 壳 / MCP 壳（各几十行），配 SQLite 适配器就能独立跑
   前提：插件接口从一开始就不能假设调用者是谁
```

> 所以本批虽然「行为不变」，**接口形状必须按下一批来设计**：
> 上游/下游两根适配轴、能力声明与显式降级、说明书与事实分字段返回、
> wake 回执 —— 这几样事后补的代价远大于现在留出来。

## 九、本批怎么落地

### V1 + V2 两条线都要迁

**这是核心验收标准，不是可选项。** VPS 自托管用户跑的就是 V1 形态，
只做 V2 等于他们永远拿不到。

```
V2（云上）        worker.py 的 wake system prompt 里感知那几句   → 从插件取
                  context.py 的 perception policy                → 从插件取
                  tool_schema.py 里感知工具的说明                → 从插件取
                  tool_catalog_v2 / tool_executor_v2             → 只取感知那部分

V1（VPS 自托管）  chat_resident_consumer.py 的
                  _native_reachout_perception_context            → 从插件取
                  io_cli 的 perception 命令                      → 接插件
```

**顺序：先 V2 后 V1。** V2 好验证；V1 那条同时服务云上和自托管用户，最谨慎，放最后。
**「V1 待办」必须写进 FEATURE_LOG，不许做完 V2 就当本批完成。**

### 先做「prompt / 协议资产清单」

上面四处 prompt 分散在两条线，**没有这份清单，迁移一定会漏**。
逐条列出：适用哪条线、哪种回合（前台 / 主动）、挂在哪个 role 层、
原文是什么、属于「插件的静态说明书」还是「runtime 的对话/安全协议」。

### 验收标准

```
① 分两类比，不能笼统说「逐字节不变」
   字节级   prompt 每个片段和最终拼接 · tool schema 和顺序 ·
            HTTP 返回 JSON · 错误码
   语义级   冻结时钟、id、输入之后，比状态变化 · 叫醒决策 ·
            job/context 关联 · 幂等 · 失败行为

② 矩阵至少四格，V1 不是一格
   V2 云上 / hosted resident / 自托管 VPS resident / 各自的 agent mode
   ★ chat_resident_consumer.py 用 _HOSTED 区分托管与自托管，行为不同

③ 新能力的迁移配置必须显式关闭
   安静时段、每日上限是这次新加的，基线里没有。
   迁移配置写成「安静时段关闭、每日上限无限」，
   不许顺手启用新默认 —— 那就不是迁移了

④ 先立基准，再动代码
   主动开口、被动查询、历史趋势、照片叫醒各捞一组真实样本作对照

⑤ 一次只切一条线
   特别是 VPS 那条 —— 共享文件，不能只靠单测宣布两端等价

⑥ 文档同步进入完成门槛
   架构页、自托管信任模型、changelog、OpenAPI，不要留到最后补
```

## 附录 A · 为什么切在这几条线上（现状）

判断力现在散在五个地方，没有任何一处是「感知判断力」这个整体：

```
catalog.py            声明有哪些能力      ← 这块已经做对了，是数据驱动的
resolve.py            原始值 → 标签
differ_v2.py          变没变
signal_state_v2.py    变没变（持久化那半，夹着 DB 和 HMAC）
gate.py + controls_v2 值不值得叫醒
glance.py             怎么概括成一瞥
```

更要命的是「模型该怎么读这份感知」的规矩，**两条线各长了一套，各自还散在好几处**：

```
V1（VPS）  chat_resident_consumer.py 的 _native_reachout_perception_context
           一瞥不是待汇报清单 · 最多挑 2-3 件 · 不许念具体数字 ·
           信号偏低时更轻，别叠加担忧、别下诊断

V2（云上）  worker.py `_WAKE_SYSTEM_PROMPT`
             glance 只是提示 · 最多一个主题 · 别变成设备/健康报告 ·
             用 attention_facts 避免打断和重复
           context.py `_RUNTIME_PERCEPTION_*_POLICY`
           tool_schema.py 里还有一份工具读法
```

逐条对下来：

```
最多说几件      V1「2-3 件」  V2「1 个主题」   ← 不一致，V2 更严
别念具体数字    V1 有         V2 无
状态低时更轻    V1 有         V2 无
别打断/别重复   V1 无         V2 有
```

**没有任何一个地方能一眼看全「感知该怎么读」** —— 这就是要收拢的东西。

## 附录 B · 硬约束

```
① 上游适配器不是装饰
   感知的数据不会自己来。「装上就有」能不能成立，取决于快捷指令那一档好不好用

② 并发和原子性是硬约束，不是实现细节
   现在的变更判定靠事务 + FOR UPDATE（signal_state_v2.py:163），
   每日历史增量靠行锁（store.py:547）—— 没有这些，重复上报、乱序、
   同时间冲突会直接产生错误叫醒。存储适配器契约必须写死：
     · 观察值按「用户 + 信号」原子 compare-and-update
     · 保留 source_event_id 幂等、旧时间戳拒绝、同时刻不同值的冲突语义
     · 历史 rollup 原子 read-modify-write
     · 冷却 / 每日额度 / wake 已接受记录，原子竞争
   ★ 不同后端能力不一样（SQLite 单写者 ≠ Postgres 行锁），
     所以照 Memory Garden 那条：适配器**声明**自己支持哪些保证，
     不支持的**显式上报、不许静默降级**

③ 凭据边界
   凭据不进插件。插件只传 user_context，适配器自己从请求上下文取

④ 加密在 IO 这边不是透明的一层
   它绑定「谁的、第几版、哪一号」，解密要发请求到 enclave 且必须带凭据。
   是带身份的远程调用，会超时、会部分失败、批量时要分页

⑤ 真正的工作量不在拆 import
   在解开判断与机制的交织。signal_state_v2 把判据和 DB / HMAC 混在一起，
   gate 把机械闸和产品分寸混在一起

⑥ 共享文件要格外小心
   chat_resident_consumer.py 同时被云上 host 和自托管 VPS 用
```

## 附录 C · 本批不做

```
两条线说明书的差异对齐
   V1 有「别念数字、状态低时更轻」，V2 有「最多一个主题」和防重复打断，
   内容不同。谁对谁错是产品判断，拉平会让用户直接感觉到 io 变了 ——
   不能混在迁移批里。差异原样搬进插件当配置项，改完之后单开一批讨论。
   ★ 本批唯一「明知不一致但故意不修」的地方，必须留在待办里

感知能力的插件契约粒度
   一个插件 = 一个能力包（自带全套判断），还是 = 只声明数据形状？
   等内核成型再定，本批先把判断力收拢

第三方感知源 · 开源发布 · CLI 壳 · MCP 壳
   本批不做，但接口从一开始按「能被壳包住」「能接第三方上游」设计
```

## 附录 D · 需要确认

```
1. 本批的完成口径（这条不定，实现者对「做完了」的理解会不一样）：
   (a) 只是「可独立发布的代码形状」：判断力收拢完、两条线共用，

4. 插件的仓库形态：先在 feedling-mcp 里独立成包，还是一开始就单独建仓？
   （倾向前者：先在仓库内收拢，等接口稳了再拆出去。）
