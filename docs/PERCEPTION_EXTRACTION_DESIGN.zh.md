# 主动感知系统提取 · 需求设计

> 承接《Memory Garden 内核提取》的做法，对象换成主动感知。
> **本批范围：把主动感知提取成一个能独立发布的模块，IO 是它的第一个使用者。**
> **本批只做迁移重构，不改业务** —— 验收是「行为逐字节不变」。
>
> 代码基线 `origin/test@d9a54e00`。

---

## 一、这东西是什么

一句话：**给任何 agent 装上眼睛和分寸感。**

```
之前：别人的 agent    你不说话，它永远不知道你在干嘛，也永远不会先开口
之后：装上这个模块    你走到公司，它知道；昨晚没睡好，它知道；
                      它还知道什么时候该说一句、什么时候该闭嘴
```

打个比方：**模块是「眼睛和分寸感」，agent 是「这个人本身」。**
眼睛看到什么、值不值得张嘴 —— 模块管；真张嘴说什么话、什么语气 —— agent 管。

### 别人缺的不是采集，是「该不该开口」

动手前扫了一圈现有生态：

```
采集 + 被动查询    一堆。health-export-mcp（190 个 HealthKit 指标）、
                   FreeReps（Apple Watch + Oura 自托管 + MCP）、apple-health-mcp……
                   全是「agent 问、它答」

主动开口           ProactiveAgent（45 星）：只看对话节奏决定该不该说话，
                                            不看任何现实世界信号
                   ContextAgent（arXiv 2505.14668）：用可穿戴数据判断该不该主动
                                            服务，是论文原型，不是能装的库

两边接起来的       没有
```

所以定位是：**采集不是卖点**（别人做得比我们全），**「信号变了 → 该不该打断人 → 怎么说才不像监控」这条链才是**。采集要带，但它的角色是「让模块开箱能跑的电池」，不是招牌。

参考：
- https://github.com/leomariga/ProactiveAgent
- https://arxiv.org/abs/2505.14668
- https://github.com/PhilipAD/health-export-mcp
- https://github.com/meltforce/FreeReps

## 二、要解决什么

### 问题一：同一份感知，两条线给模型的说明书不一样

IO 现在有两条线跑两套代码：自托管 VPS（V1）和云上托管（V2）。同一张感知「一瞥」，两边告诉模型「该怎么读它」的话完全不同：

```
V1（VPS）    一大段英文，教得很细：
             这是低分辨率的一瞥，不是待汇报清单 · 最多挑 2-3 件 ·
             不许念具体数字（分钟 / 度数 / 睡眠时长）·
             信号偏低时（深夜、悲伤的歌、没睡好）要更轻，别叠加担忧、别下诊断

V2（云上）   两句话：
             把有用的事实自然用进回答 · glance 只是布尔提示
```

用户能直接感觉到的差别：

```
同样是「深夜 + 在听悲伤的歌 + 昨晚睡了 5 小时」
   VPS 上的 io    轻轻一句「还没睡啊」
   云上的 io      可能三件事一起说，还把「5 小时 12 分钟」念出来 → 像被监控
```

V1 那些规矩明显是踩出来才写的（「别叠加担忧」不会凭空想到），**V2 一条都没继承**。

> ⚠️ **本批不修这个差异**（见第十节）。差异原样搬进模块当一个配置项，
> 两条线各自保持现在的行为；要不要拉平，改完之后单开一批讨论。

### 问题二：感知的判断力散在五个地方

没有任何一处是「感知判断力」这个整体：

```
catalog.py            声明有哪些能力      ← 这块已经做对了，是数据驱动的
resolve.py            原始值 → 标签
differ_v2.py          变没变
signal_state_v2.py    变没变（持久化那半，夹着 DB 和 HMAC）
gate.py + controls_v2 值不值得叫醒
glance.py             怎么概括成一瞥
```

纯判断和机制（数据库、环境变量、加密）缠在一起，所以每次加一条判断都要在好几个文件里各补一遍 —— 这正是 V2 漏掉说明书的根因。

## 三、边界：模块管什么，IO 管什么

### 判据（先定这一条，后面都能自己推）

```
换一个 agent 装上去，这件事该不该跟着变？

不该变 → 模块      「从家到公司算一次变化」，换谁装上都一样
该变   → 消费方    「用户正忙着跟我说话呢」，只有 agent 自己知道
```

### 模块 · 核心（不可替换）

```
能力表             有哪些信号 · 字段名 · 保质期 · 哪个字段归哪个能力
上报解析校验       字段形状、非法值、过期即 null（「不知道」，不许猜）
变没变的判据       心率跳两下不算变，从家到公司算变
去抖冷却           手机抖一下不许连叫两遍
值不值得打断       哪些事件算叫醒源（到达 / 拍照 / 久别解锁 / 屏幕共享起止）
时钟上的分寸       安静时段 · 一天最多打扰几次 · 距上次多久
一瞥的形状         只出是 / 否，不出数值
读法说明书         别念数字 · 最多挑 2-3 件 · 信号偏低时更轻
历史计算           rollup · 趋势 · 什么算「显著变化」
perception_* 工具  定义 + 实现
```

### 模块 · 电池（自带默认，可整块换掉）

```
存储      SQLite（默认）        ← IO 换成自己那套 Postgres + 加密
上游      iOS 快捷指令包 / Swift 采集 SDK / 手环适配器
性格      陪伴型（默认）/ 助手型 / 闷葫芦
上报端点  挂到宿主的 HTTP 服务上
```

### 消费方 · 只需实现三个钩子

```
resolve_user(req)    这条上报是谁的 —— 模块只认一个不透明 id，不碰账号
on_wake(reason)      模块说「该开口了，因为他刚到公司」→ 你决定怎么开口
get_glance()         每轮拿一张一瞥，自己决定拼进上下文哪一层
```

### 消费方 · 模块完全不碰

```
账号 · 鉴权 · 多租户
加密与 enclave                 IO 特有，模块里连这个概念都不该有
对话上的分寸                   他正在跟我说话 / 刚聊完五分钟 /
                               连着三条主动消息都没理 —— 模块看不见这些
叫醒之后的工程                 入队 · 并发 · 幂等 · 失败退避
prompt 放哪一层                V2 特意放 assistant role 防伪装成用户消息，
                               那是 runtime 协议，不是感知的事
调模型 · 说什么
界面                           设置页 · 权限引导文案
```

### 五个容易切错的地方

```
① 两种「别烦我」，长得像，归属不同
   模块   「1 分钟内同一个地点别重复叫」   噪声，换谁装上都不该重复
   模块   「凌晨 2 点别叫我」              时钟上的分寸，做成配置
   IO     「他正忙着跟我说话呢」           对话状态，模块根本看不见

② 权限
   模块   「step_count 归 steps 管，不归 vitals 管」   字段归属，不该变
   IO     「这个用户到底授权了没」                     有账号系统的是它

③ 照片
   模块   「拍照算叫醒源」「30 秒内连拍算一张」
   IO     「照片字节存哪、谁能解密」

④ prompt
   模块   说明书写什么
   IO     放哪一层、怎么跟其它上下文拼

⑤ 保质期
   全在模块 —— 「位置 15 分钟、睡眠 24 小时」是感知语义的一部分，
                过期变 null、agent 看到 null 当「不知道」也是
```

## 四、两条完整流程，每一步标清谁负责

### 流程一：你到公司了，io 主动说了句话

```
07:40  你走到公司楼下
   │
   ▼
┌────────────────────────────────────────────────────────┐
│ 【模块】手机上报：纬度 31.23 经度 121.47               │
│ 【模块】查你自己标过的地点 → 算出「公司」              │
│         ★ 经纬度当场扔掉，agent 永远看不到             │
└────────────────────────────────────────────────────────┘
   │
   ▼
┌────────────────────────────────────────────────────────┐
│ 【IO】  这条是谁的？→ 用户 A                            │
│ 【IO】  存起来（IO 这边要加密存，走存储适配器）          │
└────────────────────────────────────────────────────────┘
   │
   ▼
┌────────────────────────────────────────────────────────┐
│ 【模块】从家到公司 —— 这算变化，而且值得说一句          │
│ 【模块】但 1 分钟内到过一次了 → 这次不叫                │
│ 【模块】现在是安静时段吗？（配置：23:00-08:00）         │
│         现在 7:40，不是 → 放行                          │
└────────────────────────────────────────────────────────┘
   │  模块喊：「该开口了，因为他刚到公司」
   ▼
┌────────────────────────────────────────────────────────┐
│ 【IO】  等一下 —— 他现在正在跟我聊天吗？刚聊完吗？       │
│         连着三条主动消息都没理吗？                      │
│         ★ 这些模块看不见，只能 IO 判                    │
│         都没有 → 继续                                   │
└────────────────────────────────────────────────────────┘
   │
   ▼
┌────────────────────────────────────────────────────────┐
│ 【模块】给一张「一瞥」—— 全是是 / 否，没有数字：        │
│           到了常去的地方 = 是                           │
│           昨晚睡眠有变化 = 是                           │
│           最近拍了照片   = 否                           │
│ 【模块】外加一段说明书：                                │
│           「这只是一瞥，不是待汇报清单。最多挑两三件，  │
│             别念具体数字。他状态偏低时话要更轻。」      │
└────────────────────────────────────────────────────────┘
   │
   ▼
┌────────────────────────────────────────────────────────┐
│ 【IO】  想了想：睡眠那条我想看细一点                    │
│         → 调模块的工具，拿到真实数据（昨晚 5 小时）     │
│ 【IO】  决定说什么：「到公司啦？昨晚好像没睡够，悠着点」 │
│         ★ 台词完全是 IO 的事，模块不写话                │
└────────────────────────────────────────────────────────┘
```

**关键分工**：模块说的是「**该开口了，因为他刚到公司**」，不是「你去跟他说到公司了」。

### 流程二：你主动问它

```
你：「我最近睡得怎么样？」
   │
   ▼
【IO】   这个得查 → 调模块的工具
   │
   ▼
【模块】 跟存储要最近两周的睡眠 → 算出趋势：比上周少了
         ★ 模块自己不带数据库，只说「帮我捞出来」
   │
   ▼
【IO】   从自己的库里捞出来给它（IO 这边要解密）
   │
   ▼
【模块】 算完返回：本周均值下降，最低点在前天
   │
   ▼
【IO】   「这周比上周少了快一小时，前天那晚最短。是在忙什么吗？」
```

这条路**没有「打断」这回事** —— 你问它答。所以就算性格调成「闷葫芦」（永不主动开口），这条路照样能用。

### 历史存哪：模块定形状，IO 出库

```
模块定    存成什么形状、多久算一天、什么叫「比上周少了」
IO 出     一个真正的数据库（IO 用自己那套加密的）
默认      别人接的话给个 SQLite，不用自己写
```

## 五、配置

### 分三层，越往下越少人碰

```
第 1 层  性格          一行定 80% 的人
         preset: companion    陪伴型（IO 用这个）
                 assistant    助手型：少打扰，只在明确有用时开口
                 silent       闷葫芦：只感知不主动开口，纯给工具查

第 2 层  全局旋钮      五六个，人人会调
         存哪儿 · 启用哪些信号 · 安静时段 · 一天最多打扰几次

第 3 层  逐信号覆盖    高级，按需
         location.debounce_sec: 300      默认 60，我这场景不想这么灵
         photos.wake: false              拍照别叫我
         health_sleep.ttl_sec: 172800    我手环两天才同步一次，别当过期
```

性格差在哪，一个例子：

```
深夜 + 在听悲伤的歌 + 昨晚没睡好
   陪伴型   「还没睡啊」
   助手型   不吭声 —— 这不算一件「有用」的事
   闷葫芦   永远不主动说，但你问它「我最近睡得怎么样」它答得出来
```

### 用户级配置是另一码事

```
部署级（接入方在配置文件里定）    性格 · 存哪 · 启用哪些信号 · 阈值
用户级（终端用户在 app 里点的）   我不想让它看健康数据 · 别在深夜叫我

★ 用户级：模块只定义「有哪些开关可点」，存在哪、界面长什么样归消费方
  —— 因为它得跟消费方的账号系统绑在一起
```

### 三条纪律

```
① 配置能改参数，不能改判断力
   ✅ 「到达锚点的去抖从 60 秒改成 300 秒」
   ❌ 「到达锚点这件事怎么算」—— 想改就换性格，或自己实现一个策略类
   否则判断力又散回配置里，这次提取就白做了

② 默认必须是开的
   开关是出问题时快速止血用的，不是「等人来打开的门」
   （踩过：默认关的开关，上了 prod 好几天才发现功能压根没生效）

③ 每个默认值要在文档里写清为什么是这个数
   「位置 15 分钟过期」不能是拍脑袋 —— 写不出理由的阈值就不该有
```

### 坚决不给配的四件事

一旦开放，整个设计就塌了：

```
✗ 一瞥里出不出具体数值
  给了这个开关所有人都会打开，然后 agent 开始念体检报告 —— 地基就没了

✗ 原始经纬度要不要落库
  永远不落。想存原始值的人该去用采集库，不是用这个

✗ 过期字段要不要「用旧值凑合」
  过期就是 null，null 就是不知道。给了这个开关，
  agent 会拿三天前的位置当现在

✗ 关掉说明书直接给模型看原始数据
  那就是现在 V2 的状态，也正是将来要修的东西
```

## 六、数据怎么进来

### 三档，难度递减

```
最省事   iOS 快捷指令包        用户导入几条自动化就开始上报
         ★ 不用写 Swift、不用过审、不用交 99 刀开发者费
         ★ 这一档决定这模块在开源界有没有人用

中等     Swift 采集 SDK        集成进自己的 app，拿到完整能力
                               （健康 / 定位 / 后台保活）

自己来   写个上游适配器        手环 API / 桌面 / Home Assistant，几十行
```

### 一个 iOS 事实：有些东西原生查不到

**iOS 不给 app 查「用户刚打开了哪个 app」** —— 没这个 API，也没这个权限。

```
定位 / 健康 / 日历 / 天气    原生权限就能查，IO 现在直接查
他在用哪个 app               查不到，只能靠用户自己配自动化上报
```

IO 现在的做法：设置页给一条 URL，用户去快捷指令 app 里建自动化，一个 app 配两条（打开一条、关闭一条）。所以 **IO 现在只知道用户亲手配过的那几个 app**。

### 包里先带这 6 个快捷指令

主要给「没有 app 的开源用户」用 —— 他们什么都查不到，快捷指令是唯一入口。

```
到家 / 到公司        位置变化 —— 最核心，叫醒的主力
打开 / 关闭某 app    IO 现在就在用的那条
每天早上 8 点        把昨晚睡眠 + 今天天气一起送上来
专注模式开 / 关      在忙还是有空，一个信号顶很多
连上充电器           准备睡了的强信号
起床（睡眠专注结束） 一天的起点
```

挑这几个的理由：**都是 iOS 自动化能自己触发的**，用户配一次就不用再管。

> ⚠️ **待实机验证**：iOS 自动化有的能「直接运行」，有的每次都要弹窗确认。
> 每次弹窗的话这套就没法用。这 6 个触发器分别属于哪一类，
> **必须实机试一遍再写进实现计划**，不许凭印象。

## 七、形态与分层

```
                      感知模块（判断力，纯函数）
                                │
        ┌───────────────────────┴───────────────────────┐
        │                                               │
   上游适配器：数据从哪来                     下游适配器：状态存哪
   ├── iOS 快捷指令       ← 开源默认           ├── SQLite         ← 开源默认
   ├── Swift SDK          ← IO 用              ├── Postgres + 加密 ← IO 用
   ├── 手环 / 健康 API                         └── 内存（测试用）
   └── Home Assistant

        壳（谁来调）：直接 import ← IO 用 · CLI · MCP server
```

**IO 走「直接 import + Postgres 加密适配器 + 自己的 app 采集」**，同进程调函数 —— 每次上报都要跑，走跨进程不划算。

**IO 自己接上去要写的东西**：

```
三个钩子      这条上报是谁的 · 该开口时干嘛 · 每轮拿一瞥
两个替换件    存储换成加密的 · 采集换成自己的 app
```

其余全在模块里。**IO 走的路必须和别人完全一样** —— 不能有「IO 专用后门」，否则模块早晚腐化。

## 八、V1 + V2 两条线都要迁

**这是本批的核心验收标准，不是可选项。**

```
之前   同一份感知，V2 一套读法、V1 一套读法，改一边漏一边
之后   两条线调同一个模块，判断只有一份
```

各自要动的地方：

```
V2（云上）        model_api_runtime/v2/context.py 那段说明书 → 改成从模块取
                  tool_catalog_v2 / tool_executor_v2         → 改成用模块带的

V1（VPS 自托管）  tools/chat_resident_consumer.py 里
                  _native_reachout_perception_context 那段    → 同上
                  io_cli 的 perception 命令                   → 接模块
```

**顺序：先 V2 后 V1。** V2 好验证；V1 那条同时服务云上和自托管用户，动它最谨慎，放最后。

> 🔴 **「V1 待办」必须写进 FEATURE_LOG，不许做完 V2 就当这批完成。**
> VPS 自托管用户跑的就是 V1 那套形态，只做 V2 等于他们永远拿不到。

## 九、验收标准

**本批只做迁移重构，不改业务。** 所以验收是硬的：

```
① 行为逐字节不变
   两条线各自跟自己现在的行为对齐 —— V2 跟 V2 比，V1 跟 V1 比
   两边的说明书差异原样搬进模块当配置，不许趁重构顺手拉平

② 先立基准，再动代码
   主动开口、被动查询、历史趋势、照片叫醒各捞一组真实样本作对照
   没有基准就无从验起

③ 一次只切一条线
   V2 的一瞥、V2 的工具、V1 的一瞥、V1 的工具分开切，不要一次改完整个 worker
   特别是 VPS 那条 —— chat_resident_consumer.py 同时服务云上和自托管用户，
   不能只靠单测宣布两端等价

④ 文档同步进入完成门槛
   这是架构和公开工具行为的变更，仓库规范要求同步架构页、
   自托管信任模型、changelog 和 OpenAPI，不要留到最后补
```

## 十、本批不做（已讨论，存档）

```
云上「念数字」的说明书对齐
   V2 缺 V1 那套「别念数字、别叠加担忧、最多挑 2-3 件」的规矩。
   补了之后云上用户会明显觉得 io 变克制 —— 这是用户能直接感觉到的行为变更，
   不能混在迁移批里。差异原样搬进模块当配置项，改完之后单开一批讨论。
   ★ 这条是本批唯一「明知有问题但故意不修」的地方，必须留在待办里。

插件契约的粒度
   一个插件 = 一个能力包（自带全套判断），还是 = 只声明数据形状（判据统一在内核），
   等内核成型了再定。本批先把判断力收拢。

开源发布 · CLI 壳 · MCP 壳
   本批不做，但内核接口从一开始就按「能被壳包住」设计
   —— 壳是几十行转接代码，前提是内核不假设调用者是谁。
```

## 十一、已知硬约束

```
① 上游适配器不是可选的装饰
   感知的数据不会自己来。记忆的输入是对话（本来就有），
   感知的输入必须新建一条采集链路 —— 这是两者最大的不同。
   「装上就有」能不能成立，取决于快捷指令那一档好不好用。

② 加密在 IO 这边不是透明的一层
   它绑定了「谁的、第几版、哪一号」，解密要发请求到 enclave 且必须带凭据。
   是带身份的远程调用，会超时、会部分失败、批量时要分页。
   模块只见明文，但 IO 侧这一层比想象中重。

③ 真正的工作量不在拆 import
   在解开判断与机制的交织。signal_state_v2 把判据和 DB / HMAC 混在一起，
   gate 把机械闸和产品分寸混在一起。分不开这些，模块就抽不干净。

④ 共享文件要格外小心
   chat_resident_consumer.py 同时被云上 host 和自托管 VPS 用，
   改一处两边都受影响。
```
